# kronika-writer

[English version](README.md)

`kronika-writer` превращает ограниченные по размеру окна сбора в долговременный
PGM-сегмент. Он управляет буферами строк, интернированием строк сегмента,
журналом `active.parts` версии 1, восстановлением после сбоя и финализацией
(функция `seal`). SQL-источники, двоичное представление и структура каталога
данных лежат в других крейтах.

## Окно сбора

`SectionBuffers::push<T: Section>` накапливает строки для зарегистрированного
типа. При достижении `MAX_SECTION_ROWS` метод возвращает непоместившуюся строку,
чтобы вызывающий сбросил буфер и повторил push без потери. `flush` кодирует
секции данных в порядке type_id, добавляет словари, вычисляет временной диапазон
и возвращает самодостаточную PGM-часть. После успешного flush буферы пусты.

`dict::encode` преобразует текущий снимок интернера в отсортированные
`dict.strings` и `dict.blobs`. Строки снимков адресуют их через `str_id`.

## Интернер (`Interner`)

`Interner` владеет идентичностью словаря открытого сегмента. Текущий снимок
хранит полные байты в пределах `DictLimits`. После успешной записи
`flush_window` заменяет их короткими метаданными — для обнаружения коллизий,
дедупликации и финального размещения. Повторяющийся SQL или план не остаётся
полностью продублированным до финализации.

При коллизии, конфликте размещения или переполнении байтового бюджета операция
не портит предыдущее состояние. `DictError::Full` требует flush или досрочной
финализации сегмента.

## Журнал (`Journal`)

`Journal::open(&WriterOwner, config)` открывает корневой `active.parts` через
право доступа из `kronika-layout`. Новый журнал создаётся как синхронизированный
36-байтовый пустой заголовок версии 1; корректный пустой журнал не бывает
файлом нулевой длины.

Журнал версии 1 начинается с магического числа `PGKJNL1\0`. Заголовок с
контрольной суммой хранит состояние `empty` или `active`,
[`SegmentId`][layout] активного сегмента и
точное число байтов следующих кадров. `append(segment_id, part)` проверяет
PGM-часть и записывает её кадр `PGMP`. При первом добавлении идентификатор
сегмента и первый кадр становятся долговременными на одной границе
синхронизации. Следующие добавления обязаны использовать тот же идентификатор.

При открытии полностью проверяются заголовок и тело кадров, но весь файл не
загружается в память. Файл без заголовка, другая версия, оборванный или
повреждённый журнал отклоняется и остаётся без изменений. Файл нулевой длины
доказуемо пуст и инициализируется заново как пустой заголовок.
Версия 1 — первый и единственный поддерживаемый формат журнала. Публичного
выпуска PgKronika ещё не было, поэтому другого формата и механизма миграции нет.

`JournalConfig::max_journal_len` ограничивает физический размер файла с учётом
временного 32-байтового маркера сброса. При каждом дописывании, включая первый
кадр, место под маркер резервируется заранее. Если кадр не помещается,
возвращается `JournalError::Full`, и коллектор может сначала финализировать
сегмент. Версия 1 допускает не более 1 ГиБ на журнал, 1 000 000 кадров на
журнал и 64 МиБ на одну PGM-часть. Настройками эти абсолютные пределы можно
только уменьшить.

`reset` допустим только после успешной публикации. Сначала он добавляет в конец
файла и синхронизирует маркер с прежней длиной, `SegmentId` и контрольной
суммой заголовка. Затем записывает `JournalHeader::EMPTY` и вызывает
`sync_data`, пока маркер и тело кадров ещё сохранены. Только после этой
синхронизации файл усекается до 36 байт и `sync_data` вызывается второй раз.
Если процесс завершился после записи маркера, следующий `Journal::open`
проверяет его и заканчивает сброс. Неудачный откат или ошибка после
подтверждения маркера переводит открытый журнал в состояние `poisoned`:
продолжать сбор с ним нельзя.

## Финализация (`seal`)

`seal(journal, owner, SegmentAddress)` потоком копирует тела секций во временный
файл в каталоге дня UTC и пишет общий финальный каталог. При публикации PGM
файл синхронизируется, каноническое имя `YYYY/MM/DD/N.pgm` добавляется жёсткой
ссылкой, каталог дня синхронизируется, временное имя удаляется, затем каталог
синхронизируется ещё раз. Существующий файл не перезаписывается; восстановление
считается успешным, только если готовый PGM структурно корректен и побайтово
совпадает с результатом.

После получения блокировки записи коллектор при запуске удаляет только
распознанные временные файлы публикации PGM, оставшиеся после сбоя. Временные
файлы OVF и проверки записи модуля обзора удаляет только владелец этого модуля.

Повторные записи секций сохраняются в порядке каталога; модуль записи не сливает
и не переупаковывает их. Он также не очищает журнал, не выбирает `SegmentId` и не
управляет сроками хранения — это зона ответственности жизненного цикла
коллектора. `SegmentAddress` вычисляет единственный допустимый путь по
идентификатору, и модуль записи принимает только этот адрес в строгом
календарном дереве.

Ошибки журнала, проверки, назначения и синхронизации при финализации вынесены
в отдельные варианты ошибок. Канонический API — [`src/lib.rs`](src/lib.rs),
обрамление — [`../kronika-format/`](../kronika-format/), пути и права записи —
[`../kronika-layout/`](../kronika-layout/).
