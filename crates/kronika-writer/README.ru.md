# kronika-writer

[English version](README.md)

`kronika-writer` превращает ограниченные по размеру окна сбора в долговременный
PGM-сегмент. Он управляет буферами строк, интернированием строк сегмента,
файлом `active.parts`, восстановлением после сбоя и финализацией (seal).
SQL-источники и двоичная раскладка лежат в других крейтах.

## Окно сбора

`SectionBuffers::push<T: Section>` накапливает строки для зарегистрированного
типа. При достижении `MAX_SECTION_ROWS` метод возвращает непоместившуюся строку,
чтобы вызывающий сбросил буфер и повторил push без потери. `flush` кодирует
секции данных в порядке type_id, добавляет словари, вычисляет временной диапазон
и возвращает самодостаточную PGM-часть. После успешного flush буферы пусты.

`dict::encode` преобразует текущий снапшот интернера в отсортированные
`dict.strings` и `dict.blobs`. Строки снимков адресуют их через `str_id`.

## Interner

`Interner` владеет идентичностью словаря открытого сегмента. Текущий снапшот
хранит полные байты в пределах `DictLimits`. После успешной записи
`flush_window` заменяет их короткими метаданными — для обнаружения коллизий,
дедупликации и финального размещения. Повторяющийся SQL или план не остаётся
полностью продублированным до seal.

При коллизии, конфликте размещения или переполнении байтового бюджета операция
не портит предыдущее состояние. `DictError::Full` требует flush или досрочного
seal.

## Journal

`Journal::open(path, config)` потоком сканирует `active.parts`. Пик памяти —
одна часть ограниченного размера, декодированный каталог, буфер ресинхронизации
и короткая ссылка на каждую корректную часть.

Повреждённый хвостовой кадр усекается до последней корректной границы.
Повреждение в середине (или не соответствующее паттерну torn tail) остаётся на
диске и в `OpenReport`. `append` проверяет PGM-часть, пишет кадр `PGMP`,
синхронизирует файл и возвращает ссылку. `JournalConfig::max_journal_len` —
жёсткий предел; следующий кадр немедленно получает `JournalError::Full`.

`reset` обрезает журнал. Сбрасывать его можно только после успешной публикации
сегмента.

## Seal (финализация)

`seal(journal, destination)` проверяет каждую записанную часть и читает каждое
тело по проверенному диапазону каталога. Для каждого зарегистрированного
`type_id` данных он декодирует все тела журнала, объединяет строки, применяет
ключ сортировки реестра и все остальные столбцы как детерминированный полный
порядок, затем создаёт одно каноническое тело Parquet. Словарные тела
декодируются и нормализуются максимум в одно тело `dict.strings` и одно тело
`dict.blobs`. Точные повторы словарных записей дедуплицируются; конфликт
значений, метаданных или размещения прерывает seal.

Итоговые тела используют Parquet 1.0, значения PLAIN, уровни RLE и Zstd уровня
6; словарное кодирование, статистика и индексы смещений отключены. До
добавления окна коллектор проверяет суммарное число строк, число дочерних
значений `List<i32>`, строки и сохранённые байты словаря, одностраничный бюджет
PLAIN для каждого физического столбца и предел закодированного тела 8 МиБ. Во
время seal те же ограничения повторно проверяются при декодировании и
кодировании.

Публикация использует собственный соседний временный файл, синхронизацию и
жёсткую ссылку без замены. Если `destination` уже содержит в точности те байты,
которые получаются из журнала, повторная попытка завершается успешно и не
меняет файл. Другой существующий файл даёт `SealError::AlreadyExists`;
destination и журнал остаются без изменений. Вызывающий очищает журнал только
после `Ok`. Writer не выбирает имя файла и не управляет сроками хранения — это
зона ответственности жизненного цикла коллектора.

Ошибки журнала, валидации, destination и синхронизации при seal вынесены в
отдельные варианты ошибок. Канонический API — [`src/lib.rs`](src/lib.rs),
обрамление — [`../kronika-format/`](../kronika-format/).
