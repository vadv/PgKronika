# kronika-registry

[English version](README.md)

`kronika-registry` задаёт общий язык между сбором, записью и чтением данных
PgKronika. Запись каталога PGM содержит смещение, размер, число строк, CRC32C и
другие поля, но единственным идентификатором схемы является числовой `type_id`.
По этому числу реестр определяет:

- как называются и физически представлены столбцы тела секции;
- какие значения являются накопительными счётчиками, текущими значениями,
  метками и временем снимка;
- как сортировать строки и какие метки объединяют отсчёты в один временной ряд;
- как сопоставить несколько схем одного источника после обновления PostgreSQL;
- каким кодеком превратить типизированные строки в Parquet и прочитать их
  обратно.

Это не отдельный процесс, файл конфигурации или таблица внутри PGM. Реестр
скомпилирован в библиотеки и бинарники PgKronika как статический список
`TypeContract`. Полный контракт в PGM не записывается: `kronika-writer` и
`kronika-reader` должны одинаково понимать каждый `type_id`.
Parquet-тело содержит физические имена и типы столбцов, но не сообщает их
роли, `identity`, `semantics` и признаки сбора. Декодер использует встроенную
схему Parquet для проверки, а не как замену реестру.

Параметры запуска перечислены в разделе
[«Что можно настраивать»](#что-можно-настраивать). У самого реестра настроек
времени выполнения нет.

## Место в потоке данных

```text
PostgreSQL / Linux / cgroup / журнал PostgreSQL
        |
        | модуль источника выбирает структуру для его версии
        | строковые и двоичные значения интернируются: байты -> StrId
        v
типизированные строки из kronika-registry
        |
        | Section::encode
        | точная Arrow-схема -> сортировка -> Parquet + Zstd-3
        v
тело секции
        |
        | kronika-writer добавляет запись каталога и словари
        v
active.parts / готовый PGM
        |
        | каталог: type_id, offset, len, rows, CRC32C
        | CRC32C -> поиск контракта -> проверка схемы -> декодирование
        v
kronika-reader
        |
        | разрешение StrId, объединение версий, временные ряды и разности
        v
pg_kronika-web / kronika-analytics
```

Внешнюю разметку файла, каталог, `StrId` и правила размещения словарных
значений задаёт [`kronika-format`](../kronika-format/README.ru.md). Реестр
резервирует `type_id` словарей и отвечает за смысл и кодек тела типизированной
секции. [`kronika-writer`](../kronika-writer/README.ru.md) кодирует словарные
тела и записывает части и готовые сегменты;
[`kronika-reader`](../kronika-reader/README.ru.md) декодирует словари и строит
логические запросы.

### Три значения слова «секция»

| Термин | Что он означает |
| --- | --- |
| Физическая секция PGM | Запись каталога и указанный ею диапазон байтов. Для зарегистрированных типов тело является самостоятельным файлом Parquet. |
| Тип секции | Один `type_id` и его кодек. У типизированных секций есть `TypeContract`; словари являются исключением и имеют отдельные идентификаторы и кодеки без записи в `registry()`. Например, `1_005_003` задаёт схему `pg_stat_database` для PostgreSQL 14–17. |
| Логическая секция | Объединение всех зарегистрированных версий с одинаковым `name`. Например, четыре версии `pg_stat_database` читаются как один источник. |

Трейт `Section` реализован для типа Rust-структуры, описывающей одну строку, а
не для каждого экземпляра строки. Закрытый трейт и внутренний макрос
`#[derive(Section)]` не позволяют стороннему крейту незаметно добавить
собственную схему.

## Что хранит контракт

`registry()` возвращает статический список контрактов. Один `TypeContract`
содержит:

| Поле | Практический эффект |
| --- | --- |
| `type_id` | Выбирает точную схему и кодек тела. Идентификатор не вычисляется из имени, OID или хеша, а назначается в `#[section(id = ...)]`. |
| `name` | Объединяет версии одной логической секции при чтении. |
| `semantics` | Задаёт режим сбора: какие строки входят в тело и при каком условии оно появляется. |
| `columns` | Фиксирует порядок, тип, роль, допустимость `NULL` и необязательный признак сбора для каждого столбца. |
| `sort_key` | Задаёт канонический порядок строк перед кодированием. |
| `identity` | Задаёт метки одного временного ряда для расчёта разностей. Если список пуст, `kronika-reader` использует `sort_key` без `ts`. |
| `deprecated` | Помечает схему, выведенную из записи; контракт остаётся в реестре для чтения старых данных. Сейчас у зарегистрированных контрактов значение `false`. |

Контракт не содержит SQL, расписание, правила отбора N строк, тайм-ауты, период
ротации или источник сброса счётчика. Эти решения принадлежат модулям
источников, сборщику, модулю записи и модулю чтения. Признаки сбора являются
частью описания отдельных столбцов, а не расписанием выполнения запросов.

### Роли столбцов

В реестре есть ровно четыре варианта `ColumnClass`:

| Роль | Что хранится | Что делает `kronika-reader` |
| --- | --- | --- |
| `Timestamp` | Обязательный `ts: Ts`, время снимка в микросекундах с начала эпохи Unix. | Ставит строки на временную ось. |
| `Label` | Идентификатор или атрибут сущности: OID, PID, имя, тип, флаг. | Может включить столбец в ключ ряда; сам по себе `Label` ещё не означает `identity`. |
| `Cumulative` | Накопительный счётчик, например `xact_commit`. | Сравнивает соседние отсчёты одного ряда и вычисляет приращение и скорость в секунду. |
| `Gauge` | Текущее значение, например `numbackends`, возраст XID или размер. | Возвращает исходные значения без вычитания соседних точек. |

`identity` не является пятой ролью столбца. Это отдельный список имён
`Label`-столбцов. Аналогично, отдельного класса `Constant` нет.

Физические типы включают узкие целые числа, `f32`, `f64`, `bool`, `Ts`,
`StrId` и `ColumnType::ListI32`. Последний соответствует Arrow
`List<Int32>` и полю Rust `Vec<i32>`. Кодек использует самый узкий подходящий
тип: например, PID хранится как `i32`, а не `i64`. `Option<T>` означает
физически допустимый `NULL`; обязательный столбец с `NULL` считается ошибкой
декодирования.

## Как читать `type_id`

Идентификатор записывают в коде как `C_SSS_VVV`:

```text
1_005_003
| |   |
| |   `-- VVV: версия схемы хранения, 003
| `------ SSS: номер типа внутри класса, 005
`-------- C: класс секции, 1
```

На диске это обычный `u32` со значением `1005003`; подчёркивания существуют
только для чтения числа человеком. Поля означают:

- `C`: класс секции;
- `SSS`: выделенный номер типа внутри класса;
- `VVV`: версия физической схемы и её смысла.

`SSS` не является `source_id` экземпляра PostgreSQL. `VVV` не является версией
PostgreSQL или формата PGM. Какой `VVV` соответствует конкретной версии
источника, решает код модуля источника.

| Класс | Значение | Текущее использование |
| ---: | --- | --- |
| `1` | `Snapshot` | Все типизированные контракты текущего `registry()`. Сюда пока входят и секции событий журнала. |
| `2` | `Event` | Класс известен `TypeId`, но зарегистрированных контрактов с ним сейчас нет. |
| `3` | `Dictionary` | `dict.strings = 3_001_001` и `dict.blobs = 3_002_001`; они кодируются отдельно и не входят в `registry()`. |
| `10` | `Chart` | Зарезервирован в `TypeId`; зарегистрированных контрактов сейчас нет. |

Класс в `type_id` не задаёт режим `semantics`; `lint` не проверяет их
соответствие. Поэтому наличие класса в перечислении не означает наличие
готового источника или кодека.

### Не путать идентификаторы

| Идентификатор | Что он различает |
| --- | --- |
| `type_id` | Схему тела секции, например версию `pg_stat_activity`. |
| PGM `source_id` | Непрозрачное значение `u64`, которое `pg_kronika-collector` копирует из `KRONIKA_SOURCE_ID` в метаданные сегмента. Реестр его не интерпретирует. |
| `StrId` | Текстовое или бинарное значение в словарных секциях PGM. |
| `query_id`, `plan_id`, OID, PID | Данные PostgreSQL или ОС внутри строки; они не выбирают кодек. |

## Пример: обновление PostgreSQL и `pg_stat_activity`

`pg_stat_activity` менялся между версиями PostgreSQL. Один `type_id` не может
описать все варианты без догадок:

| PostgreSQL | Rust-структура | `type_id` | Отличие |
| --- | --- | ---: | --- |
| 10–12 | `PgStatActivityV1` | `1_001_001` | Нет `leader_pid` и `query_id`. |
| 13 | `PgStatActivityV2` | `1_001_002` | Добавлен `leader_pid`. |
| 14–18 | `PgStatActivityV3` | `1_001_003` | Добавлен `query_id`. |

`kronika-source-pg` узнаёт основную версию сервера при подключении и выбирает
подходящий SQL и структуру. Для `pg_stat_statements` схема выбирается отдельно
по версии расширения из `pg_extension`, а не по основной версии PostgreSQL.

Во всех трёх контрактах:

```text
name      = "pg_stat_activity"
semantics = SnapshotFull
sort_key  = ["ts", "pid"]
identity  = []             # kronika-reader использует pid из sort_key
```

`kronika-reader`, содержащий все три контракта, находит известные `type_id` с
этим `name`, проверяет одинаковый `sort_key` и строит объединение столбцов.
Столбцы идут в порядке первого появления: сначала вся схема V1, затем
`leader_pid` из V2 и `query_id` из V3. При чтении старого тела отсутствующие
значения становятся `NULL`:

```text
тело 1_001_001: ts | pid | datname | ... | state_change
тело 1_001_002: ts | pid | leader_pid | datname | ... | state_change
тело 1_001_003: ts | pid | leader_pid | datname | ... | query | query_id | ... | state_change
                                      |
                                      v
логическая pg_stat_activity:
ts | pid | datname | ... | state_change | leader_pid? | query_id?
```

Знак `?` здесь означает, что в объединённом представлении столбец допускает
`NULL`, в том числе потому, что старые схемы его не содержали.

Старый PGM переписывать не нужно, пока `kronika-reader` сохраняет контракт
старого `type_id`. Неизвестный `type_id` автоматически понятным не становится:
контейнер можно открыть и незнакомую секцию пропустить, но прямой вызов
`decode_any` вернёт `UnknownType`.

Даже добавление столбца, допускающего `NULL`, требует нового `type_id`. Декодер
проверяет точное число, порядок, типы и допустимость `NULL` по Arrow-схеме; он
не угадывает совместимость по содержимому Parquet.

### Где хранятся строковые значения

Столбцы `datname`, `usename`, `query` и другие строки не дублируют текст в
каждой строке `pg_stat_activity`. В теле хранится `StrId`, а байты находятся в
словарных телах PGM:

Ниже показана связь столбцов, а не посимвольный дамп Parquet. На диске `ts`
является `i64`, а каждый `StrId` является `u64`; обозначения `S_database` и
`S_query` заменяют конкретные числовые значения, одинаковые в обоих телах.

```text
тело pg_stat_activity, type_id = 1_001_003
+----------------+------+--------------------+------------------+
| ts             | pid  | datname            | query            |
+----------------+------+--------------------+------------------+
| 12:00:00       | 8241 | StrId(S_database)  | StrId(S_query)   |
+----------------+------+--------------------+------------------+

тело dict.strings, type_id = 3_001_001
+--------------------+------------------------------------------+
| str_id             | bytes                                    |
+--------------------+------------------------------------------+
| S_database         | "orders"                                 |
| S_query            | "select * from orders where id = $1"     |
+--------------------+------------------------------------------+
```

Короткие значения находятся в `dict.strings`, большие или усечённые могут
находиться в `dict.blobs`. Точная разметка и правила дедупликации описаны в
разделе [«Где физически живут строки»](../kronika-format/README.ru.md#где-физически-живут-строки).

## Пример: скорость транзакций из `pg_stat_database`

Для PostgreSQL 14–17 модуль источника формирует тип `1_005_003`. Одна строка
относится к одной базе данных:

```text
name      = "pg_stat_database"
sort_key  = ["datid", "ts"]
identity  = ["datid"]
```

Пусть для `datid = 16384` собраны два снимка с интервалом 60 секунд:

| Время | `datid` | `xact_commit` (`Cumulative`) | `numbackends` (`Gauge`) | `blk_read_time` (`Cumulative`) |
| --- | ---: | ---: | ---: | ---: |
| `12:00:00` | `16384` | `10 000` | `4` | `800 мс` |
| `12:01:00` | `16384` | `10 120` | `7` | `860 мс` |

`kronika-reader` сначала группирует обе строки по `identity = ["datid"]`, затем
интерпретирует каждый столбец по его роли:

```text
xact_commit:
    delta = 10 120 - 10 000 = 120 транзакций
    rate  = 120 / 60 = 2 транзакции/с

numbackends:
    значения ряда = 4, 7
    разность 7 - 4 не вычисляется, потому что это Gauge

blk_read_time при допустимых чтениях track_io_timing:
    delta = 860 - 800 = 60 мс
    rate  = 60 / 60 = 1 мс/с
```

Первая точка накопительного ряда не имеет предыдущего отсчёта и получает
`FirstPoint`. Если следующий `xact_commit` упадёт с `10 120` до `20`,
`kronika-reader` вернёт `Reset`, а не `-168,3 транзакции/с`. Интервал без
читаемого сегмента или части даёт `Gap`. Сведения `collection_coverage` и
`snapshot_coverage` являются отдельным сигналом и сами по себе не создают
`Gap`. Только две соседние допустимые точки дают приращение и скорость.

`blk_read_time` в PostgreSQL равен нулю, когда `track_io_timing` выключен.
Чтобы этот ноль не выглядел измеренным временем, контракт связывает столбец с
`reset_metadata.track_io_timing`. Для интервала между снимками
`kronika-reader` рассматривает дискретные чтения этого признака:

- последнее чтение на начало интервала равно `true`, а далее до конца интервала
  нет зафиксированных `false` или `NULL`: разность сохраняется;
- начальное состояние неизвестно либо есть чтение `false` или `NULL`:
  результат `NotCollected`.

Изменение GUC между двумя чтениями обнаружить невозможно. Кроме того,
`reset_metadata` хранит значение из сессии сборщика; интерпретация агрегатных
счётчиков предполагает одинаковую настройку у всех сессий, внёсших вклад.

Признак сбора не выключает SQL и не изменяет записанное исходное значение. Он
управляет интерпретацией уже прочитанной разности. В PostgreSQL 18 контракт
`PgStatIoV2` выбирает `track_wal_io_timing` для `read_time`, `write_time`,
`extend_time` и `fsync_time` у строк `object = "wal"`. Для `writeback_time` и
остальных строк остаётся `track_io_timing`.

### `NULL`, ноль и отсутствие измерения

| Состояние | Значение |
| --- | --- |
| `NULL` в столбце, допускающем `NULL` | Источник не вернул значение для конкретной строки. Например, `datname` отсутствует у общей строки `datid = 0`. |
| Число `0` | Реальное сохранённое значение. Нулевое приращение счётчика означает отсутствие прироста, а не отсутствие данных. |
| `NotCollected` | Причина отсутствия рассчитанного значения в ответе `kronika-reader`: показатель нельзя считать собранным на всём интервале. Это не ячейка Parquet. |
| `FirstPoint`, `Reset`, `Gap` | Другие причины, по которым для накопительного счётчика нет допустимой разности. |

Поиск аномалий выполняется позже: `kronika-analytics` получает рассчитанные
скорости для `Cumulative` и исходные значения для `Gauge`. Формулы, минимальное
число точек и пример с `xact_commit` описаны в
[`kronika-analytics`](../kronika-analytics/README.ru.md#как-pgkronika-определяет-аномалию).

## Режимы сбора

`Semantics` описывает, что означает одно тело секции. Он не запускает сбор и не
задаёт его период.

| `Semantics` | Обещание источника | Текущие примеры |
| --- | --- | --- |
| `SnapshotFull` | Обычный сбор пишет весь результат, который вернул модуль источника. Это не доказывает, что исходное представление PostgreSQL или ОС читалось без ограничений. | Большинство `pg_stat_*`, секций ОС и cgroup. |
| `ConditionalFull` | Полный снимок появляется только при выполнении условия сбора. Отсутствие тела само по себе не равно пустому источнику. | `pg_locks`, `pg_stat_progress_vacuum`, `pg_vacuum_observation`. |
| `EventStream` | Тело содержит события, замеченные за интервал сегмента. | Типизированные события журнала PostgreSQL. |
| `Changed` | Пишутся изменившиеся строки накопительных счётчиков и опорная строка `is_baseline`. | Поддерживается перечислением `Semantics` и `lint`, но текущих зарегистрированных контрактов нет. |
| `OnChange` | Снимок пишется при изменении либо при периодическом обновлении. | `pg_settings`, `os_mountinfo`, `os_topology`. |

Режим сбора не доказывает полноту конкретного снимка. Отбор N строк, тайм-аут,
недостаточные права или потеря на стороне сборщика являются отдельными
сигналами. Если источник не записал сведения о полноте, вывести её из
`semantics` нельзя.

## Полнота снимка

Число строк нельзя использовать как доказательство полноты. Реестр определяет
две служебные секции:

| Логическая секция | Что сообщает |
| --- | --- |
| `collection_coverage` (`1_023_001`) | Для типа `source_type_id`: нижняя оценка числа строк `total`, признак её неточности `unknown_total`, число записанных строк `collected`, предел `max_n`, ось `order_by`, граница `cutoff_value` и причина: `0` отбор N строк, `1` тайм-аут, `2` недостаточные права, `3` другое. |
| `snapshot_coverage` (`1_038_001`) | Для попытки получить снимок из нескольких строк: состояние чтения, видимость, число замеченных и надёжно записанных строк, а также пара `collector_pid` и `collector_started_at`. |

Старый сегмент без `snapshot_coverage` имеет неизвестную полноту, а не
автоматически полную. Служебная секция не восстанавливает отброшенные строки и
не меняет автоматически каждый ответ запроса. Она предоставляет сведения о
полноте; конкретный потребитель должен явно учитывать их при построении
результата.

## Кодирование и проверки

Внутренний макрос `#[derive(Section)]` строит из одной именованной
Rust-структуры:

- `TypeContract`;
- точную Arrow-схему;
- кодирование и декодирование Parquet;
- вычисление диапазона `ts`.

Перед записью кодек проверяет число строк, строит Arrow-массивы, сортирует
`RecordBatch` по `sort_key` и пишет самостоятельный файл Parquet с Zstd уровня
3. Служебные данные Arrow не дублируются, поле `created_by` оставляется пустым.

При чтении `decode_any`, `decode_rows` и `Section::decode` принимают
`VerifiedSection`: CRC32C тела уже должен совпасть со значением каталога. До
чтения данных проверяются размер тела, метаданные Parquet, число групп строк и
заявленное число строк. Затем декодер требует точного совпадения схемы и
запрещает `NULL` в обязательных столбцах.

Жёсткие пределы скомпилированы в код:

| Предел | Значение |
| --- | ---: |
| Строк в одном теле | `65 536` |
| Размер одного тела | `8 МиБ` |
| Групп строк Parquet | `16` |
| Элементов `ListI32` в одной строке | `4 096` |
| Элементов `ListI32` во всём теле | `262 144` |

Превышение предела, неизвестный `type_id`, несовпадение схемы, неверный CRC или
ошибка Parquet возвращают `CodecError`. Кодек ничего не обрезает автоматически.
Модуль источника должен уменьшить объём до кодирования. При усечении таблиц,
индексов, запросов и планов текущий `pg_kronika-collector` пишет
`collection_coverage`; другие пределы источников не создают эту секцию
автоматически. Ошибка кодирования срывает текущее окно;
`pg_kronika-collector` фиксирует ошибку и продолжает работу в следующем цикле.

`lint` проверяет уникальность `type_id`, наличие столбцов ключей, требования к
`ts`, `identity` и `Changed`, а также допустимый `eps_abs`. `lint_references`
проверяет ссылки признаков сбора, их булев тип, селекторы строк и
согласованность между версиями. Эти проверки сейчас не сопоставляют класс
`type_id` с режимом `semantics`.

## Что можно настраивать

У `kronika-registry` нет CLI, переменных окружения или конфигурационного файла.
Оператор не может во время запуска изменить `type_id`, схему, роли столбцов,
ключи, Zstd-3 или пределы кодека.

| Задача | Где она настраивается |
| --- | --- |
| Частота `pg_stat_activity`, `pg_stat_database`, ОС и других источников | `*_INTERVAL_S` в [`pg_kronika-collector`](../../bins/pg_kronika-collector/README.ru.md#расписание). |
| Отбор N таблиц, индексов, запросов и планов | `KRONIKA_PG_MAX_TABLES`, `KRONIKA_PG_MAX_INDEXES`, `KRONIKA_PG_MAX_STATEMENTS` и `KRONIKA_PG_MAX_PLANS` в [ограничениях сборщика](../../bins/pg_kronika-collector/README.ru.md#ограничения-cardinality-и-хранения). |
| Тайм-ауты, исключённые базы и бюджет цикла | `KRONIKA_PG_STATEMENT_TIMEOUT_MS`, `KRONIKA_PG_LOCK_TIMEOUT_MS`, `KRONIKA_PG_IDLE_IN_TX_TIMEOUT_MS`, `KRONIKA_PG_HEAVY_TIMEOUT_CAP_MS`, `KRONIKA_PG_EXCLUDE_DATABASES` и `KRONIKA_CYCLE_DB_BUDGET_MS` в [настройках подключений](../../bins/pg_kronika-collector/README.ru.md#подключения-и-ограничения-запросов). |
| Ротация открытого сегмента и предел журнала | `KRONIKA_SEGMENT_MAX_BYTES` задаёт порог по сырым байтам `active.parts` после добавления окна; `KRONIKA_SEGMENT_MAX_AGE_S` задаёт возраст; `KRONIKA_JOURNAL_MAX_BYTES` является жёстким пределом журнала. См. [ограничения сборщика](../../bins/pg_kronika-collector/README.ru.md#ограничения-cardinality-и-хранения). |
| Окно, шаг и порог поиска аномалий | [Параметры запросов `pg_kronika-web`](../kronika-analytics/README.ru.md#аномалии-и-инциденты). |

`BytesPool` является ограниченным пулом повторно используемых входных буферов и
не кэширует распакованные Arrow-массивы. Его `buffer_limit` решает, можно ли
удержать возвращённый буфер, но не запрещает выданному буферу временно вырасти.
Компоненты PgKronika сейчас не предоставляют оператору настройки `BytesPool`.

## Как изменить реестр

Изменение типа секции затрагивает совместимость данных, поэтому одного нового
поля в Rust-структуре недостаточно:

1. Определите, остаётся ли прежний смысл логической секции. Новая сущность
   получает новый `SSS`; новая схема той же сущности увеличивает `VVV`.
2. Не переиспользуйте существующий `type_id`. Даже новый столбец, допускающий
   `NULL`, требует новой версии.
3. Добавьте структуру и аннотации в `src/codec/`, затем включите её контракт в
   `registry()` в `src/lib.rs`.
4. В модуле источника явно выберите новую схему по версии PostgreSQL,
   расширения или другого источника.
5. Сохраните тип и роль общих столбцов, а также `sort_key`, если версии должны
   объединяться одним `name`. Изменение состава `identity` меняет ключи и может
   разделить старые и новые ряды; перестановка тех же имён ключ не меняет.
6. Добавьте тесты прямого и обратного преобразования, схемы, пределов и `lint`.
   Для признака сбора обновите межсекционные проверки.
7. Синхронно обновите таблицу распределения идентификаторов и документацию.

Исполняемая схема находится в [`src/lib.rs`](src/lib.rs),
[`src/contract.rs`](src/contract.rs) и [`src/codec/`](src/codec/). Правила
распределения и перечень типов находятся в
[`docs/type-registry.md`](../../docs/type-registry.md), а дополнительные
заметки о режимах сбора в
[`docs/type-registry/semantics.md`](../../docs/type-registry/semantics.md).
Эти документы также описывают зарезервированные и проектируемые варианты:
наличие записи в заметках не означает, что текущий `registry()` уже содержит
кодек.
