# kronika-registry

[English version](README.md)

`kronika-registry` задаёт общий язык между сбором, записью и чтением данных
PgKronika. Запись каталога PGM содержит смещение, размер, число строк, CRC32C и
другие поля, но единственным идентификатором схемы служит числовой `type_id`.
По этому числу реестр определяет:

- имена и физическое представление столбцов тела секции;
- какие значения — накопительные счётчики, gauge, метки или время снимка;
- порядок сортировки строк и какие метки объединяют отсчёты в один временной ряд;
- как несколько схем одного источника после обновления PostgreSQL образуют одну
  логическую секцию;
- каким кодеком типизированные строки превращаются в Parquet и читаются обратно.

Это не отдельный процесс, файл конфигурации или таблица внутри PGM. Реестр —
статический список `TypeContract`, скомпилированный в библиотеки и бинарники
PgKronika. Полный контракт в PGM не записывается: writer и reader должны
одинаково понимать каждый `type_id`. Parquet-тело содержит физические имена и
типы столбцов, но не объявляет их роли, `identity`, `semantics` и ворота сбора.
Декодер использует встроенную схему Parquet для проверки, а не как замену
реестру.

Параметры запуска перечислены в разделе
[«Что можно настраивать»](#что-можно-настраивать). У самого реестра настроек
времени выполнения нет.

## Место в потоке данных

```text
PostgreSQL / Linux / cgroup / журнал PostgreSQL
        |
        | источник выбирает структуру под свою версию
        | строковые и двоичные значения интернируются: байты -> StrId
        v
типизированные строки из kronika-registry
        |
        | Section::encode
        | точная Arrow-схема -> сортировка -> Parquet + Zstd-3
        v
тело секции
        |
        | kronika-writer добавляет запись каталога и словари
        v
active.parts / готовый PGM
        |
        | каталог: type_id, offset, len, rows, CRC32C
        | CRC32C -> поиск контракта -> проверка схемы -> декодирование
        v
kronika-reader
        |
        | разрешение StrId, объединение версий, временные ряды, diff
        v
pg_kronika-web / kronika-analytics
```

Внешнюю разметку файла, каталог, `StrId` и правила размещения словарей задаёт
[`kronika-format`](../kronika-format/README.ru.md). Реестр резервирует
словарные `type_id` и владеет смыслом и кодеком тела типизированной секции.
[`kronika-writer`](../kronika-writer/README.ru.md) кодирует словарные тела и
пишет части и готовые сегменты;
[`kronika-reader`](../kronika-reader/README.ru.md) декодирует словари и строит
логические запросы.

### Три значения слова «секция»

| Термин | Что он означает |
| --- | --- |
| Физическая секция PGM | Запись каталога и диапазон байтов, на который она указывает. Для зарегистрированного типа тело — самодостаточный файл Parquet. |
| Тип секции | Один `type_id` и его кодек. У типизированных секций есть `TypeContract`; словари — исключение: у них отдельные идентификаторы и кодеки без записи в `registry()`. Например, `1_005_003` задаёт схему `pg_stat_database` для PostgreSQL 14–17. |
| Логическая секция | Объединение всех зарегистрированных версий с одинаковым `name`. Например, четыре версии `pg_stat_database` читаются как один источник. |

Трейт `Section` реализован для Rust-структуры, описывающей одну строку, а не
для каждого экземпляра строки. Закрытый трейт и внутренний макрос
`#[derive(Section)]` не дают стороннему крейту незаметно зарегистрировать
собственную схему.

## Что хранит контракт

`registry()` возвращает статический список контрактов. Один `TypeContract`
содержит:

| Поле | Что это значит на практике |
| --- | --- |
| `type_id` | Выбирает точную схему и кодек тела. Назначается в `#[section(id = ...)]`, а не вычисляется из имени, OID или хэша. |
| `name` | Объединяет версии в одну логическую секцию при чтении. |
| `semantics` | Определяет, какие строки попадают в тело и при каком условии оно появляется. |
| `columns` | Фиксирует порядок, физический тип, роль, допустимость `NULL` и необязательные ворота сбора для каждого столбца. |
| `sort_key` | Задаёт канонический порядок строк перед кодированием. |
| `identity` | Задаёт метки одного временного ряда для расчёта diff. Если пуст, reader использует `sort_key` без `ts`. |
| `deprecated` | Помечает схему, которую больше не пишут; контракт остаётся для чтения старых данных. Сейчас у всех зарегистрированных контрактов `false`. |

Контракт не содержит SQL, расписание, правила top-N, тайм-ауты, ротацию
сегментов или источник сброса счётчика. Эти решения — за модулями источников,
коллектором, writer и reader. Ворота сбора — свойство отдельных столбцов, а не
расписания запросов.

### Роли столбцов

В реестре ровно четыре варианта `ColumnClass`:

| Роль | Что хранится | Что делает reader |
| --- | --- | --- |
| `Timestamp` | Обязательный `ts: Ts`, время снимка в микросекундах Unix. | Ставит строки на временную ось. |
| `Label` | Идентификатор или атрибут сущности: OID, PID, имя, тип, флаг. | Может войти в ключ ряда; сам по себе `Label` ещё не означает `identity`. |
| `Cumulative` | Накопительный счётчик, например `xact_commit`. | Сравнивает соседние отсчёты одного ряда и считает приращение и скорость в секунду. |
| `Gauge` | Мгновенное значение, например `numbackends`, возраст XID или размер. | Возвращает исходные значения, не вычитая соседние точки. |

`identity` — не пятая роль столбца. Это отдельный список имён `Label`-столбцов.
Класса `Constant` тоже нет.

Физические типы: узкие знаковые и беззнаковые целые, `f32`, `f64`, `bool`,
`Ts`, `StrId` и `ColumnType::ListI32`. Последний соответствует Arrow
`List<Int32>` и Rust-полю `Vec<i32>`. Кодек выбирает самый узкий подходящий тип:
PID хранится как `i32`, а не `i64`. `Option<T>` разрешает физический `NULL`;
`NULL` в обязательном столбце — ошибка декодирования.

## Как читать `type_id`

В коде идентификатор пишут как `C_SSS_VVV`:

```text
1_005_003
| |   |
| |   `-- VVV: версия схемы хранения, 003
| `------ SSS: номер типа внутри класса, 005
`-------- C: класс секции, 1
```

На диске это обычный `u32` со значением `1005003`; подчёркивания — только для
глаз. Части означают:

- `C`: класс секции;
- `SSS`: выделенный номер типа внутри класса;
- `VVV`: версия физической схемы и её смысла.

`SSS` различает семейства секций. `VVV` — не версия PostgreSQL и не версия
контейнера PGM. Соответствие между конкретной версией входных данных и `VVV`
задаёт код модуля источника.

| Класс | Значение | Текущее использование |
| ---: | --- | --- |
| `1` | `Snapshot` | Все типизированные контракты из текущего `registry()`. Сюда пока входят и секции событий журнала PostgreSQL. |
| `2` | `Event` | Класс известен `TypeId`, но зарегистрированных контрактов с ним сейчас нет. |
| `3` | `Dictionary` | `dict.strings = 3_001_001` и `dict.blobs = 3_002_001`; кодируются отдельно, в `registry()` не входят. |
| `10` | `Chart` | Зарезервирован в `TypeId`; зарегистрированных контрактов сейчас нет. |

Класс в `type_id` и `semantics` контракта — разные вещи. Линтер не проверяет их
соответствие, так что наличие класса в перечислении само по себе не означает
наличия готового источника или кодека.

### Не путать идентификаторы

| Идентификатор | Что он различает |
| --- | --- |
| `type_id` | Схему тела секции — например, одну версию `pg_stat_activity`. |
| `StrId` | Текстовое или двоичное значение в словарных секциях PGM. |
| `query_id`, `plan_id`, OID, PID | Данные PostgreSQL или ОС внутри строки; кодек они не выбирают. |

## Пример: обновление PostgreSQL и `pg_stat_activity`

`pg_stat_activity` менялся между версиями. Один `type_id` не может описать все
варианты без догадок:

| PostgreSQL | Rust-структура | `type_id` | Отличие |
| --- | --- | ---: | --- |
| 10–12 | `PgStatActivityV1` | `1_001_001` | Нет `leader_pid` и `query_id`. |
| 13 | `PgStatActivityV2` | `1_001_002` | Добавлен `leader_pid`. |
| 14–18 | `PgStatActivityV3` | `1_001_003` | Добавлен `query_id`. |

Источник узнаёт мажорную версию сервера при подключении и выбирает подходящий
SQL и структуру. Для `pg_stat_statements` схема выбирается по версии расширения
из `pg_extension`, а не по мажорной версии PostgreSQL.

У всех трёх контрактов:

```text
name      = "pg_stat_activity"
semantics = SnapshotFull
sort_key  = ["ts", "pid"]
identity  = []             # reader использует pid из sort_key
```

Сборка `kronika-reader`, содержащая все три контракта, находит их `type_id` по
`name`, проверяет совпадение `sort_key` и строит объединение столбцов. Столбцы
идут в порядке первого появления: сначала вся схема V1, затем `leader_pid` из
V2, затем `query_id` из V3. При чтении старого тела отсутствующие значения
становятся `NULL`:

```text
тело 1_001_001: ts | pid | datname | ... | state_change
тело 1_001_002: ts | pid | leader_pid | datname | ... | state_change
тело 1_001_003: ts | pid | leader_pid | datname | ... | query | query_id | ... | state_change
                                      |
                                      v
логическая pg_stat_activity:
ts | pid | datname | ... | state_change | leader_pid? | query_id?
```

Знак `?` означает, что в объединённом представлении столбец допускает `NULL` —
в том числе потому, что старые схемы его не содержали.

Старый PGM переписывать не нужно, пока reader хранит контракт старого `type_id`.
Неизвестный `type_id` не становится самодокументированным: контейнер можно
открыть и незнакомую секцию пропустить, но прямой вызов `decode_any` вернёт
`UnknownType`.

Даже добавление nullable-столбца требует нового `type_id`. Декодер проверяет
точное число, порядок, типы и допустимость `NULL` по Arrow-схеме; совместимость
по содержимому Parquet он не угадывает.

### Где хранятся строковые значения

Столбцы `datname`, `usename`, `query` и другие строки не дублируют текст в
каждой строке `pg_stat_activity`. В теле хранится `StrId`, а байты живут в
словарных телах PGM.

Ниже — связь столбцов, а не посимвольный дамп Parquet. На диске `ts` — `i64`,
каждый `StrId` — `u64`; `S_database` и `S_query` обозначают конкретные числовые
значения, общие для обоих тел.

```text
тело pg_stat_activity, type_id = 1_001_003
+----------------+------+--------------------+------------------+
| ts             | pid  | datname            | query            |
+----------------+------+--------------------+------------------+
| 12:00:00       | 8241 | StrId(S_database)  | StrId(S_query)   |
+----------------+------+--------------------+------------------+

тело dict.strings, type_id = 3_001_001
+--------------------+------------------------------------------+
| str_id             | bytes                                    |
+--------------------+------------------------------------------+
| S_database         | "orders"                                 |
| S_query            | "select * from orders where id = $1"     |
+--------------------+------------------------------------------+
```

Короткие значения живут в `dict.strings`, большие или усечённые — в
`dict.blobs`. Точная разметка и правила дедупликации описаны в разделе
[«Где физически живут строки»](../kronika-format/README.ru.md#где-физически-живут-строки).

## Пример: скорость транзакций из `pg_stat_database`

Для PostgreSQL 14–17 источник пишет тип `1_005_003`. Одна строка — одна база:

```text
name      = "pg_stat_database"
sort_key  = ["datid", "ts"]
identity  = ["datid"]
```

Пусть для `datid = 16384` собраны два снимка с интервалом 60 секунд:

| Время | `datid` | `xact_commit` (`Cumulative`) | `numbackends` (`Gauge`) | `blk_read_time` (`Cumulative`) |
| --- | ---: | ---: | ---: | ---: |
| `12:00:00` | `16384` | `10 000` | `4` | `800 мс` |
| `12:01:00` | `16384` | `10 120` | `7` | `860 мс` |

Reader сначала группирует обе строки по `identity = ["datid"]`, затем
интерпретирует каждый столбец согласно его роли:

```text
xact_commit:
    delta = 10 120 - 10 000 = 120 транзакций
    rate  = 120 / 60 = 2 транзакции/с

numbackends:
    значения ряда = 4, 7
    разность 7 - 4 не вычисляется — это Gauge

blk_read_time при допустимых чтениях track_io_timing:
    delta = 860 - 800 = 60 мс
    rate  = 60 / 60 = 1 мс/с
```

Первая точка накопительного ряда не имеет предыдущего отсчёта и получает
`FirstPoint`. Если следующий `xact_commit` упадёт с `10 120` до `20`, reader
вернёт `Reset`, а не `-168,3 транзакции/с`. Интервал без читаемого сегмента или
части даёт `Gap`. `collection_coverage` и `snapshot_coverage` — отдельный
сигнал, сами по себе `Gap` они не создают. Приращение и скорость дают только
две соседние допустимые точки.

`blk_read_time` в PostgreSQL равен нулю, когда `track_io_timing` выключен.
Чтобы этот ноль не выглядел измеренным временем, контракт привязывает столбец к
`reset_metadata.track_io_timing`. Для интервала между снимками reader
просматривает дискретные чтения этого признака:

- последнее чтение на начало интервала — `true`, и до конца интервала нет
  зафиксированных `false` или `NULL`: разность принимается;
- начальное состояние неизвестно либо есть чтение `false` или `NULL`: результат
  `NotCollected`.

Смену GUC между чтениями заметить невозможно. Кроме того, `reset_metadata`
хранит значение из сессии коллектора; интерпретация агрегатных счётчиков
предполагает, что все сессии, внёсшие вклад, используют одну настройку.

Ворота сбора не выключают SQL и не меняют записанное исходное значение. Они
управляют интерпретацией уже декодированной разности. В PostgreSQL 18 контракт
`PgStatIoV2` выбирает `track_wal_io_timing` для `read_time`, `write_time`,
`extend_time` и `fsync_time` в строках `object = "wal"`. Для `writeback_time`
и остальных строк действует `track_io_timing`.

### `NULL`, ноль и отсутствие измерения

| Состояние | Значение |
| --- | --- |
| `NULL` в nullable-столбце | Источник не вернул значение для этой строки. Например, `datname` отсутствует у общей строки `datid = 0`. |
| Число `0` | Реальное сохранённое значение. Нулевое приращение счётчика — отсутствие прироста, а не отсутствие данных. |
| `NotCollected` | Причина в ответе reader: метрику нельзя считать собранной на всём интервале. Это не ячейка Parquet. |
| `FirstPoint`, `Reset`, `Gap` | Другие причины, по которым у накопительного счётчика нет допустимой разности. |

Поиск аномалий — позже. `kronika-analytics` получает рассчитанные скорости для
`Cumulative` и исходные значения для `Gauge`. Формулы, минимум точек и пример с
`xact_commit` — в
[`kronika-analytics`](../kronika-analytics/README.ru.md#как-pgkronika-определяет-аномалию).

## Режимы сбора

`Semantics` описывает, что означает одно тело секции. Он не запускает сбор и не
задаёт его период.

| `Semantics` | Обещание источника | Текущие примеры |
| --- | --- | --- |
| `SnapshotFull` | Обычный сбор пишет полный результат, который вернул модуль источника. Это не доказывает, что исходное представление PostgreSQL или ОС читалось без ограничений. | Большинство `pg_stat_*`, секций ОС и cgroup. |
| `ConditionalFull` | Полный снимок появляется только при выполнении условия сбора. Отсутствие тела само по себе не равно пустому источнику. | `pg_locks`, `pg_stat_progress_vacuum`, `pg_vacuum_observation`. |
| `EventStream` | Тело содержит события, замеченные за интервал сегмента. | Типизированные события журнала PostgreSQL. |
| `Changed` | Пишутся изменившиеся строки накопительных счётчиков и опорная строка `is_baseline`. | Поддерживается перечислением `Semantics` и линтером, но зарегистрированных контрактов пока нет. |
| `OnChange` | Снимок пишется при изменении или при периодическом обновлении. | `pg_settings`, `os_mountinfo`, `os_topology`, `pg_log_source_status`. |

Режим сбора не доказывает полноту конкретного снимка. Top-N, тайм-аут,
недостаточные права и потери на стороне коллектора — отдельные сигналы. Если
источник не записал сведения о полноте, вывести её из `semantics` нельзя.

| Логическая секция | Что означает строка `OnChange` |
| --- | --- |
| `pg_log_source_status` (`1_039_001`) | Состояние источника журнала PostgreSQL при первом наблюдении, после изменения `state`, `reason`, парсера или пути либо при периодическом обновлении. Успешное чтение без новых строк даёт `collecting`; это служебное состояние не участвует в поиске аномалий и оценке здоровья. |

## Полнота снимка

Число строк — не доказательство полноты. Реестр определяет две provenance-секции:

| Логическая секция | Что сообщает |
| --- | --- |
| `collection_coverage` (`1_023_001`) | Для `section_type_id`: нижняя оценка `total`, флаг неточности `unknown_total`, число записанных строк `collected`, предел `max_n`, ось `order_by`, граница `cutoff_value` и причина: `0` — top-N, `1` — тайм-аут, `2` — недостаточные права, `3` — другое. |
| `snapshot_coverage` (`1_038_001`) | Для попытки получить многострочный снимок: состояние чтения, видимость, число замеченных и надёжно записанных строк, а также `collector_pid` и `collector_started_at`. |

Старый сегмент без `snapshot_coverage` имеет неизвестную полноту, а не
автоматически полную. Provenance-секция не восстанавливает отброшенные строки и
не меняет автоматически каждый ответ запроса. Она предоставляет сведения о
полноте; каждый потребитель должен явно их учесть при построении результата.

## Кодирование и проверки

Внутренний макрос `#[derive(Section)]` из одной именованной Rust-структуры
строит:

- `TypeContract`;
- точную Arrow-схему;
- кодировщик и декодировщик Parquet;
- вычисление диапазона `ts`.

Перед записью кодек проверяет число строк, строит Arrow-массивы, сортирует
`RecordBatch` по `sort_key` и пишет самодостаточный файл Parquet с Zstd уровня
3. Метаданные Arrow опускаются, `created_by` остаётся пустым.

При чтении `decode_any`, `decode_rows` и `Section::decode` принимают
`VerifiedSection`: CRC32C тела уже должен совпасть с записью каталога. До
чтения данных проверяются размер тела, метаданные Parquet, число групп строк и
заявленное число строк. Затем декодер требует точного совпадения схемы и
отвергает `NULL` в обязательных столбцах.

Жёсткие пределы зашиты в кодек:

| Предел | Значение |
| --- | ---: |
| Строк в одном теле | `65 536` |
| Размер одного тела | `8 МиБ` |
| Групп строк Parquet | `16` |
| Элементов `ListI32` в одной строке | `4 096` |
| Элементов `ListI32` во всём теле | `262 144` |

Превышение предела, неизвестный `type_id`, несовпадение схемы, неверный CRC или
ошибка Parquet возвращают `CodecError`. Кодек никогда не обрезает автоматически.
Модуль источника должен уменьшить вывод до кодирования. При усечении таблиц,
индексов, запросов и планов текущий коллектор пишет `collection_coverage`;
другие пределы источников не создают эту секцию автоматически. Ошибка
кодирования срывает текущее окно; коллектор фиксирует ошибку и продолжает
работу в следующем цикле.

`lint` проверяет уникальность `type_id`, наличие ключевых столбцов, требования
к `ts`, `identity` и `Changed`, а также допустимый `eps_abs`. `lint_references`
проверяет ссылки ворот сбора, их булев тип, селекторы строк и согласованность
между версиями. Сейчас линтер не проверяет соответствие класса `type_id` и
`semantics`.

## Что можно настраивать

У `kronika-registry` нет CLI, переменных окружения или конфигурационного файла.
Оператор не может изменить во время работы `type_id`, схему, роли столбцов,
ключи, Zstd-3 или пределы кодека.

| Задача | Где настраивается |
| --- | --- |
| Частота `pg_stat_activity`, `pg_stat_database`, ОС и других источников | `*_INTERVAL_S` в [`pg_kronika-collector`](../../bins/pg_kronika-collector/README.ru.md#расписание). |
| Top-N таблиц, индексов, запросов и планов | `KRONIKA_PG_MAX_TABLES`, `KRONIKA_PG_MAX_INDEXES`, `KRONIKA_PG_MAX_STATEMENTS` и `KRONIKA_PG_MAX_PLANS` в [ограничениях коллектора](../../bins/pg_kronika-collector/README.ru.md#ограничения-кардинальности-и-хранения). |
| Тайм-ауты, исключённые базы и бюджет цикла | `KRONIKA_PG_STATEMENT_TIMEOUT_MS`, `KRONIKA_PG_LOCK_TIMEOUT_MS`, `KRONIKA_PG_IDLE_IN_TX_TIMEOUT_MS`, `KRONIKA_PG_HEAVY_TIMEOUT_CAP_MS`, `KRONIKA_PG_EXCLUDE_DATABASES` и `KRONIKA_CYCLE_DB_BUDGET_MS` в [настройках подключений](../../bins/pg_kronika-collector/README.ru.md#подключения-и-ограничения-запросов). |
| Ротация открытого сегмента и предел журнала | `KRONIKA_SEGMENT_MAX_BYTES` — порог по сырым байтам `active.parts` после добавления окна; `KRONIKA_SEGMENT_MAX_AGE_S` — возраст; `KRONIKA_JOURNAL_MAX_BYTES` — жёсткий предел журнала. См. [ограничения коллектора](../../bins/pg_kronika-collector/README.ru.md#ограничения-кардинальности-и-хранения). |
| Окно, шаг и порог поиска аномалий | [Параметры запросов `pg_kronika-web`](../kronika-analytics/README.ru.md#аномалии-и-инциденты). |

`BytesPool` — ограниченный пул переиспользуемых входных буферов, не кэширует
распакованные Arrow-массивы. Его `buffer_limit` решает, удерживать ли
возвращённый буфер, но не запрещает выданному буферу временно вырасти. Текущие
компоненты PgKronika не выставляют настройки `BytesPool` оператору.

## Как изменить реестр

Изменение типа секции затрагивает совместимость данных — одного нового поля в
Rust-структуре недостаточно:

1. Решите, сохраняется ли смысл логической секции. Новая сущность получает новый
   `SSS`; новая схема той же сущности увеличивает `VVV`.
2. Никогда не переиспользуйте существующий `type_id`. Даже новый nullable-столбец
   требует новой версии.
3. Добавьте структуру и аннотации в `src/codec/`, затем включите её контракт в
   `registry()` в `src/lib.rs`.
4. В модуле источника явно выберите новую схему по версии PostgreSQL, расширения
   или другого источника.
5. Сохраните тип и роль общих столбцов, а также `sort_key`, если версии должны
   объединяться под одним `name`. Изменение состава `identity` меняет ключ ряда и
   может разделить старые и новые ряды; перестановка тех же имён — нет.
6. Добавьте тесты round-trip, схемы, пределов и линтера. Для ворот сбора
   обновите межсекционные проверки.
7. В том же изменении обновите таблицу распределения идентификаторов и
   документацию.

Исполняемая схема — в [`src/lib.rs`](src/lib.rs),
[`src/contract.rs`](src/contract.rs) и [`src/codec/`](src/codec/). Распределение
идентификаторов и перечень типов — в
[`docs/type-registry.md`](../../docs/type-registry.md), дополнительные заметки
о режимах сбора — в
[`docs/type-registry/semantics.md`](../../docs/type-registry/semantics.md).
Эти документы также описывают зарезервированные и проектируемые варианты; запись
в заметках не означает, что текущий `registry()` уже содержит кодек.
