# kronika-format

[English version](README.md)

`kronika-format` задаёт двоичный контракт, который позволяет одному процессу
PgKronika закончить запись сегмента, а другому — открыть его позже. Это не
самостоятельный конвертер и не универсальный формат аналитических данных.

Внутри PgKronika крейт связывает путь записи на диск с путём чтения:

```text
PostgreSQL / Linux / cgroup / журнал PostgreSQL
        |
        v
pg_kronika-collector собирает одно окно
        |
        v
kronika-registry кодирует типизированные строки в тела секций
        |
        v
kronika-writer строит самодостаточную часть PGM
        |
        v
active.parts --seal--> <первая_метка_времени>.pgm
                              |
                              v
                  kronika-store / kronika-reader
                              |
                              v
                       pg_kronika-web
```

Журнал `active.parts` и готовые файлы `.pgm` лежат прямо в
`KRONIKA_OUT_DIR`. Например:

```text
$KRONIKA_OUT_DIR/
|-- active.parts
|-- <первая_метка>.pgm
`-- <следующая_метка>.pgm
```

Отдельных файлов для строк нет. Пока сегмент открыт, словарные тела находятся
в самодостаточных PGM-частях внутри `active.parts`. При запечатывании код
записи декодирует части, нормализует словари и пишет один компактный PGM.

Крейт формата задаёт обрамление PGM, байты журнального кадра, концевой каталог,
контрольные суммы CRC32C, `StrId` и модель словарей с ограничениями. Он не
отвечает за:

- семантику данных PostgreSQL и Linux и схемы секций — их задаёт
  [`kronika-registry`](../kronika-registry/README.ru.md);
- кодирование Parquet, буферизацию, файловый журнал и `seal` — их реализует
  [`kronika-writer`](../kronika-writer/README.ru.md);
- интервалы сбора, ротацию и ограничения источников — их задаёт
  [`pg_kronika-collector`](../../bins/pg_kronika-collector/README.ru.md);
- поиск файлов, типизированные запросы, HTTP, сроки хранения, шифрование
  и удалённое хранилище.

## От окна сбора до сегмента

Коллектор создаёт новый интернер и буферы строк для каждого непустого цикла
сбора. Реестр сортирует каждую секцию снимка по ключу её контракта и кодирует
её. Код записи добавляет словарные секции, строит самодостаточную PGM-часть,
упаковывает её в 16-байтный журнальный кадр, дописывает в `active.parts` и
синхронизирует запись.

Коллектор дописывает окна, пока сегмент не закроется по возрасту, размеру,
принудительной ротации, давлению журнала или лимиту компактного результата.
При запечатывании:

1. каждая записанная часть проверяется и учитывается в лимитах до начала
   публикации;
2. каждая секция данных декодируется в канонически отсортированную
   последовательность;
3. последовательности сливаются группами не более 32, а промежуточные тела
   пишутся рядом с целевым файлом в пределах жёсткого лимита;
4. словарные записи проверяются и дедуплицируются по `str_id`;
5. для каждого присутствующего `type_id` пишется ровно одно компактное тело,
   затем один концевой каталог и хвостовой индекс;
6. соседний временный файл синхронизируется, публикуется без замены другого
   готового файла, затем синхронизируется родительский каталог;
7. коллектор очищает `active.parts` только после успешной публикации.

При ошибке запечатывания синхронизированный журнал остаётся для следующей
попытки. Код записи сообщает объёмы исходных данных, промежуточных файлов,
результата и всех записей, а также принятый лимит памяти. Эти значения
используются в квалификации релиза и диагностике.

### Окна, части, секции и тела

В описании формата четыре уровня:

- **окно сбора** — один непустой цикл коллектора;
- **PGM-часть** — самодостаточная запись одного окна: свой маркер PGM, тела,
  каталог и хвостовой индекс;
- **секция** — одна запись каталога: `type_id`, смещение, длина, число строк
  и CRC32C;
- **тело секции** — байтовый диапазон, на который указывает запись каталога.
  Код записи помещает туда самодостаточный файл Parquet.

Пока сегмент открыт, каждая часть упакована в свой журнальный кадр:

```text
active.parts
|
+-- журнальный кадр #1
|   `-- PGM-часть окна #1
|       |-- маркер PGM
|       |-- тела данных и словарей
|       |-- каталог части
|       `-- хвостовой индекс
|
`-- журнальный кадр #2
    `-- PGM-часть окна #2
        |-- маркер PGM
        |-- тела данных и словарей
        |-- каталог части
        `-- хвостовой индекс
```

Внутри каждой части код записи размещает непустые тела данных по возрастанию
`type_id`, затем `dict.strings`, затем `dict.blobs`. Отсутствующая словарная
секция не занимает места. Код чтения находит каждое тело через каталог.

Запечатывание сегмента объединяет части:

```text
active.parts                         <первая_метка>.pgm

кадр [часть окна #1]                 маркер PGM
кадр [часть окна #2] -- seal() ->    одно тело для каждого присутствующего type_id
...                                  одно нормализованное тело dict.strings, если нужно
                                     одно нормализованное тело dict.blobs, если нужно
                                     один концевой каталог
                                     один хвостовой индекс
```

В готовом PGM нет явных границ окон. Строки из всех принятых окон расположены
в каноническом порядке реестра. Каталог описывает типы секций, а не окна сбора.

## Разметка готового PGM

Все целые — little-endian. В каноническом выводе текущего модуля записи поля
упакованы без выравнивающих отступов. Пусть в каталоге `N` записей, а суммарный
размер тел секций — `B` байт:

```text
смещение  размер        содержимое
0         4             маркер PGM
4         B             тело 0, тело 1, ... в порядке каталога
4+B       32*N          записи каталога
...       40            метаданные каталога
...       8             хвостовой индекс
```

Точный размер файла:

```text
pgm_bytes = B + 32*N + 52
catalog_len = 32*N + 40
```

52 постоянных байта — начальный маркер, метаданные каталога и хвостовой индекс.
Внешнего сжатия нет. Тела текущего PGM упакованы без зазоров, а `type_id`
строго возрастают.

### Запись каталога: 32 байта

| Смещение | Поле | Тип | Значение |
| ---: | --- | --- | --- |
| 0 | `type_id` | `u32` | Схема секции из `kronika-registry`. |
| 4 | `flags` | `u32` | Зарезервировано; текущая запись пишет ноль. |
| 8 | `offset` | `u64` | Абсолютное смещение тела от начала файла. |
| 16 | `len` | `u64` | Размер тела в байтах. |
| 24 | `rows` | `u32` | Число логических строк в теле. |
| 28 | `crc32c` | `u32` | CRC32C этого тела. |

Каждый присутствующий `type_id` встречается ровно один раз. Записи каталога и
их плотно упакованные тела расположены по возрастанию `type_id`.

### Метаданные каталога: 40 байт

| Смещение | Поле | Тип | Значение |
| ---: | --- | --- | --- |
| 0 | `min_ts` | `i64` | Самая ранняя метка среди секций, микросекунды Unix. |
| 8 | `max_ts` | `i64` | Самая поздняя метка среди секций, микросекунды Unix. |
| 16 | `source_id` | `u64` | Идентификатор источника; ноль означает, что он не задан. |
| 24 | `entry_count` | `u32` | Число 32-байтных записей перед этим блоком. |
| 28 | `format_version` | `u32` | Значение внутреннего контракта каталога; код записи пишет `1`. |
| 32 | `crc32c` | `u32` | CRC32C записей и метаданных; при расчёте поле обнулено. |
| 36 | `reserved` | `u32` | Зарезервировано; текущая запись пишет ноль. |

Коллектор копирует в поле `KRONIKA_SOURCE_ID` и не требует соответствующей
записи в `dict.strings`. Код чтения считает `source_id` непрозрачным
идентификатором, а не ссылкой на строку.

### Хвостовой индекс: 8 байт

| Смещение | Поле | Тип | Значение |
| ---: | --- | --- | --- |
| 0 | `catalog_len` | `u32` | Записи плюс 40 байт метаданных; сам индекс не входит. |
| 4 | `magic` | 4 байта | Непрозрачный маркер PGM. |

Поэтому читатель начинает с конца, а не с первой секции:

1. прочитать последние восемь байт;
2. по `catalog_len` найти начало каталога;
3. декодировать каталог и проверить его CRC32C;
4. прочитать нужное тело по абсолютным `offset` и `len`;
5. проверить CRC32C тела и только затем отдать байты кодеку реестра.

### Пример: снимок и два словаря в одном PGM

Упрощённый PGM для PostgreSQL 15–18: одно тело `pg_stat_activity`, одно тело
коротких строк и одно тело больших значений. Пусть их размеры `S`, `T` и `L`,
тогда `B = S + T + L`.

```text
смещение

0       +----------------------------------------------------------+
        | маркер PGM                                               | 4 байта
4       +----------------------------------------------------------+
        | тело #0: pg_stat_activity, type_id=1_001_003             | S байт
        | Parquet: ts | pid | datname=H | query=Q | ...            |
4+S     +----------------------------------------------------------+
        | тело #1: dict.strings, type_id=3_001_001                 | T байт
        | Parquet: str_id | bytes                                  |
4+S+T   +----------------------------------------------------------+
        | тело #2: dict.blobs, type_id=3_002_001                   | L байт
        | Parquet: str_id | stored_bytes | full_len | ...          |
4+B     +----------------------------------------------------------+
        | запись каталога #0: type=1_001_003, offset=4, len=S      | 32 байта
36+B    | запись каталога #1: type=3_001_001, offset=4+S, len=T    | 32 байта
68+B    | запись каталога #2: type=3_002_001, offset=4+S+T, len=L  | 32 байта
100+B   +----------------------------------------------------------+
        | метаданные каталога                                      | 40 байт
140+B   +----------------------------------------------------------+
        | catalog_len=136 | маркер PGM                              | 8 байт
148+B   +----------------------------------------------------------+
```

Для трёх тел `catalog_len = 3 * 32 + 40 = 136`, весь файл — `B + 148` байт.
Если в сегменте нет больших значений, тело `dict.blobs` и его запись
отсутствуют.

Показанные выше Parquet-строки — это **декодированное содержимое**, а не
буквальный текст в файле. Внутреннее кодирование и Zstd означают, что байты
текста не обязаны лежать в PGM как есть.

В текущих файлах PgKronika тело данных или словаря обычно является
самодостаточным файлом Parquet со своим обрамлением `PAR1 ... PAR1`. Контейнер
PGM считает эти байты непрозрачными и не разбирает метаданные столбцов.

В репозитории есть побайтовая фикстура
[`minimal.pgm`](tests/fixtures/minimal.pgm) — 88 байт: маркер PGM,
четырёхбайтное тело `01 02 03 04`, одна запись каталога, метаданные и хвостовой
индекс. В [`tests/fixture.rs`](tests/fixture.rs) зафиксированы все смещения
и проверяется побайтовое воспроизведение.

## Компактные тела секций

Для `kronika-format` тела непрозрачны. Рабочий код записи использует один
физический профиль для каждого итогового тела данных и словаря:

| Свойство | Текущее значение |
| --- | --- |
| Строки | Не более 65 536 |
| Закодированное тело | Не более 8 МиБ |
| `row group` | Ровно одна |
| Страницы данных | Ровно одна для каждого `column chunk` |
| Кодирование значений | `PLAIN`; словари Parquet отключены |
| Сжатие | Zstandard уровня 6 |
| Статистика и индексы страниц | Отключены |
| Метаданные схемы Arrow | Опущены |
| `created_by` | Пустая строка |

Строки данных используют полный канонический порядок реестра: сначала
объявленные столбцы ключа сортировки, затем все остальные физические столбцы
как детерминированные дополнительные ключи. Одинаковые физические строки
сохраняют кратность. Строки словарей строго упорядочены по `str_id`.

До публикации код записи проверяет лимиты строк, страниц, закодированного тела,
работы чтения, памяти, входа, промежуточных файлов и результата. Код чтения
проверяет контейнер, схему, число строк, байты, декодированную память и CRC.
Параметры Parquet для готовых PGM проверяются тестами записи, оракулом всех 75
схем, BDD полного жизненного цикла и квалификацией релиза.

Сквозного сжатия всего файла нет. Каждое тело Parquet, каталог PGM и
журнальное обрамление остаются независимо адресуемыми. Код чтения может найти и
проверить одно тело, не распаковывая остальные секции.

## Физическое хранение строк

Секция снимка не хранит исходный текст в каждой записи. В столбце `StrId`
лежит только `u64 = xxh3_64(исходные_байты)`. Ноль означает «нет значения».
Это число — **не** файловое смещение: исходные байты надо искать под тем же
идентификатором в отдельных словарных телах Parquet.

Текущая запись создаёт два типа словарных секций:

| `type_id` | Секция | Столбцы после декодирования |
| ---: | --- | --- |
| `3_001_001` | `dict.strings` | `str_id`, полное поле `bytes` |
| `3_002_001` | `dict.blobs` | `str_id`, `stored_bytes`, `full_len`, `truncated`, необязательный `full_sha256` |

Обе секции — **внутри PGM**, рядом со снимками. `dict.blobs` — не отдельный
файл, не TOAST и не внешнее объектное хранилище.

### Короткая строка `postgres`

Для байтов `postgres`
`H = xxh3_64(b"postgres") = 0x0939566173e67ada`. Если два серверных процесса
PostgreSQL в одном окне подключены к этой базе, данные находятся в одном
физическом файле. Ниже показано декодированное содержимое без посторонних тел:

```text
$KRONIKA_OUT_DIR/<первая_метка>.pgm  (один файл)

[ маркер PGM ]
[ тело Parquet pg_stat_activity, type_id=1_001_003
  после декодирования:
  pid | datname
  101 | H
  102 | H ]
[ тело Parquet dict.strings, type_id=3_001_001
  после декодирования:
  str_id | bytes
  H      | b"postgres" ]
[ концевой каталог
  offset,len -> всё тело pg_stat_activity
  offset,len -> всё тело dict.strings ]
[ хвостовой индекс ]
```

Секция снимка содержит два логических значения `StrId`, представленных как
`u64`, а словарь — одну запись с байтами `postgres`. На следующем уровне
разметка выглядит так:

```text
запись каталога PGM: type_id=3_001_001, offset=X, len=T
                            |
                            v
диапазон [X, X+T): самодостаточное тело Parquet
|-- "PAR1"
|-- row group #0
|   |-- column chunk str_id: кодирует H
|   `-- column chunk bytes: кодирует b"postgres"
|-- метаданные Parquet и их длина
`-- "PAR1"
```

Байты находятся в `column chunk` столбца `bytes` тела `dict.strings`. Они
закодированы как `PLAIN` в единственной странице данных Zstandard-6. Тело
`pg_stat_activity` хранит только `H`. Каталог PGM хранит смещение и длину всего
словарного тела, а не одного значения; более точные смещения находятся в
метаданных Parquet. Чтобы сопоставить `H` с исходной строкой, нужно
декодировать словарное тело.

Блоки «после декодирования» показывают логические значения, а не байты на
диске. Две ссылки не обязаны занимать ровно 16 байт, а кодирование и сжатие не
обязаны сохранять `postgres` в файле как открытую последовательность байтов.

Чтение идёт через концевой каталог:

```text
(1) хвостовой индекс -> концевой каталог

(2) каталог -> тело pg_stat_activity
            -> декодировать Parquet
            -> datname=H

(3) каталог + H -> тело dict.strings и/или dict.blobs
                -> декодировать запись со str_id=H
                -> b"postgres"
                -> datname="postgres"
```

В PGM нет индекса `StrId -> смещение` для отдельных значений. Полное чтение
словаря посещает единственное тело каждого присутствующего словарного типа и
строит карту в памяти. Прицельный путь overview читает те же тела, но сохраняет
только заранее запрошенные идентификаторы.

### Большие и усечённые значения

При текущих ограничениях коллектора размещение работает так:

| Исходное значение | Секция | Что сохранено на диске |
| --- | --- | --- |
| `postgres`, 8 байт | `dict.strings` | Все 8 байт. |
| Текст плана, 20 КиБ | `dict.blobs` | Все 20 КиБ, `full_len=20480`, `truncated=false`, SHA-256 отсутствует. |
| `/proc/PID/cmdline`, 80 КиБ | `dict.blobs` | Первые 64 КиБ, `full_len=81920`, `truncated=true` и SHA-256 от исходных 80 КиБ. |

`StrId` усечённого значения вычисляется по всем исходным байтам, а не по
сохранённому префиксу. Отброшенный остаток из PGM не восстановить. Текст плана
по умолчанию ограничен `KRONIKA_PG_MAX_PLAN_TEXT=32768`, поэтому он попадает
в `dict.blobs`, но не достигает порога усечения при настройках по умолчанию.
Даже разрешённый максимум плана в 64 КиБ обрезается источником до интернирования,
так что словарь считает полученные байты полным значением.

Модель и коллектор намеренно используют разные лимиты:

| Ограничение | `DictLimits::default()` | Текущий коллектор | Действие |
| --- | ---: | ---: | --- |
| Порог большого значения | 4 КиБ | 4 КиБ | Значения не короче порога попадают в `dict.blobs`. |
| Предел усечения | 1 МиБ | 64 КиБ | У более длинного значения хранится префикс ровно этой длины. |
| Потолок сохранённых байтов | 64 МиБ | 16 МиБ | Обычное новое значение отклоняется при превышении; обязательные горячие значения освобождены. |

Значения коллектора заданы в коде, а не переменными окружения. Потолок считает
сохранённые байты значений после усечения, без метаданных Parquet. При
превышении обычное новое значение отклоняется с `DictError::Full`. Это не
абсолютный предел закодированной секции — обязательные горячие строки от
проверки освобождены. Текущий коллектор не завершает сегмент автоматически при
достижении 16 МиБ: в зависимости от источника цикл либо падает, либо опускает
отдельные записи или текстовые поля.

`SegmentDicts` также моделирует подмножество `dict.hot_strings`, но текущая
запись не создаёт третью словарную секцию. Эти значения пишутся в обычное тело
`dict.strings`; тела `dict.hot_strings` в файле нет.

### Нормализация всего сегмента

Интернер каждого окна обнаруживает коллизии и не хранит одинаковые байты
дважды внутри одной части. При запечатывании записи из всех частей
нормализуются для всего сегмента. Записи с одинаковыми `str_id`, байтами и
метаданными объединяются в одну строку. Различающиеся байты, метаданные
усечения или размещение одного `str_id` сразу в двух словарных секциях
прерывают запечатывание до публикации. В готовом PGM каждый ненулевой `str_id`
встречается ровно один раз, по возрастанию.

## `active.parts` и восстановление после сбоя

`active.parts` — журнал на диске для ещё не завершённого сегмента. Каждый кадр:
16-байтный заголовок и одна полная PGM-часть.

```text
внутренний маркер кадра | part_len: u64 | header_crc32c: u32 | PGM-часть
```

CRC заголовка покрывает первые 12 байт. PGM-часть содержит собственные маркер,
тела, каталог и хвостовой индекс, поэтому кадр можно проверить до принятия.

Для чистого журнала с `P` кадрами, `N` записями в каталогах частей и `B`
байтами тел частей:

```text
active_parts_bytes = B + 32*N + 68*P
```

Размер запечатанного файла нельзя получить простым вычитанием обрамления:
код записи декодирует и заново кодирует строки в меньшее число тел и словарных
записей. Точный размер после уплотнения равен итоговому `B + 32*N + 52`.

Максимальный размер принимаемой части по умолчанию — 64 МиБ. Потоковый сканер
восстановления держит в памяти тело одной PGM-части (не больше `max_part_len`)
и окно ресинхронизации. Окно по умолчанию — 1 МиБ, передаётся сканеру отдельным
аргументом, а не полем `JournalLimits`.

Повреждённые участки классифицируются, а не сваливаются в одну кучу:

| Класс | Что произошло | `Journal::open` | Запуск коллектора |
| --- | --- | --- | --- |
| `TornTail` | Последний кадр не дописан, либо корректный заголовок задаёт кадр до конца файла, но вложенный PGM не проходит проверку. | Обрезает файл по последней корректной границе. Теряется не более последней части. | Запечатывает предшествующие корректные части до подключения к PostgreSQL. |
| `Middle { resumed_at }` | За повреждённым участком найден следующий корректный кадр. | Сохраняет байты и сообщает о повреждении. | Завершает работу с ошибкой и оставляет `active.parts` для диагностики. |
| `QuarantinedTail` | Повреждённый конечный участок, после которого нет корректного кадра. | Сохраняет байты и сообщает о повреждении. | Завершает работу с ошибкой и оставляет `active.parts` для диагностики. |

При запуске коллектор сразу запечатывает восстановленные части с данными,
имеющими метки времени. Части без таких данных отбрасываются сбросом журнала
без создания PGM. После успешной синхронизации целевого файла и родительского
каталога коллектор очищает журнал. При ошибке запечатывания журнал остаётся
нетронутым, а запуск коллектора завершается с ошибкой. Повреждения, кроме
оборванного хвоста, не пропускаются и не очищаются.

## Куда уходят байты

Размер в основном определяется телами Parquet, а не 52 постоянными байтами
контейнера. Запечатывание удаляет структурные повторы, не отбрасывая уже
принятые строки:

| Механизм | Действие |
| --- | --- |
| Объединение по типу | Тела одного типа из разных окон становятся одним телом с одним набором служебных данных Parquet. |
| Нормализация словаря | Равные записи `str_id` становятся одной проверенной записью всего сегмента. |
| Каноническая сортировка | Результат детерминирован, похожие значения расположены рядом. |
| `PLAIN` и Zstandard-6 | Столбцы не используют словари Parquet и сжимаются по фиксированному профилю. |
| Без статистики и индексов страниц | Неиспользуемые запросами PGM метаданные отсутствуют. |
| Компактные типы реестра | Физическая ширина целых и столбцы `StrId` соответствуют зарегистрированной схеме. |

Лимиты сбора не относятся к уплотнению. Усечение больших значений, top-N, интервалы
источников и лимиты текста могут удалить данные до их попадания в журнал.
Код записи PGM не учитывает это как результат уплотнения.

Поддерживаемая квалификация релиза использует рабочий путь `Journal -> seal ->
PgmUnit`. Она требует 20 запусков запечатывания в новых процессах, фикстуру с
реальными промежуточными файлами и слиянием группами не более 32, точное
равенство после повторного открытия и оракул всех 75 схем. Квалификация отдельно
фиксирует логический и выделенный на диске размер PGM и OVF, фактическое время, CPU,
пиковый RSS, объём промежуточных файлов, I/O процесса, общий объём записи,
задержки перезапуска и запросов и источники чтения PGM/OVF. Команды запуска и
проверки приведены в
[`overview-parity-v1.md`](../../docs/qualification/overview-parity-v1.md).

Зафиксированное
[исследование физического сокращения](../../docs/superpowers/specs/2026-07-26-pgm-size-reduction-research.md)
сохраняет набор данных, контрольные суммы, ограничения и измерения по каждому
фактору. Его результаты не являются обещанием размера в рабочем развёртывании.

## Параметры, влияющие на размер файлов

У самой разметки PGM нет ручек сжатия. Оператор управляет объёмом и
группировкой собираемых данных через `pg_kronika-collector`:

| Настройка | По умолчанию | Что меняется |
| --- | ---: | --- |
| Переменные источников `*_INTERVAL_S` | 1–3600 с, зависит от источника | Рост интервала даёт меньше снимков ценой временного разрешения. `KRONIKA_INTERVAL_S=5` задаёт только базовый интервал планировщика. |
| `KRONIKA_PG_MAX_TABLES`, `KRONIKA_PG_MAX_INDEXES`, `KRONIKA_PG_MAX_STATEMENTS`, `KRONIKA_PG_MAX_PLANS` | `500` | Меньшие значения сокращают число строк и объём словарей, но исключают объекты за пределами top-N. |
| `KRONIKA_PG_MAX_PLAN_TEXT` | 32 768 байт | Максимальная длина текста одного плана за чтение. |
| `KRONIKA_PG_PLAN_TEXT_BUDGET` | 8 МиБ | Общий бюджет текстов планов за чтение; ноль отключает их сбор. |
| `KRONIKA_SEGMENT_MAX_BYTES` | 64 МиБ | Завершает сегмент после этого числа сырых байтов `active.parts`; `0` завершает после каждого окна. Меняет гранулярность файлов, но не сжатие Parquet. |
| `KRONIKA_SEGMENT_MAX_AGE_S` | 900 с | Предельный возраст открытого сегмента. В основном меняет временной диапазон и число файлов. |
| `KRONIKA_JOURNAL_MAX_BYTES` | 1 ГиБ | Жёсткий предел проверяется перед каждым дописыванием. Если сегмент уже открыт, коллектор сначала завершает его и повторяет попытку; окно больше предела отклоняется. Это не целевой размер PGM. |

Смена лимитов источников меняет полноту наблюдений и расход диска. Возраст и
размер ротации определяют, сколько окон уплотняется в один PGM, но не меняют
профиль физического кодирования. Все интервалы и правила проверки приведены в
[документации коллектора](../../bins/pg_kronika-collector/README.ru.md).

## Целостность и ограничения

CRC32C покрывает каждое тело секции, каталог и заголовок каждого журнального
кадра. Она обнаруживает случайную порчу; это не аутентификация, не подпись и
не шифрование.

`kronika-format` проверяет обрамление, длину и CRC32C каталога, границы секций,
а для полных частей — CRC32C тел. Слои выше требуют внутреннее значение
контракта каталога и ограничивают размеры каталога, секций, строк, `row group` и
декодируемой рабочей памяти. Изменённая схема секции получает отдельный
`type_id`.

Контракт определяют:

- [`src/lib.rs`](src/lib.rs), [`src/catalog.rs`](src/catalog.rs) и
  [`src/parts.rs`](src/parts.rs) для двоичной разметки;
- [`src/dictionary.rs`](src/dictionary.rs) для инвариантов словарей;
- [`kronika-registry`](../kronika-registry/README.ru.md) для схем секций и
  лимитов Parquet;
- [`kronika-writer`](../kronika-writer/README.ru.md) для дописывания частей и
  запечатывания PGM.
