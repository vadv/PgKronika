# kronika-format

[English version](README.md)

`kronika-format` задаёт двоичный контракт, благодаря которому один процесс
PgKronika может закончить запись сегмента, а другой — открыть его позднее. Это
не самостоятельный конвертер и не универсальный формат аналитических данных.

Внутри PgKronika крейт связывает запись данных с последующим чтением:

```text
PostgreSQL / Linux / cgroup / журнал PostgreSQL
        |
        v
pg_kronika-collector собирает одно окно данных
        |
        v
kronika-registry кодирует типизированные записи в тела секций
        |
        v
kronika-writer строит самодостаточную часть PGM
        |
        v
active.parts --формирование итогового PGM--> <первая_метка_времени>.pgm
                                      |
                                      v
                          kronika-store / kronika-reader
                                      |
                                      v
                               pg_kronika-web
```

Журнал `active.parts` и итоговые файлы `.pgm` находятся непосредственно в
`KRONIKA_OUT_DIR`. Например:

```text
$KRONIKA_OUT_DIR/
|-- active.parts
|-- <первая_метка_времени>.pgm
`-- <следующая_первая_метка_времени>.pgm
```

Отдельных файлов для строковых значений нет. Пока сегмент открыт, словарные
тела находятся в частях PGM внутри `active.parts`. При завершении сегмента
модуль записи без изменений копирует эти тела в итоговый `.pgm`.

Крейт формата отвечает за разметку `PGM1` и `PGMP`, концевой каталог,
контрольные суммы CRC32C, `StrId` и модель словарей с ограничениями. Он
намеренно не отвечает за:

- смысл данных PostgreSQL и Linux и схемы секций — это задача
  [`kronika-registry`](../kronika-registry/README.ru.md);
- кодирование Parquet, буферизацию, файловый журнал и завершение сегмента
  (`seal`) — это задача [`kronika-writer`](../kronika-writer/README.ru.md);
- интервалы сбора, ротацию и ограничения источников — это задача
  [`pg_kronika-collector`](../../bins/pg_kronika-collector/README.ru.md);
- поиск файлов, типизированные запросы, HTTP, сроки хранения, шифрование и
  удалённое хранилище.

## От окна сбора до сегмента

В текущей реализации коллектор создаёт новый словарь и новые буферы записей для
каждого непустого цикла сбора. Реестр сортирует каждую секцию снимка по
ключу, заданному её контрактом, и кодирует её. Модуль записи добавляет
словарные секции, строит самодостаточную часть PGM, помещает её в кадр `PGMP`,
дописывает кадр в `active.parts` и вызывает `sync_data`.

Коллектор добавляет новые окна, пока не сработает одно из условий завершения:
порог размера, предельный возраст, принудительная ротация или предел журнала.
При завершении сегмента:

1. проверяются каталоги записанных частей;
2. в начало итогового файла записывается один `PGM1`;
3. все тела секций копируются в порядке частей и записей каталога;
4. абсолютные смещения переписываются в один концевой каталог;
5. временный файл в том же каталоге синхронизируется и публикуется без
   перезаписи уже существующего файла;
6. `active.parts` очищается только после успешной публикации.

Это важно для понимания размера: текущий `seal` **не** объединяет, не
дедуплицирует и не перекодирует тела Parquet. Он удаляет обрамление отдельных
частей и строит один каталог вокруг исходных тел.

### Окно, часть, секция и тело

В описании формата используются четыре разных уровня:

- **окно сбора** — данные одного непустого цикла коллектора;
- **часть PGM** — самодостаточный контейнер с данными одного окна, собственными
  `PGM1`, телами, каталогом и хвостовым указателем;
- **секция** — логический блок, описанный одной записью каталога: `type_id`,
  смещение, длина, число табличных строк и CRC32C;
- **тело секции** — диапазон байтов, на который указывает запись каталога.
  Текущий модуль записи помещает в него самостоятельный файл Parquet.

Пока сегмент открыт, каждая часть PGM хранится внутри отдельного кадра `PGMP`
журнала:

```text
active.parts
|
+-- кадр PGMP #1
|   `-- часть PGM окна #1
|       |-- "PGM1"
|       |-- тела секций данных
|       |-- тела dict.strings / dict.blobs
|       |-- каталог части
|       `-- хвостовой указатель
|
`-- кадр PGMP #2
    `-- часть PGM окна #2
        |-- "PGM1"
        |-- тела секций данных
        |-- тела dict.strings / dict.blobs
        |-- каталог части
        `-- хвостовой указатель
```

Внутри каждой части текущий модуль записи сначала располагает тела непустых
секций данных по возрастанию `type_id`, затем `dict.strings`, затем
`dict.blobs`. Отсутствующая словарная секция место не занимает. Такой порядок
использует текущий модуль записи; сам формат фиксированных смещений не задаёт.
Читатель находит каждое тело по каталогу.

После завершения сегмента обрамление отдельных частей исчезает:

```text
active.parts                         <первая_метка_времени>.pgm

PGMP [часть окна #1]                 "PGM1"
PGMP [часть окна #2]   -- seal() -->  тела окна #1, включая его словари
...                                  тела окна #2, включая его словари
                                     ...
                                     один общий концевой каталог
                                     один хвостовой указатель
```

В итоговом PGM нет отдельных маркеров границ окон. Принадлежность тела
конкретному окну явно не записана: о ней можно лишь судить по порядку и
содержимому. Каталог хранит сведения о секциях, а не номер окна.

## Разметка итогового PGM v1

Все целые числа записаны от младшего байта к старшему. В каноническом файле,
созданном текущим модулем записи, между полями нет выравнивающих вставок.
Пусть в каталоге `N` записей, а суммарный размер тел секций равен `B` байт:

```text
смещение  размер        содержимое
0         4             "PGM1"
4         B             тело секции 0, тело секции 1, ... в порядке каталога
4+B       32*N          записи каталога
...       40            метаданные каталога
...       8             хвостовой указатель
```

Точный размер файла:

```text
pgm_bytes = B + 32*N + 52
catalog_len = 32*N + 40
```

Постоянные 52 байта состоят из начальной сигнатуры, метаданных каталога и
хвостового указателя. Общего слоя сжатия поверх файла нет. Формулы описывают
файл, созданный текущим модулем записи. Низкоуровневый валидатор v1 допускает
находящиеся в границах файла промежутки и пересечения секций.

### Запись каталога: 32 байта

| Смещение | Поле | Тип | Значение |
| ---: | --- | --- | --- |
| 0 | `type_id` | `u32` | Идентификатор схемы секции, зарегистрированной в `kronika-registry`. |
| 4 | `flags` | `u32` | Зарезервировано; текущий модуль записи пишет ноль. |
| 8 | `offset` | `u64` | Абсолютное смещение тела от первого байта файла. |
| 16 | `len` | `u64` | Размер тела в байтах. |
| 24 | `rows` | `u32` | Число табличных строк в теле. |
| 28 | `crc32c` | `u32` | CRC32C этого тела секции. |

Один `type_id` может встречаться много раз. В файлах текущего коллектора это
обычно означает, что несколько последовательных окон создали по одному телу
одной и той же логической секции. Для секций диаграмм повторные записи могут
описывать разные сущности. Порядок записей значим и сохраняется.

### Метаданные каталога: 40 байт

| Смещение | Поле | Тип | Значение |
| ---: | --- | --- | --- |
| 0 | `min_ts` | `i64` | Самая ранняя метка времени секций, микросекунды Unix. |
| 8 | `max_ts` | `i64` | Самая поздняя метка времени секций, микросекунды Unix. |
| 16 | `source_id` | `u64` | Идентификатор источника; ноль означает, что источник не задан. |
| 24 | `entry_count` | `u32` | Число 32-байтных записей перед этим блоком. |
| 28 | `format_version` | `u32` | Версия разметки контейнера; текущий модуль записи пишет `1`. |
| 32 | `crc32c` | `u32` | CRC32C записей каталога и метаданных; при расчёте это поле заполнено нулями. |
| 36 | `reserved` | `u32` | Зарезервировано; текущий модуль записи пишет ноль. |

Низкоуровневые API `Catalog` и `PartMeta` исторически описывают `source_id` как
`StrId` строки `{cluster_id}/{pg_system_identifier}`. Текущий коллектор вместо
этого копирует в поле произвольный `KRONIKA_SOURCE_ID` и не гарантирует
соответствующую запись в `dict.strings`. Поэтому при чтении файлов текущего
коллектора `source_id` нужно считать непрозрачным идентификатором, а не
разрешимой ссылкой на строку.

### Хвостовой указатель: 8 байт

| Смещение | Поле | Тип | Значение |
| ---: | --- | --- | --- |
| 0 | `catalog_len` | `u32` | Записи каталога и 40 байт метаданных; сам указатель в длину не входит. |
| 4 | `magic` | 4 байта | `"PGM1"`. |

Поэтому чтение начинается с конца файла, а не с первой секции:

1. прочитать последние восемь байт;
2. по `catalog_len` найти начало каталога;
3. декодировать каталог и проверить его CRC32C;
4. прочитать нужное тело по абсолютным `offset` и `len`;
5. проверить CRC32C тела и только затем передать байты кодеку реестра.

### Пример: снимок и два словаря в одном PGM

Ниже показан упрощённый итоговый PGM для PostgreSQL 14–18. В нём есть одно
тело `pg_stat_activity`, одно словарное тело с короткими строковыми значениями
и одно словарное тело с крупными значениями. Пусть их размеры равны `S`, `T` и
`L`, а `B = S + T + L`.

```text
смещение

0       +----------------------------------------------------------+
        | "PGM1"                                                   | 4 байта
4       +----------------------------------------------------------+
        | тело #0: pg_stat_activity, type_id=1_001_003             | S байт
        | столбцы: ts | pid | datname=H | query=Q | ...            |
4+S     +----------------------------------------------------------+
        | тело #1: dict.strings, type_id=3_001_001                 | T байт
        | столбцы: str_id | bytes                                  |
4+S+T   +----------------------------------------------------------+
        | тело #2: dict.blobs, type_id=3_002_001                   | L байт
        | столбцы: str_id | stored_bytes | full_len | ...          |
4+B     +----------------------------------------------------------+
        | запись каталога #0: type=1_001_003, offset=4, len=S      | 32 байта
36+B    | запись каталога #1: type=3_001_001, offset=4+S, len=T    | 32 байта
68+B    | запись каталога #2: type=3_002_001, offset=4+S+T, len=L  | 32 байта
100+B   +----------------------------------------------------------+
        | метаданные каталога                                      | 40 байт
140+B   +----------------------------------------------------------+
        | catalog_len=136 | "PGM1"                                 | 8 байт
148+B   +----------------------------------------------------------+
```

Для трёх тел `catalog_len = 3 * 32 + 40 = 136`, поэтому полный размер файла
равен `B + 148`. Если в окне нет больших значений, тело `dict.blobs` и его
запись каталога отсутствуют. Каждое непустое окно может добавить несколько
тел, поэтому в итоговом каталоге один `type_id` часто встречается несколько
раз.

В текущих файлах PgKronika тело данных или словаря обычно является
самодостаточным файлом Parquet, поэтому у него есть собственное обрамление
`PAR1 ... PAR1`. Контейнер PGM считает тело непрозрачной последовательностью
байтов и не разбирает сведения о столбцах. Подписи `ts | pid | ...` и
`str_id | ...` показывают столбцы после декодирования, а не байты на диске.
Из-за внутреннего кодирования и Zstd текст не обязан встречаться в PGM в
открытом виде.

В репозитории также есть побайтовая фикстура
[`minimal.pgm`](tests/fixtures/minimal.pgm) размером 88 байт: `PGM1`, одно
четырёхбайтное тело `01 02 03 04`, одна запись каталога, метаданные и
хвостовой указатель. В [`tests/fixture.rs`](tests/fixture.rs) указаны все
смещения и проверяется точное воспроизведение каждого байта.

## Что находится в телах секций

Для `kronika-format` тела непрозрачны, но текущая реализация PgKronika кодирует
снимки и словари как самодостаточные файлы Parquet:

- страницы столбцов внутри каждого тела Parquet сжимаются Zstd уровня 3;
- табличные строки снимков сортируются по каноническому ключу контракта, а
  словарные записи — по `str_id`;
- одно тело ограничено 65 536 табличными строками и 8 МиБ;
- декодер принимает не более 16 групп строк Parquet;
- избыточная схема Arrow не записывается, а `created_by` очищается до пустой
  строки.

Удаление вложенной схемы Arrow убирает из каждого тела копию логической схемы;
точная экономия зависит от контракта секции. Низкоуровневая схема Parquet
остаётся, потому что она нужна декодеру для чтения столбцов.

Сжатия всего файла Zstd нет. Заголовок и концевой блок каждого тела Parquet,
каталог PGM и обрамление PGM/PGMP не входят в общий поток Zstd. Читатель может
найти и проверить одно тело, не распаковывая остальные секции.

## Где физически лежат строковые значения

Секция снимка не хранит исходный текст в каждой записи. Столбец типа `StrId`
содержит только `u64`, равный `xxh3_64(original_bytes)`. Ноль означает
отсутствующее значение. Это не файловое смещение: исходные байты нужно искать
по тому же идентификатору в отдельных словарных телах Parquet.

Текущий модуль записи создаёт два типа словарных секций:

| `type_id` | Секция | Столбцы после декодирования |
| ---: | --- | --- |
| `3_001_001` | `dict.strings` | `str_id`, полное значение `bytes` |
| `3_002_001` | `dict.blobs` | `str_id`, `stored_bytes`, `full_len`, `truncated`, необязательный `full_sha256` |

Словарные тела записываются **в тот же PGM** рядом с телами снимков.
`dict.blobs` — не отдельный файл, не PostgreSQL TOAST и не внешнее объектное
хранилище.

### Короткая строка `postgres`

Для байтов `postgres` получается
`H = xxh3_64(b"postgres") = 0x0939566173e67ada`. Если два серверных процесса
PostgreSQL из одного окна подключены к этой базе, данные находятся в одном
физическом файле следующим образом. Содержимое Parquet показано после
декодирования, остальные тела опущены:

```text
$KRONIKA_OUT_DIR/<первая_метка_времени>.pgm  (один файл)

[ "PGM1" ]
[ тело Parquet pg_stat_activity, type_id=1_001_003
  после декодирования:
  pid | datname
  101 | H
  102 | H ]
[ тело Parquet dict.strings, type_id=3_001_001
  после декодирования:
  str_id | bytes
  H      | b"postgres" ]
[ концевой каталог
  offset,len -> всё тело pg_stat_activity
  offset,len -> всё тело dict.strings ]
[ хвостовой указатель ]
```

В секции снимка получаются два логических значения `StrId`, представленных как
`u64`, а в словаре — одна запись с байтами `postgres`. На уровень ниже их
расположение выглядит так:

```text
запись каталога PGM: type_id=3_001_001, offset=X, len=T
                             |
                             v
диапазон байтов [X, X+T): самостоятельное тело Parquet
|-- "PAR1"
|-- группа строк #0
|   |-- блок столбца str_id: кодирует H
|   `-- блок столбца bytes: кодирует b"postgres"
|-- метаданные Parquet и их длина
`-- "PAR1"
```

Сами байты принадлежат блоку столбца `bytes` тела `dict.strings`. Parquet может
поместить значение в словарную или обычную страницу внутри этого блока; её
сжимает Zstd-3. В теле `pg_stat_activity` остаётся только `H`. Каталог PGM
хранит смещение и длину всего тела словаря, но не отдельного значения; более
мелкие смещения описывают уже метаданные Parquet. Поэтому получить текст по
`H` без декодирования словарного тела нельзя.

Блоки «после декодирования» показывают логические значения, а не байты на
диске. Точный объём двух ссылок не обязан равняться 16 байтам, а текст
`postgres` из-за кодирования и сжатия не обязан встречаться в файле как
открытая последовательность байтов.

Путь чтения проходит через концевой каталог:

```text
(1) хвостовой указатель -> концевой каталог

(2) каталог -> тело pg_stat_activity
            -> декодирование Parquet
            -> datname=H

(3) каталог + H -> все тела dict.strings и dict.blobs
                -> декодирование записи str_id=H
                -> b"postgres"
                -> datname="postgres"
```

Отдельного глобального индекса `StrId -> offset` в PGM нет. При полном чтении
читатель обрабатывает все тела `dict.strings` и `dict.blobs` и строит таблицу
соответствий `str_id -> значение` в памяти. Метод
`resolve_overview_dictionary`, используемый в `overview`, тоже читает
словарные тела, но сохраняет только заранее запрошенные идентификаторы.

### Большое и усечённое значение

При ограничениях текущего коллектора размещение выглядит так:

| Исходное значение | Секция | Что остаётся на диске |
| --- | --- | --- |
| `postgres`, 8 байт | `dict.strings` | Все 8 байт. |
| План, 20 КиБ | `dict.blobs` | Все 20 КиБ, `full_len=20 480`, `truncated=false`, без SHA-256. |
| `/proc/PID/cmdline`, 80 КиБ | `dict.blobs` | Первые 64 КиБ, `full_len=81 920`, `truncated=true` и SHA-256 исходных 80 КиБ. |

`StrId` усечённого значения вычисляется по всем исходным байтам, а не по
сохранённому префиксу. Отброшенный хвост восстановить из PGM нельзя. План по
умолчанию ограничен `KRONIKA_PG_MAX_PLAN_TEXT=32 768`, поэтому может попасть в
`dict.blobs`, но при настройках по умолчанию не достигает порога усечения.
Источник ограничивает текст плана до передачи в `Interner`. Поэтому `Interner`
считает полученные байты полным значением и не помечает его как усечённое.

Библиотечные значения и фактические ограничения коллектора различаются:

| Ограничение | `DictLimits::default()` | Текущий коллектор | Действие |
| --- | ---: | ---: | --- |
| Порог большого значения | 4 КиБ | 4 КиБ | Значения не короче порога попадают в `dict.blobs`. |
| Предел усечения | 1 МиБ | 64 КиБ | У более длинного значения сохраняется префикс ровно такой длины. |
| Предел сохранённых байтов | 64 МиБ | 16 МиБ | Новое значение через `intern` отклоняется при превышении предела; значения через `intern_hot` от него освобождены. |

Значения коллектора сейчас заданы в коде, а не переменными окружения. Предел
учитывает сохранённые байты значений после усечения, но не служебные данные
Parquet. При его превышении `intern` возвращает `DictError::Full`. Текущий
коллектор не завершает сегмент автоматически при достижении 16 МиБ: в
зависимости от источника цикл завершается ошибкой либо отдельные записи или
текстовые поля пропускаются.

`SegmentDicts` умеет помечать короткие значения как часто используемые
(`hot`), но текущий модуль записи всё равно помещает их в `dict.strings`;
отдельной секции `dict.hot_strings` в PGM нет.

### Где заканчивается дедупликация

Один экземпляр `SegmentDicts` обнаруживает коллизии хэша и хранит одну копию
одинаковых байтов. Однако текущий коллектор создаёт новый `Interner` для каждого
цикла сбора. Поэтому дедупликация работает внутри одного окна, а не внутри всего
итогового PGM.

При полном чтении повторы объединяются по `str_id` без сравнения байтов.
Сохраняется первая запись из `dict.strings`; каждая последующая запись из
`dict.blobs` заменяет текущее значение, а остальные записи из `dict.strings`
игнорируются. При адресном чтении для `overview` выбранные повторы
дополнительно проверяются на согласованность: сравниваются `bytes`, `full_len`
и `truncated`, а противоречия отклоняются. Для усечённого значения читатель
требует наличия `full_sha256`, но не сравнивает значения SHA-256. Оба варианта
объединяют записи только в памяти и не удаляют физические копии из PGM.

## `active.parts` и восстановление после сбоя

`active.parts` — сохраняемый на диске журнал открытого сегмента.
Каждый кадр содержит 16-байтный заголовок и одну полную часть PGM:

```text
"PGMP" | part_len: u64 | header_crc32c: u32 | часть PGM
```

Контрольная сумма заголовка покрывает первые 12 байт. Вложенная часть содержит
свои `PGM1`, тела, каталог и хвостовой указатель, поэтому кадр можно полностью
проверить перед добавлением.

Для чистого журнала с `P` кадрами, общим числом записей секций `N` и суммарным
размером тел `B`:

```text
active_parts_bytes = B + 32*N + 68*P
sealed_pgm_bytes   = B + 32*N + 52
seal_saves         = 68*P - 52
```

Это экономия только на обрамлении. Для 70 окон она равна 4 708 байтам; тела
Parquet и все `N` записей каталога сохраняются.

Максимальный размер принимаемой части по умолчанию равен 64 МиБ. Потоковое
восстановление держит в памяти тело одной части PGM размером не более
`max_part_len` и окно поиска следующего кадра. Размер такого окна по умолчанию
равен 1 МиБ и передаётся сканеру отдельно; в `JournalLimits` этого поля нет.

Повреждённые участки классифицируются по их положению:

| Класс | Что произошло | `Journal::open` | Запуск коллектора |
| --- | --- | --- | --- |
| `TornTail` | Последний кадр не дописан. Либо кадр по указанной в корректном заголовке длине заканчивается ровно в конце файла, но вложенная часть PGM не проходит проверку. | Обрезает файл по последней корректной границе. Теряется не более последней части. | Обрабатывает предшествующие корректные части по правилу ниже. |
| `Middle { resumed_at }` | После некорректного участка найден следующий корректный кадр. | Сохраняет байты для диагностики и сообщает о корректных частях с обеих сторон. | Если корректные части найдены, обрабатывает их и затем очищает весь журнал. |
| `QuarantinedTail` | В конце найден некорректный участок, после которого нет целого кадра. | Сохраняет байты и сообщает о более ранних корректных частях. | Если корректные части найдены, обрабатывает их и затем очищает весь журнал. |

При запуске коллектор сразу формирует итоговый PGM из восстановленных частей,
содержащих данные с временными метками. Если таких данных нет, журнал очищается
без формирования PGM. После успешного формирования итогового PGM очищается весь
журнал, включая сохранённые `Journal::open` повреждённые байты. Если сформировать
итоговый PGM не удаётся, коллектор регистрирует ошибку в логах, также очищает
журнал и начинает сбор заново. Если корректных частей нет, итоговый PGM по
результатам восстановления не формируется: `TornTail` к этому моменту уже
обрезан, а повреждения других типов остаются, и после них можно добавлять новые
кадры.

## Из чего складывается размер

В текущей реализации размер в основном определяется телами секций, а не
постоянными 52 байтами контейнера или 32-байтными записями каталога.

### Что уже уменьшает размер без потери данных

| Механизм | Что удаляется или сжимается | Граница действия |
| --- | --- | --- |
| `StrId` и словарь | Повторяющийся короткий текст заменяется значением в столбце `u64`; байты записываются один раз. | Одна копия на окно, а не на весь итоговый PGM; точный размер столбца задаёт Parquet. |
| Parquet и Zstd-3 | Страницы каждого столбца кодируются и сжимаются независимо от других тел. | Повторы между разными телами Parquet не используются. |
| Каноническая сортировка | Близкие по ключу значения оказываются рядом; результат детерминирован. | Выигрыш от сжатия зависит от данных и не гарантирован. |
| Узкие типы столбцов | Например, `pid` хранится как `i32`, а не как `i64`; текстовые метки вынесены в словарь. | Тип каждого столбца фиксируется контрактом секции. |
| Исключение метаданных Arrow | В каждом теле нет второй копии логической схемы Arrow; `created_by` пуст. | Физическая схема и концевой блок Parquet остаются. |

### Что уменьшает размер ценой данных

Это ограничения входа, а не сжатие:

| Механизм | Что отбрасывается | Цена |
| --- | --- | --- |
| Усечение `dict.blobs` | Хвост значения после 64 КиБ. | Полный текст восстановить нельзя; остаются длина и SHA-256. |
| `*_MAX_TABLES`, `*_MAX_INDEXES`, `*_MAX_STATEMENTS`, `*_MAX_PLANS` | Объекты за пределами первых N позиций. | Наблюдения по ним не попадают в PGM. |
| Интервалы источников | Состояние между двумя опросами не фиксируется. | Снижается временное разрешение. |
| Бюджеты текстов планов | Тексты сверх лимита одного чтения. | Числовые сведения о плане могут сохраниться без текста. |

Пределы возраста и размера сегмента относятся к группировке файлов. Они меняют
число PGM и небольшой объём обрамления, но сами по себе не объединяют тела
Parquet и не устраняют повторяющиеся словарные записи.

### Откуда берутся повторы между окнами

В каждом окне сбора для каждого непустого типа секции создаётся отдельное тело
Parquet. Даже секция снимка с одной табличной строкой содержит схему Parquet,
сведения о столбцах и завершающий блок. Поэтому в 15-минутном сегменте один
`type_id` может иметь десятки маленьких тел и десятки копий служебных данных.

Словарные секции тоже создаются для каждого окна. На примере `postgres` это
выглядит так. Схема показывает логическое содержимое тел после декодирования:

```text
до завершения сегмента:

active.parts
|-- PGMP [часть #1:
|          тело pg_stat_activity #1: pid=101, H; pid=102, H
|          dict.strings #1: H -> b"postgres"]
`-- PGMP [часть #2:
           тело pg_stat_activity #2: pid=103, H
           dict.strings #2: H -> b"postgres"]

после завершения сегмента (`seal`):

"PGM1"
|-- тело pg_stat_activity #1
|-- тело dict.strings #1: H -> b"postgres"
|-- тело pg_stat_activity #2
|-- тело dict.strings #2: H -> b"postgres"
|-- общий каталог
`-- хвостовой указатель

3 ссылки StrId | 1 уникальный H | 2 словарные записи на диске
```

При текущем завершении сегмента (`seal`) сохраняются обе словарные записи и оба
самостоятельных тела `pg_stat_activity`. Возможная перепаковка выглядит иначе:

```text
"PGM1"
|-- одно или несколько укрупнённых тел pg_stat_activity
|-- одно тело dict.strings: H -> b"postgres"
|-- общий каталог
`-- хвостовой указатель

3 ссылки StrId | 1 уникальный H | 1 физическая словарная запись
```

Для этого недостаточно склеить байты. Нужно декодировать Parquet, объединить
тела одного `type_id`, проверить равенство повторных словарных записей,
отсортировать табличные строки по каноническому ключу, разбить результат по
рабочим пределам и снова закодировать. Такая перепаковка пока не входит в
`seal`.

### Подходы, которые пока не реализованы

| Подход | Откуда берётся экономия | Ограничение |
| --- | --- | --- |
| Перепаковка при завершении сегмента | Тела одного `type_id` объединяются, повторные словарные записи удаляются. | Нужны декодирование и повторное кодирование, проверка коллизий, сортировка, разбиение по пределам и полный цикл проверки записи и чтения. |
| Один `Interner` на весь открытый сегмент | Повторное значение не записывается в словарь следующего окна. | Текущая часть PGM самодостаточна. Если следующее окно ссылается на словарь предыдущего, чтение отдельного кадра и восстановление после сбоя требуют нового контракта. |
| Более высокий уровень Zstd для Parquet | Страницы отдельного тела могут стать меньше. | Требует больше CPU и по-прежнему не использует повторы между телами. Уровень 3 сейчас жёстко задан. |
| Внешнее сжатие всего PGM | Общий поток сжатия может использовать повторы между словарями, концевыми блоками и соседними окнами. | Пропадает прямой доступ к телу по `offset`; нужен новый слой хранения или изменение формата. |

Первые два подхода устраняют структурные повторы. Повышение уровня Zstd меняет
только локальное сжатие и не заменяет перепаковку.

### Экспериментальная оценка перепаковки в 16,5–16,7 раза

В репозитории есть игнорируемый тест
[`repack_estimate`](../../bins/pg_kronika-demo/tests/repack_estimate.rs),
который запускают вручную. Он группировал тела по `type_id` и для каждой
успешно декодированной группы оценивал размер одного тела Parquet с Zstd-3;
при ошибке разбора или записи оставался исходный размер. Внутри каждого
словарного `type_id` эксперимент оставлял первую словарную запись для каждого
`str_id`, не проверяя равенство остальных столбцов у дубликатов. Согласно
отчёту, все тела удалось разобрать, но тест не закрепляет это условие проверкой,
а вывод программы и файлы PGM не сохранены в репозитории. Предложенное
преобразование сохраняет разметку контейнера PGM v1.

| Записанный сегмент | Исходный PGM | Оценка после перепаковки | Сокращение |
| --- | ---: | ---: | ---: |
| Первые 15 минут | 17,8 МиБ | около 1,08 МиБ | 16,5 раза |
| Вторые 15 минут | 17,6 МиБ | около 1,06 МиБ | 16,7 раза |
| Последние 7 минут | 5,4 МиБ | около 0,53 МиБ | 10,3 раза |

Фраза «в 17 раз» — это округление оценки 16,7 раза, а не отдельный замер.
В исследованном наборе данных основными причинами оказались:

- секции Parquet с одной табличной строкой размером 2,4–6,8 КиБ каждая;
- 458 записей дерева блокировок в 211 почти пустых секциях общим размером
  1,9 МиБ;
- 71 468 записей словаря при примерно 3200 уникальных `str_id`, то есть около
  22 записей на одно уникальное значение в среднем;
- уменьшение готового PGM до 9–10% внешним `zstd -19` в контрольном опыте:
  файл содержал много повторяющихся фрагментов, но опыт не разделял вклад
  словарей, концевых блоков Parquet и самих снимков.

Эти числа показывают резерв оптимизации, а не коэффициент сжатия текущей
реализации:

- основной `seal` по-прежнему копирует тела без объединения и дедупликации;
- тест только оценивал размеры тел и не создавал новый PGM с проверкой полного
  цикла записи и чтения;
- эксперимент объединял до 1 000 000 табличных строк в одно тело Parquet и не
  проверял действующие пределы 65 536 табличных строк и 8 МиБ на секцию,
  поэтому не показал, как разбить результат на секции v1, которые примет
  текущий читатель;
- исходный прогон длился 37 минут, а не час: 71 МиБ/ч получено как
  `17,8 МиБ * 4`; три файла занимали 40,8 МиБ за 37 минут, что соответствует
  примерно 66,2 МиБ/ч;
- 4,3 МиБ/ч после перепаковки — тоже экстраполяция;
- в прогоне был выключен сбор журнала PostgreSQL, а `cross_source_join`
  завершался ошибкой; обе неисправности были устранены позднее, поэтому замер
  нужно повторить на актуальном стенде с включённым PG-log и исправленным
  `cross_source_join`;
- исходные PGM не добавлены в репозиторий, а отключённые тесты не выполняют
  этот замер в обычном CI.

Точная методика, команды и недостающие проверки находятся в
документе
[`2026-07-24-pgm-compaction.md`](../../docs/superpowers/plans/2026-07-24-pgm-compaction.md).
Для рабочей реализации нужны сортировка объединённых записей по каноническому
ключу, проверка словарей, разбиение с учётом пределов секций, проверка
совпадения табличных строк после записи и повторного чтения и новые измерения.
Одной смены уровня сжатия недостаточно.

## Параметры, влияющие на размер файлов

У разметки PGM нет собственных настроек сжатия. Оператор управляет объёмом и
группировкой собранных данных через `pg_kronika-collector`:

| Настройка | Значение по умолчанию | Что меняется |
| --- | ---: | --- |
| Переменные источников `*_INTERVAL_S` | 1–3600 с в зависимости от источника | Увеличение интервала уменьшает число снимков и завершающих блоков Parquet, но снижает временное разрешение. `KRONIKA_INTERVAL_S=5` задаёт только шаг планировщика. |
| `KRONIKA_PG_MAX_TABLES`, `KRONIKA_PG_MAX_INDEXES`, `KRONIKA_PG_MAX_STATEMENTS`, `KRONIKA_PG_MAX_PLANS` | `500` | Меньшие значения сокращают число табличных строк и объём словарей, но исключают объекты вне первых N позиций. |
| `KRONIKA_PG_MAX_PLAN_TEXT` | 32 768 байт | Максимальная длина текста одного плана за чтение. |
| `KRONIKA_PG_PLAN_TEXT_BUDGET` | 8 МиБ | Общий бюджет текстов планов за чтение; ноль выключает их сбор. |
| `KRONIKA_SEGMENT_MAX_BYTES` | 64 МиБ | Завершает открытый сегмент после указанного числа сырых байтов `active.parts`; значение `0` завершает сегмент после каждого окна. Меняет размер отдельных файлов, но не сжатие Parquet. |
| `KRONIKA_SEGMENT_MAX_AGE_S` | 900 с | Предельный возраст открытого сегмента. В основном меняет временной диапазон и число файлов. |
| `KRONIKA_JOURNAL_MAX_BYTES` | 1 ГиБ | Если добавление очередного кадра, кроме первого, превысило бы порог, сегмент завершается досрочно. Это не целевой размер PGM. |

Уменьшение ограничений источников сокращает расход диска ценой полноты данных.
Изменение только возраста или размера ротации не устраняет повторные
завершающие блоки Parquet и словарные записи в текущей реализации. Все
интервалы и правила проверки перечислены в
[документации коллектора](../../bins/pg_kronika-collector/README.ru.md).

## Целостность, ограничения и совместимость

CRC32C покрывает каждое тело секции, каталог и заголовок `PGMP`. Она
обнаруживает случайную порчу, но не аутентифицирует файл, не заменяет
электронную подпись и не шифрует данные.

`kronika-format` проверяет структуру кадра и контейнера, длину и CRC32C
каталога, границы секций, а при полной проверке — CRC32C тел секций. Компоненты
верхнего уровня задают дополнительные правила: текущий читатель итоговых файлов
PGM принимает версию контейнера 1 и ограничивает размеры каталога и секций,
число табличных строк и групп строк Parquet. Несовместимая схема секции
получает новый `type_id`; изменение разметки PGM требует новой версии
контейнера.

Актуальные контракты и реализация:

- [`src/lib.rs`](src/lib.rs), [`src/catalog.rs`](src/catalog.rs) и
  [`src/parts.rs`](src/parts.rs) — двоичный контракт;
- [`src/dictionary.rs`](src/dictionary.rs) — инварианты словарей;
- [`kronika-registry`](../kronika-registry/README.ru.md) — схемы секций и
