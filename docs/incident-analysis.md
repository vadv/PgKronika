# Как читать анализ инцидентов

`GET /v1/incidents` находит эпизоды аномалий, группирует близкие эпизоды одного
узла и проверяет их диагностическими линзами. Линза возвращает проверяемый
вывод (`finding`) и данные, на которых он основан.

Finding не является установленной первопричиной. Он означает только, что
сохранённые данные удовлетворили известному условию в выбранном окне.
Параметры запроса и общие ограничения API описаны в
[`pg_kronika-web`](../bins/pg_kronika-web/README.ru.md#конечные-точки).

## С чего начинать

Сначала проверьте верхний уровень ответа:

| Поле | Вопрос |
| --- | --- |
| `analysis_status` | Был ли анализ запущен и какой результат получен? |
| `clustering_complete` | Все ли доступные эпизоды прочитаны и сгруппированы? |
| `complete` | Полна ли вся подсистема относительно каталога возможностей? |
| `coverage_by_section` | Есть ли разрывы в использованных логических секциях? |
| `data_quality` | Какие ограничения входных данных уже известны? |
| `skipped` | Какие секции, оценки или работы пропущены и почему? |
| `catalog` | Какие линзы применены, а какие неактивны из-за требований? |
| `log` | Что нашла отдельная ветка типизированных stderr-событий? |

`complete` сейчас всегда равен `false`: реализован не весь каталог
диагностических возможностей. Это не означает, что каждый конкретный запрос
остановился с ошибкой. Для завершённости текущего запроса смотрите
`clustering_complete`, `finding_evaluation_status` и `skipped`.

## Состояния анализа

| `analysis_status` | Значение |
| --- | --- |
| `no_data` | В выбранном диапазоне нет пригодных входных данных |
| `missing_node_identity` | Нельзя доказать идентичность узла |
| `conflicting_node_identity` | В диапазоне встретились противоречивые идентичности узла |
| `partial` | Чтение, группировка или оценка остановились по ошибке либо пределу |
| `insufficient_data` | Данные прочитаны, но пригодных позиций для анализа нет |
| `calm` | Анализ завершён, кандидаты на инцидент не найдены |
| `incidents_detected` | Анализ завершён и вернул один или несколько инцидентов |

`clustering_complete=true` относится к чтению, оценке эпизодов аномалий и их
группировке. Оно не доказывает полноту PostgreSQL, ОС или stderr-журнала.

## Инцидент и finding

Сокращённая форма одного результата:

```json
{
  "analysis_status": "incidents_detected",
  "clustering_complete": true,
  "complete": false,
  "incidents": [
    {
      "interval": { "from": 1700000000000000, "to": 1700000180000000 },
      "incident_key": "...",
      "members": [
        {
          "logical_section": "pg_stat_database",
          "column": "blks_read",
          "identity": [5],
          "from": 1700000000000000,
          "to": 1700000120000000
        }
      ],
      "findings": [
        {
          "lens_id": "PG-CACHE-010",
          "role": "coincident",
          "confidence": "medium",
          "scope": {
            "logical_section": "pg_stat_database",
            "column": "blks_read",
            "identity": [5]
          },
          "evidence": []
        }
      ],
      "evaluation_complete": true,
      "finding_evaluation_status": "complete"
    }
  ]
}
```

`members` — исходные эпизоды аномалий. `findings` — дополнительные проверки
данных вокруг них. Пустой `findings` при
`finding_evaluation_status=complete` означает, что активные линзы не нашли
своих условий. При `partial` причина находится в `skipped.evaluations`.

`lens_id` является стабильным машинным идентификатором. `slug` используется в
каталоге как читаемое машинное имя, но не заменяет `lens_id`. Локализованные
заголовки принадлежат UI и не входят в машинный ответ.

## Доказательства счётчиков

`counter_aggregate` содержит:

- формулу и исходные операнды;
- сумму допустимых приращений каждого операнда;
- единицы и назначение операндов;
- порог и рассчитанное значение;
- фактические границы использованных интервалов;
- число пригодных и исключённых интервалов;
- причины исключения.

Интервалы объединяются только при совпадающих концах и длительности. Сброс,
разрыв, непригодная разность, несовпавший интервал и потеря числовой точности
не превращаются в ноль.

Порог покрытия 70% считается по концам интервалов, замеченным хотя бы у одного
операнда. Это не то же самое, что `coverage.source_period`. Период источника
оценивается как медиана наблюдаемых интервалов. Для устойчивой оценки нужны не
менее трёх интервалов.

Если период доказать нельзя:

- `observed_source_period_us` и `expected_interval_count` равны `null`;
- `source_window_completeness` равен `"unknown"`;
- `expected_interval_count_reason` содержит структурированную причину.

Если период известен, полнота равна числу пригодных интервалов, делённому на
ожидаемое число. Значение может быть больше единицы и намеренно не
ограничивается.

## Доказательства мгновенных значений

Evidence с `type=gauge` содержит время наблюдения, число снимков, измерение,
порог и оценку периода источника. `measurement.kind` принимает:

- `value` — одно значение;
- `ratio` — отношение двух значений с отдельными единицами;
- `trend` — изменение между первой и последней точкой за фактическое время.

Отношение величин с разными единицами не является безразмерным автоматически.
Например, `milliseconds / count` даёт `milliseconds_per_call`.
`operand_unit` и `headroom` заполняются только для совместимых единиц.

Числа в evidence публикуются как `ieee754_binary64`. Целочисленное значение,
которое нельзя представить точно, исключается с причиной `numeric_limit`.

## Роли и причинность

Возможные роли:

| Роль | Что утверждается |
| --- | --- |
| `lead` | Есть отдельное структурное доказательство направления к другому участнику |
| `amplifier` | Условие могло усиливать наблюдаемую проблему |
| `downstream` | Есть структурное доказательство, что участник находится ниже по связи |
| `coincident` | Условие наблюдалось одновременно, направление не доказано |

Обычные метрики одного снимка считаются одновременными. Положение timestamp
внутри инцидента не назначает `lead` или `downstream`.

Текущее структурное исключение — ребро `pg_locks.blocked_by`, полученное из
`pg_blocking_pids`:

- blocker получает `lead`;
- waiter получает `downstream`;
- PID `0` обозначает prepared transaction;
- повтор `(waiter_pid, blocker_pid)` в одном снимке удаляется;
- транзитивные рёбра не строятся.

Это направление ожидания блокировки, а не доказательство первопричины всего
инцидента. Сохранённое evidence не содержит цель и режим блокировки, поэтому
имеет `evidence_completeness=edge_only` и предел confidence `medium`.

Совпадение PID, числового identity или времени само по себе не создаёт связь
между секциями. Для `cross_section_entity_join` нужны явно совместимые
идентичности и подтверждённое происхождение: общий токен снимка, сохранённая
связь либо ограниченное отображение жизненных интервалов. При отсутствии
такого доказательства capability остаётся неактивной.

## События stderr

События обрабатываются отдельной веткой `log`. Сейчас каталог содержит 28
метрических или snapshot-линз и 14 веток stderr. Две event-ветки переиспользуют
`PG-CONN-014` и `OS-FS-027`, поэтому всего получается 40 уникальных `lens_id`.

`log.complete=false`, потому что источник stderr не доказывает полного
покрытия журнала. Положительное событие также имеет ограниченный смысл:

- SIGKILL не доказывает выбор процесса OOM killer;
- PANIC не доказывает повреждение данных;
- `out of shared memory` не означает исчерпание физической RAM;
- slow-query подтверждает только превышение настроенного порога;
- локальный `invalid record length` может быть обычным концом WAL;
- отсутствие события ничего не доказывает без полного покрытия источника.

SQL, параметры, адреса, имена ролей и баз, пути и команды архивации могут
содержать секреты. Event-линзы редактируют такие поля; сырой payload журнала
endpoint инцидентов не возвращает.

## Где проверять реализацию

- [`handlers/incidents.rs`](../bins/pg_kronika-web/src/handlers/incidents.rs) —
  параметры и запуск endpoint;
- [`incident_input.rs`](../bins/pg_kronika-web/src/incident_input.rs) —
  ограниченное чтение секций и качество входа;
- [`incident/`](../bins/pg_kronika-web/src/incident/) — каталог линз,
  группировка, evidence, роли и пределы;
- [`incident_response.rs`](../bins/pg_kronika-web/src/incident_response.rs) —
  точная JSON-проекция;
- [`tests/incidents.rs`](../bins/pg_kronika-web/src/tests/incidents.rs) —
  внешний контракт endpoint.

Новая линза должна использовать ограниченный типизированный вход, объявлять
capabilities, соблюдать общий бюджет работы и сохранять детерминированный
порядок. Стабильный `lens_id` нельзя менять после публикации.
