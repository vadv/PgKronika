# Текущая архитектура PgKronika

Этот документ объясняет границы компонентов и путь данных в текущем рабочем
пространстве. Состав пакетов задаёт корневой [`Cargo.toml`](../Cargo.toml), а
разрешённые зависимости бинарников проверяет
[`xtask`](../xtask/src/main.rs).

## Процессы

Пользователь запускает два процесса:

| Процесс | Что читает | Что пишет или отдаёт |
| --- | --- | --- |
| `pg_kronika-collector` | PostgreSQL, локальные `/proc`, `/sys`, cgroup и при настройке stderr-журнал PostgreSQL | `active.parts` и готовые `.pgm` в локальном каталоге |
| `pg_kronika-web` | Готовые PGM, корректные части `active.parts` и соседние файлы производных фактов | UI, JSON API и метрики Prometheus |

Коллектор не открывает сетевой порт. Веб-процесс не подключается к PostgreSQL.
Они обмениваются данными только через каталог:

```text
PostgreSQL ─┐
/proc,/sys ─┼─> pg_kronika-collector ─> active.parts ─> N.pgm
stderr log ─┘                                      │
                                                   ├─> pg_kronika-web ─> UI / JSON
                                                   └─> N.ovf
```

`pg_kronika-archiver` и `pg_kronika-dump` пока являются заглушками. Удалённая
архивация, автоматическое удаление исходных PGM, доставка оповещений и MCP в
рабочем пространстве не реализованы.

## Путь записи

1. `kronika-source-pg`, `kronika-source-os` и `kronika-source-log` читают
   источники с установленными ограничениями по времени, строкам и байтам.
2. Источники выбирают зарегистрированную Rust-структуру для версии PostgreSQL,
   расширения или системного файла. `kronika-registry` задаёт точную схему,
   `type_id`, роли столбцов, ключи и кодек Parquet.
3. `kronika-writer` интернирует строки, кодирует типизированные секции и словари
   в самодостаточную часть PGM.
4. Часть добавляется в `active.parts` как журнальный кадр. Успешное добавление
   синхронизирует кадр с диском.
5. При достижении порога размера, возраста, журнала или лимита компактного
   результата, а также по `SIGUSR2`, операция `seal` проверяет части, сливает
   строки данных каждого `type_id` группами не более 32, нормализует словари и
   пишет по одному компактному телу на тип. Временный PGM синхронизируется,
   публикуется без замены другого готового файла, затем синхронизируется
   родительский каталог.

При запуске коллектор сканирует `active.parts`. Неполный последний кадр, а
также кадр с корректным заголовком до конца файла и некорректным телом
PGM-части обрезаются до последней корректной границы. Корректные части прежнего
запуска сначала превращаются в готовый сегмент, и только после этого начинается
новый сбор. Прочее повреждение в середине или конце журнала сохраняется для
диагностики, а запуск завершается с ошибкой. При ошибке `seal` журнал также
остаётся нетронутым.

Физическая разметка описана в
[`kronika-format`](../crates/kronika-format/README.ru.md), а журнал и операция
`seal` — в [`kronika-writer`](../crates/kronika-writer/README.ru.md).

## Путь чтения

1. `kronika-store::LocalDir` сканирует активный журнал и перечисляет готовые
   PGM. Эти операции последовательны и не образуют один атомарный снимок
   каталога.
2. `kronika-reader::LocalDirSnapshot` открывает наблюдённые готовые файлы и
   активные части. Активная часть скрывается только при точном совпадении её
   каталога с уже опубликованным PGM; одного пересечения по времени
   недостаточно.
3. Считыватель проверяет обрамление, внутренний контракт каталога, границы и
   CRC32C, а затем передаёт тело кодеку `kronika-registry`. Схемы одного
   логического источника объединяются по имени секции.
4. Для накопительных столбцов `kronika-reader` вызывает
   `kronika-analytics::diff`. Сброс, первая точка, разрыв, неверный интервал и
   выключенный сбор остаются разными состояниями и не заменяются нулём.
5. `pg_kronika-web` ограничивает объём запросов и выполняет поиск аномалий.
   Для `pg_store_plans` он отдельно проверяет непрерывность снимков, сбросов,
   версии расширения и экземпляра; reset-контекст принимается только с точным
   `ts` снимка планов. Затем сервис передаёт в чистые ядра смеси планов и
   буферную работу на вызов. Ответ ограничен по размеру, явно сообщает
   применимость и полноту данных и не выдаёт эти сигналы за причинный диагноз.
6. Числовые эпизоды группируются по времени и экземпляру узла. Активные
   диагностические правила читают типизированные дельты счётчиков внутри окна
   инцидента, возвращают ограниченное число выводов, а неподключённые вопросы
   остаются в неактивном каталоге.

Для временной шкалы считыватель может сохранить рядом с `N.pgm` проверяемый
файл `N.ovf` с производными фактами. Исходные данные читаются из PGM:
отсутствующий, устаревший, повреждённый или относящийся к другому PGM файл
фактов перестраивается. Активные данные сворачиваются отдельно и публикуются
только после сверки их поколения с точным дескриптором готового сегмента.

Подробности логических запросов и файлов фактов находятся в
[`kronika-reader`](../crates/kronika-reader/README.ru.md). Формулы аномалий
описаны в [`kronika-analytics`](../crates/kronika-analytics/README.ru.md), а
интерпретация ответа об инцидентах — в
[`incident-analysis.md`](incident-analysis.md).

## Ответственность пакетов

| Пакет | Владеет | Не владеет |
| --- | --- | --- |
| `kronika-format` | Обрамление PGM и журнальных кадров, каталог, CRC32C и словари | Схемы Parquet и политика хранения |
| `kronika-derive` | Генерация внутренней реализации `Section` | Публичное расширение реестра сторонними крейтами |
| `kronika-registry` | `type_id`, схемы, кодеки, роли столбцов, ключи и ворота сбора | SQL, расписание и файловый жизненный цикл |
| `kronika-writer` | Буферы секций, интернер, `active.parts`, восстановление и `seal` | Источники и запросы чтения |
| `kronika-store` | Доступное только для чтения перечисление локальных PGM и сканирование журнала | Декодирование секций и удалённые хранилища |
| `kronika-reader` | Проверенное декодирование, снимки, логические запросы, разности и файлы фактов | HTTP и сбор PostgreSQL |
| `kronika-analytics` | Независимые от источника разности, аномалии и правила оценки | Извлечение PGM, хранение и HTTP |
| `kronika-source-pg` | SQL PostgreSQL и преобразование версий в строки реестра | Запись PGM |
| `kronika-source-os` | Ограниченное чтение Linux `/proc`, `/sys` и cgroup | Расписание и ротация |
| `kronika-source-log` | Чтение хвоста stderr, разбор событий и учёт пропусков | Кодеки реестра и запись |
| `pg_kronika-collector` | Жизненный цикл сбора, расписание, бюджеты и ротация | API чтения |
| `pg_kronika-web` | HTTP, аутентификация, запросы временной шкалы и анализ | Сбор и утверждение первопричины |
| `kronika-bdd` | Интеграционная матрица PostgreSQL 15–18 | Рабочий процесс продукта |
| `xtask` | Проверка разрешённых зависимостей | Сборка выпуска |

## Границы зависимостей

Команда

```sh
cargo run -p xtask -- check-deps
```

проверяет транзитивные зависимости четырёх бинарников:

```text
collector -> format, derive, registry, writer, source-pg, source-os, source-log
web       -> format, derive, registry, writer, store, reader, analytics
archiver  -> format, store
dump      -> format, derive, registry, store, reader, analytics
```

`kronika-writer` входит в граф web только при сборке исполняемого файла
квалификации на точном коммите; обычный сервер не включает feature
`qualification`. Список задаёт максимально допустимый граф зависимостей, но
сам по себе не подтверждает реализацию функции бинарника.

## Целостность и качество данных

- PGM использует CRC32C для каталога и тел секций. CRC обнаруживает
  случайную порчу, но не является подписью или шифрованием.
- Несовместимая схема получает новый `type_id`. Считыватель не угадывает
  совместимость по содержимому Parquet.
- Размер выборки не доказывает её полноту. `collection_coverage`,
  `snapshot_coverage`, пропуски считывателя и сообщения коллектора являются
  разными сигналами.
- Неизменившийся измеренный счётчик даёт нулевое приращение. Сброс или
  отсутствие данных приращения не дают.
- Лимиты строк, байтов, времени и числа сущностей применяются до крупных
  выделений памяти и описаны в README компонента, которому они принадлежат.

## Граница безопасности

Коллектор имеет доступ к PostgreSQL и локальным системным данным, но не
принимает входящие сетевые соединения. Веб-процесс имеет доступ к каталогу
сегментов и сети, но не содержит клиента PostgreSQL.

PGM может содержать SQL, планы, имена объектов, аргументы процессов и текст
журнала. Ограничьте права на каталог и резервные копии. Веб-сервер не
реализует TLS; встроенную Basic Auth следует использовать на loopback или за
обратным прокси с защищённым транспортом. Проверки готовности и `/metrics`
остаются публичными.

## Зрелость

Все пакеты имеют общую версию `0.0.0`, не публикуются на crates.io и
собираются одним рабочим пространством. Реализованы локальный сбор, PGM,
считывание и веб-интерфейс. Выпускной архив, политика совместимости релизов,
удалённая архивация и управление сроком хранения исходных PGM пока отсутствуют.

Датированные записи в [`superpowers/`](superpowers/) объясняют отдельные
решения, но не заменяют код, тесты и текущие README.
