# Проверка функционального соответствия overview `parity-v1`

Артефакт проверки создаётся на основе исходных данных для одного конкретного
коммита Git. Он проверяет соответствие документу
`docs/superpowers/specs/2026-07-22-overview-index-timeline-api.md`, но не
гарантирует воспроизводимости производительности на любом оборудовании.

## Набор данных «плотный час»

Набор `overview-dense-hour-v2` содержит ровно 720 снапшотов
`pg_stat_database` с интервалом пять секунд, одну строку контекста сброса и
полный состав источника для каждого снапшота. Конвейер извлечения создаёт
эталонные секции счётчиков, gauge, сбросов, покрытия и событий. Валидатор
записывает:

- размеры источника, файла фактов и декодированных блоков;
- логический объём данных в памяти и объём одного закреплённого набора фактов;
- отдельно — постоянную часть метрик и переменную часть строк событий;
- точное число рядов, отсчётов, сбросов, состояний, интервалов покрытия и
  фактов;
- объём постоянной части метрик на сохранённый отсчёт, без установления
  нормативного предела.

Допустимые размеры на диске и в памяти задаёт владелец развёртывания:

```text
OVERVIEW_DENSE_DISK_BUDGET_BYTES
OVERVIEW_DENSE_RESIDENT_BUDGET_BYTES
```

Если обе переменные отсутствуют, артефакт содержит значение
`owner_deferred`. Точные размеры, объём I/O и быстродействие всё равно
проверяются, но решение о допустимости размеров для развёртывания не
принимается. Задать только одну переменную нельзя. Если заданы обе, итоговая
проверка требует, чтобы измеренные объёмы не превышали эти пределы.

## Режимы и состояние памяти

Артефакт фиксирует модель хранения в одном каталоге, который целиком
принадлежит PgKronika. Активный журнал и готовая пара «источник + факты»
лежат рядом:

```text
active.parts
dense-hour.pgm
dense-hour.ovf
```

Артефакт также содержит точные имена PGM и OVF и подтверждает совпадение их
базового имени (stem).

Валидатор выполняет девять режимов: `derived-cold`, `restart-warm`,
`process-hot`, `range-cold/facts-warm`, `live`, `concurrent-identical`,
`concurrent-disjoint`, `memory-only` и `oracle-profile`.

В режиме `derived-cold` каждая итерация начинается с нового каталога данных, в
котором есть только `dense-hour.pgm`. Измеряется рабочий путь построения:
бюджет задачи, извлечение фактов и атомарная запись сайдкар-файла
`dense-hour.ovf`. Для `restart-warm` корректный OVF создаётся до измерения, а в
каждой итерации создаётся новый `FactStore`. Поэтому между итерациями не
сохраняются ни рабочие данные процесса, ни декодированная запись в памяти.
Каталоги данных каждого режима остаются рядом с выходным артефактом как
дополнительное подтверждение.

Результаты девяти режимов сохраняют полные измерения рабочих конечных точек.
В режимах HTTP рабочий маршрутизатор и регистратор метрик создаются до запуска
таймера запроса; в измерение по-прежнему входят загрузка фактов, проекция,
сериализация ответа и чтение его тела. Поскольку в этих результатах
преобладают HTTP и JSON, артефакт также содержит отдельный компактный профиль
`compact sealed facts read + bucket`, требуемый §18.4.6. Неизменные ограничения
p95 25%/25%/50% применяются к компактному профилю, а оба профиля и все исходные
отсчёты сохраняются в артефакте.

«Холодный» здесь означает новый экземпляр reader'а и пустое состояние памяти
процесса. Валидатор не очищает страничный кэш ОС, поэтому выставляет
`storage_cold=false`. Для измерения с холодным накопителем нужна отдельная
управляемая процедура на конкретной связке узла и файловой системы; подменять
ею этот результат нельзя.

## BDD для PostgreSQL и жизненного цикла процесса

Точный перечень подтверждений включает восемь сценариев: по одному сценарию
сквозной временной шкалы и жизненного цикла настоящего процесса
`pg_kronika-web` для каждой версии PostgreSQL с 15-й по 18-ю. Сценарии
жизненного цикла запускаются так:

```bash
DEBUG=1 make test-bdd TAGS=@timeline_web_lifecycle
DEBUG=1 make test-bdd TAGS='@timeline_web_lifecycle and @pg15'
```

Первая команда проверяет PostgreSQL 15–18, вторая оставляет только PostgreSQL
15 для целевой диагностики. В каждом сценарии запускается настоящий
исполняемый файл `pg_kronika-web` с отдельным каталогом данных. По HTTP
выполняются запросы к обработчикам `overview`, `events`, `health` и `cursor`, а
также к конечной точке метрик Prometheus. Для проверки перезапуска создаются
новые процессы. Готовность определяется явным сообщением после открытия порта.
Для завершения используется штатная остановка или проверяемое аварийное
завершение, а место публикации управляется барьером. Фиксированных задержек и
циклов повторных запросов нет.

Сценарии подтверждают создание и проверку сайдкар-файла `N.ovf`, повторное
чтение без тел PGM и перезаписи OVF, атомарное восстановление после повреждения
и всех видов устаревшего идентификатора, отказ от временного файла
незавершённой публикации, ограниченный fallback-кэш с последующим
долговременным восстановлением, восстановление после отмены, истечение курсора
прошлого процесса, сохранность исходных файлов и однозначный конфликт второго
владельца. Валидатор принимает только восемь точных сочетаний файла и имени
сценария из
[таблицы подтверждений overview](overview-parity-v1-traceability.md).

## Локальная проверка

```bash
cargo run --release --manifest-path bins/pg_kronika-web/Cargo.toml \
  --example overview_parity_qualification --features qualification -- \
  --output target/qualification/overview.raw.json
python3 scripts/validate-overview-qualification.py \
  target/qualification/overview.raw.json
```

В CI выполняется итоговая проверка структуры, I/O и производительности. Затем
сохраняются исходный JSON, JSON с результатом проверки и файлы SHA-256.
Сохранённый артефакт для конкретного коммита проверяется так:

```bash
python3 scripts/validate-overview-qualification.py \
  overview.final.json --exact-head GIT_SHA --final
```

Итоговое подтверждение также требует, чтобы все связанные проверки, задания
BDD, покрытие и квалификационное задание выполнялись в рамках одного запуска
GitHub Actions и одного коммита. Смешивать результаты разных запусков или
использовать результат из рабочего дерева с незакоммиченными изменениями нельзя.
Значение `owner_deferred` не означает, что размеры одобрены для развёртывания;
если пределы заданы, они обязательны.
