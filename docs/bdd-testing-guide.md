# Как писать BDD-тесты PgKronika

BDD проверяет наблюдаемое поведение коллектора и веб-API на живых PostgreSQL
15–18. Сценарий создаёт известное состояние, получает PGM и сравнивает
декодированные данные с конкретным ожиданием или независимым запросом к
PostgreSQL.

Команды запуска и устройство Docker/Nix-образа описаны в
[`testing.md`](testing.md). Источники истины для синтаксиса сценариев:

- текущие [feature-файлы](../crates/kronika-bdd/features/);
- зарегистрированные [шаги](../crates/kronika-bdd/src/steps/);
- реализация [оракулов](../crates/kronika-bdd/src/harness/oracle.rs).

## Жизненный цикл сценария

Матрица PostgreSQL поднимается один раз на процесс. Сценарии выполняются
последовательно и обычно проходят такой путь:

1. Выбирают версию PostgreSQL и создают отдельную базу.
2. Выполняют SQL, который формирует проверяемое состояние.
3. При необходимости оставляют именованные сессии, транзакции или ожидания
   активными.
4. Запускают коллектор до готового сегмента.
5. Декодируют нужную секцию и сравнивают её с ожиданием или оракулом.
6. Закрывают сессии и удаляют состояние сценария.

Пропущенный шаг является ошибкой. При провале средство запуска добавляет
декодированные строки, данные оракула, вывод коллектора и журналы PostgreSQL.

## Правила сценария

1. **Входные данные видны в `.feature`.** DDL, исходные строки и запросы,
   создающие блокировку или нагрузку, записываются в docstring. Rust-шаг
   реализует инфраструктуру, а не скрывает смысл сценария.
2. **Проверяются конкретные значения.** Укажите ключ строки и ожидаемые
   столбцы. Проверка только наличия секции допустима лишь тогда, когда именно
   наличие является контрактом.
3. **Оракул независим от коллектора.** Не копируйте SQL источника целиком.
   Проверяйте смысл через системное представление, точечный запрос каталога или
   явно записанное преобразование.
4. **Живое состояние удерживается до снимка.** Сессия-блокер, ожидающая сессия
   и открытая транзакция не должны завершиться до проверки.
5. **Один `Then` проверяет один контракт.** Ошибка должна однозначно называть
   секцию, ключ, столбец и несовпавшее значение.
6. **Версия и ограничения явны.** Добавляйте теги версии, `@serial` и другие
   существующие теги, когда сценарий зависит от мажора PostgreSQL, глобального
   состояния или времени.
7. **Очистка обязательна.** Сценарий не оставляет транзакции, роли, расширения,
   базы, схемы или фоновые задачи следующему сценарию.

## Ссылки на секции

В тексте сценария используется доменное имя из таблицы псевдонимов BDD,
например:

```text
pg_stat_database.pg14_17
pg_stat_io.pg16_17
pg_locks.pg14_18
replication_instance
```

Числовой `type_id` нужен только тесту самого реестра или выбора версии схемы.
Для проверки столбца шаг принимает форму `section <секция> <столбец>`:

```gherkin
Then section pg_stat_database.pg14_17 tup_inserted matches the floor oracle:
  """
  SELECT 10::bigint
  """
```

Не придумывайте псевдоним в feature-файле. Добавьте его в разбор ссылок
средства запуска и покройте модульным тестом.

## Проверка строки

Для синглтона:

```gherkin
Then section pg_stat_wal.pg15_17 has exactly one row:
  | wal_records | 12 |
  | wal_fpi     | 3  |
```

Для строки по ключу:

```gherkin
Then section pg_stat_user_tables.pg16_17 has a row with relname = "probe" and datname = [scenario database]:
  | n_live_tup | 10 |
```

Для именованной сессии:

```gherkin
Then section pg_locks.pg14_18 has a row for session "W":
  | pid           | [W]           |
  | blocked_by    | [H]           |
  | lock_locktype | transactionid |
  | lock_mode     | ShareLock     |
  | lock_granted  | false         |
```

`[W]` и `[H]` разрешаются в PID сессий, а `[]` обозначает пустой
`ListI32`. `[scenario database]` и `[second database]` разрешаются в базы,
созданные текущим сценарием.

## Оракулы

| Вид | Что доказывает | Состояние |
| --- | --- | --- |
| `exact` | Значения столбца равны результату SQL после приведения типов | Реализован |
| `transformed` | Равенство после преобразования, явно записанного в SQL оракула | Реализован |
| `subset` | Каждое значение оракула присутствует в секции | Реализован |
| `floor` | Хотя бы одно значение секции не меньше каждой нижней границы | Реализован |
| `ceiling` | Каждое ненулевое значение секции не превышает одну верхнюю границу | Реализован |
| `top-n` | Состав, порядок, предел и покрытие усечённой выборки | Зарезервирован, пока возвращает ошибку |
| `schema` | Только физическую схему без живого PostgreSQL | Зарезервирован, пока возвращает ошибку |

`transformed` использует тот же механизм сравнения, что и `exact`. Отличие в
контракте SQL: преобразование единиц, `NULL`, времени или версии схемы должно
быть видно в самом запросе оракула.

Для монотонного счётчика, который может измениться во время снимка, используйте
пару чтений:

```gherkin
Given the window floor for section pg_current_wal_lsn.current_wal_lsn is captured as:
  """
  SELECT pg_wal_lsn_diff(pg_current_wal_lsn(), '0/0')::int8
  """
When the collector snapshots the segment
Then section pg_current_wal_lsn.current_wal_lsn is between the captured floor and:
  """
  SELECT pg_wal_lsn_diff(pg_current_wal_lsn(), '0/0')::int8
  """
```

Это отдельная оконная проверка, а не вид оракула.

## Когда нужен отдельный Rust-шаг

Переиспользуйте общий шаг, если смысл полностью выражается:

- ключом строки и таблицей ожидаемых значений;
- сравнением одного столбца с поддерживаемым оракулом;
- проверкой `NULL`, разрешением строки из словаря или отсутствием секции.

Отдельный шаг оправдан, если нужны несколько согласованных запросов, состояние
одной сессии, доменная нормализация или проверка ответа веб-API. Даже в этом
случае SQL и ожидаемый результат должны оставаться видимыми в `.feature`.

## Антипаттерны

- проверка «есть правдоподобная строка» вместо строки созданной сущности;
- общий шаг наподобие `seals X rows`, который скрывает подготовку и проверки;
- SQL подготовки, спрятанный в Rust;
- копия SQL коллектора в качестве единственного оракула;
- фиксированный `sleep` вместо ожидания наблюдаемого состояния;
- зависимость от результата предыдущего сценария;
- проверка `has_X`, когда можно проверить конкретное значение;
- использование зарезервированного оракула как будто он реализован.

## Готовность сценария

Новый или изменённый сценарий готов, когда:

- вход, версия PostgreSQL и причина тегов понятны из `.feature`;
- каждая проверка привязана к созданной сущности или независимому оракулу;
- ограничения `NULL`, усечения, top-N и версий схемы отражены явно;
- живые сессии удерживаются до снимка и всегда закрываются;
- провал содержит достаточно данных, чтобы отличить ошибку окружения от
  несовпадения контракта;
- `cargo test -p kronika-bdd` и нужный BDD-набор проходят.
