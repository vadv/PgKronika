# Типизированный многофайловый OpenAPI и локальный smoke

Дата: 2026-07-29. Целевая ветка: актуальный `main`.

## Статус и область действия

Документ заменяет решения о нетипизированных успешных ответах, одном
`swagger.yaml` и ручной приёмке из
`2026-07-29-openapi-swagger-migration.md`. Сохраняются принятые ранее решения:

- Rust-код и единый `OpenApiRouter` остаются источником истины;
- `/swagger-ui/` и `/openapi.json` строятся из того же реестра маршрутов;
- `/healthz`, `/readyz` и `/metrics` не входят в OpenAPI;
- ошибки используют компактное тело `{code, params}`;
- внешних потребителей и требований обратной совместимости OpenAPI пока нет.

Работа охватывает 15 документированных `GET /v1/*` операций, их успешные тела,
фактические статусы ошибок, многофайловый экспорт и локальную проверку против
уже запущенного demo. Новые HTTP-маршруты и изменения формата существующих
ответов не входят в работу.

## Цели

1. Описать в OpenAPI реальные JSON-тела успешных ответов, а не только код
   `200`.
2. Описать фактически возможные статусы каждой операции и тело `ApiError`.
3. Дать читаемое без специальных инструментов YAML-дерево с пояснениями,
   примерами и относительными `$ref`.
4. Исключить ручное редактирование YAML и расхождение документа с Axum.
5. Автоматически обойти все операции локально против demo и показать, что API
   читает содержательные данные.

## Нецели

- Новый публичный API или изменение JSON-сериализации.
- Обещание непустых массивов для любого допустимого окна.
- Fuzzing, негативное тестирование и обязательный CI smoke.
- Сверка каждого значения с живым PostgreSQL.
- Ручной YAML как второй источник истины.
- Генерация клиентских библиотек.

## Источник истины

Источник истины состоит из Rust response DTO и аннотаций обработчиков:

```text
Rust handlers + response DTO
          |
          | utoipa
          v
единый OpenApi в памяти
     |               |
     | runtime       | make openapi
     v               v
/openapi.json     openapi/openapi.yaml
Swagger UI        openapi/paths/*.yaml
                  openapi/schemas/*.yaml
```

Обработчик возвращает именованный DTO с `serde::Serialize` и
`utoipa::ToSchema`. Аннотация `utoipa::path` связывает операцию с этим типом и
со списком статусов. Генерируемые YAML-файлы коммитятся, но вручную не
редактируются.

Пояснения находятся в стандартных полях OpenAPI `summary`, `description`,
`examples`, а также в описаниях схем, полей и ответов. YAML-комментарии `#` не
используются как часть контракта, поскольку сериализаторы их не сохраняют.

## Модель ответов

Каждый `200` с JSON-телом указывает `application/json` и именованную схему.
Существующие типизированные ответы получают `ToSchema`. Ответы, которые сейчас
собираются через `serde_json::json!` или `serde_json::Value`, переводятся на
DTO без изменения сериализованного JSON.

Общие динамические структуры моделируются явно:

- строка секции является объектом с `additionalProperties: ApiValue`;
- `ApiValue` является `oneOf` для целого, вещественного числа, строки,
  логического значения, `null`, blob-объекта и массива целых чисел;
- batch-ответ является объектом с
  `additionalProperties: SectionPageResponse`;
- diff, временные ряды и диагностические ответы используют отдельные
  именованные схемы;
- пустые массивы остаются допустимыми там, где пустое окно или отсутствие
  находок является корректным результатом.

Имена DTO и схем должны описывать публичный JSON, а не внутренний алгоритм.
Поля DTO получают краткое контрактное описание: единицы, временной формат,
nullable-семантику и ограничения.

## Статусы и ошибки

Каждая операция перечисляет все статусы, которые может вернуть её текущая
реализация. В частности:

- `200` содержит конкретную успешную схему;
- `304` у `/v1/ui/catalog` не содержит body;
- применимые `400`, `404`, `409`, `413`, `429`, `500` и `503` ссылаются на
  общую `ApiError`;
- стандартные заголовки `Allow`, `Retry-After` и `WWW-Authenticate`
  документируются там, где они возможны.

Список статусов выводится из существующих конструкторов `ApiError`, ветвей
обработчиков и тестов. Универсальный `default` не заменяет известный статус.
Неожиданный внутренний сбой документируется как `500`.

Общий `IntoResponses` или другой общий фрагмент допустим только для одинаковых
ответов. Он не должен приписывать операции статус, который обработчик вернуть
не может.

## Домены

Каждая операция имеет ровно один обязательный tag:

- `core`: версия и статическая метаинформация;
- `sections`: каталог, сегменты, строки, batch и diff;
- `analytics`: аномалии и инциденты;
- `timeline`: overview, events и health;
- `ui`: catalog, summary и heatmap.

Exporter отклоняет операцию без доменного tag, с несколькими доменными tags или
с повторяющимся `operationId`.

## Многофайловый экспорт

Коммитится следующая структура:

```text
bins/pg_kronika-web/openapi/
  openapi.yaml
  README.md
  paths/
    core.yaml
    sections.yaml
    analytics.yaml
    timeline.yaml
    ui.yaml
  schemas/
    common.yaml
    sections.yaml
    analytics.yaml
    timeline.yaml
    ui.yaml
```

`openapi.yaml` является стандартным корневым документом OpenAPI 3.1. Он
содержит metadata, tags, относительные ссылки на Path Item и ссылки на
компоненты. Файлы `paths/*.yaml` и `schemas/*.yaml` являются YAML-фрагментами,
доступными через стандартные относительные `$ref`.

Paths распределяются по tag. Exporter обходит граф `$ref` от операций каждого
домена:

- схема, достижимая только из одного домена, попадает в файл этого домена;
- схема, достижимая из нескольких доменов, попадает в `common.yaml`;
- циклы обходятся с множеством посещённых схем;
- ссылки переписываются относительно файла, в котором они находятся.

Exporter работает со структурой `OpenApi` и сериализуемыми YAML-значениями, а
не со строковыми заменами.

## Атомарность и проверка экспорта

`make openapi` выполняет следующие действия:

1. Строит единый `OpenApi` из production-реестра.
2. Проверяет `operationId`, доменные tags, успешные response schemas и ссылки.
3. Записывает дерево во временный соседний каталог.
4. Читает созданные файлы, разрешает созданные exporter-ом ссылки и собирает
   нормализованный документ.
5. Сравнивает его с исходным `OpenApi`.
6. Заменяет committed-каталог только после успешного сравнения.

Порядок paths, операций, ответов, компонентов и полей детерминирован.
Неиспользуемые и неразрешимые схемы считаются ошибкой. При любой ошибке старое
дерево остаётся нетронутым.

Корневое расширение `x-generated-by` называет exporter и команду обновления.
`openapi/README.md` кратко сообщает, что файлы сгенерированы, указывает источник
истины и команды чтения, обновления и bundle.

Старый `bins/pg_kronika-web/swagger.yaml` удаляется. `make openapi` заменяет
`make swagger`. CI повторяет генерацию и требует чистый diff всего
`bins/pg_kronika-web/openapi/`.

Bundled-документ не коммитится. Runtime продолжает отдавать его как
`/openapi.json`; отдельная команда может записать YAML bundle под `target/` для
инструмента, которому нужен один файл.

## Локальный demo smoke

`make demo-api-smoke` работает против уже запущенного `make demo-up`. Команда
не запускает и не останавливает контейнер.

Проверка использует закреплённую версию Schemathesis через `uvx` и runtime
`/openapi.json`. Запускаются только positive/examples-сценарии: цель smoke
состоит в обходе реальных операций, а не в fuzzing или проверке ошибочных
входов.

Последовательность:

1. Проверить `/healthz` и дождаться успешного `/readyz`.
2. Дождаться первого временного окна, в котором demo отдал сегменты.
3. Подставить текущее `from/to`, существующие имена секций и допустимые
   `view/metric`.
4. Вызвать каждую из 15 операций.
5. Проверить status, content type и response schema средствами Schemathesis.
6. Выполнить лёгкую проверку содержательности по `operationId`.

Статические примеры допустимых section names, `view` и `metric` добавляются в
OpenAPI и одновременно улучшают Swagger UI. Текущее время вычисляется hook-ом,
поскольку статический пример `from/to` быстро устаревает.

Проверка содержательности не требует точных значений:

- version и каталоги содержат ожидаемые непустые метаданные;
- segments, section, batch и diff содержат хотя бы один реальный объект,
  строку или ряд;
- heatmap и summary содержат хотя бы одну серию или представление;
- anomalies, incidents и events могут не содержать находок, но должны сообщить
  непустое покрытие, обработанные секции или quality metadata для запрошенного
  окна;
- overview и health должны содержать данные временного окна.

Custom check хранит множество успешно подтверждённых `operationId` и после
прогона сообщает об операции без содержательного `2xx`. Итоговый вывод
показывает operation, фактический URL, статус и короткое свидетельство:
например, `rows=20`, `segments=2` или `coverage=present`.

Smoke не включается в CI. Он завершается ненулевым кодом при недоступном demo,
истечении ограниченного ожидания, пропущенной операции, нарушении схемы или
отсутствии содержательных данных.

## Тестирование

Изменение выполняется через TDD.

Проверки контрактных DTO:

- сериализация до и после типизации даёт тот же JSON;
- representative response каждого домена проходит собственную
  сгенерированную JSON Schema;
- nullable, `additionalProperties` и `oneOf` отражают реальные значения;
- каждый фактический статус обработчика присутствует в OpenAPI.

Проверки exporter-а:

- операция без tag, с неверным tag или повторным `operationId` отклоняется;
- single-domain и shared schemas раскладываются в ожидаемые файлы;
- циклические ссылки не зацикливают обход;
- относительные `$ref` разрешаются;
- экспорт детерминирован;
- ошибка не заменяет прежний каталог;
- собранный из файлов документ семантически равен исходному.

Проверки интеграции:

- `/openapi.json` и Swagger UI продолжают использовать production-реестр;
- `make openapi` не оставляет Git diff после повторного запуска;
- локальный smoke достигает всех 15 операций на demo.

Обязательные project gates сохраняются:

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo run -p xtask -- check-deps
```

## Границы памяти

Типизация не должна создавать вторую копию HTTP-ответа. Handler строит DTO
вместо промежуточного `serde_json::Value` либо сериализует уже существующую
структуру. Коллекции сохраняют действующие query limits и cache limits.

Exporter является developer-командой и держит документ OpenAPI целиком, размер
которого ограничен числом скомпилированных маршрутов и схем. Обход `$ref`
использует множество посещённых имён и не растёт повторно на циклах. YAML-файлы
пишутся по одному во временный каталог.

Schemathesis ограничивает число positive/examples-вызовов и размер ответа
существующими API limits. Smoke не сохраняет все demo-ответы одновременно:
для отчёта остаются только короткие счётчики и свидетельства.

## Качество комментариев

Rustdoc на DTO описывает публичный контракт: смысл поля, единицы, формат,
nullable-семантику и ограничение. Он не пересказывает сериализацию и не
описывает внутренние шаги handler-а. Ориентирующие комментарии exporter-а
допустимы только для алгоритма владения схемами и переписывания ссылок.

## Приёмка

Работа принята, когда выполнены все условия:

1. Все 15 операций имеют именованную успешную response schema.
2. OpenAPI перечисляет фактические статусы и `304` без body.
3. `bins/pg_kronika-web/openapi/openapi.yaml` и доменные вложения читаются
   обычным YAML-редактором и содержат пояснения.
4. Все `$ref` разрешаются, а round-trip равен runtime-документу.
5. `swagger.yaml` удалён, `make openapi` детерминирован, CI проверяет дерево.
6. `/openapi.json` и `/swagger-ui/` продолжают работать.
7. `make demo-api-smoke` против уже запущенного demo подтверждает все операции
   и печатает краткий отчёт о данных.
8. Project gates проходят.
