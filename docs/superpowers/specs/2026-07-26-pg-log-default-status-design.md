# PgKronika — сбор журнала PostgreSQL по умолчанию

Версия: 0.1
Дата: 2026-07-26
Статус: согласованный проект

## 1. Цель

После установки `pg_kronika-collector` пытается собирать поддерживаемый файловый
`stderr` PostgreSQL без дополнительного флага. Оператор явно отключает источник
только при необходимости.

PgKronika хранит отдельное состояние источника журнала. По этим данным оператор
отличает исправный, но тихий журнал от отсутствующего или нечитаемого файла.
Состояние источника описывает качество сбора и не считается оценкой состояния
самой базы данных.

## 2. Текущее поведение и причина изменения

Сейчас `KRONIKA_PG_LOG_ENABLED` по умолчанию равен `false`, если не задан
`KRONIKA_LOG_PATH`. Стенд `pg_kronika-demo` отдельно переопределяет это значение
на `true`.

Автоматическое обнаружение выполняет следующие действия:

1. Проверяет `log_destination`.
2. Вызывает `pg_current_logfile('stderr')`.
3. Для относительного пути использует `KRONIKA_LOG_ROOT` или `data_directory`.
4. Читает найденный файл с сохранённой позиции.

Такое обнаружение не гарантирует доступ к данным:

- при выключенном `logging_collector` функция `pg_current_logfile` возвращает
  `NULL`;
- файл обычно принадлежит пользователю PostgreSQL и по умолчанию имеет режим
  `0600`;
- путь внутри PostgreSQL может отсутствовать в файловом пространстве контейнера
  коллектора;
- текущая реализация разбирает только текстовый `stderr`, но не `csvlog`,
  `jsonlog`, journald или syslog.

Кроме того, интервал повторного обнаружения сейчас действует только после
нахождения источника. При отсутствии файла коллектор может повторять запрос и
записывать одинаковый `pg_log_gap` каждые 5 секунд.

## 3. Решение

### 3.1 Сбор включён по умолчанию

`KRONIKA_PG_LOG_ENABLED` остаётся булевым параметром. Новый трёхпозиционный режим
не вводится.

Правила выбора значения:

| Условие | Результат |
| --- | --- |
| `KRONIKA_PG_LOG_ENABLED` задан | Используется явно заданное значение. |
| Переменная не задана | Сбор включён. |

`KRONIKA_LOG_PATH` только переопределяет путь. Он не включает источник и не
отменяет явное `KRONIKA_PG_LOG_ENABLED=0`.

`pg_kronika-demo` больше не обязан устанавливать собственное значение по
умолчанию. Явное значение из окружения по-прежнему имеет приоритет.

### 3.2 Граница поддерживаемого источника

Первая версия решения поддерживает только файловый `stderr`:

- путь, явно заданный через `KRONIKA_LOG_PATH`;
- путь, обнаруженный через `pg_current_logfile('stderr')`;
- последний сохранённый путь, пока повторное обнаружение временно не работает.

Коллектор не меняет `logging_collector`, `log_destination`, `log_file_mode` и
другие параметры PostgreSQL. Он также не меняет владельца, группу или режим
файла.

Поддержка `csvlog`, `jsonlog`, journald, syslog и журналов контейнерного runtime
не входит в эту работу.

### 3.3 Начальная позиция

При первом обнаружении файла коллектор начинает с его конца, если
`KRONIKA_LOG_START_AT_BEGINNING` не задан явно. Автоматическое включение поэтому
не загружает старый журнал и не меняет действующий контракт этого параметра.

Первая строка состояния `collecting` подтверждает успешное чтение начиная с
момента наблюдения. Она не объявляет полным более ранний диапазон.

## 4. Состояние источника

### 4.1 Новый контракт PGM

Реестр получает логическую секцию `pg_log_source_status` с новым
`type_id=1_039_001` и семантикой `on_change`.

```text
ts                   ts    T
state                u8    L
reason               u8    L
parser_kind          u8    L
source_path          str?  L
dict_dropped_fields  u8    G
```

Поля:

| Поле | Значение |
| --- | --- |
| `ts` | Время проверки источника в микросекундах Unix. |
| `state` | Итоговое состояние сбора после обнаружения и попытки чтения. |
| `reason` | Причина итогового состояния или дополнительной деградации. |
| `parser_kind` | `0=stderr`, `1=csvlog`, `2=unknown`. |
| `source_path` | Использованный или последний известный путь; `NULL`, если путь не найден. |
| `dict_dropped_fields` | Число строковых полей, не попавших в словарь текущего окна. |

`source_path` ограничен тем же пределом в 5120 байт, что и путь в
`pg_log_gap`. Переполнение словаря не удаляет строку состояния: путь становится
`NULL`, а `dict_dropped_fields` увеличивается.

### 4.2 Значения `state`

| Код | Имя API | Условие |
| ---: | --- | --- |
| `0` | `collecting` | Текущий цикл успешно открыл и обработал файл, включая случай без новых строк. |
| `1` | `collecting_degraded` | Последний известный файл успешно обработан, но обновить сведения об источнике не удалось. |
| `2` | `unavailable` | Текущий цикл не смог безопасно читать поддерживаемый файл. |
| `3` | `disabled` | Оператор установил `KRONIKA_PG_LOG_ENABLED=0`. |

`collecting_degraded` не доказывает потерю строк. Это предупреждение о том, что
после ротации коллектор может не найти новый файл, пока обнаружение не
восстановится.

### 4.3 Значения `reason`

| Код | Имя API | Значение |
| ---: | --- | --- |
| `0` | `none` | Ошибки нет. |
| `1` | `postgres_unavailable` | Во время обнаружения нет соединения с PostgreSQL. Читаемый последний путь определяет итоговый `state`. |
| `2` | `no_current_logfile` | PostgreSQL не сообщил текущий файл `stderr`. |
| `3` | `unsupported_format` | Настроенный или явно выбранный формат не поддерживается. |
| `4` | `discovery_query_failed` | Запрос обнаружения завершился ошибкой. |
| `5` | `missing_file` | Путь известен, но файл отсутствует. |
| `6` | `permission_denied` | Процесс коллектора не может открыть файл из-за прав. |
| `7` | `read_error` | Чтение завершилось другой ошибкой ввода-вывода. |

Для `collecting` используется `reason=none`. Для `disabled` также используется
`reason=none`.

`collecting_degraded` получает `postgres_unavailable` или
`discovery_query_failed`: старый путь читается, но его нельзя подтвердить или
обновить.

Для `unavailable` причина выбирается по наиболее поздней попытке чтения. Ошибка
чтения имеет приоритет над ошибкой обнаружения, потому что именно она объясняет,
почему данные не собираются.

## 5. Частота и переходы

### 5.1 Интервалы

Сохраняются действующие периоды:

| Параметр | Значение по умолчанию | Назначение |
| --- | ---: | --- |
| `KRONIKA_PG_LOG_INTERVAL_S` | `5` | Попытка дочитать известный файл. |
| `KRONIKA_LOG_DISCOVERY_INTERVAL_S` | `60` | Повторное обнаружение пути. |
| `KRONIKA_PG_LOG_STATUS_INTERVAL_S` | `300` | Heartbeat неизменившегося состояния. |

`KRONIKA_PG_LOG_STATUS_INTERVAL_S` обязан быть больше нуля.

Интервал обнаружения действует независимо от того, найден ли источник. Между
двумя сроками обнаружения коллектор не повторяет SQL-запросы, а использует
последний результат и последний путь.

### 5.2 Запись состояния

Строка `pg_log_source_status` создаётся:

- при первой попытке сбора после запуска;
- при любом изменении `state`, `reason`, `parser_kind` или `source_path`;
- при неизменном состоянии не реже одного раза за
  `KRONIKA_PG_LOG_STATUS_INTERVAL_S`.

Переход записывается в ближайшем цикле журнала. Heartbeat создаёт окно PGM даже
при отсутствии PostgreSQL log-событий.

Одинаковое состояние между heartbeat не создаёт новые строки и не увеличивает
`pg_log_gap`.

### 5.3 Переходы

```text
                              чтение успешно
        +----------------------------------------------------+
        |                                                    v
   unavailable <---- ошибка чтения ---- collecting <---- запуск
        |                                |   ^
        | чтение восстановилось          |   |
        +--------------------------------+   |
                                             |
                    discovery не работает,  |
                    старый файл читается     |
                                             v
                                  collecting_degraded

   любое состояние ---- KRONIKA_PG_LOG_ENABLED=0 ----> disabled
```

После перезапуска загруженное состояние tailer считается свидетельством того,
что файл ранее успешно читался. Новая попытка всё равно определяет текущее
состояние и записывает первую строку status.

## 6. Разделение status и gap

`pg_log_source_status` отвечает на вопрос, работал ли источник в момент
проверки. `pg_log_gap` сообщает о доказанной или возможной потере уже
наблюдавшегося потока либо о деградации прочитанных данных.

### 6.1 Начальная недоступность

Если после запуска файл ещё ни разу не читался, состояния
`no_current_logfile`, `unsupported_format`, `permission_denied` и другие
записываются только в `pg_log_source_status`. Коллектор не создаёт одинаковый
gap на каждом цикле.

### 6.2 Потеря работавшего источника

Если файл ранее успешно читался, переход в `unavailable` создаёт не больше одной
строки `pg_log_gap` для непрерывного отказа в пределах одного запуска
коллектора:

| Status reason | Gap reason |
| --- | --- |
| `missing_file` | `missing_file` |
| `permission_denied` | `permission_denied` |
| `read_error` | `source_unavailable` |

Повторные попытки во время того же отказа обновляют heartbeat status, но не
дублируют gap. После восстановления следующий независимый отказ может создать
новый gap. После перезапуска новый процесс также вправе один раз зафиксировать
продолжающийся отказ: состояние дедупликации gap отдельно на диске не хранится.

Ошибка обнаружения при успешно читаемом последнем пути переводит источник в
`collecting_degraded`, но не создаёт gap.

### 6.3 Действующие причины потерь

Текущие строки `pg_log_gap` для backlog, усечения физической строки,
невалидного UTF-8, бинарных данных, sparse hole, ротации, переполнения словаря,
ограничения бюджета, parser drop и timestamp fallback сохраняют действующую
семантику.

Числовые коды существующего контракта не переиспользуются и не удаляются.
Старые PGM остаются читаемыми.

## 7. API

### 7.1 Сырые данные

Новая секция автоматически появляется в `/v1/sections` и читается через
`/v1/section/pg_log_source_status`.

### 7.2 Последнее состояние источника

`GET /v1/sources` добавляет к каждому источнику поле `pg_log`:

```json
{
  "source_id": 7,
  "min_ts": 1785060000000000,
  "max_ts": 1785063600000000,
  "segments": 3,
  "pg_log": {
    "state": "collecting",
    "reason": "none",
    "observed_at": 1785062400000000,
    "parser": "stderr",
    "source_path": "/var/lib/postgresql/log/postgresql.log"
  }
}
```

API выбирает последнюю строку status данного `source_id`. Для старых данных без
секции он возвращает:

```json
{
  "state": "unknown",
  "reason": "no_status",
  "observed_at": null,
  "parser": null,
  "source_path": null
}
```

`unknown` и `no_status` являются значениями API, а не кодами PGM.

Поле `observed_at` обязательно для сохранённой строки. API не объявляет старую
строку текущей и не вычисляет `stale` по настенным часам: тот же процесс
обслуживает как живой каталог, так и исторический архив.

Изменение `/v1/sources` аддитивно. Существующие поля и их значения не меняются.

### 7.3 Аналитика

Status описывает качество входных данных:

- `collecting` означает доступность поддерживаемого источника в момент
  проверки;
- `collecting_degraded` означает доступность с риском не заметить следующую
  смену пути;
- `unavailable` и `disabled` означают `not_collected` для log-возможностей;
- отсутствие status означает неизвестное качество, а не исправность.

Эта работа не добавляет штраф к оценке состояния PostgreSQL и не меняет пороги
аномалий. Status может влиять только на полноту и доступность log-возможностей.

## 8. Наблюдаемость процесса

Структурированный лог `pg_log_discovery` перестаёт повторять одинаковое состояние
каждые 5 секунд. Коллектор пишет сообщение уровня `info` при переходе состояния
и сообщение уровня `debug` при heartbeat.

Сообщение перехода содержит:

- прежнее и новое состояние;
- причину;
- parser kind;
- известный путь;
- время до следующего обнаружения.

Содержимое PostgreSQL log-сообщений в эту диагностику не попадает.

## 9. Совместимость и безопасность

- Формат PGM не меняется: добавляется зарегистрированный тип секции.
- Старые средства чтения пропускают неизвестный `type_id` по действующему
  контракту совместимости.
- Новое средство чтения принимает старые сегменты без status.
- Существующие коды `pg_log_gap` сохраняются.
- Явное `KRONIKA_PG_LOG_ENABLED=0` продолжает полностью останавливать чтение и
  обнаружение, но создаёт status `disabled`.
- Путь журнала уже мог храниться в `pg_log_gap`; новая секция делает его
  периодическим диагностическим значением. Защита `/v1` и правила доступа к
  PGM остаются обязательными.
- Новый контракт не хранит содержимое строк журнала, SQL или параметры.
- Коллектор не повышает файловые или PostgreSQL-привилегии и не изменяет
  конфигурацию сервера.

## 10. Проверки

### 10.1 Конфигурация

- без `KRONIKA_PG_LOG_ENABLED` сбор включён;
- явное значение `0` отключает сбор даже при `KRONIKA_LOG_PATH`;
- `KRONIKA_PG_LOG_STATUS_INTERVAL_S=0` отклоняется;
- значение по умолчанию равно 300 секундам.

### 10.2 Реестр и кодек

- контракт `1_039_001` проходит lint реестра;
- строки со всеми состояниями проходят encode/decode round trip;
- `source_path=NULL` и потеря строки в словаре сохраняют status.

### 10.3 Машина состояний

- первый успешный пустой read создаёт `collecting`;
- отсутствие пути создаёт `unavailable/no_current_logfile`;
- permission error создаёт `unavailable/permission_denied`;
- ошибка discovery при успешном read создаёт `collecting_degraded` без gap;
- повторение одного отказа не дублирует status до heartbeat и не дублирует gap;
- восстановление создаёт `collecting`;
- новый отказ после восстановления создаёт новый gap;
- discovery не выполняется раньше заданного срока при отсутствии источника;
- heartbeat создаётся после заданного интервала при неизменном состоянии.

### 10.4 Интеграция

- BDD с живым PostgreSQL проверяет обнаружение через
  `pg_current_logfile('stderr')`, а не только `KRONIKA_LOG_PATH`;
- тихий читаемый файл создаёт status `collecting` без log-событий;
- ротация сохраняет чтение и обновляет путь;
- `/v1/sources` возвращает последнее состояние;
- старый fixture без новой секции возвращает `unknown/no_status`.

Тесты с правами файла выполняются только на Unix. Остальные проверки машины
состояний остаются платформенно независимыми.

## 11. Критерии приёмки

Работа завершена, если одновременно выполнены условия:

1. Новый collector без log-переменных пытается обнаружить и читать `stderr`.
2. Явный `KRONIKA_PG_LOG_ENABLED=0` останавливает запросы и чтение.
3. Тихий читаемый файл не выглядит как отсутствующий источник.
4. Отсутствующий или нечитаемый файл имеет конкретный status и не создаёт
   строку gap каждые 5 секунд.
5. Временная ошибка discovery не останавливает чтение последнего доступного
   файла.
6. Повторное обнаружение соблюдает интервал и до первого найденного файла.
7. `/v1/sources` показывает последнее подтверждённое состояние и время проверки.
8. Старые PGM и старые ответы API сохраняют совместимость.
9. Status не меняет оценку состояния PostgreSQL и используется только как
   свидетельство качества сбора.
10. Unit-, registry-, reader-, web- и BDD-проверки проходят на поддерживаемых
    версиях PostgreSQL.

## 12. Не входит в работу

- поддержка `csvlog`, `jsonlog`, journald, syslog и журналов контейнерного
  runtime;
- автоматическое изменение настроек PostgreSQL и файловых прав;
- чтение старого журнала без явного `KRONIKA_LOG_START_AT_BEGINNING=1`;
- гарантированное доказательство полноты всех физических строк `stderr`;
- новые правила аномалий или оценки состояния;
- отдельный HTTP-сервер метрик в процессе коллектора.
