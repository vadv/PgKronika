# pg_kronika-dump: офлайн-инспекция данных и карантин журнала

Дата: 2026-07-27. Базируется на main после #127 (UTC-дерево сегментов,
journal v1) и предполагает мерж #126 (одно Parquet-тело на `type_id`,
zstd-6, единый словарь сегмента).

## Цель

Один офлайн-инструмент, который отвечает на три вопроса без web-процесса
и без PostgreSQL:

1. Что лежит в дереве данных: сегменты, дни, размеры, окна времени.
2. Что конкретно внутри одного PGM: какие типы, сколько строк, сколько
   байт хранится и сколько распаковывается, каков уровень компрессии.
3. Что уцелело в повреждённом `active.parts`: какие окна целы, где и
   какое повреждение.

Потребители: оператор при инциденте (без web), разработчик при отладке
формата и размеров, форензика отложенных повреждённых журналов.

## Не цели

- Не сервер, не демон, не интерактивный режим.
- Не ремонт: dump никогда не пишет в данные. Единственный формат
  вывода — JSON в stdout.
- Не экспорт для внешних систем (CSV, Parquet-выгрузки) — вне объёма.
- Не query-движок: нет фильтров по значениям, диапазонам, источникам.
  Единица выборки — файл или дерево целиком.
- Не замена web: никаких линз, аномалий, инцидентов.

## Часть 1. Карантин повреждённого журнала (изменение collector)

Приоритет коллектора — начать писать новый файл. Повреждение уже
записанного журнала не должно останавливать сбор будущих данных.

Поведение при ошибке открытия `active.parts` на старте:

- Файл нулевой длины лечится на месте (реализовано в #127).
- Любая другая ошибка формата или целостности (оборванный заголовок,
  несовпадение длины тела, порванный кадр, чужая версия): коллектор
  переименовывает файл в `active.parts.damaged.<unix-us>` в корне
  данных (`renameat` + fsync корня), пишет событие уровня error с
  причиной и путём улики, затем создаёт новый пустой журнал и
  продолжает обычный старт.
- Ошибки ввода-вывода (EACCES, EIO) карантину не подлежат: состояние
  носителя неизвестно, коллектор завершается с ошибкой как сейчас.

Грамматика layout (`kronika-layout`) расширяется одним классом имён:
`active.parts.damaged.<u64>` — распознаваемая запись корня. Скан
не читает такие файлы и не считает их ошибкой; web продолжает работать
при их наличии. GC их не удаляет: улику убирает оператор. Число улик не
ограничивается; каждая видна в событиях коллектора и в выводе dump.

`<unix-us>` — время карантина в микросекундах Unix; имя каноническое
(без ведущих нулей, парсится тем же строгим числовым парсером, что и
`SegmentId`).

Данные не теряются и не скрываются: деградация видима (событие, улика,
сводка dump), но сбор продолжается. Это сознательное изменение
fail-stop-политики #127 для одного случая — повреждения журнала;
fail-stop для неизвестных записей корня и невалидных PGM сохраняется.

## Часть 2. CLI

```text
pg_kronika-dump <path> [--rows] [--limit N]
```

Тип входа определяется автоматически:

| Вход | Режим |
| --- | --- |
| Каталог | Сводка дерева данных |
| Файл с магией `PGM1` | Разбор одного PGM |
| Иначе | Разбор журнала (включая карантинные улики) |

- Вывод — один JSON-объект в stdout. Диагностика — в stderr.
- Коды выхода: 0 — успех (в том числе по повреждённому журналу: его
  разбор — штатная работа), 1 — ошибка чтения входа, 2 — неверное
  использование.
- `--rows` печатает декодированные строки данных; без флага — только
  метаданные и статистика.
- `--limit N` — потолок строк на секцию при `--rows`; по умолчанию
  1000. Урезание отражается в выводе полем `truncated: true`.
- Разрешённые зависимости уже зафиксированы в xtask: format, derive,
  registry, store, reader, analytics.

## Часть 3. JSON по режимам

Числа байтов — точные, u64. Времена — микросекунды Unix, как в
`SegmentId`.

### 3.1 Дерево

```json
{
  "kind": "tree",
  "root": "/var/lib/pg_kronika",
  "journal": {"state": "active", "segment_id": 1753598000000000,
              "frames": 12, "bytes": 1048576},
  "quarantine": [
    {"name": "active.parts.damaged.1753500000000000", "bytes": 524288}
  ],
  "days": [
    {"day": "2026/07/26", "segments": [
      {"segment_id": 1753500000000001, "pgm_bytes": 9000000,
       "ovf": true, "sections": 34,
       "stored_bytes": 8800000, "decoded_bytes": 30500000,
       "ratio": 3.47,
       "first_window_us": 1753500000000001,
       "last_window_us": 1753586400000000}
    ]}
  ],
  "totals": {"segments": 120, "pgm_bytes": 1080000000,
             "stored_bytes": 1050000000, "decoded_bytes": 3600000000,
             "ratio": 3.43}
}
```

Сводка строится тем же строгим сканом layout, что у collector/web, с
теми же лимитами обхода. `--rows` в этом режиме — ошибка использования.

### 3.2 Один PGM

```json
{
  "kind": "pgm",
  "path": ".../2026/07/26/1753500000000001.pgm",
  "segment_id": 1753500000000001,
  "file_bytes": 9000000,
  "windows": {"count": 70, "first_us": 1753500000000001,
              "last_us": 1753586400000000},
  "dictionary": {"entries": 15000, "stored_bytes": 400000,
                 "decoded_bytes": 1600000, "share_of_file": 0.044},
  "sections": [
    {"type_id": "S_015_001", "type_name": "pg_stat_activity",
     "rows": 42000, "stored_bytes": 1200000, "decoded_bytes": 5100000,
     "ratio": 4.25, "share_of_file": 0.133}
  ],
  "totals": {"stored_bytes": 8800000, "decoded_bytes": 30500000,
             "ratio": 3.47}
}
```

- `type_name` берётся из registry; неизвестный `type_id` выводится с
  `"type_name": null` — это данные, а не ошибка.
- `decoded_bytes` — точный размер после распаковки Parquet-тел; для
  ответа «как жмётся» нужны реальные, а не оценочные числа. Декод
  ограничен теми же потолками, что в reader; при превышении секция
  помечается `"decoded_bytes": null, "decode_skipped": "limit"`.
- С `--rows` в каждую секцию добавляется
  `"rows_data": [...], "truncated": bool` — строки как JSON-объекты с
  именами колонок из схемы типа; значения словаря разыменованы.

### 3.3 Журнал (целый или повреждённый)

```json
{
  "kind": "journal",
  "path": ".../active.parts.damaged.1753500000000000",
  "header": {"state": "active", "segment_id": 1753500000000000,
             "recorded_body_len": 500000},
  "physical_bytes": 524288,
  "frames": [
    {"offset": 36, "part_bytes": 250000, "windows": 3,
     "crc_ok": true}
  ],
  "valid_prefix_bytes": 250036,
  "damage": {"offset": 250036, "kind": "torn_frame",
             "detail": "frame header declares 300000 bytes, 24252 remain"},
  "recoverable": {"frames": 1, "windows": 3,
                  "first_us": 1753500000000001,
                  "last_us": 1753500600000000}
}
```

- Используется диагностический resync-сканер `kronika-format` (в
  production-пути запрещён; dump — его единственный потребитель).
- У целого журнала `damage: null`, `valid_prefix_bytes` равен длине
  файла.
- `--rows` разбирает PGM-части валидных кадров как в режиме 3.2.

## Ограничения ресурсов

Dump наследует потолки reader/format: лимиты обхода дерева, 64 MiB на
каталог PGM, per-section потолок декодирования. Сводка дерева не
декодирует тел (только каталоги); полная распаковка происходит лишь в
режиме одного файла. Инструмент офлайновый и однопроходный — счётчиков
запросной конкуренции нет.

## Тесты

- Golden-тесты JSON на фикстурах: дерево с двумя днями, PGM после
  коалесинга #126, целый журнал, журнал с torn frame, карантинная
  улика.
- Тест точности `ratio`: собранный фикстурой PGM с известными
  stored/decoded размерами.
- `--rows` с `--limit`: урезание и флаг `truncated`.
- Карантин коллектора: интеграционный тест «повреждённый журнал →
  старт успешен, улика на месте, событие записано, новый журнал пуст»;
  BDD-сценарий: Given порванный active.parts, When коллектор
  стартует, Then сбор работает и улика перечислена в dump дерева.
- Скан web при наличии улики: refresh проходит, предупреждений формата
  нет.
