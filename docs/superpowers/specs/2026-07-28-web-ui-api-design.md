# Web API для интерфейса: бюджет чтений и материализация рядов

Дата: 2026-07-28. Базируется на main после #132. Расширяет контракт
индекса обзора (2026-07-22-overview-index-timeline-api.md): добавляет
блоки OVF и ручки, не меняя PGM, протокол запечатывания и существующие
блоки. Пороговые правила колонок не входят в объём — они развиваются
серией линз по спеке недостающих метрик (metrics-gap, PR #133).

## Задача

Макет интерфейса v5 показывает одновременно четыре поверхности:

- лента записи за сутки: кривая состояния, события, пропуски, маркеры;
- heatmap активности сущностей: top-строки секции × время, с
  переключением метрики и baseline-сравнением;
- таблица секции под курсором времени: строки, rate-колонки,
  спарклайны трендов;
- панель деталей: инциденты, все поля строки, связанные сущности.

Наивная реализация читает тела PGM на каждый жест: смена курсора,
вкладки, метрики heatmap, зума. Декодирование секции стоит словарь
юнита целиком плюс Parquet-тела, и для окна в сутки это ~96 сегментов.
Требование этой спеки: стоимость каждого жеста фиксирована и мала, а
неизменяемые запечатанные данные никогда не декодируются повторно.

## Модель стоимости чтений

| Хранилище | Стоимость | Когда допустимо |
| --- | --- | --- |
| OVF, позиционное чтение блока | десятки КиБ, кэш в памяти | любой жест |
| PGM, декод секций одного сегмента | словарь + тела секций | только по явному действию, 1–2 сегмента |
| PGM, декод окна из многих сегментов | сотни МиБ декода | никогда в горячем пути; один раз на сегмент при построении фактов |
| Активные данные | память процесса | любой жест |

Принцип: контракт ручек не раскрывает, откуда пришли данные (OVF,
PGM, активное представление). Источник — деталь реализации; это
позволяет менять раскладку блоков без смены API.

## Не цели

- Внешние аннотации (`POST /v1/annotations`, деплой-маркеры) —
  отложены, пишущих ручек нет.
- Полный прогон движка инцидентов по суточному окну на каждый опрос.
  Маркеры ленты — проекция notable-фактов; движок инцидентов работает
  только по сфокусированному окну через существующий `/v1/incidents`.
- Каталог порогов и вердиктов для всех колонок таблиц. Frame отдаёт
  вердикты только там, где уже есть реализованные линзы; остальное —
  значения без окраски.
- Композитная ручка «всё для первого экрана». Открытие страницы —
  несколько независимых запросов дешёвых семейств; экономия
  round-trip'ов не оправдывает связывание контрактов.
- Виртуализация, i18n, ARIA — требования к клиенту, не к API.

## Семейства ручек и бюджет жестов

Ручки делятся на три семейства по классу стоимости.

Timeline — широкий диапазон: факты и блоки OVF, активное
представление и метаданные каталога. Ноль декодирования PGM:

- `GET /v1/timeline/overview`, `/v1/timeline/events`,
  `/v1/timeline/health` — существуют, без изменений; закрывают ленту
  (кривая состояния, глифы событий, пропуски, маркеры notable).
- `GET /v1/timeline/heatmap` — новая, см. ниже.
- `GET /v1/sections/summary` — новая: счётчики и флаги отклонений
  для панели вкладок.
- `GET /v1/storage` — новая: занятость дерева данных для попапа
  «диск».

Frame — снимок секции под курсором. Декодирует секции нужных type_id
ровно одного сегмента, на границе сегмента — двух:

- `GET /v1/frame/{section}` — новая, см. ниже.

Detail — лениво, по явному клику:

- `GET /v1/entity/{section}/{id}` — новая, история одной сущности;
  единственная ручка, которой разрешён проход по PGM нескольких
  сегментов, с жёстким пределом диапазона.
- `/v1/incidents` — существует; вызывается только для окна фокуса.

Бюджет по жестам интерфейса:

| Жест | PGM-сегментов | OVF |
| --- | --- | --- |
| открытие страницы | 1–2 (frame) | блоки диапазона |
| шаг курсора ←/→ | 0–1 (сосед уже декодирован) | 0 |
| смена вкладки | 1–2 | 0 |
| зум окна, свёртка heatmap | 0 | уже в кэше |
| смена метрики heatmap | 0 | блок уже прочитан |
| baseline-сравнение (Δ-режим) | 0 | 0 (клиент считает) |
| выбор строки (док) | 0 (данные из frame) | 0 |
| история сущности | по пределу ручки | 0 |
| фокус инцидента | окно фокуса | — |

Чтобы «смена вкладки» и «шаг курсора» держали бюджет, web держит
ограниченный LRU декодированных сегментов: ключ — дескриптор
содержимого сегмента, значение — декодированные секции. Повторный
запрос другой вкладки на том же курсоре попадает в тот же сегмент.

## Карта интерфейса: каждый элемент макета и его ручка

Полный перечень поверхностей макета v5. «Существует» — ручка уже в
main и не меняется; «новая» — контракт в этой спеке; «клиент» —
элемент не требует запросов.

| Элемент макета | Ручка | Статус |
| --- | --- | --- |
| чип инстанса | `/v1/sources` | существует |
| чип «база»: список значений | строки `/v1/frame/pg_stat_database` | новая |
| чип «база»: применение фильтра | параметр `db` ручки frame | новая |
| чип роли и репликации | роль — instance-секция, реплики и lag — `/v1/frame/pg_stat_replication`; один сегмент | новая |
| чип «данные»: свежесть, покрытие, пропуски | `/v1/timeline/health` | существует |
| попап чипа «данные»: пропущенные линзы | `skipped` из `/v1/incidents` | существует |
| попап чипа «данные»: диск и прогноз | `/v1/storage` | новая |
| счётчики critical/warning в шапке | `/v1/timeline/events` (notable за окно) | существует |
| баннеры stale / collector down | `/v1/timeline/health` (свежесть) | существует |
| лента: кривая состояния | `points` из `/v1/timeline/health` | существует |
| лента: глифы событий | `/v1/timeline/events` | существует |
| лента: серые полосы пропусков | покрытие в `/v1/timeline/health` | существует |
| лента: маркеры инцидентов | `/v1/timeline/events` (notable) | существует |
| вкладки: счётчики и точки отклонений | `/v1/sections/summary` | новая |
| heatmap | `/v1/timeline/heatmap` | новая |
| таблица секции, пресеты, счётчик строк | `/v1/frame/{section}` | новая |
| фильтр строк в тулбаре | клиент, по загруженным строкам | клиент |
| док «Инциденты»: findings, каталог линз | `/v1/incidents` на окне фокуса | существует |
| док «Строка»: все поля | данные уже в ответе frame | клиент |
| drill-down: планы queryid, сессия блокера, история | `/v1/entity/{section}/{id}` | новая |
| меню: дамп снапшота JSON | `/v1/section/{name}`, `/v1/sections/batch` | существует |
| меню: контекст для AI, ссылка Grafana, «⧉ ссылка» | клиент, из загруженного состояния | клиент |
| REPLAY/LIVE, курсор, зум, baseline | клиентское состояние; данные — через frame и timeline | клиент |

Значение `{section}` в путях frame и entity — имя секции реестра, как
его отдаёт `/v1/sections` (`pg_stat_statements`, `pg_stat_activity`,
…); короткие коды вкладок макета — отображение на клиенте. Схемы
колонок для рендера таблиц клиент берёт один раз из `/v1/sections`
(существует: реестр с именами, типами и классами колонок). Точный
счётчик строк активной вкладки приходит из frame и замещает
приближение из `/v1/sections/summary`.

## Материализованные ряды: новый блок OVF с двумя проекциями

Пер-сущностные ряды (спарклайны, heatmap) сегодня не существуют ни в
каком виде, кроме тел PGM. Они материализуются один раз на сегмент в
OVF и с этого момента читаются позиционно. EntitySparks и
HeatmapSeries — две проекции одного физического блока `EntitySeries`;
формат блока, идентичность сущностей, семантика значений и
построитель зафиксированы отдельной спекой
(2026-07-28-entity-series-block-design.md), здесь — их назначение и
состав.

Жизненный цикл — тот же, что у остальных фактов сегмента: строит
владелец `.pgkronika-overview.owner.lock` при построении фактов
запечатанного сегмента, публикация без перезаписи, файл живёт и
умирает вместе с сегментом в ротации. Отдельного файла нет: layout,
dump и ротация структурно не меняются, позиционные чтения не
дорожают от соседства с большим блоком.

Хвост за последним запечатанным сегментом отдаёт построитель активных
данных из памяти; шов проходит по границе последнего seal и виден в
ответе только как обычное покрытие.

### Временная сетка

Каноническое разрешение блоков — минутные бакеты UTC. Сегмент при
`KRONIKA_SEGMENT_MAX_AGE_S=900` даёт до 15 бакетов; рано запечатанный
— меньше. Блок хранит маску минут, в которых были снапшоты: отсутствие
данных не кодируется нулём. Ручки агрегируют минуты в запрошенное
число бакетов на сервере.

### Значения серий

Значение серии в бакете — u8-квант 0..255 относительно максимума этой
серии в сегменте; максимум хранится рядом в физических единицах
(f64). Клиент и ручка восстанавливают абсолютную шкалу умножением,
кросс-сегментная нормализация — через максимумы. Спарклайну и heatmap
нужна форма, а не десятичная точность; ошибки квантования ≤0.4%
принимаются осознанно.

Для counter-колонок значение бакета — сумма дельт снапшотов внутри
минуты, для gauge — максимум. Первая минута после пропуска покрытия
не восстанавливается и остаётся вне маски.

### Проекция EntitySparks

Тренд-столбец таблицы. Одна каноническая метрика на секцию,
зафиксированная версией семантики:

| Секция | Каноническая метрика |
| --- | --- |
| statements | Δ total_exec_time |
| plans | Δ total_time |
| activity | доля снапшотов минуты в состоянии active |
| user_tables | Δ (n_tup_ins + n_tup_upd + n_tup_del) |
| user_indexes | Δ idx_scan |
| processes | Δ (utime + stime) |
| locks | длительность ожидания/удержания |
| log events | число событий |

Состав: top-64 сущностей секции по сумме канонической метрики за
сегмент. Секции с малой кардинальностью (progress_vacuum) в блок не
входят — их тренд виден из frame без доплаты.

Заголовок каждой секции в блоке дополнительно несёт её полный счётчик
сущностей за сегмент (population, включая сущности вне top-64).
Построитель видит все строки секции при декодировании, счётчик
достаётся бесплатно; существующий блок EntityStates для этого не
годится — он заполняется только репликационными сущностями.

Механический top-N — осознанная политика: сущность вне top-64 сегмента
не имеет спарклайна в этом сегменте, frame отдаёт для неё пустой тренд
с признаком «вне top», а полная история доступна через
`/v1/entity/...`.

### Проекция HeatmapSeries

Полоса активности. Метрики соответствуют переключателям макета:

| Секция | Метрики |
| --- | --- |
| activity | wait, cpu, io |
| statements | time, calls, io, temp |
| plans | time, calls |
| user_tables | io, writes, dead |
| user_indexes | io, scans |
| processes | cpu, io |
| locks | wait |
| log events | count |

Состав: top-64 сущностей на пару (секция, метрика) по сумме за
сегмент; сущности дедуплицируются через таблицу строк OVF. Добавление
метрики — bump версии семантики блока, а не формата OVF.

### Версии и пересборка

Блок несёт одну версию семантики в заголовке; каталог секций,
метрик и ключей этой версии фиксирует спека блока. Читатель,
ожидающий более новую версию, считает блок отсутствующим. Владелец лока обнаруживает сегменты с отставшими или
отсутствующими блоками и пересобирает их факты в фоне, новейшие
сегменты первыми — это единственный случай повторного декодирования
запечатанного PGM. Ручки на такие сегменты отвечают честным
`pending` (см. ниже), не блокируясь.

### Смета размера

Опорные замеры: OVF сегодня 34–44 КиБ на сегмент
(pgm-size-reduction-v1.json), запечатанный PGM после коалессинга —
от ~280 КиБ (pgm-coalesced-sections-production-v1.json) до ~950 КиБ
(сегмент исследования #124).

Блок EntitySeries (обе проекции без дублирования канонических
серий, кодек `None`): прирост ~60–70 КиБ на сегмент; детальная
раскладка и обоснование кодека — в спеке блока.

Итог: OVF растёт до ~95–115 КиБ на сегмент (×2.6–2.8); за сутки при
96 сегментах итоговые OVF занимают ~9–11 МиБ бюджета ротации, из них
прирост от блока — ~5.5–6.5 МиБ. Против PGM исследования это единицы
процентов; против худшего коалесснутого сегмента индекс достигает
трети тела — доктрина «спутник много меньше тела» на таких сегментах
размывается, что принимается как компромисс. Числа сметы проверяются
на демо-стенде до фиксации формата блока.

## Контракты новых ручек

Общие правила: параметры проходят существующий allowlist
`QueryParams`, времена — микросекунды; имена `from_us`/`to_us`/`at_us`
ниже — семантическая нотация родительской спеки, wire-имена
параметров следуют существующим ручкам (`from`, `to`). Пределы
диапазона — как у timeline (31 день). Ошибки — `ApiProblem`.
Каждый ответ несёт качество данных диапазона: число снапшотов,
пропуски, признак активного хвоста.

### GET /v1/timeline/heatmap

`section`, `metric`, `from_us`, `to_us`, `buckets` (1..256, по
умолчанию 56), `top` (1..64, по умолчанию 8).

Ответ: сетка бакетов; строки — сущность, максимум серии в физических
единицах, значения по бакетам (абсолютные, не кванты; ручка
восстанавливает шкалу из блоков); `pending` — список сегментов
диапазона, чьи блоки ещё не построены или отстали по версии. Клиент
показывает по ним пустые колонки и повторяет запрос позже; Δ-режим
считается на клиенте из тех же значений.

```json
{
  "grid": { "from_us": 0, "to_us": 0, "buckets": 56 },
  "rows": [
    { "entity": "…", "unit": "…", "max": 0.0,
      "values": [0.0], "present": [true] }
  ],
  "pending": ["<segment id>"],
  "quality": { "snapshots": 0, "gaps": [] }
}
```

Top-строки диапазона — слияние top-списков сегментов по суммарному
значению. Сущность, попавшая в top не во всех сегментах, получает
маску отсутствия в непокрытых, это отображаемое свойство данных, а не
ошибка.

### GET /v1/frame/{section}

`at_us`, `span_us` (окно спарклайнов и трендов), `db` (фильтр
db-scope секций), `preset` (набор колонок), `limit`.

Сервер выбирает последний снапшот с `ts ≤ at_us` и его
предшественника; ответ фиксирует оба `ts` и `ts` соседних снапшотов,
чтобы клавиши ←/→ шагали точно, без угадывания времени клиентом.

Строки: значения снимка; для counter-колонок — скорость из разности
пары снапшотов; тренд-столбец — из EntitySparks за `span_us` (для
строк вне top-64 — признак отсутствия). Вердикты порогов включаются
только для колонок с реализованными линзами и несут порог и baseline;
колонка без линзы отдаётся без вердикта. Счётчик строк секции —
точный из прочитанного снимка.

```json
{
  "snapshot_ts_us": 0, "prev_ts_us": 0,
  "neighbors": { "prev_us": 0, "next_us": 0 },
  "rows": [
    { "key": "…", "values": {}, "rates": {},
      "verdicts": [
        { "column": "…", "level": "warn",
          "threshold": "…", "baseline": 0.0 }
      ],
      "spark": { "values": [0.0], "max": 0.0, "in_top": true } }
  ],
  "population": 0,
  "quality": { "snapshots": 0, "gaps": [] }
}
```

### GET /v1/entity/{section}/{id}

`from_us`, `to_us`. Полная история одной сущности: значения всех
колонок по снапшотам. Единственная ручка с проходом по PGM многих
сегментов, поэтому диапазон ограничен 6 часами на запрос; больший
период клиент собирает постраничными вызовами. Ручка нужна для
дока-детали и для трендов сущностей вне top-64.

```json
{
  "columns": ["…"],
  "snapshots": [ { "ts_us": 0, "values": [null] } ],
  "quality": { "snapshots": 0, "gaps": [] }
}
```

### GET /v1/sections/summary

`at_us`. Для каждой секции — приближённый счётчик сущностей
(population из заголовка EntitySparks последнего сегмента с
`ts ≤ at_us`, см. блок выше) и признак notable-фактов секции в окне.
Только OVF и активное представление; вызывается в общем опросе
вместе с timeline. Для секций, не входящих в EntitySparks, счётчик
отсутствует и вкладка показывает счёт только будучи активной.

```json
{
  "sections": [
    { "section": "…", "population": 0, "approximate": true,
      "notable": false }
  ]
}
```

### GET /v1/storage

Без параметров. Данные для попапа «диск»: занятые байты дерева по
классам (PGM, OVF, журнал, карантин), свободное место раздела
(statvfs), темп записи из размеров и времени недавних сегментов и
прогноз до заполнения раздела. Бюджет ротации ручка не показывает:
`KRONIKA_RETENTION` — конфигурация коллектора, web её не знает;
передача бюджета в web — вне объёма этой спеки.

```json
{
  "used": { "pgm": 0, "ovf": 0, "journal": 0, "quarantine": 0 },
  "fs_free": 0,
  "write_rate_per_day": 0,
  "full_in_days": null
}
```

`full_in_days: null` — прогноза нет (нулевой или отрицательный темп,
например при работающей ротации в установившемся режиме).

## Порядок реализации

1. Блок EntitySeries: формат, bounds, построение при seal-факте,
   фоновая пересборка по версии, live-хвост. Проверка сметы размера
   на демо-стенде.
2. `/v1/timeline/heatmap` поверх блоков, с `pending`-семантикой;
   лёгкие ручки того же класса — `/v1/sections/summary` и
   `/v1/storage`.
3. `/v1/frame/{section}`: LRU декодированных сегментов, пара
   снапшотов, тренды из блоков.
4. `/v1/entity/{section}/{id}`.

Каждый шаг самостоятелен и приносит наблюдаемое поведение; порядок
выбран так, что ни один шаг не создаёт мёртвого кода.
