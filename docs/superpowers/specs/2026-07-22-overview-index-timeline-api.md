# PgKronika — индекс обзора и API временной шкалы

Версия: 0.5
Дата: 2026-07-25
Исходный статус документа: реализованный контракт `parity-v1`, ожидающий
итоговой проверки.

**Статус: PARTIAL.**

- **Уже реализовано:** весь `parity-v1`; все 18 строк приёмки закрыты и
  связаны с executable evidence.
- **Осталось:** четыре решения §23 — калиброванные factor
  curves/profiles/thresholds; deployment limits для disk/RSS/FD/queue/cursor
  TTL; maintenance/topology для planned shutdown и replication participants;
  будущие UI rendering/localization. Также нужно согласовать устаревшие
  flat-child/flat-scan clauses с UTC-раскладкой.

## 1. Цель и статус решений

PgKronika должна быстро строить обзор событий и линию состояния для
произвольного временного диапазона. Повторный запрос, запрос после перезапуска
процесса и многодневный диапазон не должны заново декодировать тела
PGM-сегментов, если рядом с ними находятся допустимые файлы фактов. Свежие
данные из `active.parts` должны появляться с задержкой не больше нескольких
циклов обновления.

`Parity-v1` включает постоянный индекс фактов на диске, которым управляет
считыватель. Хранение только в памяти может быть промежуточным этапом
разработки, но не считается выпуском `parity-v1`.

PGM остаётся единственным источником истины. Средство записи, формат PGM и
протокол запечатывания не меняются. Индекс принадлежит слою считывания, хранит
факты, не зависящие от формул представления, и может быть удалён без потери
исходных данных.

Нормативные разделы задают контракт `parity-v1`. Таблицы состояния фиксируют
поведение, реализованное в PR #114. Окончательное соответствие подтверждается
только критериями §20 на одном точном коммите и в одной попытке CI.

Числовые кривые оценки состояния и продуктовые пороги требуют отдельной
калибровки. Эта спецификация фиксирует их входные данные, алгебру, покрытие,
версионирование и ограничения, но не выдаёт непроверенные пороги за доказанную
модель состояния.

Нормативные слова «обязан», «нельзя» и «допускается» задают контракт v1.
Псевдокод описывает семантику протокола и хранения, а не ABI Rust.

## 2. Определения

| Термин | Значение |
| --- | --- |
| PGM | Неизменяемый запечатанный сегмент PgKronika, источник истины для закрытого диапазона. |
| Активная часть | Завершённый кадр с допустимой CRC в `active.parts`. Незавершённый хвост частью не считается. |
| Дескриптор сегмента | Идентификатор содержимого PGM, вычисленный из его каталога, хвоста и длины. |
| Факты сегмента | Канонический индекс одного запечатанного PGM: сохранённые наблюдения и факты, отсчёты метрик с временными метками, сбросы, состояния, пропуски, покрытие и происхождение. |
| Построитель активных данных | Единственный изменяемый построитель без потерь, который сворачивает каждую завершённую активную часть ровно один раз. |
| Представление активных данных | Неизменяемый снимок активных фактов с поколением журнала и обработанной позицией. |
| Представление индекса | Атомарный снимок упорядоченных дескрипторов запечатанных сегментов и одного точного поколения активных данных. Все части запроса читаются из одного снимка. |
| `EventObservation` | Сохранённое PGM-наблюдение в форме источника: отдельная строка, сгруппированная строка или пропуск. |
| `EventFact` | Канонический нормализованный факт, не зависящий от политики представления и выведенный из одного или нескольких наблюдений или отсчётов с явным происхождением. Не равен одноимённой текущей структуре веб-API из §7.4. |
| `NotablePolicy` | Версионированное чистое преобразование, которое классифицирует, выбирает и упорядочивает наблюдения и факты для `/events` и краткого списка; результат не записывается в канонические блоки. |
| `IncidentDiagnosis` | Отдельный корреляционный вывод о возможной причине с подтверждениями и оценкой уверенности. Не является наблюдением или фактом и в текущей реализации отсутствует. |
| `FactKey` | Идентификатор фактов, связывающий точный дескриптор содержимого и версии контрактов; определён в §10.1. |
| `FactBuildKey` | Полный неизменяемый идентификатор одной задачи построения: `(FactKey, SegmentLineageId)`. Он используется для допуска, координации одной задачи, резервного хранения в памяти и проверки; путь файла от него не зависит. |
| Точность сохранённых данных | Точность относительно строк и счётчиков, которые фактически дошли до PGM. Она не означает полноту исходного журнала PostgreSQL. |
| Проекция | Состояние, краткий список, сводка, прореживание или HTTP-представление, вычисленное из фактов для текущей версии правил. |

## 3. Объём продукта и контракт функционального соответствия

### 3.1 Входит в `parity-v1`

- `GET /v1/timeline/overview` для компактной сводки событий и состояния за
  диапазон.
- `GET /v1/timeline/health` для временной шкалы состояния с достоверным
  покрытием каждой точки.
- `GET /v1/timeline/events` для стабильной постраничной выдачи значимых
  наблюдений и фактов.
- Соседний файл фактов `N.ovf` для каждого запечатанного `N.pgm` в одном
  каталоге `KRONIKA_WEB_DIR`, который целиком принадлежит PgKronika.
- Инкрементальный построитель активных данных без потерь для завершённых частей.
- Прямое чтение PGM и ленивое перестроение отсутствующего, несовместимого,
  повреждённого или не соответствующего источнику OVF.
- Ограниченное хранение в памяти декодированных фактов, проекций и точных
  ответов.
- Ограниченное резервное хранение в памяти, если публикация OVF невозможна.
- Ограниченные, безопасные при отмене задачи построения и объединение
  одинаковых задач по каждому `FactBuildKey`.
- Квоты, сборка мусора, метрики, проверки повреждений и измерения после
  перезапуска.

### 3.2 Наблюдаемый контракт функционального соответствия

1. Повторный одинаковый запрос к запечатанным данным в одном процессе не читает
   тела PGM и не повторяет вычисление представления, если точный ответ уже есть
   в памяти.
2. После перезапуска допустимый соседний OVF обслуживает внутреннюю часть
   запечатанного диапазона без чтения тел PGM и декодирования секций.
3. Новый диапазон, шаг или фильтр поверх уже существующих фактов не требует
   декодирования PGM, если сохранённых измерений достаточно.
4. Многодневный запрос читает только пересекающиеся компактные блоки с
   ограниченным параллелизмом.
5. Завершённый кадр активных данных становится виден не позже установленного
   предела свежести; ожидающий или оборванный хвост отмечается отдельно.
6. Запечатывание, разбиение на части и сегменты и порядок объединения не меняют
   сохранённые факты, покрытие и результат одной версии правил.
7. Ни один пропуск обязательных данных не превращается в `score=1.0`.
8. Числовая оценка состояния принимается по зафиксированным эталонным наборам
   данных, покрытию и отсутствию ложных зелёных значений; задержка и размер
   проверяются на версионированном профиле узла и файловой системы без
   неподтверждённых сравнительных заявлений.

### 3.3 Границы v1

- Новые сборщики и новые секции PGM не требуются.
- Текущий источник `stderr` остаётся ограниченным и сгруппированным; обзор не
  обещает восстановить отброшенные строки.
- Историческая причина происшествия не выводится из одного маркера, сигнала
  или категории.
- OVF не становится архивом и не продлевает срок хранения PGM.
- Графики отложены владельцем: извлечение данных для графиков, специальные
  блоки, конечная точка и контракт отрисовки не входят в `parity-v1`. Их
  стоимость не измерена и не оценивается подстановкой синтетических размеров.

## 4. Инварианты и честность данных

### 4.1 Источник истины и производные файлы

1. PGM и допустимые завершённые части активного журнала — единственные
   источники фактов.
2. Файл фактов версионируется и является производным. Отсутствующий,
   несовместимый, повреждённый, слишком большой или не соответствующий PGM
   файл игнорируется и перестраивается из PGM.
3. Изменять несовместимый файл фактов на месте нельзя. Новые факты атомарно
   заменяют тот же соседний `N.ovf`.
4. Ошибка чтения, записи или сборки мусора не превращает корректно вычисленный
   ответ в ошибку.
5. Ошибка исходного PGM не маскируется как отсутствие OVF. Она становится
   пропуском источника или типизированной ошибкой источника.
6. Удаление всех производных OVF влияет только на задержку первого чтения.

### 4.2 Три уровня точности

Ответ обязан различать:

| Уровень | Что гарантируется |
| --- | --- |
| `fact_exact` | Путь через индекс семантически равен принудительному прямому декодированию тех же строк PGM той же версией извлечения. |
| `retained_exact` | Каждое сохранённое наблюдение или группа учитывается ровно один раз, включая `occurrence_count`. |
| `source_complete` | Все физические события источника были собраны. Для текущего источника журнала это обычно нельзя доказать. |

`pg_log_errors` хранит группы `(normalized pattern, severity, sqlstate)` с
временной меткой первого появления и полем `count`; за один цикл сбора остаётся
не больше 32 групп. Число наблюдений жизненного цикла также ограничено.
Средство чтения хвоста, синтаксический анализатор и словарь имеют собственные
ограничения и признаки пропусков. Поэтому `/events` точен относительно
сохранённых наблюдений и групп, но не относительно физических строк `stderr`.

Сгруппированная строка остаётся одним наблюдением с `occurrence_count`. Её
нельзя синтетически разворачивать в N событий: временные метки, PID и порядок
остальных появлений неизвестны.

### 4.3 Никаких ложных нулей и зелёных значений при пропусках

- Отсутствующее, неподдерживаемое, несобранное и измеренный ноль — разные
  состояния.
- Пустой интервал состояния имеет `score=None`, а не `1.0`.
- Отсутствующий фактор не создаёт нулевой штраф.
- Ограничения журнала и сборщика переводят полноту событий в `partial`, даже
  если временная выборка непрерывна.
- API и слой представления не интерполируют состояние через пропуски; будущий
  пользовательский интерфейс обязан сохранить тот же контракт.
- Сброс, уменьшение или пропуск счётчика разрывает интервал; он не превращается
  в нулевую скорость.

### 4.4 Каноническое состояние не бывает намеренно неполным

Канонические факты запечатанных и активных данных имеют одинаковую семантику.
Ограничения ответа, первые N элементов и пределы предварительного просмотра
применяются только после построения полного набора сохранённых фактов.

Если жёсткое ограничение памяти или построения всё же не позволяет удержать
каноническое состояние активных данных:

1. построитель переходит в `Incomplete`;
2. ответ публикует причину и покрытие потерь;
3. продвижение активного состояния в файл фактов запечатанного сегмента
   запрещено;
4. запечатанный сегмент строится заново из PGM;
5. запрос может восстановить точность сохранённых данных прямой ограниченной
   свёрткой активных частей;
6. без такой свёртки `/events` честно возвращает частичный интервал активных
   данных.

### 4.5 Проверяемая арифметика

Счётчики и длины складываются проверяемыми операциями. Молчаливое насыщение
запрещено. Переполнение делает блок или индекс непригодным для сохранения либо
ответ неполным с машиночитаемой причиной; переполненное значение не выдаётся
за точное.

## 5. Сквозной поток данных

```text
завершённые кадры active.parts
        │ RefreshDelta(поколение, PartId, обработанная позиция, повреждения)
        ▼
изменяемый полный LiveBuilder
        │ публикация неизменяемого снимка
        ▼
LiveView ─────────────────────────────────────────────┐
                                                     │
запечатанный PGM -> SegmentDescriptor -> соседний OVF │
        │                         │                    │
        │                         ├-> резерв в памяти  │
        │                         └-> построение из PGM│
        │                              + попытка публикации
        ▼                                              ▼
строки журнала ─────> EventObservation ─────> канонический EventFact
метрики/состояния ──> отсчёты/сбросы/состояния ─────> EventFact
        │                                              │
        └──────── упорядоченные SegmentFacts ──> неизменяемый IndexView
                                                      │
                           одно поколение на запрос
                                                      ▼
          выбранные факты + левые/правые граничные отсчёты
                                                      │
                    проекции состояния/событий/API
                                                      ▼
                     ответы overview/health/events
```

Текущая реализация проходит весь показанный путь для поддерживаемого реестра:
создаёт `EventObservation`, канонические `EventFact`, отсчёты счётчиков и
измерений, маркеры сбросов, состояния сущностей и покрытие. Неподдерживаемая
раскладка остаётся явной ошибкой или пропуском, а не предполагаемым нулём.

### 5.1 Изменения при обновлении

Считыватель обязан публиковать семантические изменения, а не только новую
длину файла:

```text
RefreshDelta {
  previous_view_generation: u64,
  new_view_generation: u64,
  sealed_added: Vec<SegmentDescriptor>,
  sealed_removed: Vec<SegmentDescriptor>,
  journal: JournalDelta {
    generation_id: JournalGenerationId,
    previous_valid_len: u64,
    new_valid_len: u64,
    completed_parts: Vec<PartDescriptor>,
    transition: Append | Reset | Replaced | Uncertain,
    tail_pending: Option<ByteRange>,
    damages: Vec<SourceDamage>,
  },
}
```

`generation_id` меняется при смене inode или устройства, усечении, замене,
разрыве метаданных или любом переходе, который нельзя доказать как дописывание.
Перезапись без изменения длины нельзя считать отсутствием изменений.
`Uncertain` всегда переводит состояние активных данных в перестроение.

`PartId` — ключ идемпотентности внутри поколения журнала. Он связывает позицию
кадра, точный дескриптор каталога и содержимого части и длину. Повторная
доставка одного `PartId` не меняет построитель.

### 5.2 Обработка запроса

Один запрос:

1. Захватывает один `Arc<IndexView>`.
2. Проверяет `[from_us,to_us)`, ограничения и выбранные источники.
3. Строит упорядоченный план дескрипторов запечатанных сегментов, одного
   поколения активных данных и граничных соседних отсчётов.
4. Проверяет хранилище точных ответов в памяти.
5. Загружает нужные блоки фактов из памяти или соседних OVF; при отсутствии
   запускает ограниченную общую задачу построения.
6. Обрезает наблюдения и отсчёты по точному диапазону и применяет семантику
   свёртки из §6.
7. Применяет текущие правила состояния и значимости.
8. Формирует покрытие, потери и метаданные ответа из того же представления.
9. Сохраняет проекцию или ответ в памяти только под полным `FactSetId`.

Запрос никогда не смешивает новый набор запечатанных данных со старым
представлением активных данных.

### 5.3 Объединение нескольких сегментов

- Выбор сегментов использует снимок источника как авторитетный каталог
  диапазонов; каталог данных не сканируется при каждом запросе.
- Факты объединяются в детерминированном порядке диапазона, источника и
  происхождения.
- Аддитивные счётчики складываются с проверкой переполнения.
- Покрытие объединяется как объединение полуоткрытых интервалов, а не как сумма
  долей.
- Наборы событий объединяются по стабильному идентификатору; логическое
  устранение повторов сбоя относится к отдельным правилам проекции.
- Отсчёты измерений и счётчиков сначала объединяются в упорядоченные ряды,
  затем сворачиваются. Готовые штрафы и оценки не объединяются.

## 6. Время, диапазоны, интервалы и свёртки

### 6.1 Единый контракт времени

- Все новые диапазоны HTTP и интервалы состояния — полуоткрытые
  `[from_us,to_us)`.
- `from_us < to_us`; временные метки — знаковые микросекунды Unix в UTC.
- Событие с временной меткой сортировки `t` принадлежит ровно одному интервалу,
  где `start <= t < end`.
- `max_ts` каталога PGM остаётся включающей границу метаданной. Планировщик
  преобразует её, но внешний контракт не становится включающим границу.
- `effective_range` совпадает с запрошенным диапазоном. Последний интервал
  состояния может быть короче `effective_step_us`; диапазон не округляется
  молча.

### 6.2 Семантика шага

```text
effective_step_us = max(
  requested_step_us,
  ceil((to_us - from_us) / MAX_HEALTH_POINTS)
)
```

Если `step_us` не задан, правила выбирают его из диапазона и возвращают
фактическое значение. Шаг не объявляется более точным, чем периодичность
источника: разреженные точки получают частичное или неизвестное покрытие, а не
выдуманные отсчёты.

Факты на диске хранят естественные временные метки, а не итоговые интервалы.
Поэтому новый шаг не перестраивает файлы фактов.

### 6.3 Граничные отсчёты

Для диапазона планировщик может читать:

- последний отсчёт каждого нужного ряда перед `from_us`;
- первый отсчёт после `to_us`;
- маркеры сбросов и пропусков между граничными отсчётами и диапазоном.

Граничные отсчёты нужны для пар счётчика, взвешенного по времени измерения и
перехода состояния. Они не включаются в ответ событий и счётчиков, но входят
в `FactSetId`, потому что влияют на свёртку.

### 6.4 Обрезка событий и сгруппированных счётчиков

- Отдельное наблюдение включается по точной или резервной метке `sort_ts_us`.
- Сгруппированная строка журнала включается целиком по сохранённой первой или
  резервной временной метке.
- `occurrence_count` сгруппированной строки не распределяется по времени: PGM
  не содержит временных меток остальных появлений.
- Если источник знает только интервал, наблюдение пересекает диапазон как
  интервальный факт и не превращается в точечное событие.

### 6.5 Семантика счётчиков

Каждая соседняя пара одного ряда образует интервал-кандидат:

```text
CounterInterval {
  previous: (ts_us, value, reset_epoch),
  current:  (ts_us, value, reset_epoch),
  delta: u64,
  duration_us: u64,
  quality: Valid | Reset | Gap | NonMonotonicTime | Missing,
}
```

Пара допустима только когда `current.ts > previous.ts`, семейство и эпоха
сброса совпадают, в покрытии нет пропуска и счётчик не уменьшился. Уменьшение
или сброс создаёт границу, а не нулевую разность.

В v1 допустимая пара относится к временной метке более позднего отсчёта. Для
интервала используются пары, у которых `current.ts_us` лежит внутри него. Это
даёт детерминированные произвольные полуоткрытые диапазоны без
пропорционального размазывания неизвестных приращений.

- Число и скорость: `sum(delta) / sum(duration_us)` по допустимым парам, а не
  среднее скоростей отдельных пар.
- Для отношения счётчиков числитель и знаменатель суммируются отдельно, а
  деление выполняется после объединения.
- Пара может использовать предшествующий граничный отсчёт, но принадлежит
  только интервалу текущего отсчёта.
- Отсутствие допустимых пар даёт `None`, а не ноль.

### 6.6 Измерения и взвешивание по времени

- Для мгновенного измерения `max` и `min` берутся только по реально
  сохранённым отсчётам в интервале.
- Для измерения состояния с объявленной моделью удержания граничный отсчёт
  создаёт допустимый интервал до следующего отсчёта или `max_gap_us`;
  экстремумы могут учитывать это подтверждённое состояние внутри интервала.
- Среднее по отсчётам равно `sum(values)/count`, а не среднему средних.
- Взвешенное по времени среднее допускается только для фактора с явно заданной
  кусочно-постоянной моделью.
- Удержание действует между соседними допустимыми отсчётами одной эпохи
  покрытия и не дольше собственного для фактора `max_gap_us`.
- Интервал пересекается с интервалом ответа математически; пропуск не
  заполняется, перенос последнего значения через него запрещён.
- Исходные отсчёты, временные метки, граничные отсчёты и покрытие сохраняются
  в фактах, поэтому правила могут выбирать максимум или взвешенное по времени
  среднее без перестроения PGM.

### 6.7 Оценка состояния и прореживание по худшей точке

Состояние сначала вычисляется в совместных временных ячейках, образованных
границами допустимых интервалов факторов, нижних пределов событий и интервалов
запроса. Одна ячейка использует только одновременно подтверждённые наблюдения.

При прореживании:

1. выбирается реально вычисленная исходная точка или ячейка с минимальной общей
   числовой оценкой;
2. штрафы факторов и доменов берутся из той же точки;
3. покомпонентные максимумы из разных моментов не объединяются;
4. любой подтверждённый маркер нижнего предела переносится в интервал
   независимо от числовой оценки;
5. интервал без обязательного покрытия остаётся `Unknown`.

Такое прореживание сохраняет худшее доказанное состояние и не создаёт
«призрачный минимум» из несинхронных пиков.

## 7. Модель событий, классификация, значимость и диагностика

### 7.1 Четыре разных сущности

```text
сохранённая строка журнала ─> EventObservation ─> канонический EventFact ─┐
сохранённая строка метрики ─> отсчёт/сброс/состояние ───────> EventFact ─┤
                                                                       ├─> результат NotablePolicy
                                                                       └─> IncidentDiagnosis
```

`NotablePolicy` — проекция представления, а `IncidentDiagnosis` — отдельная
корреляционная модель; они не являются последовательными стадиями
обязательного преобразования каждого события. Ни один слой не имеет права
молча подменять другой:

- наблюдение с `signal=9` означает наблюдение SIGKILL, а не OOM;
- уровень `PANIC` означает PANIC, а не доказанное физическое повреждение;
- эвристическая категория `DataCorruption` не доказывает повреждение данных;
- похожий на SQLSTATE маркер из `stderr` остаётся разобранным подтверждением, а
  не гарантированным структурированным SQLSTATE;
- немедленное завершение — административный факт жизненного цикла, а не
  автоматическая катастрофическая причина;
- отсутствие наблюдения ничего не доказывает при частичном или неизвестном
  покрытии.

### 7.2 `EventObservation`

```text
EventObservation {
  observation_id: [u8; 32],
  identity_quality: SourceExact | ContentDerived | Approximate,

  source_type_id: u32,
  provenance: ObservationProvenance,

  shape: Individual | GroupedCount | Gap,
  time: ObservationTime,
  occurrence_count: u64,

  payload: ObservationPayload,
  evidence_quality: Structured | Parsed | Heuristic | DerivedExact,
  quality_flags: bitset,
  loss: Option<LossSummary>,
}

ObservationTime {
  sort_ts_us: i64,
  occurred_at_us: Option<i64>,
  observed_interval: Option<[i64, i64)>,
  quality: Exact | FirstInGroup | RepresentativeSample | MaxDurationSample |
           ParsedWithoutVerifiedOffset | CollectionFallback | IntervalOnly,
}

ObservationProvenance {
  section_body_id: [u8; 32],
  catalog_entry_ordinal: u32,
  row_ordinal: u32,
  dictionary_context_id: [u8; 32],
  source_locator: Option<SourceLocator>,
}
```

`occurrence_count=1` для отдельных наблюдений и переходов. Сгруппированная
строка ошибки сохраняет исходный `count`; `count=0` недопустим.

`dictionary_context_id` — хеш канонического набора `(StrId, resolved bytes)`
для всех ссылок на словарь, которые влияют на наблюдение. Он нужен потому, что
одинаковые байты секции с одинаковыми `StrId` могут иметь другую семантику при
другом контексте словаря.

### 7.3 Стабильный идентификатор при запечатывании

Средство записи при запечатывании дословно копирует тела секций и сохраняет
порядок каталога. V1 использует это происхождение:

```text
segment_lineage_id = SHA-256(
  "pgk-overview-lineage-v1" ||
  source_descriptor
)

observation_id = SHA-256(
  "pgk-overview-observation-v1" ||
  segment_lineage_id ||
  source_type_id ||
  section_body_id ||
  catalog_entry_ordinal ||
  row_ordinal ||
  dictionary_context_id
)
```

`source_descriptor` уже включает упорядоченную раскладку всех записей
каталога, поэтому отдельная копия первой записи в retained metadata не нужна.
`section_body_id` хеширует точное тело нужной секции вместе с `type_id` и
длиной. `catalog_entry_ordinal` считается по всему каталогу сегмента и вместе с
`row_ordinal` различает повторения одинакового тела внутри одного
происхождения. Порядковые номера сохраняются после обычного запечатывания.

Гарантия ограничена текущим контрактом источника:

- идентификатор стабилен при обычном переходе от активных данных к
  запечатанным и при повторном построении производных фактов;
- версия правил или формулы в идентификатор не входит;
- повторная упаковка или новое разбиение на сегменты может изменить
  происхождение;
- дескриптор PGM и первый дескриптор записи каталога определяют происхождение
  без пути, имени файла или отдельного идентификатора хранилища;
- когда источник не содержит смещения файла или идентификатора сеанса, API
  возвращает `identity_quality=ContentDerived`, а не обещает идентификатор
  уровня источника.

Целевое логическое устранение повторов, например строки ошибки совместимости и
строки жизненного цикла одного сбоя, может выполнять `NotablePolicy` только по
доказанной связи. Оно не меняет канонические идентификаторы наблюдений и не
складывает независимые счётчики. Текущие правила классифицируют наблюдения по
одной записи и такой связи не заявляют.

### 7.4 `EventFact`

```text
EventFact {
  fact_id: [u8; 32],
  kind: EventKind,
  shape: FactShape,
  interval: [i64, i64),
  count: u64,
  entity: Option<EntityRef>,
  payload: EventPayload,
  supporting_observation_ids: Vec<[u8; 32]>,
  evidence_quality: EvidenceQuality,
  coverage: CoverageRef,
}
```

`EventFact` остаётся независимым от политики представления: он может утверждать
`pg.lifecycle.child_signal_termination` или `os.cgroup.oom_kill_delta`, но не
`postgres_was_killed_by_oom` без отдельной диагностики.

Текущая реализация материализует и проверяет `EVENT_FACTS`. Веб-API сохраняет
стабильную внешнюю структуру `EventFact`: для наблюдений она содержит
семантический `event_id`, физический `event_instance_id` и точное
подтверждающее наблюдение; для канонических фактов метрик и состояний она
использует `fact_id`, сущность, интервал и сохранённые идентификаторы
подтверждений. Изменение внешней формы требует повышения
`response_schema_version`.

### 7.6 Проверенное соответствие источников

Для всех восьми поддерживаемых секций журнала `observation_id` выводится из
`SegmentLineageId`, `source_type_id`, идентификатора тела секции, порядковых
номеров записи каталога и строки, а также контекста словаря. Происхождение
запечатанного сегмента включает точный дескриптор PGM и не зависит от пути.
Идентификатор активных данных имеет качество `Approximate` до доказанного
перехода.

| Секция PGM | Канонический результат | Единицы, происхождение и потери |
| --- | --- | --- |
| `1_022_001 pg_log_errors` | Сгруппированное `EventObservation::ErrorGroup` и соответствующий `EventFact`; `occurrence_count` равен сохранённому `count` | Число сохранённых появлений; усечение словаря и потеря групп отмечаются явно |
| `1_024_001 pg_log_checkpoints` | Отдельное наблюдение и факт начала, завершения или слишком частой контрольной точки | Миллисекунды, KiB и счётчики остаются типизированными полями; потери словаря и качество времени сохраняются |
| `1_025_001 pg_log_autovacuum` | Отдельное наблюдение и факт autovacuum или autoanalyze | Единицы исходных полей сохраняются; несуществующая сущность или сброс не придумываются |
| `1_026_001 pg_log_slow_queries` | Сгруппированное наблюдение и факт медленного запроса | Длительность в миллисекундах, число сохранённых появлений и время представительного запроса |
| `1_027_001 pg_log_lock_waits` | Отдельное наблюдение и факт ожидания или получения блокировки | Длительность в миллисекундах; неподтверждённое постоянство сущности не предполагается |
| `1_028_001 pg_log_lifecycle` | Отдельное наблюдение и факт сигнала дочернему процессу, сбоя, завершения или готовности | PID и сигнал — полезная нагрузка, а не доказательство причины |
| `1_029_001 pg_log_gap` | `EventObservation::Gap` и явное покрытие с потерями | Сохраняются пропущенные байты, число отброшенных строк и доказанный нижний предел |
| `1_030_001 pg_log_temp_files` | Отдельное наблюдение и факт временного файла | Размер в байтах; сущность или сброс без доказательства не создаются |

Разрешённый список метрик материализует:

- `pg_stat_database` типов `1_005_001..=1_005_004`;
- состояние экземпляра и сбросов `1_015_001`, `1_020_001`, `1_021_001`;
- физическую репликацию `1_033_001` и слоты `1_034_001..=1_034_003`;
- файловые системы PostgreSQL `1_036_001..=1_036_002`;
- память процесса в cgroup `1_037_001`;
- `vmstat` `1_106_001` и память cgroup `1_202_001`;
- покрытие сбора `1_023_001` и `1_038_001`.

Для этих типов извлечение создаёт доказанные описания рядов, отсчёты
счётчиков и измерений, маркеры сбросов, состояния сущностей, покрытие факторов
и связанные факты событий. Тип, единица, сущность, семейство сброса и качество
покрытия задаются разрешённым списком, а не выводятся из имени столбца. Новая
зарегистрированная раскладка вне списка завершается `UnsupportedLayout`; это
влияет на покрытие источника и не превращается в нулевое измерение.

### 7.7 Полезная нагрузка группы ошибок

```text
ErrorGroupPayload {
  severity: Error | Fatal | Panic | Warning | Log,
  category: Lock | Constraint | Serialization | Timeout | Connection |
            Auth | Syntax | Resource | DataCorruption | System | Other,
  sqlstate: Option<[u8; 5]>,
  normalized_pattern: Option<TextRef>,
  database: Option<TextRef>,
  user: Option<TextRef>,
  dropped_fields: bitset,
}
```

В фактах хранится совместное измерение `(severity, category, sqlstate)`, а не
только три отдельных карты. Иначе нельзя ответить, сколько именно ошибок
`Resource` уровня `FATAL` было в диапазоне. Уровни, категории и жизненный цикл
кодируются небольшими закрытыми массивами; SQLSTATE и сигналы — упорядоченными
уникальными ограниченными векторами, а не порядком обхода `HashMap`.

Целевой канонический `EventFact` сохраняет только ограниченный
нормализованный шаблон и явно перечисленные измерения, не зависящие от правил.
Текущий `EventObservation` в форме источника также удерживает ограниченные
поля примера, подробностей, подсказки, контекста и выражения, а также базы
данных и пользователя в `STRING_TABLE`; это не означает, что их надо
дублировать в `EVENT_FACTS`. Если будущему каноническому контракту правил
потребуются дополнительные поля, соответствие и сокрытие данных фиксируются
явно, `extractor_semantics_version` повышается, а факты перестраиваются из PGM.

### 7.8 `NotablePolicy`

```text
NotablePolicy {
  policy_version: u32,
  rules: ordered stable rules,
  required_evidence_quality: per-rule minimum,
  correlation_and_dedup: stable rule set,
  ranking: stable total order,
  response_cap: projection-only limit,
}
```

Целевые правила могут использовать уровень, категорию, SQLSTATE, вид события,
скорость и временное окно, сущность, число появлений и качество подтверждений.
Они обязаны:

- не менять `observation_id`/`fact_id`;
- не записывать класс значимости обратно в канонические факты;
- применять ограничение только к странице ответа или предварительному
  просмотру;
- возвращать `omitted_count` и `next_cursor`, если элементы остались;
- сохранять потери источника отдельно от пропусков из-за ограничения ответа;
- различать `PANIC`, `integrity_evidence`, `out_of_memory_observation`,
  `sigkill_observation`, `storage_capacity`, `authentication`, `contention`,
  `connection_capacity`, `replication`, `maintenance` и `system`, не заявляя
  недоказанную причинную связь.

Текущий `NotablePolicy::v1` классифицирует сохранённые `EventObservation` и
доказанные канонические факты метрик или состояний, но не выполняет причинную
корреляцию. Его стабильные коды внешнего протокола:

- `server_child_sigkill` и `server_child_signal_termination`;
- `panic_severity_observation`;
- `filesystem_space`;
- `postgres_out_of_memory_observation`;
- `connection_saturation`;
- `deadlock_observation`;
- `corruption_sqlstate_observation`;
- `lock_not_available_observation`;
- `query_canceled_observation`;
- `serialization_failure_observation`;
- `auth_failure_observation`;
- `authorization_failure_observation`;
- `permission_denied_observation`;
- `oom_kill_observation`;
- `filesystem_capacity_zero`.

Эти коды называют наблюдения. `sigkill`, `out_of_memory` и `integrity_error`
остаются разными классами подтверждений и не объединяются в причину без
`IncidentDiagnosis`.

Начальные пороги из прежних эвристик не являются контрактом корректности.
Всплески ошибок аутентификации, отмен запросов и ошибок приложения, а также
исчерпание соединений требуют калибровки скорости и временного окна и
достаточного покрытия, а не безусловного вывода о критическом состоянии.

### 7.9 `IncidentDiagnosis`

```text
IncidentDiagnosis {
  diagnosis_id: [u8; 32],
  diagnosis_kind: stable code,
  interval: [i64, i64),
  supporting_fact_ids: Vec<[u8; 32]>,
  contradicting_or_missing_evidence: Vec<EvidenceRef>,
  confidence: Low | Medium | High,
  diagnosis_policy_version: u32,
}
```

Индекс обзора не хранит диагноз как канонический факт. Допустимы формулировки
вроде «SIGKILL совпал с приращением `oom_kill` в cgroup»; недопустимы
«SIGKILL доказал OOM» или «PANIC доказал повреждение» без дополнительных
фактов.

В текущей реализации зарезервирован только `diagnosis_policy_version`;
рабочий `IncidentDiagnosis` и причинная корреляция отсутствуют.

### 7.10 Планируемые источники подтверждений

| Входные данные | Что они позволят доказать |
| --- | --- |
| Структурированный `csvlog` или `jsonlog` с `log_time`, SQLSTATE, PID или сеансом и смещением источника | Точный для источника идентификатор появления и структурированные поля. |
| Журнал ядра или аудит жертвы OOM с PID, временем запуска и cgroup | Конкретную связь процесса с OOM. |
| Жизненный цикл systemd, Patroni или Kubernetes | Кто запросил перезапуск или завершение. |
| Ошибка файловой системы, inode, квота, режим только для чтения и события ext4/XFS | Отличие ENOSPC от квоты, режима только для чтения или повреждения и затронутую точку монтирования. |
| Состояние SMART/NVMe | Подтверждение со стороны носителя или контроллера устройства. |
| Объявленная топология репликации и состояние сети или канала | Потерю обязательной реплики и обоснованный сетевой диагноз. |

До появления этих полей классификация расширяется видами наблюдений, но не
выдуманными причинами.

## 8. Модель состояния

### 8.1 Разделение непрерывной оценки, нижнего предела и состояния

```text
HealthPoint {
  interval: [i64, i64),
  continuous_score: Option<f64>,
  overall_score: Option<f64>,
  overall_state: Unknown | Normal | Degraded | Critical,

  health_policy_version: u32,
  factor_set_id: [u8; 16],
  factor_penalties: Vec<FactorPenalty>,
  domain_penalties: Vec<DomainPenalty>,
  floor_evidence: Vec<FloorEvidence>,
  coverage: Vec<FactorCoverage>,
}
```

`continuous_score` описывает непрерывную нагрузку на ресурсы и эксплуатационное
состояние. `floor_evidence` содержит отдельные доверенные наблюдения
критических событий. `overall_state` объединяет их для пользовательского
интерфейса, не стирая неизвестное состояние.

Если обязательный домен не покрыт, обе числовые оценки равны `None`. Доверенный
нижний предел при этом всё равно задаёт `overall_state=Critical` и остаётся в
`floor_evidence`; неизвестная непрерывная оценка не превращается в выдуманный
ноль. При полном обязательном покрытии доверенный нижний предел делает
`overall_score=0.0`.

Полная таблица решений:

```text
if any required domain is unknown:
  continuous_score = None
  overall_score = None
  overall_state = Critical if trusted floor exists else Unknown
else:
  continuous_score = product(1 - known domain penalties)
  overall_score = 0.0 if trusted floor exists else continuous_score
  overall_state = Critical if trusted floor exists
                  else state_thresholds(overall_score)
```

### 8.2 Факторы и домены

Каждый фактор имеет стабильный `FactorId`, единицу измерения, правило
применимости, свёртку, правило допустимости и пропусков и монотонную кривую
штрафа `[0,1]`.

Начальные домены:

| Домен | Текущие входные данные |
| --- | --- |
| `database_error_pressure` | совместные счётчики уровня, категории и SQLSTATE и приращения отказов сеансов БД |
| `connection_capacity` | текущее отношение числа соединений к пределу и сохранённые наблюдения наподобие 53300 |
| `contention` | заблокированные сеансы, ожидания блокировок и приращения взаимоблокировок |
| `cpu_pressure` | CPU узла и cgroup, PSI CPU и нагрузка готовых к выполнению процессов |
| `memory_pressure` | PSI памяти, использование, пределы и события cgroup, факты OOM узла и cgroup |
| `storage_pressure` | ввод-вывод диска, доказанная ёмкость точки монтирования PostgreSQL, наблюдения временных файлов и заполнения диска |
| `maintenance` | приращения запрошенных и синхронизированных контрольных точек, сообщения о слишком частых контрольных точках и запас XID/MXID |
| `replication` | задержка, состояние и потеря слота при объявленной применимости |

Плановая контрольная точка и активный autovacuum сами по себе не являются
негативными факторами. Риск закольцовывания оценивается отдельно по XID и
MXID. Входные данные первых N объектов заморозки сохраняют `source_total` и
полноту совокупности.

### 8.3 Формула

Для ячейки одного временного среза:

```text
factor_penalty[f] = curve_f(reduced_fact_f) in [0, 1]

domain_penalty[d] = max(
  factor_penalty[f] for f in domain d
  after dedup by supporting fact identity
)

continuous_score = product(
  1 - domain_penalty[d]
  for known applicable domains
)
```

Максимум внутри домена снижает двойной учёт коррелированных непрерывных
сигналов: давление памяти cgroup вместе с PSI и число заблокированных
процессов вместе с ожиданиями блокировок не умножаются как независимые
доказательства одной цепочки. Коррелированные наблюдения нижнего предела
устраняются отдельно по идентификаторам подтверждающих фактов; они не участвуют
в произведении как обычные штрафы.

Между доменами используется произведение дополнений. Это порядковый
эксплуатационный индекс, а не вероятность. Для фиксированного набора факторов
и штрафов в `[0,1]` оценка ограничена и монотонна; исчезновение фактора не
входит в свойство монотонности.

### 8.4 Семантика обязательных доменов

`HealthPolicy` содержит:

```text
RequiredFactorProfile {
  profile_id,
  required_domains: Vec<DomainId>,
  required_factors_by_domain: Map<DomainId, Vec<FactorId>>,
  optional_factors: Vec<FactorId>,
  minimum_covered_ratio_by_factor,
}
```

Домен считается известным, только когда все применимые факторы, помеченные
обязательными для этого профиля, имеют достаточное покрытие в расчётной ячейке
и не пересечены потерей или пропуском, делающими результат недопустимым.
Отсутствующий необязательный фактор не блокирует оценку, но и не создаёт
нулевой штраф.

`factor_set_id` — хеш версии правил состояния, профиля, контракта реестра,
упорядоченных применимых факторов и точного упорядоченного набора факторов и
доменов, фактически участвовавших в этой точке. Если необязательный фактор
пропал, идентификатор меняется. Оценки сравнимы только при одинаковых
`health_policy_version` и `factor_set_id`.

### 8.5 Покрытие

```text
FactorCoverage {
  factor_id: FactorId,
  applicability: Applicable | NotApplicable | Unsupported,
  state: Complete | Partial | Gap | Unknown | NotCollected,
  interval: [i64, i64),
  expected_period_us: Option<u64>,
  present_samples: u64,
  covered_duration_us: u64,
  source_population: Option<{ collected: u64, total: u64 }>,
  loss_reasons: bitset,
  lost_count_lower_bound: Option<u64>,
  exactness: RetainedExact | LowerBound | Unknown,
}
```

`covered_ratio = covered_duration_us / bucket_duration_us` может
присутствовать как проекция для отображения, но не заменяет эту структуру и не
определяет допустимость оценки.

Покрытие журнала не объявляется `Complete`, пока контракт источника не может
это доказать. Отсутствие `pg_log_gap` само по себе не является доказательством
полноты `stderr`.

### 8.6 Нижние пределы

Доверенные подтверждения нижнего предела включают только факты достаточного
качества, например:

- наблюдение сбоя жизненного цикла — нижний предел доступности;
- структурированный PANIC — нижний предел доступности, но не вывод о
  повреждении;
- SQLSTATE XX001/XX002 или приращение ошибок контрольной суммы — подтверждение
  нарушения целостности;
- приращение `oom_kill` в cgroup или на узле — подтверждение OOM-kill;
- структурированное наблюдение 53100 — подтверждение заполнения диска, причём
  затронутая файловая система указывается только при доказанном соответствии.

Не являются автоматическим доверенным нижним пределом:

- один сигнал 9;
- общая категория `Resource`, `System` или `DataCorruption`;
- SQLSTATE 53200 как доказательство OOM ядра;
- немедленное завершение без интервала недоступности или контекста
  обслуживания;
- отсутствие отправителя репликации без полной предыдущей и текущей топологии.

### 8.7 Объяснимость

V1 не публикует искусственные аддитивные `contributions`. API отдаёт:

- нормализованные штрафы факторов;
- штраф домена и список определивших его факторов;
- исходное и свёрнутое значение и единицу измерения;
- покрытие каждого фактора;
- подтверждения нижнего предела с идентификаторами фактов.

Это однозначно объясняет оценку. Если позже понадобится распределить общее
снижение между факторами, такое распределение получит отдельную
версионированную математическую спецификацию.

## 9. Логическое содержимое фактов сегмента

### 9.1 Обязательные канонические блоки

Каждый OVF содержит следующие виды блоков. Блок может быть естественно пустым,
если выбранный PGM не содержит соответствующих строк, но обязательный базовый
блок не может отсутствовать:

| Блок | Содержимое | Реализация |
| --- | --- | --- |
| `SOURCE_MANIFEST` | Перечень записей каталога, раскладка и схема PGM, поддерживаемые и неподдерживаемые секции, происхождение содержимого, источник и диапазон | Заполняется для каждой записи каталога |
| `EVENT_OBSERVATIONS` | Сохранённые наблюдения в форме источника, упорядоченные по `(sort_ts_us, observation_id)` | Заполняется для восьми разрешённых раскладок журнала из §7.6 |
| `EVENT_FACTS` | Нормализованные факты, не зависящие от политики, и ссылки на подтверждающие наблюдения | Заполняется фактами журнала, счётчиков и переходов состояний |
| `LOSS_COVERAGE` | Наличие секций, интервалы покрытия, `pg_log_gap`, ограничения и потери, полнота состава, качество хвоста и источника | Заполняется покрытием каталога и сборщиков, известными пропусками и доказанными нижними пределами |
| `GAUGE_SAMPLES` | Значения с временными метками, идентификаторы фактора, ряда и сущности, единицы, качество и эпоха покрытия | Заполняется разрешёнными измерениями PostgreSQL, ОС и cgroup |
| `COUNTER_SAMPLES` | Накопительные значения с временными метками, ряд и сущность, семейство сброса и эпоха | Заполняется разрешёнными накопительными метриками |
| `RESET_MARKERS` | Границы сбросов по семействам, перезапуска postmaster и источника | Заполняется доказанным контекстом PostgreSQL и ОС |
| `ENTITY_STATES` | Полные ограниченные снимки сущностей, размер состава и состояние для доказанных переходов | Заполняется для репликации, слотов и других поддерживаемых составов |
| `STRING_TABLE` | Ограниченные канонические строки UTF-8 или байты для нормализованных шаблонов и других явно сохранённых ссылок | Заполняется общими строками наблюдений и фактов; может быть естественно пустым |

Контейнер создаёт девять записей каталога блоков. Число записей само по себе не
доказывает наличие данных: естественно пустой блок имеет нулевые число
элементов и тело и остаётся отличим от отсутствующего обязательного блока.

Формат допускает будущее разбиение по виду, логическому идентификатору фактора
или источника и временному диапазону, чтобы запрос декодировал только
пересечение и соседние граничные отсчёты. Текущий писатель PGKOVF создаёт один
базовый блок каждого вида и отвергает дубликат вида; несколько блоков одного
вида требуют явного расширения формата и схемы.

### 9.2 Необязательные ускоряющие блоки

Неизвестный необязательный блок разрешено пропустить, только если он избыточен
и не влияет на каноническую семантику. V1 допускает:

- итоговые счётчики событий всего сегмента;
- индекс поиска граничных отсчётов;
- индекс смещений временных меток по видам;
- заранее вычисленные упорядоченные ключи для двоичного поиска.

Готовые `HealthPoint`, набор значимых событий и итоговые интервалы графиков не
являются каноническими фактами. Если они когда-либо будут сохраняться на
диске, это будет отдельный вид файла проекции с версиями правил и тем же
резервным прямым чтением.

### 9.3 Минимально достаточные факты

| Операция | Что хранится | Что нельзя восстановить после преждевременного агрегирования |
| --- | --- | --- |
| Счётчики событий | Наблюдение с временной меткой, совместные измерения, `occurrence_count`, потери | Физические временные метки появлений в сгруппированной строке |
| Максимум или минимум измерения | Естественные отсчёты и временные метки | Экстремумы произвольного поддиапазона из одного максимума всего сегмента |
| Среднее по отсчётам | Отсчёты или точные сумма и число на разрезаемом блоке | Среднее из средних без числа элементов |
| Взвешенное по времени измерение | Отсчёты, правило допустимости и пропусков, граничные отсчёты | Точный срез из грубого интеграла без граничного состояния |
| Приращение или скорость счётчика | Упорядоченные отсчёты, семейство и эпоха сброса, пропуски | Пару через сброс или пропуск; произвольный срез из концов сегмента |
| Отношение счётчиков | Отдельные отсчёты или приращения числителя и знаменателя | Отношение усреднённых отношений |
| Исчезновение сущности | Полные наборы до и после и стабильный идентификатор | Переход через неполный снимок или пропуск |
| Состояние | Факты факторов одного временного среза и покрытие | Объединение готовых штрафов или оценок; максимумы компонентов из разных моментов |
| Процентиль | Исходные отсчёты или версионированный эскиз | Точный процентиль из минимума, максимума, суммы и числа |

V1 выбирает компактные отсчёты с временными метками. Грубые канонические
базовые интервалы не используются как единственный источник. Необязательные
сводки ускоряют объединение внутренней части диапазона, но исходный блок с
временными метками остаётся доступным для точного среза границ.

### 9.4 Правила канонического кодирования

- Целые числа имеют фиксированную ширину и порядок байтов little-endian либо
  явно описанный ограниченный `varint` внутри схемы блока.
- Числа с плавающей точкой имеют формат IEEE-754 binary64; NaN и бесконечность
  запрещены, `-0.0` канонизируется в `0.0`.
- Небольшие закрытые домены кодируются массивами фиксированного размера.
- SQLSTATE — ровно пять байтов в упорядоченном уникальном векторе.
- Сигналы — упорядоченный уникальный вектор `(i32,u64)`.
- Коллекции переменной длины имеют префикс длины и жёсткие ограничения числа и
  байтов, проверяемые до выделения памяти.
- Карты кодируются упорядоченными уникальными векторами ключей и значений;
  порядок `HashMap` в Rust никогда не попадает на диск.
- Временные метки и идентификаторы внутри блоков следуют каноническому полному
  порядку.
- Декодер потребляет весь декодированный блок; лишние байты делают блок
  недопустимым.
- Текстовые байты ограничены, проверяются по объявленному виду текста и
  никогда не локализуются неявно.

## 10. Физический формат фактов сегмента

### 10.1 Размещение и `FactKey`

`KRONIKA_WEB_DIR` — один каталог, который целиком принадлежит PgKronika.
Активный журнал, запечатанный PGM и его производный OVF находятся рядом:

```text
<KRONIKA_WEB_DIR>/active.parts
<KRONIKA_WEB_DIR>/N.pgm
<KRONIKA_WEB_DIR>/N.ovf
```

`N.ovf` имеет в точности ту же основную часть имени, что и `N.pgm`.
`SegmentContext` принимает только имя непосредственного дочернего файла с
непустой основной частью и точным расширением `.pgm`; разделители пути и
нулевой байт запрещены. Дополнительного каталога, идентификатора хранилища,
хеша пути или производного имени нет.

```text
FactKey = SHA-256(
  "pgk-overview-fact-key-v1" ||
  source_descriptor ||
  file_kind ||
  fact_schema_version ||
  extractor_semantics_version ||
  registry_contract_version
)
```

Полный неизменяемый идентификатор задачи построения:

```text
FactBuildKey = (FactKey, SegmentLineageId)
```

`FactKey` связывает содержимое источника и версии контрактов.
`SegmentLineageId` различает сохранённые появления одинакового содержимого.
`FactBuildKey` используется для координации одной задачи построения, допуска
ресурсов, резервного хранения в памяти и декодированных записей. Он не
участвует в имени `N.ovf` и не создаёт отдельную блокировку для каждого ключа.

Два сегмента с одинаковым `FactKey`, но разным `SegmentLineageId` не
объединяют задачи построения или записи в памяти. Версии правил состояния,
краткого списка и HTTP-ответа в `FactKey` не входят.

### 10.2 Дескриптор PGM и происхождение

Дескриптор содержимого v1:

```text
source_descriptor = SHA-256(
  "pgk-pgm-catalog-layout-v1\0" ||
  min_ts_le ||
  max_ts_le ||
  format_version_le ||
  window_count_le ||
  entry_count_u128_le ||
  for each ordered entry (
    offset_le || type_id_le || flags_le ||
    body_len_le || rows_le || body_crc32c_le
  )
)
```

Это тот же 32-байтовый `CatalogLayoutDigest`, который уже хранится в
`CatalogSummary` и `SegmentDescriptor`; второй digest на каждый сегмент не
удерживается. Дескриптор связан с содержимым PGM в пределах модели целостности
каталога и обнаруживает обычную замену или повреждение без чтения тел секций.

Модель угроз v1 предполагает, что PGM и OVF принадлежат одному доверенному
пользователю операционной системы, а PGM после публикации неизменяем. CRC32C
защищает от случайного повреждения, но не от злоумышленника с правом записи.
SHA-256 над каталогом с CRC не превращает CRC в криптографическую проверку
подлинности тела.

Проверка после перезапуска требует нулевого числа чтений тел PGM. Поэтому
незаметное изменение бита в теле при неизменном каталоге нельзя одновременно
обнаруживать при каждом чтении OVF. Его обнаруживает ограниченная фоновая
проверка исходных секций или последующее прямое чтение. После ошибки такой
проверки сегмент помечается как повреждённый источник, и старый OVF больше не
маскирует пропуск.

### 10.3 Фиксированный заголовок v3

Все поля сериализуются по отдельности в порядке байтов little-endian.
Использовать `repr(C)` Rust или размещение полей структуры в памяти нельзя.

Заголовок v3 занимает ровно 184 байта:

| Offset | Поле | Тип | Контракт |
| ---: | --- | --- | --- |
| 0 | `magic` | `[u8;8]` | `b"PGKOVF\0\0"` |
| 8 | `container_version` | `u16` | `3` |
| 10 | `header_len` | `u16` | `184` |
| 12 | `file_kind` | `u16` | `1 = SegmentFacts` |
| 14 | `header_flags` | `u16` | v1: `0` |
| 16 | `fact_schema_version` | `u32` | Логическая форма фактов |
| 20 | `extractor_semantics_version` | `u32` | Семантика извлечения PGM и свёртки |
| 24 | `registry_contract_version` | `u32` | Контракт поддерживаемых типов и раскладок |
| 28 | `source_format_version` | `u32` | Версия контейнера PGM |
| 32 | `source_min_ts_us` | `i64` | Включающая границу метаданная PGM |
| 40 | `source_max_ts_us` | `i64` | Включающая границу метаданная PGM |
| 48 | `source_file_len` | `u64` | Точная длина PGM |
| 56 | `source_descriptor` | `[u8;32]` | Дескриптор содержимого PGM |
| 88 | `fact_key` | `[u8;32]` | Проверяемый `FactKey` |
| 120 | `segment_lineage_id` | `[u8;32]` | Проверяемое происхождение сегмента |
| 152 | `directory_offset` | `u64` | v3: `184` |
| 160 | `directory_count` | `u32` | `1..=MAX_DIRECTORY_ENTRIES` |
| 164 | `directory_entry_len` | `u16` | v3: `64` |
| 166 | `descriptor_kind` | `u16` | Дескриптор каталога `1` |
| 168 | `file_len` | `u64` | Точная длина файла фактов |
| 176 | `directory_crc32c` | `u32` | CRC точных байтов каталога блоков |
| 180 | `header_crc32c` | `u32` | CRC заголовка с обнулённым полем CRC |

Неизвестные сигнатура, версия, вид файла, флаги или вид дескриптора делают файл
несовместимым. Условие `source_min_ts_us <= source_max_ts_us` обязательно.
Дескриптор, `FactKey`, происхождение, версии, диапазон и длина PGM сверяются с
выбранным файлом до допуска блоков.

### 10.4 Запись каталога блоков v1

Каждая запись занимает 64 байта:

| Offset | Поле | Тип |
| ---: | --- | --- |
| 0 | `block_kind` | `u32` |
| 4 | `block_schema_version` | `u16` |
| 6 | `block_flags` | `u16` |
| 8 | `logical_id` | `u32` |
| 12 | `reserved` | `u32` |
| 16 | `offset` | `u64` |
| 24 | `stored_len` | `u64` |
| 32 | `decoded_len` | `u64` |
| 40 | `item_count` | `u32` |
| 44 | `block_crc32c` | `u32` |
| 48 | `min_ts_us` | `i64` |
| 56 | `max_ts_us` | `i64` |

`logical_id` — стабильный идентификатор фактора или производителя блока либо
`0` для блоков всего сегмента. `reserved` обязан быть нулевым.

Флаги блока v1:

- bit 0 `REQUIRED_FOR_FACT_SCHEMA`;
- bit 1 `CANONICALLY_SORTED`;
- bit 2 `HAS_TIME_RANGE`;
- биты 8..11 задают кодек: `0=None`; значение `1` зарезервировано для
  возможного будущего `Zstd`;
- остальные биты обязаны быть нулевыми.

Текущее средство записи всегда пишет `BlockCodec::None`, а текущий считыватель
принимает только его. Для `None` CRC считается по сохранённым байтам, а
`stored_len` и `decoded_len` обязаны совпадать. `Zstd` сейчас считается
несовместимым, не является реализованной оптимизацией и не используется в
заявлениях о размере или производительности. Его будущее включение требует
явного решения о совместимости и версионировании, ограниченного
декодирования в буфер точной длины и отдельного набора проверок повреждений.

### 10.5 Семантика обязательных и необязательных расширений

- Неизвестный обязательный `block_kind` или схема обязательного блока делает
  файл несовместимым и запускает перестроение.
- Неизвестный необязательный блок безопасно пропускается.
- Канонический блок нельзя объявить необязательным только ради совместимости с
  будущими версиями.
- Необязательные блоки могут быть только избыточными ускорителями из §9.2.
- Неизвестный флаг блока или кодек всегда делает файл несовместимым.
- Отсутствующий обязательный базовый блок делает файл повреждённым или
  неполным; обязательный блок с нулём элементов допустим.

### 10.6 Допуск и ограничения

Ограничения безопасности v1 относятся к корректности и защите от отказа в
обслуживании, а не к заявлениям о производительности:

| Ограничение | Значение v1 |
| --- | ---: |
| Длина файла фактов | 512 MiB |
| Записи каталога | 4096 |
| Байты каталога | 256 KiB |
| Один сохранённый блок | 64 MiB |
| Один декодированный блок | 128 MiB |
| Элементы одного блока | 1 048 576 |
| Наблюдения событий одного сегмента | 1 048 576 |
| Отсчёты одного блока логического ряда | 1 048 576 |
| Ключи SQLSTATE в одном агрегате | 65 536 |
| Ключи сигналов в одном агрегате | 1 024 |
| Интервалы покрытия одного сегмента | 262 144 |
| Один сохранённый нормализованный шаблон | 64 KiB |
| Декодированные байты таблицы строк | 64 MiB |

Превышение ограничения не обрезает канонические факты. Сегмент становится
`Uncacheable(limit)`, ответ строится потоковым прямым чтением в пределах работы
запроса и публикует соответствующую метрику ускорения. Если одновременно
сработало ограничение канонических активных данных, их состояние становится
`Incomplete` по §4.4.

Порядок допуска:

1. Проверить безопасное имя непосредственного дочернего `N.pgm` и вывести из
   него только соседнее имя `N.ovf`.
2. Открыть каталог данных, PGM и OVF относительно дескриптора каталога с
   `NOFOLLOW`; принимать только обычные файлы.
3. Проверить длину OVF и прочитать 192-байтовый заголовок; проверить сигнатуру,
   версии, вид, флаги и CRC заголовка.
4. Проверяемой арифметикой подтвердить смещение, число и размер записей
   каталога блоков, а также точный диапазон каталога.
5. Прочитать ограниченный каталог блоков и проверить его CRC.
6. Сравнить ожидаемые дескриптор PGM, `FactKey`, `SegmentLineageId`, диапазон,
   формат и длину входного файла.
7. Проверить канонический порядок, известные флаги, нулевые зарезервированные
   поля, временные границы, непересекающиеся диапазоны блоков и точный
   `file_len`.
8. Выбрать только нужные блоки; до выделения памяти проверить сохранённую и
   декодированную длину и число элементов.
9. Проверить CRC блока и равенство длин для `None`. Для любого будущего кодека
   сначала проверить предел декодированной длины и точную длину результата,
   затем логические инварианты декодера.
10. Проверить упорядоченность и уникальность ключей, диапазоны перечислений,
    конечность чисел с плавающей точкой, переполнение счётчиков, ссылки и
    полное потребление блока.

Ошибка в выбранном блоке отвергает весь OVF. Частично использовать исправные
блоки повреждённого файла нельзя: однозначным запасным путём остаётся
перестроение из PGM.

### 10.7 Надёжная публикация

1. Получить исключительное право записи в каталог через
   `.pgkronika-overview.owner.lock` и локальный шлюз публикации.
2. Повторно открыть и проверить соседний `N.pgm` с `NOFOLLOW`.
3. Создать уникальный временный файл
   `.pgkronika-overview.tmp-<pid>-<sequence>` в том же каталоге с
   `CREATE|EXCL|NOFOLLOW` и правами `0600`.
4. Записать полностью сформированный контейнер и вызвать `sync_all(file)`.
5. Повторно проверить временный файл тем же путём допуска и с ожидаемыми
   заголовочными данными.
6. Атомарно переименовать временный файл поверх того же `N.ovf` и вызвать
   `sync_all` для каталога.
7. Удалить только собственный временный файл при ошибке или после завершения.

Допустимый существующий `N.ovf` переиспользуется. Устаревший, несовместимый,
повреждённый или не соответствующий выбранному PGM файл безопасно заменяется
атомарным переименованием по тому же пути. Ошибка публикации после успешного
построения не отменяет вычисленный ответ.

## 11. Версии и идентификаторы

### 11.1 Независимые оси версий

| Версия | Что меняет | Что инвалидирует |
| --- | --- | --- |
| `container_version` | Обрамление заголовка и каталога | Совместимость декодера; при отсутствии — файл фактов |
| `fact_schema_version` | Логические канонические факты и поля | Файл фактов |
| `extractor_semantics_version` | Соответствие PGM, нормализацию, семантику свёртки и сбросов | Файл фактов |
| `registry_contract_version` | Поддерживаемые типы и раскладки PGM и обязательные входные данные | Файл фактов |
| `health_policy_version` | Набор факторов, кривые, домены, нижние пределы и обязательный профиль | Только проекцию и ответ состояния |
| `notable_policy_version` | Выбор, устранение повторов, ранжирование и ограничения | Только проекцию и ответ событий |
| `diagnosis_policy_version` | Модель корреляции и причин | Только диагноз происшествия |
| `response_schema_version` | Форму JSON внешнего протокола | Сохранённый сериализованный ответ |
| `cursor_version` | Кодирование и проверку курсора | Только курсор |

Изменение правил состояния или значимости не перестраивает факты, когда
сохранённых измерений достаточно. Новые правила по шаблону или полю источника,
для которых фактов недостаточно, повышают версию семантики извлечения и
запускают управляемое перестроение из PGM.

### 11.2 `FactSetId` и ключ проекции в памяти

```text
FactSetId = SHA-256(
  ordered sealed FactBuildKeys ||
  boundary-halo FactBuildKeys ||
  live journal_generation ||
  live folded_watermark ||
  live fact_digest ||
  source/loss generation
)
```

TTL не является частью идентификатора. Любое изменение поколения или
обработанной позиции активных данных, дескриптора запечатанного сегмента,
граничных отсчётов, состояния потерь или применимых правил естественно меняет
ключ в памяти.

### 11.3 Совместимость файла фактов

- Декодер контейнера может поддерживать несколько старых совместимых версий.
- Несовпадение версий фактов, извлечения или реестра не исправляется внутри
  старого содержимого: соседний OVF отвергается, факты строятся из PGM и
  атомарно заменяют тот же файл.
- Неизвестная обязательная входная раскладка запрещает считать отсутствие
  измеренным нулём. Перестроение сегмента завершается `UnsupportedLayout` и
  неизвестным покрытием, если текущий извлекатель её не понимает.

## 12. Машины состояний

### 12.1 Запечатанный сегмент

```text
Absent
  ├─ попадание в память ----------------------------> ReadyMemory
  ├─ файл-кандидат -> HeaderAdmitted -> ReadyDisk --> ReadyMemory
  │                       └─ отказ -----------------> SoftRejected -> Build
  └─ промах ----------------------------------------> Build

Build --общий допуск + одна задача на FactBuildKey----> Building
  ├─ PGM успешно прочитан ---------------------------> ReadyMemory
  │                                                    └─ попытка публикации
  │                                                         ├─ успех -> ReadyDisk
  │                                                         └─ отказ -> PersistBackoff
  ├─ ошибка источника -------------------------------> SourceFailed
  └─ ограничение фактов -----------------------------> Uncacheable
```

`Missing`, `Incompatible`, `Corrupt`, `WrongSource` и ошибка ввода-вывода OVF
являются устранимыми ошибками производного файла. `SourceMissing`, `SourceIo`,
`SourceCorrupt` и `UnsupportedLayout` влияют на покрытие результата и не
переименовываются в отсутствие OVF.

Текущая реализация сначала проверяет декодированные факты в памяти и допустимый
соседний OVF. Только затем она входит в ограниченный планировщик построения.
Одинаковые `FactBuildKey` объединяются одной безопасной при отмене задачей, а
разные задачи ограничены общей взвешенной ёмкостью, числом работников,
очередью, параллелизмом одного запроса и временем ожидания.

### 12.2 Построитель активных данных

| Состояние | Инвариант | Разрешённый ответ |
| --- | --- | --- |
| `Empty` | Журнал доказанно пуст | Только запечатанные данные |
| `Warming` | После перезапуска или полного повторного сканирования данные ещё не свёрнуты до обработанной позиции | Допущенная прямая свёртка либо явный прогрев или пропуск хвоста |
| `Current` | Все завершённые части до обработанной позиции свёрнуты ровно один раз | Опубликованный `LiveView` и ограниченное чтение ожидающего хвоста |
| `NeedsRebuild` | Непрерывность дописывания или идентификатор не доказаны | Старое представление активных данных не публикуется как текущее |
| `Incomplete` | Жёсткое ограничение, неподдерживаемые или повреждённые завершённые данные либо переполнение | Явная потеря; продвижение запрещено |

```text
LiveState::Current {
  journal_generation,
  folded_through_offset,
  folded_part_ids,
  facts_digest,
  data_through_us,
}
```

Изменяемый построитель имеет одного писателя. `ArcSwap` публикует
`Arc<LiveView>`, но построитель не копирует весь растущий вектор для каждой
части: записи хранятся блоками с совместным использованием неизменяемых
данных, а публикация переиспользует неизменившиеся блоки. Частота публикации
ограничивается циклом обновления, а не каждой декодированной строкой.

Вычисления CPU, блокирующий ввод-вывод, декодирование PGM и Parquet,
хеширование и `fsync` выполняются в ограниченном пуле блокирующих работников.
Асинхронная задача обновления только планирует работу, ждёт результат и
атомарно публикует представление.

### 12.3 Переход при запечатывании

Совпадение временного диапазона не доказывает идентичность. Переход:

1. Обновление одновременно видит новый запечатанный `SegmentDescriptor` и
   переход журнала.
2. Считыватель строит упорядоченное происхождение нового PGM: идентификаторы
   тел секций, порядковые номера экземпляров, контекст строки и словаря и факты
   составляющих частей.
3. Кандидат активных данных допускается только из полного построителя
   `Current`.
4. Происхождение кандидата должно точно совпасть с новым запечатанным PGM по
   всем использованным входным данным; равенства временных меток недостаточно.
5. При совпадении факты активных данных можно продвинуть как готовый кандидат
   `SegmentFacts` и опубликовать по обычному надёжному протоколу.
6. При несовпадении, неопределённости или неполноте кандидат отбрасывается, а
   факты запечатанного сегмента строятся из PGM.
7. Новый набор запечатанных данных и новое или пустое поколение активных данных
   публикуются одним `IndexView`.
8. Устранение повторов на уровне запроса использует идентификаторы
   происхождения; разбиение диапазона служит только оптимизацией планировщика.

Ограничения ответа никогда не влияют на продвижение.

### 12.4 Перезапуск

1. Считыватель строит авторитетный каталог запечатанных данных из заголовков и
   каталогов PGM.
2. Для каждого непосредственного дочернего `N.pgm` рассматривается только
   соседний `N.ovf`; каталог данных не становится источником диапазонов.
3. Заголовки и каталоги OVF проверяются лениво, а тела блоков читаются по
   необходимости.
4. Допустимый OVF обслуживает запрос после перезапуска без чтения тела PGM.
5. Активный журнал получает новое доказанное поколение и входит в `Warming`.
6. Завершённые кадры сворачиваются ровно один раз. До состояния `Current`
   ответы показывают прогрев и состояние хвоста либо используют допущенное
   прямое сворачивание.
7. Хранилища фактов, проекций и ответов в памяти начинают работу пустыми.

### 12.5 Повреждение и изменение схемы

- Оборванный хвост активных данных не продвигает допустимую обработанную
  позицию и публикуется как `tail_pending`; это не повреждение завершённого
  кадра.
- Повреждённый или несовместимый OVF закрывается, учитывается метрикой,
  перестраивается из PGM и атомарно заменяется по тому же пути.
- Файл, заголовок которого описывает другой источник, никогда не допускается
  только из-за совпадения имени.
- Повреждённый исходный PGM создаёт пропуск или ошибку источника; старый OVF не
  становится самостоятельным источником истины после обнаружения повреждения.
- Изменение только формулы или правил значимости очищает ключи проекций и
  ответов, но не меняет файлы фактов и их время изменения.
- Изменение версии фактов, извлечения или реестра меняет `FactKey`; старый OVF
  перестраивается и атомарно заменяется на том же соседнем пути.

### 12.6 Срок хранения и сборка мусора

- Набор живых `FactBuildKey` строится только из последнего успешного полного
  снимка источников.
- Неопределённость при сканировании каталога запрещает удаление и не продвигает
  льготный период.
- PGM, исчезнувший из авторитетного представления, немедленно перестаёт
  участвовать в новых ответах.
- Производный OVF не продлевает срок хранения источника.
- Удаление устаревшего OVF откладывается минимум на два разных авторитетных
  поколения и на заданный временной льготный период.
- Плоское ограниченное сканирование учитывает только распознанные соседние OVF
  и собственные временные файлы публикации. Квоты по логическому размеру и
  числу файлов применяются только к этим производным объектам.
- Перед удалением повторно проверяются имя, вид файла, inode, заголовок и
  ожидаемый `FactBuildKey`; открытие выполняется с `NOFOLLOW`.
- Право изменения каталога удерживает один процесс через
  `.pgkronika-overview.owner.lock`. Остальные процессы могут читать допустимые
  OVF, но не публикуют файлы и не выполняют сборку мусора.
- Сборка мусора никогда не удаляет PGM, `active.parts` или другие файлы
  источника.

## 13. Слои чтения и резервные данные в памяти

### 13.1 Слои

```text
L0 источник: неизменяемые PGM + завершённые активные части
L1 диск:    соседние канонические файлы N.ovf
L1f память: допущенные факты после ошибки публикации
L2 память:  ограниченные по объёму декодированные блоки и проекции
L3 память:  точные сериализованные ответы
```

L1 сохраняется после перезапуска. L1f/L2/L3 существуют только в процессе.
Ни один слой не меняет семантику корректности нижнего слоя.

`FactStore::load_or_build` соблюдает строгий порядок: чтение соседнего OVF →
поиск в резервных данных памяти → построение из PGM → попытка атомарной
публикации OVF. Резервный слой заполняется только после устранимой ошибки
публикации уже построенного и полностью проверенного набора фактов. Это
детерминированный LRU по полному `FactBuildKey`, одновременно ограниченный
каноническими байтами и суммой часов сегментов. Слишком крупная запись
обслуживает текущий запрос, но не остаётся в памяти. Декодированные факты и
точные ответы также имеют отдельные ограничения по объёму и числу записей.

### 13.2 Факты и проекции в памяти

- Ключ декодированного блока фактов: `(FactBuildKey, идентификатор записи
  каталога)`.
- Значение: неизменяемый `Arc<DecodedBlock>`.
- Вытеснение: ограниченный по байтам LRU или сегментированные часы; число
  записей не используется как основной предел.
- Обрабатываемые и закреплённые байты учитываются отдельно и входят в общий
  бюджет работы.
- Запись больше предела допуска одной записи читается потоково и не нарушает
  ответ.
- Ключ проекции включает `FactSetId`, точный диапазон, фактический шаг,
  фильтры, набор факторов и версии правил.

Бюджет должен вмещать рабочий набор плотного часа с граничными отсчётами, если
он ниже настроенного верхнего предела:

```text
dense_hour_bytes = max over every contiguous 1h plan (
  sum(decoded_len of canonical intersecting blocks) +
  left/right halo blocks +
  measured decoded object overhead
)

effective_fact_budget = min(
  configured_ceiling,
  max(configured_floor, dense_hour_bytes)
)
```

После перезапуска `decoded_len` берётся из допущенных каталогов; накладные
расходы объектов уточняются по рабочим метрикам. Если
`dense_hour_bytes > configured_ceiling`, система публикует
`working_set_exceeds_ceiling` и сохраняет корректность потоковым чтением или
повторным декодированием. Спецификация не выдумывает универсальный бюджет
байтов: развёртывание обязано проверить его на своём наборе данных плотного
часа.

Активный запрос закрепляет свой рабочий набор до завершения, но не может
превысить общий бюджет обрабатываемых данных.

### 13.3 Точные ответы в памяти

```text
ResponseKey {
  endpoint,
  response_schema_version,
  fact_set_id,
  requested_range,
  effective_range,
  requested_step_us?,
  effective_step_us?,
  normalized_filters,
  health_policy_version?,
  notable_policy_version?,
  factor_set_id?,
  page/view identity?,
}
```

Значение — неизменяемое сериализованное тело вместе с типом содержимого и
метаданными состояния. Хранилище ограничено по числу байтов. Ключ ответа с
активными данными всегда включает поколение журнала и обработанную позицию;
короткий TTL не заменяет эти признаки.

### 13.4 Режимы постоянных файлов фактов

Возможности чтения и записи OVF отслеживаются независимо:

```text
PersistentCacheMode =
  ReadWrite |
  ReadOnlyBackoff { reason, next_retry_at, failures } |
  UnavailableBackoff { reason, next_retry_at, failures }

PersistFailure =
  ReadOnlyFilesystem | PermissionDenied | NoSpace | Quota |
  TransientIo | InvalidWinner
```

При `EROFS`, `EACCES`, `ENOSPC`, квоте или временной ошибке ввода-вывода:

1. вычисленные `SegmentFacts` остаются в памяти и обслуживают текущий ответ;
2. новые задачи построения используют ограниченный резервный слой памяти;
3. уже допустимые OVF продолжают читаться, если чтение доступно;
4. причина учитывается отдельно от ошибок исходного PGM;
5. `ENOSPC` или превышение квоты один раз запускает ограниченную сборку мусора,
   затем повторяет запись;
6. задержка между попытками не позволяет каждому запросу повторять одну и ту
   же ошибку;
7. фоновая проба возвращает `ReadWrite` после успешного создания,
   синхронизации и удаления собственного временного файла.

Задержка повторов v1: сначала 1 с, множитель 2, предел 5 мин, случайное
отклонение ±20%; при отказе в доступе или файловой системе только для чтения
первая повторная проверка начинается с предельного интервала. Успех сбрасывает
задержку. Эти значения относятся к эксплуатации, а не к порогам состояния или
производительности.

Состояние записи файлов фактов видно в метриках и административной
диагностике. Оно не попадает в покрытие источника и не делает корректную
временную шкалу частичной.

Текущая реализация использует эту машину состояний записи во всех API
`FactStore`: одна готовая резервировка, очистка при отмене, одна ограниченная
попытка сборки мусора и фоновая проба из обновления веб-сервера. Чтение OVF не
зависит от задержки повторной записи. Координация построений и взвешенный
допуск реализованы отдельно и не блокируют попадания в память или OVF.

### 13.5 Квота

- Отдельные бюджеты байтов: факты на диске, факты и проекции в памяти, точные
  ответы, закреплённые представления курсоров и выполняемые построения.
- Дисковая квота считает распознанные соседние OVF и собственные временные
  файлы публикации; PGM и `active.parts` в неё не входят.
- Временное превышение ограничено одним создаваемым файлом на каждое место
  записи, причём размер файла ограничен.
- Вытеснение никогда не удаляет используемый `Arc`; отвязать файл безопасно
  только после исключения из поиска и с учётом семантики платформы.
- Если освободить квоту невозможно, система продолжает работать только с
  памятью, а не обрезает факты.

Текущая реализация поддерживает необязательные пределы суммы логических
`st_size` и числа распознанных производных файлов. По умолчанию они отключены.
Допуск требует полного ограниченного сканирования и при неопределённости ничего
не удаляет. Это не квота физической файловой системы; рабочий набор «плотного
часа» проверяется отдельным квалификационным артефактом.

## 14. Конкурентность, объединение одинаковых задач и допуск

### 14.1 Одна задача на ключ

Ключ объединения одинаковых задач равен полному `FactBuildKey`. Построение
принадлежит задаче реестра, а не ведущему запросу:

```text
get_or_build(build_key):
  lock registry briefly
  if Ready -> clone Arc result
  if Building -> subscribe waiter
  if Absent -> insert Building and spawn owned task
  unlock before await
  await shared terminal result
```

Инварианты:

- блокировка реестра не удерживается во время `await`;
- отмена ожидающего запроса не отменяет общее построение и не оставляет запись
  навсегда в состоянии `Building`;
- если все ожидающие исчезли до старта, работу в очереди можно отменить;
- уже начатое ограниченное построение допускается завершить и сохранить;
- успех или ошибка пробуждает всех ожидающих;
- конечная запись удаляется или заменяется слабой ссылкой на готовый результат;
- временный отказ файла фактов или источника не сохраняется навечно;
- паника или прерывание принадлежащей реестру задачи превращается в
  типизированную конечную ошибку и очищает запись.

Текущая реализация содержит отдельные координаторы для точного HTTP
`ResponseKey` и для `FactBuildKey`. Одинаковые задачи построения получают один
общий результат. Разные `SegmentLineageId` не объединяются, отмена ожидающего
запроса не отменяет общую задачу, а завершение или ошибка освобождает запись.

### 14.2 Общие ограничения построения из PGM

Координация одной задачи не защищает от запроса на сотни разных сегментов,
которые нужно построить из PGM. Поэтому реализация одновременно ограничивает:

- общий взвешенный бюджет по оценке байтов PGM, декодированных байтов и единиц
  вычислительной работы;
- жёсткий предел одновременно строящихся ключей;
- ограниченный пул блокирующих работников;
- параллелизм одного запроса;
- предел одновременно используемых файловых дескрипторов и байтов чтения и
  записи;
- число одновременных публикаций OVF;
- справедливая очередь между запросами и источниками;
- время ожидания допуска и `Retry-After` при перегрузке;
- предел диапазона, сегментов, точек и размера страницы до материализации.

Попадания в декодированные данные памяти, OVF и точные ответы не занимают
разрешения на построение из PGM. Короткое изменение метаданных LRU допустимо;
полезная нагрузка возвращается как `Arc` без копирования.

### 14.3 Ограничения безопасности HTTP v1

| Ограничение | Значение по умолчанию | Абсолютный предел v1 |
| --- | ---: | ---: |
| Диапазон запроса | 7 дней | 31 день |
| Выбранные запечатанные сегменты | 1024 | 4096 |
| Точки состояния | 2000 | 10 000 |
| Размер страницы событий | 100 | 1000 |
| Одновременные загрузки сегментов одного запроса | 4 | 16 |
| Закреплённые представления курсоров | 128 | 1024 |
| Срок жизни представления курсора | 5 мин | 30 мин |

Развёртывание может снижать значения по умолчанию. Повышение до абсолютного
предела требует измерения памяти и файловых дескрипторов. Превышение формы
запроса возвращает машиночитаемую ошибку до построения из PGM; оно не
превращается в частичный семантический ответ.

## 15. Машинный HTTP-контракт

Рабочие маршруты `/v1/timeline/overview`, `/v1/timeline/health` и
`/v1/timeline/events` описаны в OpenAPI. Параметры обзора —
`source/from/to`; состояния — `source/from/to/step`; событий — повторяемый
`source` и `from/to/limit/cursor/min_severity/kind`. Параметры `profile` и
`entity` в псевдокоде ниже остаются будущими расширениями. Фактическая внешняя
форма проверяется OpenAPI и наборами данных обработчиков.

### 15.1 Общие метаданные

```text
TimelineMeta {
  response_schema_version: u32,
  view_generation: u64,
  fact_set_id: Base64Url,

  requested_range: { from_us: i64, to_us: i64 },
  effective_range: { from_us: i64, to_us: i64 },
  effective_step_us: Option<u64>,

  sources: Vec<u64>,
  available_sources: Vec<u64>,
  data_through_us: Option<i64>,
  store_data_through_us: Option<i64>,
  tail_pending: Option<{
    from_offset_bytes: u64,
    to_offset_bytes: u64,
  }>,
  source_status: CompleteForContract | Partial | Warming | Gap | Unavailable,
  source_freshness: Vec<SourceFreshness>,
  loss: Vec<SourceLoss>,
}
```

`CompleteForContract` означает полноту выбранного контракта сохранённых данных
и источника, а не физического журнала PostgreSQL, если сборщик не может её
доказать.

`tail_pending` относится к выбранному активному источнику и задаёт
полуоткрытый диапазон байтов незавершённого хвоста
`[from_offset_bytes, to_offset_bytes)`. Это не временной интервал и не
повреждение уже завершённой части журнала.

Ответы нейтральны к языку: они содержат стабильные коды и перечисления, числа
и идентификаторы. Локализованный текст для человека не входит в контракт API.
Будущий неизвестный код клиент отображает как исходный код с общей подписью.

### 15.2 Обзор

```http
GET /v1/timeline/overview?from=...&to=...
```

```text
OverviewResponse {
  meta: TimelineMeta,
  event_digest: {
    retained_occurrence_count: u64,
    retained_observation_count: u64,
    by_severity: [u64; 5],
    by_category: [u64; 11],
    by_sqlstate: Vec<{ code: [u8;5], count: u64 }>,
    sqlstate_other_count: u64,
    joint_top: Vec<JointErrorCount>,
    lifecycle: LifecycleCounts,
    exactness: RetainedExact | LowerBound | Unknown,
  },
  notable_preview: {
    observations: Vec<EventObservationView>,
    omitted_count: u64,
    events_query_hash: Base64Url,
  },
  health_summary: {
    worst_point: Option<HealthPoint>,
    latest_point: Option<HealthPoint>,
  },
  coverage: Vec<FactorCoverage>,
}
```

Первые N значений `by_sqlstate` и `joint_top` — проекция ответа.
`other_count` вычисляется из точного агрегата сохранённых данных, а канонический
индекс не обрезается. `notable_preview` использует ту же `NotablePolicy` и те
же идентификаторы, что `/events`.

`retained_occurrence_count` нельзя складывать со счётчиком жизненного цикла как
«общее число событий»: группы ошибок и совместимое представление жизненного
цикла могут пересекаться. Поля остаются раздельными.

### 15.3 Состояние

```http
GET /v1/timeline/health?from=...&to=...&step=...&profile=...
```

```text
HealthResponse {
  meta: TimelineMeta,
  health_policy_version: u32,
  factor_set_ids: Vec<Base64Url>,
  points: Vec<HealthPoint>,
  coverage: Vec<FactorCoverage>,
}
```

- Точки упорядочены по началу интервала.
- Интервалы не пересекаются и точно разбивают фактический диапазон, кроме явно
  пропущенного хвоста после `data_through_us`.
- Интервал без данных возвращается с `overall_state=Unknown`, числовыми
  оценками `None` и причинами покрытия.
- Состояние не интерполируется ни на сервере, ни в клиенте.
- Прореживание по худшей точке следует §6.7; факты нижнего предела не
  сглаживаются.

### 15.4 События

```http
GET /v1/timeline/events?from=...&to=...&limit=...&cursor=...
                            &min_severity=...&kind=...&entity=...
```

```text
EventsResponse {
  meta: TimelineMeta,
  notable_policy_version: u32,
  events: Vec<EventObservationView>,
  next_cursor: Option<String>,
  omitted_by_response_filter: u64,
  retained_exactness: RetainedExact | LowerBound | Unknown,
  source_completeness: Full | BoundedSubset | Unknown,
  physical_count_semantics: Exact | LowerBound | Unknown | NotApplicable,
  coverage: Vec<FactorCoverage>,
}

EventObservationView {
  event_id: Base64Url,
  event_instance_id: Base64Url,
  source_type_id: Option<u32>,
  identity_quality: SourceExact | ContentDerived | Approximate,
  sort_ts_us: i64,
  occurred_at_us: Option<i64>,
  observed_interval: Option<{ from_us: i64, to_us: i64 }>,
  occurrence_count: u64,
  event_kind: stable code,

```

Канонический порядок:
`(sort_ts_us ASC, event_id ASC, event_instance_id ASC)`. `event_id` зависит
только от опубликованной семантики и не включает путь, имя файла или
физическое происхождение сегмента, поэтому остаётся стабильным при обычном
переходе из активных данных в запечатанные. `event_instance_id` отдельно
сохраняет физическое происхождение: семантически одинаковые сохранённые
наблюдения не теряются при сортировке и постраничной выдаче. Сгруппированная
строка остаётся одним элементом страницы.

В текущей схеме ответа `events` сериализует веб-проекцию `EventFact` из §7.4,
а не канонический блок `EVENT_FACTS`. Приёмка обзора проверяет
рабочий обработчик и JSON по OpenAPI: стабильные машиночитаемые поля,
`event_id` и `event_instance_id`, подтверждения, число появлений и потери. Это
не доказывает наличие настоящего пользовательского интерфейса или проверку его
отрисовки.

### 15.5 Курсор

Курсор внешнего протокола непрозрачен и заверен секретом процесса; после
декодирования v2 имеет следующую форму:

```text
EventsCursor {
  cursor_version: u16,
  key_id: [u8;16],
  issued_at: u64,
  expires_at: u64,
  fact_set_id: [u8;32],
  query_hash: [u8;32],
  last_ts_us: i64,
  last_event_id: [u8;32],
  last_event_instance_id: [u8;32],
}
```

`query_hash` включает диапазон, нормализованные фильтры, трёхкомпонентный
порядок, версию правил краткого списка и схему ответа. `fact_set_id` привязывает
курсор к неизменяемому набору фактов.
`issued_at` и `expires_at` задаются в секундах Unix. Первая страница закрепляет
неизменяемое представление запроса и индекса. Следующая страница обязана
использовать тот же набор фактов и хеш запроса.

`min_severity` применяется только к наблюдениям с уровнем. Типизированные факты
жизненного цикла или состояния без уровня остаются доступными по `kind` и
`NotablePolicy`; вызывающая сторона, которой нужны только группы ошибок
журнала, задаёт соответствующий фильтр `kind`.

Реестр закреплённых представлений ограничен по числу, байтам и TTL. Он
удерживает нужные `Arc` представлений фактов и событий, поэтому сборка мусора
и обновление не меняют уже начатую постраничную выдачу. Если представление не
помещается в бюджет, первая страница возвращает `cursor_view_limit`, не обещая
стабильной постраничной выдачи.

Ошибки курсора:

- `invalid_cursor` — декодирование, MAC или версия;
- `cursor_query_mismatch` — изменён диапазон, фильтр или правила;
- `cursor_expired` — истёк TTL, представление вытеснено по пределу числа или
  `key_id` принадлежит прежнему процессу;
- `view_gone` — источник или представление больше нельзя удержать;
- состояние HTTP для истёкшего или утраченного представления — `410 Gone`;
  для недопустимого курсора или несовпадения — `400 Bad Request`.

После перезапуска процесса закреплённые представления в памяти исчезают,
поэтому срок старых курсоров честно истекает. Продолжение без состояния на
новом поколении активных данных запрещено.

### 15.6 Ошибки источника, OVF и перегрузка

- Повреждение OVF или ошибка его записи не включается в потери источника; это
  диагностические сведения об ускоряющем слое.
- Нечитаемый или повреждённый сегмент источника становится явным пропуском
  сегмента или источника. Если другие данные позволяют корректный частичный
  ответ, конечная точка возвращает `200` с `source_status=Partial/Gap`.
- Если авторитетное представление хранилища вообще недоступно, возвращается
  `503 source_unavailable`.
- Форма запроса выше жёсткого предела даёт `400 query_limit_exceeded` или `413`
  для слишком большого тела, без частичной обработки.
- Истечение ожидания допуска построения — `503 cold_build_overloaded` с
  `Retry-After`; попадание в память или допустимый OVF не должно приводить к
  такому ответу.

## 16. Границы модулей и крейтов

### 16.1 `kronika-analytics::overview`

Чистое ядро с небольшим числом зависимостей:

- текущий `EventObservation`, типы факторов, отсчётов и покрытия и целевой
  канонический `EventFact`;
- детерминированные свёртка, объединение и сокращение;
- правила состояния и значимости и версионированные чистые функции;
- алгебра счётчиков с проверкой переполнения;
- проверки свойств и метаморфные проверки.

Модуль не знает `Catalog`, `Part`, `Row`, `StrId`, файловую систему, Parquet
или HTTP.

### 16.2 `kronika-reader::overview`

Постоянный индекс, принадлежащий считывателю:

- выборочное извлечение секций и тел PGM;
- адресное разрешение словаря;
- дескрипторы сегмента, части и тела, а также происхождение;
- семантический `RefreshDelta`;
- кодек заголовка, каталога и блоков на диске;
- допуск OVF, атомарная публикация и типизированные ошибки чтения и записи;
- путь прямого эталонного чтения и построитель фактов;
- поиск граничных блоков.

Адресный разрешитель обязан находить указанные идентификаторы и в
`dict.strings`, и в `dict.blobs`; нельзя предполагать, что будущий
нормализованный шаблон всегда короче текущего порога разделения строк и
двоичных данных.

Семантика формулы, значимости и HTTP не входит в кодек считывателя.

### 16.3 `pg_kronika-web::overview`

Зона ответственности:

- жизненный цикл изменяемого построителя активных данных и атомарная публикация
  `IndexView`;
- ограниченные по байтам данные в памяти;
- реестр объединения одинаковых задач и общий допуск построения из PGM;
- планирование запросов, точные ответы в памяти и реестр представлений
  курсоров;
- проверка и сериализация HTTP;
- фоновое управление повторными попытками и сборкой мусора и экспорт метрик.

Внутреннее разбиение: `live`, `view`, `admission`, `memory_cache`,
`response_cache`, `cursor`, `handlers`. Новый крейт для v1 не нужен: у индекса
на диске один потребитель-считыватель, а чистая алгебра уже помещается в
аналитическом крейте.

Текущая реализация атомарно публикует пару снимка источников и временной шкалы,
обслуживает конечные точки, закрепляет представления курсоров и ограничивает
точные ответы по объёму. После M4 добавлены полный `FactBuildKey`, резервный
слой памяти с двумя пределами, единственный владелец каталога, необязательные
пределы размера и числа производных файлов, безопасная сборка мусора,
типизированное восстановление записи, координация построений, взвешенный допуск
и фоновая проверка исходных секций.

### 16.4 Типизированная модель ошибок

```text
CacheReadError =
  Missing | Incompatible | Corrupt | WrongSource | Oversized | Io

PersistError =
  ReadOnlyFilesystem | PermissionDenied | NoSpace | Quota |
  Io | InvalidWinner

SourceError =
  Missing | Io | Corrupt | UnsupportedFormat | UnsupportedLayout

BuildError =
  Source(SourceError) | LimitExceeded | Overflow | Cancelled | Internal

AdmissionError =
  QueryLimit | QueueTimeout | WorkBudget | CursorViewBudget
```

Ошибки производного файла допускают резервное чтение. Ошибки источника меняют
покрытие и результат. Ограничения и отмена не выдаются за повреждение. Внешний
протокол получает стабильный код ошибки и идентификатор запроса; путь и
внутренняя цепочка остаются в структурированных журналах.

## 17. Тестовый контракт

### 17.1 Прямой эталон и семантическое равенство

Для каждого поддерживаемого запроса должен существовать эталон принудительного
прямого чтения PGM или активных данных, обходящий производные файлы и память.
Индекс и эталон обязаны совпадать по:

- сохранённым наблюдениям, идентификаторам, `occurrence_count` и порядку;
- точным счётчикам и совместным измерениям;
- отсчётам, границам сбросов и пропусков и свёрткам факторов;
- покрытию, потерям и применимости;
- проекции состояния и значимости одной версии правил;
- принадлежности границ диапазона и интервалов.

Разрешены только явно версионированные различия кодирования внешнего протокола
или порядка полей и заданный допуск арифметики с плавающей точкой.

Текущий эталон прямого чтения сравнивает все заполненные блоки событий,
отсчётов, сбросов, состояний и покрытия. Проверки охватывают активный и
запечатанный пути, повторное чтение OVF после перезапуска, границы диапазонов,
идентификаторы, единицы и потери из §7.6. Итоговая проверка `parity-v1`
считается пройденной только по артефакту и CI по правилам §20.

### 17.2 Алгебра проверок свойств

- Проверяемые счётчики событий ассоциативны и коммутативны при отсутствии
  переполнения.
- Объединение покрытия не зависит от разбиения или порядка, пересечение не
  удваивает длительность, а доля всегда лежит в `[0,1]`.
- Объединение максимума, минимума, суммы и числа отсчётов ассоциативно при
  одинаковой семантике ряда.
- Объединение счётчиков использует связывающую пару ровно один раз; сброс или
  пропуск запрещает такую пару.
- Отношение строится из агрегированных числителя и знаменателя, а не из среднего
  отношений.
- Оценка состояния конечна, лежит в `[0,1]` и монотонна для фиксированного
  набора.
- Обязательный пропуск даёт числовую оценку `None`, а не `1.0`.
- Максимум домена не учитывает один подтверждающий факт дважды.
- Перестановка факторов не меняет оценку домена и непрерывную оценку.
- Подтверждение нижнего предела не исчезает при объединении или прореживании.

### 17.3 Метаморфные проверки разбиения и запечатывания

Для сгенерированного канонического потока:

1. Случайно разбить его на 1..100 активных частей и 1..20 запечатанных
   сегментов.
2. Случайно выбрать точку запечатывания и порядок объединения.
3. Запросить выровненные и невыровненные диапазоны и несколько шагов.
4. Сравнить прямой неразбитый путь, только запечатанные данные, запечатанные
   вместе с активными, продвинутые и перестроенные данные.
5. Повторить минимум для 10 000 начальных значений генератора.

Условия приёмки:

- точные целочисленные факты, счётчики, идентификаторы и покрытие совпадают;
- результаты с плавающей точкой совпадают побитно либо укладываются в
  документированный допуск;
- наблюдение на границе принадлежит ровно одному интервалу;
- повторяющиеся временные метки и строки не теряются;
- неполные активные данные никогда не становятся кандидатом запечатанных;
- ограничение ответа меняет только страницу или предварительный просмотр, а не
  авторитетный набор сохранённых данных.

### 17.4 Наборы данных событий

- сгруппированная ошибка с `occurrence_count > 1` остаётся одним элементом;
- ограничение 32 элементов и потери анализатора, средства чтения хвоста или
  словаря делают точность частичной или задают только нижнюю границу;
- представления ошибки жизненного цикла и совместимости не дают два значимых
  события одного сбоя;
- две разные сохранённые строки с одинаковыми `(ts,pid,signal)` остаются
  разными;
- активные и запечатанные данные дают один идентификатор по содержимому;
- повторное сканирование или попытка идемпотентны;
- сигнал 9 не создаёт диагноз или факт OOM;
- PANIC не создаёт диагноз повреждения без подтверждения целостности;
- немедленное завершение не создаёт автоматически нижний предел
  неконтролируемого отказа;
- текущие 11 категорий ошибок и поддерживаемые типизированные виды журнала
  проходят прямое и обратное преобразование;
- курсор проходит набор сохранённых результатов ровно один раз, а срок его
  действия истекает честно.

### 17.5 Наборы данных состояния, сбросов и пропусков

- полный пропуск, только PostgreSQL, только ОС и отсутствующий обязательный
  домен;
- сбой, OOM cgroup или узла, заполнение диска, подтверждение целостности;
- всплеск ошибок аутентификации, соединений или приложения;
- взаимоблокировка, заблокированные сеансы, принудительная контрольная точка;
- опасность закольцовывания счётчика и потеря слота репликации;
- сброс точно на границе сегмента;
- длинный пропуск и разреженная периодичность;
- отсутствующий блок фактора не создаёт нулевое исходное значение;
- худшая точка и нижний предел сохраняются при каждом прореживании;
- штрафы одной возвращённой точки относятся к одному временному срезу.

Эталон разреженной периодичности:

```text
t0  cgroup usage = 0
t5  cgroup sample absent
t10 cgroup usage = 10 CPU-seconds, effective quota = 1 CPU
```

Допустимый интервал равен 10 секундам, а не 5. Скорость равна 100%, а не 200%.
Если непрерывность нельзя доказать, результат равен `None`, а не нулю.
Накопительный счётчик OOM `1 -> 1` не создаёт повторное событие.

### 17.6 Проверки двоичного формата и повреждений

Обязательны модульные проверки, проверки свойств и фаззинг:

- каждое усечение заголовка, каталога или длины блока;
- неверные сигнатура, версия, вид, флаги или зарезервированное поле;
- несовпадение CRC заголовка, каталога или блока;
- переполнение умножения или сложения при разборе каталога;
- пересекающиеся или выходящие за файл смещения, лишние байты и неверная
  точная длина файла;
- для любого включённого в будущем сжатого кодека — бомба распаковки и
  несовпадение декодированной длины;
- слишком большие счётчики, строки и векторы;
- неупорядоченные или повторяющиеся ключи, недопустимые перечисления, NaN и
  бесконечность;
- отсутствующий или неизвестный обязательный блок;
- пропуск неизвестного необязательного ускорителя;
- неверные `source_descriptor`, `FactKey`, `SegmentLineageId`, диапазон или
  длина;
- состязание публикаций, замена устаревшего OVF и очистка собственных временных
  файлов;
- перестроение между версиями без изменения содержимого на месте.

Каждый недопустимый файл фактов либо приводит к резервному прямому чтению, либо
даёт ошибку исходного PGM. Паника или выделение чрезмерной памяти из-за
недоверенных длин запрещены.

### 17.7 Файлы фактов, конкурентность и отмена

- N одновременных промахов одного `FactBuildKey` выполняют одно построение.
- Одинаковый `FactKey` с разными `SegmentLineageId` выполняет независимые
  построения и создаёт независимые резервные записи.
- Отмена первого или последнего ожидающего не оставляет запись реестра.
- Паника или прерывание работника будит ожидающих типизированной ошибкой.
- 16 разных ключей построения не превышают общий бюджет работы, файловых
  дескрипторов и записи.
- Попадания в факты или ответы не занимают разрешение на тяжёлый анализ или
  построение из PGM.
- Изменение поколения или обработанной позиции активных данных инвалидирует
  ключ ответа без гонки TTL.
- `EROFS`, `EACCES`, `ENOSPC`, квота и временная ошибка ввода-вывода
  возвращают корректный ответ из памяти.
- Задержка повторов подавляет шквал записей и сбрасывается после успешной
  пробы.
- Расчёт размера и метрика плотного часа учитывают граничные отсчёты и
  накладные расходы декодирования.
- Гонка сборки мусора не удаляет используемый файл и никогда не касается PGM.

### 18.1 Наборы данных

| Диапазон | Отсчёты |

| 24 часа | 17 280 |

Оценки 4, 96 и 672 сегментов допустимы только в наборе данных с ротацией через
900 секунд без досрочного запечатывания по размеру; реальное число сегментов
измеряется.

Дополнительные наборы данных:

- периодичность с 30% разреженных или отсутствующих отсчётов;
- сброс на границе сегмента;
- повторяющиеся временные метки и побайтово одинаковые строки;
- всплеск FATAL и ошибок до ограничений сборщика;
- явный `pg_log_gap`;
- два соседних сегмента;
- два сегмента с различными `source_descriptor`;
- повреждённый блок фактов;
- повреждённая секция PGM;
- рабочий набор плотного часа;
- смешанная периодичность источников 5, 10, 30, 60 и 3600 секунд.

### 18.2 Режимы

1. `derived-cold`: новый каталог данных с PGM без соседнего OVF и пустое
   состояние процесса.
2. `restart-warm`: новый процесс, допустимый соседний OVF и пустые хранилища
   памяти.
3. `process-hot`: второй и последующие одинаковые запросы.
4. `range-cold/facts-warm`: новый диапазон, шаг или фильтр при наличии фактов.
5. `live`: запечатанные факты, активные части и ожидающий хвост.
6. `concurrent-identical`: 16 одновременных промахов одного набора фактов,
   требующих построения из PGM.
7. `concurrent-disjoint`: 16 одновременных разных диапазонов, требующих
   построения из PGM.
8. `memory-only`: ошибка публикации OVF; факты остаются в памяти с ограничением
   по объёму.
9. `oracle-profile`: зафиксированные исходные данные и файлы фактов, точная
   мощность набора и один версионированный профиль узла и файловой системы.

Новое состояние процесса и холодный накопитель или страничный кэш называются
отдельно. Нельзя выдавать прогретый страничный кэш ОС за холодный накопитель.

### 18.3 Измерения

- задержка по настенным часам p50, p95 и p99;
- время CPU и пиковый RSS;
- открытия, чтения, записи и синхронизации файлов и число байтов;
- декодированные тела, секции и строки PGM;
- прочитанные и декодированные блоки фактов;
- построения, ожидающие запросы, очередь и отказы;
- байты в памяти и на диске и вытеснения;
- задержка видимости активных данных;
- работа сборки мусора, с временными и бесхозными файлами;
- байты сериализованного ответа.

### 18.4 Начальные пороги

Это цели приёмки, а не уже измеренные результаты:

1. Наборы корректности и метаморфные проверки дают 100% семантического
   равенства.
2. Для внутренней части запечатанного диапазона `restart-warm` читает `0`
   байтов тел PGM и декодирует `0` секций PGM.
3. `process-hot`: `0` чтений и декодирований тел PGM и `0` записей OVF; p95 не
   больше 25% p95 режима `derived-cold`.
4. `restart-warm` p95 не больше 25% `derived-cold` p95.
5. `range-cold/facts-warm`: `0` чтений и декодирований тел PGM; p95 не больше
   50% p95 режима `derived-cold` на том же точном наборе данных и профиле.
6. Если HTTP и JSON преобладают в измерении конечной точки, отдельно
   запускается микротест `compact facts read + bucket`; исходные результаты
   обоих измерений сохраняются. В этом случае сравнительные пороги пунктов
   3–5 применяются к отдельному компактному профилю на том же точном наборе
   данных и профиле узла, а измерения конечной точки не удаляются и не
   переименовываются.
7. Для 16 одинаковых одновременных промахов выполняется одно построение фактов,
   возвращаются 16 успешных ответов без перегрузки или 503.
8. Нагрузка разных диапазонов остаётся в общем бюджете; RSS, файловые
   дескрипторы и число построений не выходят за настроенные пределы.
9. p95 видимости завершённого активного кадра не больше 2,5 с при цикле
   обновления раз в секунду; ожидающий хвост явно отмечен.
10. Повышение только версии формулы или значимости даёт ноль чтений PGM и не
    меняет файлы фактов и их время изменения.
11. Фиксированная часть факта метрики измеряется точным числом закодированных
    байтов с относимой долей заголовка и каталога и накладными расходами
    выделения памяти на сохранённый отсчёт. Переменные байты событий и строк
    выводятся отдельно. Если владелец задал бюджеты диска и плотного часа,
    квалификация блокируется при их превышении. Пока значения остаются
    отложенными владельцем по §23, артефакт записывает точные размеры и статус
    `owner_deferred` без решения о пригодности к развёртыванию; это не отменяет
    структурные проверки и проверки ввода-вывода и производительности.
    Универсальное заявление о числе байтов на отсчёт без артефакта запрещено.
12. При нагрузке на квоту устойчивое состояние не выше настроенной квоты, а
    временное превышение не больше ограниченного бюджета выполняющейся
    публикации.
13. Запрос плотного часа только через память остаётся корректным; если рабочий
    набор ниже верхнего предела, повтор обслуживается без чтения PGM.

Графики не входят в наборы данных или пороги §18. Их размер и задержка остаются
неизмеренными до отдельного контракта, утверждённого владельцем.

## 20. Критерии приёмки `parity-v1`

### 20.1 Матрица приёмки и состояние реализации

Все восемнадцать требований реализованы и имеют локальные проверки-кандидаты.
Итоговый `PASS` присваивается всему набору только после успешной проверки
структуры квалификационного артефакта и всех связанных заданий в одной попытке
GitHub Actions на одном точном коммите.

| ID | Обязательное требование | Реализация и проверка-кандидат |
| ---: | --- | --- |
| 1 | После перезапуска допустимый соседний OVF обслуживает внутреннюю часть запечатанного диапазона без чтения тел PGM | `restart-warm` и счётчики ввода-вывода требуют ноль чтений тел и ноль записей |
| 2 | Прямое чтение и индекс дают одинаковый результат для полных и частичных диапазонов, одного и нескольких сегментов, запечатанных и активных данных | Проверки всех семейств фактов сравнивают события, метрики, состояния, покрытие и границы диапазонов с исходным эталоном |
| 3 | Случайное разбиение и запечатывание не создают повторов, потерь или смещения границ | Метаморфные проверки и проверки свойств охватывают происхождение, объединение, граничные отсчёты и переход активных данных |
| 4 | Отсутствующий, повреждённый, несовместимый, слишком большой или чужой OVF перестраивается; ошибка публикации не ломает корректный ответ | Набор проверок контейнера и публикации подтверждает перестроение, атомарную замену и ограниченный резервный слой памяти |
| 5 | Обнаруженное повреждение PGM остаётся видимым пропуском или ошибкой источника и не скрывается старым OVF | Фоновая потоковая проверка CRC исключает повреждённый источник из допустимого набора и не использует его OVF |
| 6 | Изменение формулы состояния или правил краткого списка не перестраивает факты, пока сохранённых измерений достаточно | Эти версии не входят в `FactKey`; проверки версий подтверждают разделение фактов и представления |
| 7 | Каждый сохранённый элемент краткого списка встречается при проходе курсором ровно один раз; групповой счётчик и потери сохраняются | Проверки курсора используют закреплённое представление и канонический порядок событий |
| 8 | Идентификаторы событий сохраняются при обычном переходе активных данных в запечатанные; ограничения идентификатора по содержимому опубликованы | Проверки перехода и разных `SegmentLineageId` не используют путь, имя файла или отдельный идентификатор хранилища |
| 9 | Канонический построитель активных данных не теряет факты; превышение жёсткого предела даёт `Incomplete` и запрещает продвижение | Проверки машины состояний активных данных и продвижения подтверждают оба пути |
| 10 | Пропуск обязательного домена всегда даёт числовое `None`, а не ложное зелёное значение | Наборы данных веб-API и свойства аналитического ядра проверяют неизвестный результат |
| 11 | Доверенный нижний предел сохраняется при разбиении, запечатывании и худшем прореживании; неизвестное значение остаётся неизвестным | Свойства состояния и прореживания проверяют сохранение подтверждений |
| 12 | Для каждого фактора опубликованы покрытие, применимость и потери; один отображаемый коэффициент не служит критерием корректности | Проверки API охватывают все реализованные семейства и причины потерь |
| 13 | Скорости счётчиков используют фактический соседний интервал, семейства сбросов и пропуски; граница файла не меняет результат | Проверка граничных отсчётов охватывает сбросы, пропуски и произвольный диапазон |
| 14 | Каждое семейство имеет проверяемый путь от источника к факту, отсчёту или состоянию с единицами, сбросом, покрытием и потерями | Проверки извлечения охватывают реестр событий и метрик и отвергают неподдерживаемую раскладку явно |
| 15 | Попадания в память и OVF обходят допуск построения; одинаковые `FactBuildKey` объединяются, разные задачи глобально ограничены | Проверки веб-допуска охватывают очередь, взвешенную ёмкость, ожидание, отмену и независимые ключи |
| 16 | Резервный слой памяти ограничен байтами и часами сегментов; повторные попытки наблюдаемы; размер «плотного часа» измерен | Режим `memory-only`, точный учёт памяти и машина восстановления записи входят в квалификационный артефакт |
| 17 | Квота и сборка мусора учитывают производные файлы, безопасны при нескольких читателях и никогда не удаляют источник | Плоское сканирование, единственный владелец, льготный период, повторная проверка inode и сохранение PGM/`active.parts` покрыты набором GC |
| 18 | Все девять режимов §18 воспроизводимо выполняются на зафиксированном профиле узла и файловой системы | Средство `overview_parity_qualification` записывает режимы, размеры, ввод-вывод, задержки, профиль хранения и ссылки на проверки |

### 20.2 Доказательство приёмки

Для каждой строки §20.1 итоговый пакет обязан связать требование с именем
проверки или измерения, схемой набора данных, точным коммитом Git, запуском,
попыткой и заданиями CI, контрольной суммой артефакта, исходным результатом и
решением `PASS` или `FAIL`. Смешивание разных запусков, результат из рабочего
дерева с незакоммиченными изменениями или несовпадающий коммит блокируют
приёмку.

Приёмка обзора охватывает существующие рабочие обработчики и наборы JSON по
OpenAPI. Она проверяет `score=null` и
неизвестное состояние при обязательном пропуске, сохранение доверенного
нижнего предела, явные потери, частичность и применимость, отсутствие
интерполяции и стабильные машиночитаемые поля, не зависящие от языка. Это
приёмка API и слоя представления, а не утверждение о проверке отрисовки
несуществующего пользовательского интерфейса.

В квалификационном артефакте закреплены ровно восемь сценариев BDD: четыре
сценария сквозной временной шкалы и четыре сценария жизненного цикла
`pg_kronika-web`, по одному для PostgreSQL 15, 16, 17 и 18. Вторая группа
запускает настоящий исполняемый файл `pg_kronika-web`, по HTTP обращается к
обработчикам `overview`, `events`, `health` и `cursor`, а также к конечной
точке метрик Prometheus, штатно или принудительно завершает процесс и запускает
новый процесс с тем же отдельным каталогом данных. Она подтверждает:

1. создание соседнего `N.ovf` из запечатанного `N.pgm`, корректность ответа и
   допустимость опубликованного файла;
2. устойчивое повторное чтение без тел PGM и без перезаписи OVF;
3. атомарное восстановление повреждённого или устаревшего OVF при
   несовпадении описателя, схемы фактов, версии извлекателя, реестра или
   происхождения сегмента;
4. отказ от временного остатка незавершённой публикации и восстановление после
   отмены запроса или остановки построения;
5. честный ограниченный резервный ответ при устранимой ошибке публикации,
   последующее создание OVF и устойчивое чтение следующим процессом;
6. истечение курсора прошлого процесса при неизменном содержимом обычных
   ответов, а также однозначный конфликт второго владельца каталога без
   повреждения PGM, `active.parts` или OVF.

Сценарии используют явное сообщение готовности после открытия порта, барьер
публикации и проверку завершения процесса. Фиксированные задержки и циклы
повторных запросов не считаются доказательством. Валидатор артефакта проверяет
точные восемь сочетаний файла и имени сценария из
[таблицы подтверждений приёмки обзора](../../qualification/overview-parity-v1-traceability.md).

## 21. Вехи реализации `parity-v1`

Все этапы входят в `parity-v1`. Постоянные соседние OVF обязательны и не
переносятся в будущую продуктовую веху.

### 21.1 Основные этапы

| Этап | Изменение | Результат |
| --- | --- | --- |
| M0–M4 | PR #97–#103 | Наблюдения и покрытие, выборочное чтение PGM, контейнер PGKOVF, извлечение событий, активные данные, атомарные представления, API временной шкалы, курсоры и точные ответы в памяти |
| Завершение данных | PR #114, `de70586a`–`5454381e` | Канонические события, счётчики, измерения, сбросы и состояния; извлечение метрик; граничные отсчёты; запросы по всем поддерживаемым семействам |
| Устойчивость M5 | PR #114, `4da60055`–`8521384a` | Координация по `FactBuildKey`, взвешенный допуск, очередь и работники, типизированная перегрузка, фоновая проверка источника и полное покрытие API |
| Проверка M6 | PR #114, начиная с `5610686c` | Исходный эталон для всех семейств, квалификационный артефакт, валидатор, девять режимов и строгие локальные и CI-проверки |

Точный итоговый коммит PR #114 указывается квалификационным артефактом и
запуском CI. Промежуточный коммит или смешанные результаты доказательством
приёмки не являются.

### 21.2 Завершение канонических данных

PR #114 заполняет зарезервированные блоки только при доказанном соответствии
источника:

1. `EVENT_FACTS` хранит нейтральные к политике факты с идентификаторами
   подтверждающих наблюдений, групповыми счётчиками, качеством подтверждений и
   происхождением. `NotablePolicy` остаётся проекцией, а
   `IncidentDiagnosis` не сохраняется.
2. `COUNTER_SAMPLES` и `RESET_MARKERS` создаются только для секций PGM с
   доказанными единицами, идентификаторами рядов и сущностей, семейством сброса,
   покрытием и потерями.
3. `GAUGE_SAMPLES`, `ENTITY_STATES` и покрытие факторов строятся из
   естественных отсчётов с временными метками и полных ограниченных составов.
   Готовые точки состояния и интервалы графиков не сохраняются.
4. Неизвестные единицы, сброс, сущность или покрытие дают явный пропуск или
   `UnsupportedLayout`, а не предполагаемое нулевое значение.

### 21.3 M5. Устойчивость и допуск

M5 реализован отдельными проверяемыми частями:

1. Безопасная при отмене координация построения по `FactBuildKey`, включая
   разделение разных `SegmentLineageId`, отмену ожидающего запроса и очистку
   после любого результата.
2. Справедливый взвешенный допуск по байтам PGM, декодированным байтам, строкам
   для обработки, файловым дескрипторам, чтению, записи и публикации; число
   работников, очередь, параллелизм запроса и ожидание ограничены.
3. Состояния записи и задержка повторных попыток для `EROFS`, `EACCES`,
   `ENOSPC`, квоты и временных ошибок ввода-вывода; допускаются одна попытка
   сборки мусора и одна фоновая проба.
4. Квота и безопасная для срока хранения сборка мусора по полному
   авторитетному снимку, двум поколениям и временному льготному периоду.
   Изменять каталог может только владелец; PGM и `active.parts` не удаляются.
5. Ограниченная потоковая проверка CRC исходных секций, после которой
   повреждённый источник не может быть скрыт старым OVF.
6. Метрики §19, точный учёт рабочего набора «плотного часа» и типизированная
   диагностика перегрузки и публикации.

На всех путях сохраняются первоочередное чтение OVF, резервный слой памяти с
двумя пределами, атомарная публикация OVF и атомарная публикация представления.

### 21.4 M6. Итоговая проверка

M6 состоит из отдельных обязательных проверок:

1. Полный эталон прямого чтения, метаморфные проверки разбиения,
   запечатывания и активных данных, а также проверки повреждений и допуска для
   всех реализованных канонических семейств.
2. Версионированный набор «плотный час» и точное измерение декодированного,
   размещённого и закреплённого объёма. Утверждённые пределы развёртывания
   обязательны; до решения владельца артефакт сохраняет `owner_deferred` без
   вывода о допустимости размера.
3. Девять режимов §18 на одном точном профиле узла и файловой системы.
4. Проверки рабочего API и его JSON по §20.2, включая восемь точных сценариев
   BDD PostgreSQL 15–18 и перезапуск настоящего `pg_kronika-web`. Проверки
   отрисовки появляются только вместе с отдельно утверждённым контрактом
   пользовательского интерфейса.
5. Один машиночитаемый артефакт, который связывает все восемнадцать строк
   §20.1 с одной попыткой CI и одним точным коммитом.

Графики не входят в завершение данных, M5 или M6. Возврат к ним требует
отдельного решения владельца, точного перечня рядов, соответствия источникам,
реально поддерживаемого кодека и измеренного изменения размера.

## 22. Явные нецели и отклонённые варианты

### 22.1 Нецели v1

- Изменение средства записи, PGM или контрактов источников сборщиков.
- Точная история каждой строки журнала, если её нет в PGM.
- Согласованность производных данных между узлами.
- Криптографическая подлинность при недоверенном процессе записи без
  отдельного требования безопасности.
- Использование OVF как архива после удаления PGM.
- Неограниченный предварительный прогрев всего срока хранения.
- SSE до стабилизации представлений и курсоров.
- Новый крейт только для фактов обзора.
- Сохранение `IncidentDiagnosis` как факта источника.
- Универсальная вероятность «здоровья» без калибровочного набора и исхода.

### 22.2 Отклонённые физические варианты

**Принадлежащие средству записи `.heatmap` или `.charts`.** Такой вариант
замораживает семантику скоростей и состояния, меняет владельца PGM и требует
перестраивать данные при изменении формулы.

**Глобальный дописываемый производный индекс.** Для v1 он создаёт второй журнал
предзаписи с кадрами, блокировками, надгробиями, уплотнением и широкой областью
последствий повреждения.

**Гибридные объекты с авторитетным манифестом.** Авторитетный каталог
сегментов и диапазонов уже даёт считывателю снимок, а манифест не устраняет
выборочное чтение нескольких полезных нагрузок. Восстанавливаемая подсказка
допустима позже, если измерения докажут узкое место при запуске, сканировании
каталога или сборке мусора либо появится второй потребитель.

**Только LRU в памяти.** Не обеспечивает быстрый путь после перезапуска и для
многодневного диапазона.

**Только постоянные точные ответы.** Не заменяют факты: новый диапазон, шаг или
фильтр снова потребует чтения PGM, а правила признания ответа устаревшим станут
комбинаторными.

**Сводка событий на весь сегмент.** Недостаточна для произвольного частичного
диапазона, скоростей с учётом сбросов и стабильной постраничной выдачи.

**Заранее вычисленные `HealthPoint` или краткий список.** Изменение правил
потребует перестроения, а объединение готовых штрафов и оценок нарушит
инвариантность разбиения.

**Краткий список активных данных с потерями.** Несовместим с авторитетной
сохранённой выдачей `/events` и продвижением после запечатывания.

**Интерполяция пропусков.** Запрещена для состояния и непрерывности счётчиков:
она изображает данные, которых источник не наблюдал.

## 23. Оставшиеся продуктовые решения

Следующие решения уже закрыты:

- `KRONIKA_WEB_DIR` — один каталог, который целиком принадлежит PgKronika;
  `active.parts`, `N.pgm` и `N.ovf` находятся рядом, а PGM и OVF имеют
  одинаковую основную часть имени;
- дополнительного корня, уровня каталогов, идентификатора хранилища, хеша пути
  и производного имени файла нет; `FactKey`, происхождение и версии контрактов
  остаются проверяемыми данными заголовка;
- графики отложены владельцем и не входят в `parity-v1`; их стоимость не
  измерена;
- пока рабочего пользовательского интерфейса нет, итоговая проверка
  `parity-v1` охватывает API и его JSON, но не заявляет покрытие отрисовки.

Открыты четыре калибруемых продуктовых решения:

1. Конкретные кривые факторов, обязательные профили и пороги состояния после
   выбора измеримого исхода и калибровочных наборов.
2. Пределы диска, памяти, файловых дескрипторов, очереди построения и времени
   жизни курсора для конкретного развёртывания в пределах абсолютных
   ограничений безопасности.
3. Описания обслуживания и топологии, которые позволят подавлять плановое
   завершение и определять обязательных участников репликации.
4. Объём, отрисовка и локализация будущего рабочего пользовательского
   интерфейса, если владелец решит его добавить.

Отсутствие калибруемых значений не ослабляет обязательные проверки данных,
структуры, ввода-вывода и производительности и не означает одобрения размера
для развёртывания. Заданные значения становятся обязательными проверками
развёртывания. Их изменение версионирует правила или конфигурацию, но не меняет
PGM, физическое соответствие PGM/OVF или инварианты честности данных.
