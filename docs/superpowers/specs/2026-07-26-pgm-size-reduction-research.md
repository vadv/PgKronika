## Краткий вывод

Для готового `N.pgm` следует заменить текущую внутреннюю раскладку на месте
(in place) единым компактным физическим контрактом:

- одна секция на каждый непустой `type_id`;
- не более одной секции `dict.strings` и одной `dict.blobs`;
- проверенная дедупликация словаря по `str_id`;
- каноническая сортировка строк по контракту реестра;
- одна группа строк и одна страница данных на column chunk в пределах
  действующих ограничений секции;
- `PLAIN` без Parquet dictionary encoding;
- без статистики, column index и offset index;
- Zstandard уровня 6;
- детерминированный порядок секций и метаданных.

Публичный формат и имя файла остаются прежними: PGM и `N.pgm`. Будущая
реализация должна одним PR с чистым разрывом заменить существующие writer,
reader и внутренний format contract. После этого файлы прежней раскладки не
читаются, не преобразуются, не ищутся запасным путём и не включаются
переключателем.

В продукте остаются один PGM writer, один PGM reader и один контракт. Проект
ещё не выпускался, поэтому чистый разрыв дешевле постоянной ветки
совместимости.

Три естественных полных 15-минутных сегмента PostgreSQL 17.10 сократились с
58 232 836 до 1 596 766 байт суммарно. Для размера обновлённого файла:

| Метрика | Значение |
|---|---:|
| p50 | 524 989 байт |
| p95, nearest-rank | 549 761 байт |
| худший файл | 549 761 байт |
| взвешенный коэффициент | 36,469x |
| худший коэффициент | 35,343x |

При `n=3` empirical nearest-rank p95 неизбежно совпадает с максимумом. Это
описание наблюдаемой маленькой выборки, а не оценка хвоста генеральной
совокупности.

Отдельный восстановленный хвост длиной 62,52 секунды сократился с 1 349 538
до 224 339 байт, или в 6,016 раза. Его номинальные p50, p95 и worst равны
224 339 байтам, потому что наблюдение одно. Хвост не смешивается с полными
сегментами.

Для каждого файла доказаны:

- равенство множества семейств данных;
- точное равенство канонических Arrow batches каждого `type_id`;
- равенство нормализованного словаря;
- успешное чтение кандидата reader-ом той же ревизии;
- сохранение `source_id`, `min_ts` и `max_ts`.

На естественных полных сегментах сохранились 43 из 43 семейств. На хвосте —
42 из 42. Искусственный fixture охватывает все 75 зарегистрированных
контрактов и сохраняет 2 400 из 2 400 строк данных.
Полный отсортированный список `type_id` и SHA256 инвентаризации контрактов
зафиксированы в machine-readable summary: так проверяется не только число
семейств, но и отсутствие подмены одного контракта другим.

Предыдущая приблизительная оценка не является итогом этого исследования.
Она не создавала PGM, не проверяла round trip и оставляла непроверенные
случаи словаря. В дальнейшем следует ссылаться только на распределение выше
и явно указывать состав корпуса.

## 1. Границы исследования

Документ отвечает на один вопрос: как физически уменьшить готовый `N.pgm`,
не меняя строки, словари и временной охват.

В границы входят:

- структура секций внутри готового PGM;
- Parquet encoding и Zstandard;
- точная идентичность строк и словаря;
- стоимость записи, открытия и чтения;
- взаимодействие с производным `N.ovf`;
- ограниченная по памяти финализация;
- атомарная публикация и аварийные точки;
- семантика PostgreSQL 15–18;
- полный набор тестов и критериев приёмки будущего PR.

В границы не входят:

- retention и оценка объёма в час, день или год;
- изменение логических схем и `type_id`;
- изменение семантики counter, gauge, coverage или gap;
- сжатие OVF;
- раскладка каталогов готовых сегментов;
- архиватор, dump и миграция старых файлов.

Отдельное исследование раскладки каталогов выбрало UTC-дерево
`YYYY/MM/DD` с соседними `N.pgm` и `N.ovf`. Настоящий документ не повторяет
его обход, GC, грамматику пути или правила восстановления. Единственная
точка стыка: временный PGM создаётся и синхронизируется в том же дневном
каталоге, где будет опубликован итоговый `N.pgm`; OVF остаётся его отдельным
соседом.

### 2.5. Процентили

В JSON используется один алгоритм:

```text
nearest_rank(values, p) = sort(values)[ceil(p * n) - 1]
```

Для коэффициента худшим считается минимум, потому что меньший коэффициент
означает худшее сокращение. Для байтов, времени и RSS худшим считается
максимум.

Нельзя:

- интерполировать p95 для трёх элементов и смешивать его с nearest-rank;
- включать 62-секундный хвост в ряд 15-минутных файлов;
- называть p95 из трёх файлов устойчивой оценкой хвоста;
- выводить из этого корпуса объём хранения в час.

## 3. Рекомендуемый физический контракт

### 3.1. Чистый переход на месте

PGM остаётся единственным основным форматом контейнера. Имя готового файла
остаётся `N.pgm`, а его канонический путь — `YYYY/MM/DD/N.pgm`.

Реализация атомарно заменяет:

- текущую внутреннюю раскладку PGM;
- единственный PGM writer;
- единственный PGM reader;
- внутренние проверки writer, reader, journal и store.

Существующие магическое число заголовка и поле `format_version` образуют
внутреннюю сигнатуру, по которой несовместимый файл отклоняется до разбора
данных. Запрос на слияние с реализацией может сменить эту пару вместе с
раскладкой, но после изменения код принимает только одно текущее значение.
Никакой второй версии формата рядом не появляется. Публичные названия PGM,
расширение `.pgm` и HTTP API `/v1` из-за этого не меняются; согласование версий
не добавляется. Внутренняя сигнатура не обозначает новую версию продукта или
API.

В реализации отсутствуют:

- writer и reader прежней внутренней раскладки;
- автоматическое или ручное преобразование прежних PGM;
- двойной обход;
- резервное чтение старого файла;
- флаг функции, переменная окружения или режим времени выполнения;
- отдельный уплотнитель опубликованных сегментов.

Файл прежней внутренней раскладки в рабочем каталоге означает несовместимые
данные. Ошибка должна быть явной и типизированной. Молчаливое игнорирование
выглядело бы как пустая история.

### 3.2. Секции данных

Готовый сегмент содержит ровно одну секцию для каждого непустого
недictionary `type_id`.

Порядок секций:

1. data `type_id` по возрастанию;
2. `dict.strings`, если непуст;
3. `dict.blobs`, если непуст.

Тела идут подряд сразу после header, без gaps и overlap; затем идут catalog
и tail index. Reader до allocation ограничивает catalog length и entry count,
проверяет уникальность `type_id`, монотонные offsets, bounds, rows, CRC32C и
точное окончание последнего тела у catalog. Неизвестные flags и trailing
bytes отклоняются.

Внутри data-секции строки сортируются по полному каноническому sort key из
реестра. Стабильность исходного catalog order не используется как
доказательство порядка.

Sort key не обязан быть уникальным. Для разных строк с одинаковым sort key
writer применяет стабильный побитовый tie-breaker по всем остальным колонкам
в порядке schema: маркер NULL, затем canonical physical representation.
Для float сравниваются биты, поэтому NaN payload и signed zero сохраняются.
Полностью одинаковые строки сохраняют multiplicity; их перестановка не меняет
байты. Благодаря этому результат не зависит от разбиения и порядка входных
sections.

Действующие ограничения остаются абсолютными:

- не более 65 536 строк в секции;
- не более 8 МиБ закодированного тела;
- одна группа строк для готовой секции;
- одна data page на column chunk в пределах фиксированного page budget.

Если добавление следующего collection window превысит строковый,
словарный, per-column page или байтовый предел хотя бы одного будущего
объединённого типа, коллектор сначала финализирует накопленный сегмент.
Планировщик использует консервативные decoded-size bounds реестра и Parquet
framing overhead, а не предполагаемый коэффициент сжатия. Строки не
отбрасываются и не делятся по двум одинаковым `type_id` внутри готового PGM.
Одно окно, которое само нарушает предел, завершается прежней типизированной
ошибкой источника или буфера.

### 3.3. Словарь

Для каждого сегмента writer строит одно нормализованное отображение
`str_id -> Stored`.

Обязательные проверки:

- ID в каждой входной секции строго возрастают;
- ID строки совпадает с хешем её полных байтов;
- untruncated blob имеет `stored_len == full_len`, не содержит
  `full_sha256`, а его ID совпадает с полными байтами;
- truncated blob имеет `stored_len < full_len` и `full_sha256`;
- одинаковый ID с одинаковым представлением схлопывается;
- одинаковый ID с разными байтами или метаданными — ошибка;
- один ID должен находиться ровно в одном из `dict.strings` и `dict.blobs`;
  любое двойное размещение отклоняется, даже если доступные байты совпали;
- ID `0` не кодируется.

Выход сортируется по ID. Между двумя запусками над одинаковыми входными
байтами порядок и результат не зависят от порядка dictionary sections.

В трёх полных сегментах было 200 953 dictionary rows и 10 152 уникальных
ID в сумме по сегментам. Удалено 190 801 повторение:

| Сегмент | Строки словаря | Уникальные ID | Удалено |
|---|---:|---:|---:|
| 1 | 68 470 | 3 415 | 65 055 |
| 2 | 66 351 | 3 377 | 62 974 |
| 3 | 66 132 | 3 360 | 62 772 |
| хвост | 4 891 | 2 707 | 2 184 |

Дедупликация выполняется только внутри одного PGM. Межсегментный общий
словарь изменил бы независимость и жизненный цикл сегментов и здесь не
рассматривается.

### 3.4. Parquet

Финальный профиль эксперимента:

| Свойство | Значение |
|---|---|
| writer version | Parquet 1.0 |
| compression | Zstandard |
| level | 6 |
| max row group | 65 536 rows |
| data page size | 1 048 576 bytes в эксперименте |
| data page row limit | 65 536 |
| dictionary encoding | disabled |
| column encoding | `PLAIN` |
| statistics | none |
| column index | disabled |
| offset index | disabled |
| `created_by` | empty |

Параметр 1 МиБ — настройка writer, а не новый предел тела секции. На
измеренном корпусе у каждого column chunk одна data page. Реализация должна
закрепить одностраничность планировщиком и тестом для предельных
зарегистрированных схем, включая единственное допустимое значение, размер
которого превышает целевой размер страницы, а не полагаться на приблизительную
эвристику Parquet writer. Если граница не доказывается до encode, окно не
добавляется в текущий сегмент.

Уровень 6 — инженерная точка, а не поиск математического оптимума.
Дополнительный перебор уровней не входит в следующий PR, если новый корпус
не покажет конкретного противоречия.

## 4. Доказательство идентичности

### 4.1. Строки данных

Проверка не сравнивает только число строк. Для каждого недictionary
`type_id` она:

1. декодирует все исходные секции;
2. строит один batch;
3. сортирует по полному sort key реестра;
4. декодирует кандидат;
5. требует точного равенства Arrow `RecordBatch`.

Перед сравнением требуется равенство множеств `type_id`, а затем точное
равенство строк каждого присутствующего типа. Поэтому семейство нельзя
потерять незаметно, даже если суммарное число строк случайно совпало.
Ожидаемое отсутствие пустых зарегистрированных типов проверяется отдельно.

Результат:

| Корпус | Ожидалось типов | Найдено в кандидате | Строки source/candidate |
|---|---:|---:|---:|
| полный сегмент 1 | 43 | 43 | 71 638 / 71 638 |
| полный сегмент 2 | 43 | 43 | 69 748 / 69 748 |
| полный сегмент 3 | 43 | 43 | 69 537 / 69 537 |
| хвост | 42 | 42 | 4 978 / 4 978 |
| fixture реестра | 75 | 75 | 2 400 / 2 400 |

Будущий writer обязан фиксировать:

- порядок секций;

### 4.4. Ошибки и повреждения

Постоянный fault corpus дал ожидаемые результаты:

| Случай | Текущий reader | Исследовательский encoder |
|---|---|---|
| одинаковый ID и значение в нескольких секциях | принимает | дедуплицирует |
| обратный порядок dictionary sections | принимает | даёт те же итоговые байты |
| одинаковый ID, разные значения | текущий reader last-wins | отклоняет до публикации |
| несовместимое strings/blobs placement | текущий reader принимает | отклоняет до публикации |
| descending IDs | отклоняет | отклоняет |
| duplicate ID в одной секции | отклоняет | отклоняет |
| повреждённое тело | CRC error | не публикует |
| повреждённый каталог | catalog CRC error | не публикует |
| tail короче на один байт | tail-index error | не публикует |

Корпус создан командой `pgm_lab fault-cases OUT_DIR` и содержит 11 файлов.
Их имена, размеры и полные SHA256 находятся в JSON. Два результата для
прямого и обратного порядка секций имеют один SHA256:

```text
8d7fc38fcda7c9a0412f4252d4d0a273994d7c3edec4a32bfb1f8518bb224e46
```

конфликтов. Конфликтный словарь означает повреждённый источник.

## 5. Откуда берётся сокращение

### 5.1. Исходная структура первого сегмента

```text

             + 9 587 708 Parquet structural bytes
             +   124 756 PGM framing bytes
```

Parquet structural bytes состоят из:

```text

1 610 664 column indexes
  604 091 offset indexes
```

То есть 49,3% исходного файла — не compressed chunks. Причина — 3 897
маленьких Parquet sections.

### 5.2. Два независимых структурных изменения

Для причинности использованы два current-like ZSTD-3 counterfactual:

| Вариант | Байты | Секции | Экономия |
|---|---:|---:|---:|
| source | 19 430 424 | 3 897 | — |

| дедуплицировать только dictionary | 16 723 406 | 3 312 | 2 707 018 |

```text

19 430 424 -   953 639 = 18 476 785
```

Каждая строка таблицы — отдельный сохранённый PGM. Полные SHA256 всех
counterfactual и четырёх последовательных профилей находятся в JSON; это
исключает подмену byte accounting расчётной моделью.

Объединение data:

```text

8 849 039 Parquet structural
  104 544 PGM framing
```

Дедупликация dictionary:

```text

  597 441 Parquet structural
   18 720 PGM framing
```

Эти значения — измеренные counterfactual целых файлов. Они включают
повторное кодирование current-like writer properties и не выдаются за
теоретическую энтропию данных.

### 5.3. Footer, catalog и page indexes

После coalescing и dictionary dedup число секций падает с 3 897 до 45.

```text

```

В полном current-like кандидате остаётся:

```text

  9 212 offset index
```

Из них 2 182 217 байт исчезают как следствие уменьшения числа column chunks.
Явное выключение indexes убирает оставшиеся 32 538 байт.

PGM framing уменьшается с 124 756 до 1 492 байт. Это экономия 123 264 байт

### 6.2. Требуемая потоковая архитектура

Рабочая реализация финализации не должна читать целый журнал или все секции
одного типа в оперативную память.

Путь записи:

1. Потоково просканировать кадры журнала и каталоги, проверить их ограничения
   и собрать только ограниченный набор дескрипторов. Все размеры и смещения
   рассчитываются с проверкой переполнения; `try_reserve` вызывается до роста
   коллекций.
2. До принятия очередного окна сбора учитывать для каждого типа пределы строк,
   закодированных байтов, страниц столбцов и кардинальности словаря. При
   прогнозируемом переполнении финализировать предыдущий сегмент.
3. Для каждого `type_id` декодировать не более одного ограниченного входного
   пакета за раз.
4. Проверить локальную сортировку. Несортированный пакет преобразовать во
   временную серию с фиксированным числом строк.
5. Если диапазоны ключей последовательных пакетов не пересекаются, передавать
   их модулю записи напрямую. Иначе выполнить ограниченное многопутевое
   слияние временных серий. Оба пути передают небольшие выходные пакеты одному
   модулю записи Parquet и используют канонический физический ключ строки из
   раздела 3.2 для разрешения равенства.
6. Секции словаря сливать по идентификатору тем же ограниченным алгоритмом.
   В памяти держать только головы временных серий и текущую группу одинакового
   идентификатора.
7. После каждого типа освобождать модуль чтения, массивы Arrow и буферы слияния
   до перехода к следующему.

Каталог ограничен 64 МиБ и записывается потоково без второго буфера каталога.
Перед публикацией модуль записи повторно проверяет CRC каждой секции.

Нужен отдельный `SealWorkBudget`, учитывающий:

- дескрипторы;
- буферы декодированных данных Arrow;
- индексы сортировки;
- головы потоков слияния;
- выходной пакет;
- внутренний буфер Parquet row group;
- состояние проверки конфликтов словаря.

Рекомендуемый жёсткий предел для первой реализации — 128 МиБ сверх
долгоживущего состояния коллектора. Переполнение возвращает типизированный
`SealError::WorkBudgetExceeded`, не приводит к неограниченному выделению
памяти и не сбрасывает журнал. Ширина слияния и число строк пакета — константы
внутри этого бюджета, а не неограниченные параметры среды.

Оценка encoded bytes до Zstandard не может быть оптимистичной. Planner
доказывает предел через верхнюю оценку несжатого размера зарегистрированной
schema и ограниченный Parquet overhead, а готовое тело повторно проверяется
против 8 МиБ. Ошибка окончательной проверки сохраняет journal и не публикует
PGM.

Временные runs ограничены валидированной длиной journal и отдельным disk
budget. Они создаются рядом с итоговым файлом через `create_new`, имеют
закрытую грамматику имён и не видны reader-у. Нельзя одновременно хранить
неограниченное число поколений runs: одновременно допустимы только текущая и
следующая merge generation, а каждый записанный байт предварительно
резервируется в `SealDiskBudget`.

Проверка памяти будущего PR обязана показать:

- peak incremental RSS не более 96 МиБ на замороженных 20-МиБ сегментах;
- не более 128 МиБ на искусственном journal 1 ГиБ;
- рост RSS между 256 МиБ и 1 ГиБ входа не более 10%;
- типизированный отказ до превышения budget на враждебных schemas и
  cardinality.

Числа 96/128 МиБ — критерии реализации, а не результат текущего prototype.

## 8. OVF считается отдельно

OVF не является заменой или compressed representation PGM. PGM остаётся
источником, а OVF — производным sibling со своей идентичностью.

### 8.1. Отрицательный результат 46-минутного корпуса

Исходные PGM без изменений и кандидат запускались в отдельных сохраняемых
каталогах и контейнерах. Оба остановились на первом сегменте:

```text
source integrity check failed
```

Следствия:

- ошибка уже существует на исходном PGM;
- coalescing её не создаёт и не скрывает;
- для 46-минутного корпуса OVF bytes неизвестны;
- подставлять размер из другого файла или экстраполировать запрещено.

Это ограничение текущего `FactStore` extractor, а не доказательство
повреждения PGM: reader и полное равенство Arrow проходят.

### 8.2. Успешный двухсегментный mechanism corpus

На сохранённом корпусе, где текущий OVF строится успешно, к обоим PGM
применён тот же кандидат и заново построены sibling OVF.

считается устаревшим и не читается; новый sibling строится только из текущего
PGM штатным lifecycle. Это не вводит второй PGM reader.

## 9. PostgreSQL 15–18

Физический transform выполняется после version-specific PostgreSQL adapters.
Он не интерпретирует SQL, major version или смысл колонок. Он использует
только зарегистрированные `type_id`, schema и sort key.

Что доказано сейчас:

- исходная ревизия прошла BDD на PostgreSQL 15–18;
- естественные PGM созданы PostgreSQL 17.10;
- synthetic fixture покрывает все 75 зарегистрированных layouts;
- exact equality покрывает все типы, встреченные в естественном корпусе.

Что не доказано:

- естественный размер PGM от PostgreSQL 15, 16 или 18;
- обновлённые writer/reader на живой матрице;
- обновлённый OVF lifecycle на живой матрице.

Поэтому будущий implementation PR обязан прогнать полный producer → journal
→ обновлённый PGM → restart reader/web → OVF путь отдельно на PG15, PG16,
PG17 и PG18.
Nullable/version columns сохраняются как часть соответствующего `type_id`;
writer не объединяет разные layouts под одним ID и не угадывает major.

## 10. Отказоустойчивая финализация

Порядок публикации обновлённого PGM:

1. Вычислить итоговый путь по уже принятому `SegmentId`.
2. В том же каталоге создать уникальный временный файл через `create_new`.
3. Потоково записать магическое число, тела секций, каталог размером не более
   64 МиБ и концевой индекс. Второй буфер каталога не создаётся.
4. Сбросить буфер пользовательского пространства.
5. Вызвать `sync_all` временного файла.
6. Переоткрыть временный файл единственным обновлённым модулем чтения PGM,
   повторно проверить CRC каждой секции, обрамление, каталог, физические
   инварианты и ожидаемую идентичность.
7. Опубликовать без перезаписи существующего `N.pgm`. Основной Linux-вариант
   — `renameat2(RENAME_NOREPLACE)`: имя временного файла исчезает в той же
   операции. Допустимый вариант в той же файловой системе — жёсткая ссылка,
   которая сохраняет временное имя до отдельного `unlink`. Обычный
   `rename` с перезаписью запрещён.
8. Вызвать `fsync` родительского дневного каталога, чтобы итоговый файл стал
   долговечным.
9. Только при публикации через жёсткую ссылку удалить собственное временное
   имя и ещё раз вызвать `fsync` каталога.
10. Только после успешной публикации сбросить `active.parts` его собственным
    отказоустойчивым протоколом.

Сбой до шага 8 не позволяет считать итоговый файл долговечным. Сбой между
шагами 8 и 10 может оставить и готовый PGM, и журнал; снимок обязан устранить
точный дубль, а журнал нельзя терять. Устаревший временный файл не считается
PGM и удаляется владельцем только после проверки по закрытой грамматике.

Повтор после такого сбоя обязан быть идемпотентным. Если итоговый файл уже
есть, модуль записи с соблюдением тех же лимитов повторяет детерминированный
план и требует точного совпадения длины и SHA256 готовых байтов. Затем текущий
модуль чтения проверяет `SegmentId`, `source_id`, временной диапазон, множества
типов, строки и нормализованный словарь. Полное совпадение означает
`AlreadyPublished` и разрешает долговечный сброс журнала; любое различие
означает `DestinationConflict`. Ни один вариант не перезаписывает файл.

Прежний `active.parts` или PGM не является пустым store. Collector/web
останавливается с типизированной ошибкой несовместимой раскладки и сохраняет
байты без reset, truncate или автоматического удаления. Разрыв совместимости
не разрешает терять старый журнал.

Ошибки, которые должны оставаться различимыми:

- invalid frame/catalog/section;
- unsupported or conflicting dictionary;
- noncanonical row order;
- row, byte, cardinality, work-memory или disk-work budget;
- `AlreadyPublished` и `DestinationConflict`;
- `ENOSPC`, `EDQUOT`, `EROFS`, `EIO`;
- file sync;
- directory sync;
- publish race;
- post-write verification.

Границы библиотек возвращают исчерпывающие типизированные enum с исходным
`io::Error`, операцией и безопасным путём; binary может добавить контекст
`anyhow` только снаружи. Повреждение, исчерпание бюджета, несовместимая
раскладка, конфликт destination и повторяемая filesystem error не
сворачиваются в одну строку. Allocation и integer overflow не должны
приводить к panic.

Ни одна ошибка не сбрасывает journal и не публикует частичный destination.

## 11. Один будущий implementation PR

Следующий PR должен быть завершённым вертикальным изменением. Разносить
writer и reader по релизам нельзя: чистый разрыв не допускает состояния, в
котором одна сторона пишет формат, который другая не читает.

### 11.1. Код

1. `kronika-format`
   - заменить существующую внутреннюю раскладку PGM in place;
   - сменить внутреннюю пару «магическое число/версия» как единую сигнатуру
     раннего отказа и принимать только её;
   - синхронно обновить внутренний PGM part внутри `PGMP`;
   - проверить физические инварианты каталога готового сегмента;
   - типизированные ошибки обновлённого контракта;
   - прежнюю внутреннюю раскладку полностью удалить из production path.
2. `kronika-registry`
   - общий канонический comparator/sort projection по контракту;
   - вычислимые decoded-memory bounds зарегистрированных schemas.
3. `kronika-writer`
   - bounded planner и external merge;
   - dictionary normalization/conflict detection;
   - фиксированные writer properties;
   - `SealWorkBudget` и disk-work budget;
   - post-write verification;
   - отказоустойчивая публикация без перезаписи;
   - idempotent `AlreadyPublished` и typed `DestinationConflict`.
4. `pg_kronika-collector`
   - per-type и dictionary projected budgets;
   - досрочная финализация до нарушения контракта единственной секции;
   - incompatible `active.parts` останавливает startup без reset/truncate;
   - метрики bytes, rows, sections, wall, CPU, budget high-water и failures.
5. `kronika-reader`
   - единственный reader обновлённого PGM;
   - проверка единственности `type_id`, dictionary и physical properties;
   - decoded-size bounds и `ReadWorkBudget` до allocation;
   - сохранение query, diff и OVF semantics;
   - привязка `SourceManifest` только к текущей PGM identity.
6. `kronika-store`
   - явная диагностика прежней внутренней раскладки как incompatible store;
   - ошибка startup вместо пустого snapshot;
   - без резервной ветки чтения и двойного обхода каталогов.
7. demo, BDD и документация
   - новый reproducible fixture;
   - отчёт PGM/OVF/PGM+OVF;
   - удалить или заменить предварительный ignored estimator;
   - обновление crate README на русском и английском;
   - сохранить названия PGM, `.pgm` и HTTP API `/v1` без negotiation.

UTC `YYYY/MM/DD` и sibling path реализуются по отдельному решению. Если оно
уже в `main`, единственный PGM writer использует его API. Этот PR не
переоткрывает выбор раскладки.

### 11.2. Unit, property и fault tests

Обязательный набор:

- все 75 contracts, включая nullable/list/string/blob columns;
- точное равенство rows и type sets;
- exact normalized dictionary equality;
- identical duplicates, conflicts и strings/blobs overlap;
- входные dictionary sections во всех перестановках;
- входные data sections во всех перестановках и с разными batch boundaries;
- descending и duplicate IDs;
- duplicate data/dictionary `type_id` в итоговом catalog;
- empty types и естественно отсутствующие families;
- разные tie rows по sort key с canonical all-column tie-breaker;
- min/max `i64`, NaN bit patterns, signed zero и nullable values;
- предельные 65 536 rows, 1-МиБ page target и 8-МиБ section body;
- exact writer properties, одна row group и доказанная одна data page на
  допустимый column chunk;
- проверка досрочной финализации с запасом в одну строку или идентификатор до
  переполнения;
- deterministic bytes при 100 повторениях и разных chunk boundaries;
- byte-identical результат direct-concatenation и external-merge путей;
- corrupt body/catalog/tail;
- повреждённый Parquet с пересчитанным внешним section CRC;
- truncated input на каждой framing boundary;
- unknown type, schema mismatch и слишком крупные метаданные Parquet;
- compressed expansion выше `ReadWorkBudget` до Arrow allocation;
- checked-arithmetic overflow и отказ `try_reserve`;
- `AlreadyPublished` exact match и `DestinationConflict`;
- отказ на прежней внутренней раскладке в writer, reader, store, collector и
  web startup без изменения исходных байтов.

Property tests должны генерировать несколько входных sections каждого типа,
сравнивать обновлённый PGM с canonical in-memory oracle и проверять, что ни
один row key не потерян и не продублирован.

### 11.3. BDD PostgreSQL 15–18

Для каждого major:

1. Создать живую базу и известные PostgreSQL/OS/log состояния.
2. Собрать не менее двух collection windows.
3. Финализировать обновлённый `N.pgm`.
4. Проверить единственную текущую внутреннюю пару «магическое число/версия» и
   контракт единственной секции.
5. Сравнить rows с существующим floor oracle.
6. Перезапустить настоящий web process.
7. Выполнить section, diff, timeline, anomaly и incident smoke paths.
8. Построить sibling OVF и прочитать его новым процессом.
9. Проверить exact PGM/OVF stem и отсутствие PGM body reads на valid OVF hit.
10. Повторить с Unix socket там, где проверяются local joins; TCP остаётся
    отдельным ожидаемым режимом без local-join families.

Ни один major не может быть заменён synthetic fixture.

### 11.4. Сбои и файловые системы Linux

Fault injection после каждого шага раздела 10:

- до/после flush;
- до/после file `sync_all`;
- до/после no-replace publish;
- до/после первого directory `fsync`;
- до/после unlink temp в hard-link protocol;
- до/после второго directory `fsync` в hard-link protocol;
- до/после journal reset.

После каждого simulated restart проверяются:

- либо старый journal полностью доступен;
- либо обновлённый PGM полностью доступен;
- допустимы оба с точной dedup;
- частичный PGM никогда не виден;
- существующий destination не перезаписан;
- exact destination даёт `AlreadyPublished`, отличный —
  `DestinationConflict`;
- unknown temp не удалён;
- собственный stale temp убирается идемпотентно;
- несовместимый PGM или journal остаётся byte-identical.

Матрица запускается минимум на ext4 и XFS. Для Linux syscall contract
сохраняется `strace`; power-loss claims не выводятся из обычного process kill
без fsync fault model. Network filesystems и cross-filesystem publish в этот
контракт не входят; temp всегда создаётся в каталоге destination.

### 11.5. Benchmark acceptance

На выделенном узле с зафиксированными CPU governor, kernel, filesystem и
cache mode:

| Профиль | Критерий |
|---|---|
| три замороженных полных сегмента | worst candidate ≤ 600 000 байт |
| те же сегменты | weighted reduction ≥ 32x |
| encode | p95 ≤ 5 с |
| encode RSS | p95 ≤ 96 МиБ |
| full-decode reader RSS | p95 ≤ 32 МиБ на замороженном корпусе |
| 1-ГиБ synthetic journal | peak incremental RSS ≤ 128 МиБ |
| 256 МиБ → 1 ГиБ | рост peak RSS ≤ 10% |
| `LocalDirSnapshot` rebuild | candidate p95 ≤ 150 мкс |
| `pg_stat_activity` query | candidate p95 ≤ 30 мс |
| query I/O | ≤ 16 `pread64`, ≤ 150 КиБ |
| determinism | exact bytes across repetitions |

Эти thresholds — regression gates на указанном profile, не обещание
пользователю. Raw samples, toolchain, kernel, CPU, filesystem, cache policy,
commit и hashes входят в artifact.

Для CI без выделенного узла остаются функциональные и byte-exact synthetic
gates; нестабильные wall/RSS thresholds туда не переносятся.

## 12. Отклонённые варианты

### Offline rewrite опубликованных PGM

Меняет identity и CRC после публикации, создаёт гонки с reader/OVF и требует
миграционного lifecycle. Отклонён.

### Dual reader или feature toggle

Удваивает format surface и оставляет старый путь бессрочно. Отклонён.

### Whole-file compression

Ломает tail-first catalog open и выборочное чтение. Контрольный результат
полезен только как доказательство повторяемости. Отклонён.

### Сохранить много sections, поднять Zstandard

Не удаляет тысячи footer/catalog/index envelopes. Уровень compression не
лечит основную причину. Отклонён.

### Общий dictionary между сегментами

Нарушает self-contained PGM и связывает retention. Отклонён.

### Сжимать OVF вместо PGM

OVF производный и не заменяет источник. Это отдельная задача. Отклонён.

## 13. Ограничения результата

- Естественный producer — только PostgreSQL 17.10.
- Полных сегментов три.
- Хвост один и вынесен отдельно.
- Fixture синтетический.
- Все естественные файлы имеют `source_id = 0`; non-zero `source_id`
  проверен fixture со значением `8099562711456768513`.
- Page cache прогрет, узел общий.
- Измерения restart строят новый `LocalDirSnapshot`, но не запускают новый
  процесс.
- Прототип не потоковый и целиком материализует merged batches.
- Исходный код прототипа не входит в PR; его запуск связан полным SHA256
  бинарника, грамматикой команд и SHA256 файлов. Независимый production
  encoder ещё предстоит реализовать.
- 46-минутный OVF не построен из-за одинаковой ошибки исходного файла и
  кандидата.
- Корпус не даёт retention rate.
- Компактная внутренняя раскладка PGM пока не реализована.

Эти ограничения не отменяют exact identity и byte accounting. Они
ограничивают перенос чисел на другие нагрузки и узлы.

## 14. Проверка отчёта

Проверить JSON и все производные числа:

```sh
python3 scripts/validate-pgm-size-reduction.py
```

Проверить конкретную копию summary:

```sh
python3 scripts/validate-pgm-size-reduction.py \
  docs/qualification/pgm-size-reduction-v1.json
```

Минимальные проверки документационной ветки:

```sh
git diff --check
cargo +1.96.0 fmt --all --check
```

Скрипт проверки измерений намеренно не кодирует PGM. Исследовательский
encoder материализует вход целиком и не соответствует обязательным memory
bounds; поэтому его нельзя помещать в production tree. Выход прототипа
идентифицируется полными SHA256, а будущий bounded encoder входит целиком в
один implementation PR раздела 11.

Для повторной независимой квалификации нужны PGM с SHA256 из раздела 2.4.
Перед запуском проверяется SHA256 `pgm_lab` из раздела 2.3. Порядок команд:

```text
sha256sum pgm_lab
pgm_lab analyze SOURCE
pgm_lab compact SOURCE CANDIDATE full plain-wide-page 6 65536 1048576
pgm_lab verify SOURCE CANDIDATE
pgm_lab analyze CANDIDATE
sha256sum SOURCE CANDIDATE
pgm_lab compact SOURCE REPEAT full plain-wide-page 6 65536 1048576
cmp CANDIDATE REPEAT
```

Команда `verify` обязана реализовать все проверки раздела 4, а не только
сравнение числа строк.
