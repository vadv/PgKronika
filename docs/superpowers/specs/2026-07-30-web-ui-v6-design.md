# Web UI v6 — дизайн флагманского интерфейса

Дата: 2026-07-30. Статус: DESIGN (после брейншторма, до implementation plan).

Документ фиксирует решение о реализации веб-интерфейса PgKronika как
полноценного фронтенд-приложения. Входные артефакты: макет
`docs/web/pgkronika-ui-proposal-v5.html` (референс, не канон) и спека
`docs/superpowers/specs/2026-07-28-web-ui-api-design.md` (контракт API,
статус PARTIAL).

## Позиционирование

Веб-интерфейс — основная фича продукта. Требования владельца: быстрый,
понятный, «секси», читаемый, поддерживаемый на долгой дистанции.

Эстетика: «крутой TUI, выросший в веб» (референс-образ: atop TUI). Это не
минимализм, а максимум информации, необходимой для экспертной оценки, при
обязательной семантической подсветке: каждое значение подсвечено, каждая
метрика за гранью порога «говорит сама».

## Сценарии и приоритеты

1. **Десктоп, глубокий разбор** — первичен: пост-инцидентный анализ,
   исследование по таймлайну, dense-таблицы.
2. **Ссылки команде** — вторичен: deep-link на точное состояние (source,
   курсор, span, view, инцидент) должен восстанавливать экран один в один.
3. **Мобильный** — насильно урезан до триажа: здоровье + инциденты +
   findings. Доступ к базе за VPN, полноценный анализ с телефона не
   требуется.
4. Позже планируется MCP-интеграция — UI не стремится покрывать все
   сценарии, часть аналитики уйдёт внешним инструментам.

## Стек

- **React 19 + Vite + TypeScript (strict)** в директории `web/` корня
  репозитория.
- **TanStack Query** — кеш/инвалидация/пагинация по ключам API
  (`(source, view, at, preset, ...)`), ETag каталога, `page_stale`
  рефетч. Модель данных — дискретные снапшоты, а не поток: fine-grained
  реактивность (Svelte/Solid) не окупается, сложность сосредоточена в
  fetching/cache/URL-state — территория React-экосистемы.
- **TanStack Table** — серверные sort/filter/page по контракту
  `/v1/frame/{view}`; клиентский фильтр загруженной страницы запрещён
  спекой (ложный `matched`).
- **Свои графики** (SVG + canvas при необходимости): spine, heatmap,
  спарклайны. Без D3 и тяжёлых chart-библиотек — макет не использует их
  возможностей. uPlot — точечно, только если замеры покажут просадку.
- **URL-state store** (без отдельной state-библиотеки или с лёгкой —
  решается на этапе плана): `source, at, span, baseline, view, preset,
  focus, q, sort` — единственный источник правды, deep-link из коробки.
- **Сборка**: `vite build` → `web/dist` → `rust-embed` в
  `pg_kronika-web`. All-in-one musl бинарник «скачал-запустил-работает»
  сохраняется. Dev-режим — прокси на `vite dev`. Проводка через xtask
  и/или Makefile; node добавляется в flake и CI.

## Компоновка v6

Скелет макета v5 сохраняется (он закреплён картой поверхностей в спеке
API — нулевое трение с бэкендом), с доработками:

- **Док становится оверлеем**: таблица всегда занимает полную ширину;
  панель (деталь строки / инциденты) выезжает справа поверх, Esc
  закрывает. Состояние дока — в URL (deep-link).
- **Тонкая статус-строка снизу** вместо раздутого hints-бара: здоровье,
  счётчики ok/warn/crit, LIVE-индикатор, ключевые хоткеи.
- **Сжатая шапка**: чипы source/БД/роль/health/время — одна строка.
- **⌘K-палитра**: прыжки на вкладку/сущность/инцидент/время + действия
  (копировать ссылку, экспорт).
- Heatmap-полоса схлопывается; вертикальное пространство приоритетно
  отдаётся таблице.

Рассмотренные альтернативы: «Штаб инцидентов» (левый рейл) — отклонён
(уже таблица, отход от спеки API); «atop fullscreen» — отклонён как
отдельный скелет, его плотность и оверлей-док перенесены в v6.

## Дизайн-система

- Только тёмная тема. Токены — CSS custom properties.
- **Палитра severity (GitHub-dark)**: ok `#3fb950`, warn `#d29922`,
  crit `#f85149`, info/accent `#58a6ff`; Δ-positive/Δ-negative — отдельная
  пара токенов для baseline-режима.
- Шрифты: Inter — UI-текст, JetBrains Mono — данные.
- Сетка 4px; плотность строк — переменная: компакт (22px, дефолт) /
  стандарт (26px) / комфорт (32px), переключатель в настройках.
- **Подсветка значений**: каждая метрика красится verdict'ом из API
  (`level/threshold/baseline`); hover/клик — «why»-поповер с правилом и
  базовой линией. Колонка без lens-контракта декоративного severity не
  получает (спека).
- **Честные null**: отсутствующее значение — прочерк с причиной в
  тултипе (EACCES, not_collected, unsupported_type, нет сэмплинга).
  Никогда не ноль.

## Компонентная модель

```
AppShell
├── Header (чипы: source, БД, роль/реплика, data-health, crit/warn, часы, ⧉, ⋯)
├── AlertBar (stale / collector down)
├── Spine (24h таймлайн, маркеры событий, REPLAY/LIVE, zoom, baseline, курсор)
├── FocusBar (при выбранном инциденте)
├── TabBar (9 view: activity, statements, plans, tables, indexes, vacuum, processes, locks, events)
├── HeatmapStrip (схлопываемая; переключение метрики; Δ-режим)
├── Toolbar (пресеты, фильтр q, счётчик matched)
├── TableView (полная ширина; вердикт-раскраска ячеек; спарклайны)
├── DockOverlay (деталь строки / инциденты; Esc)
├── StatusBar (здоровье, счётчики, хоткеи)
├── CommandPalette (⌘K)
└── Popovers/Toasts (data-health, why, legend, меню)
```

Слои кода: `web/src/api/` (типизированный клиент по OpenAPI + TanStack
Query), `web/src/state/` (URL-synced store), `web/src/components/`
(панели), `web/src/charts/` (рендеры spine/heatmap/sparkline),
`web/src/design/` (токены, CSS).

## Поток данных

- Смена курсора/вкладки → запросы: `summary(source, at)` — счётчики
  вкладок; `heatmap(source, view, metric, from, to)` — полоса;
  `frame(source, view, at, preset, q, sort, page)` — таблица;
  `context(source, at)` — шапка.
- Движение курсора: визуальная линия — мгновенно прямым DOM-обновлением
  (60fps, мимо React); запросы — debounce ~150мс.
- Стрелки ←/→: prev/next snapshot из `neighbors` ответа frame.
- Baseline (Shift+клик): второй независимый запрос того же range,
  клиентский merge по `entity`; heatmap переключается в Δ-режим. Оба
  ответа кешируемы независимо (спека).
- LIVE: курсор следует за последним снапшотом; опрос health ~5с;
  stale → баннер «показана запись»; down → LIVE блокируется с причиной.

## Деградация и ошибки

- `quality.status: partial` — состояние данных, не HTTP-ошибка: панель
  показывает данные + индикатор неполноты (gaps, gated, skipped lenses).
- Ошибки `application/problem+json` с осмысленными баннерами по
  стабильным `code` (`unknown_source`, `unknown_view`, `invalid_entity`,
  `range_too_wide`, `page_stale` → рефетч, `resource_limited`,
  `corrupt_ovf`, `response_too_large`). Никаких «Something went wrong».
- Гэпы в данных — first-class: полоса на spine, причина в data-health
  поповере, честные null в сетках.
- Мобильный (<760px): только health + инциденты + findings.

## Тестирование

- **Юнит (vitest)**: verdict-раскраска (все level + null-причины),
  сериализация/парсинг deep-link, форматтеры (µs, байты, Δ), reducer'ы
  store.
- **Интеграция (vitest + msw / фикстуры реальных ответов)**: query-ключи
  и инвалидация, merge baseline Δ по entity, `quality.partial`,
  `page_stale`-рефетч.
- **E2E (playwright)**: против `pg_kronika-web` на заранее составленном
  наборе PGM-сегментов (фикстуры с известным содержимым — снапшоты,
  гэп, инцидент): курсор→frame, baseline Δ, focus инцидента, восстановление
  по deep-link, баннеры stale/down, мобильный triage.
- **Визуальная регрессия**: playwright-скриншоты ключевых состояний
  (норм / инцидент / gap / down) на тех же PGM-фикстурах.
- **Гейт CI**: строгие `tsc --noEmit`, `eslint` (strict-конфиг),
  `vitest run`, playwright в BDD-докере рядом с существующими
  проверками; `vite build` — часть сборки.

## Порядок реализации (привязка к спеке API)

Шаги фронтенда следуют за delivery steps бэкенда
(`2026-07-28-web-ui-api-design.md`, «Порядок реализации»):

1. Каркас `web/` + embed + CI-гейт; каталог (`/v1/ui/catalog`) →
   динамические вкладки/колонки/пресеты.
2. Summary + heatmap (уже реализованы на бэкенде) → Spine-полоса
   статусов, TabBar, HeatmapStrip.
3. Frame + context → TableView, Toolbar, Header.
4. Entity point/history → DockOverlay, деталь строки, история сущности.
5. Storage + incidents → data-health поповер, FocusBar, инциденты.
6. Polish: ⌘K, плотности, визуальная регрессия, мобильный triage.

## Вне объёма

- Пишущие API и пользовательские аннотации (вне объёма и у API-спеки).
- Светлая тема (токены закладываем, тему — нет).
- MCP-интеграция (отдельный будущий трек).
- Переосмысление контракта API: фронтенд следует спеке; расхождения
  заводятся отдельными спеками.
