# Блок пер-сущностных рядов: EntitySparks и HeatmapSeries

Дата: 2026-07-28. Детализирует раздел «Материализованные ряды» спеки
web API (2026-07-28-web-ui-api-design.md) до уровня, пригодного для
ревью формата и построителя. Базируется на main после #132.

## Задача

Интерфейсу нужны два пер-сущностных временных ряда, которых сегодня
нет нигде, кроме тел PGM:

- спарклайн: тренд-столбец таблицы секции — одна каноническая
  метрика на сущность за окно;
- heatmap: полоса «top-сущности секции × время» с переключением
  метрики, плюс приближённый счётчик сущностей для панели вкладок.

Решение «материализовать один раз на запечатанный сегмент внутрь
OVF» принято в спеке web API и здесь не пересматривается. Эта спека
фиксирует: почему существующие блоки не подходят, формат новых
данных, семантику значений, построение, версионирование и границы.

## Нормативная база: что уже есть в OVF

Факты о текущем формате, на которые опирается дизайн (все проверены
по `crates/kronika-reader/src/overview/`):

- Контейнер адресует блоки через directory (предел 4096 записей,
  256 КиБ) и читает их позиционно. Девять baseline-видов занимают
  коды 1..9; неизвестный читателю вид управляется флагом
  `required_for_schema`: блок без флага читатель молча пропускает.
  Это штатный путь аддитивного расширения — но только при кодеке
  `None`: проверка контейнера отвергает файл целиком при любом
  другом кодеке (`flags.codec != None` → `Incompatible`) и требует
  `stored_len == decoded_len`. Кодек `Zstd` объявлен в формате, но
  ни один существующий блок его не использует, и verify его не
  принимает.
- Естественно пустой блок обязан иметь нулевые число элементов и
  тело (§9.1 родительской спеки); «пустой заголовок» невозможен.
- `StringTable` (код 9) — ограниченная sorted-unique таблица
  байт-строк; другие блоки ссылаются на строки по индексу.
- `EntityKind` — закрытый codec-enum из семи классов (Database …
  Filesystem). Классов для statement, plan, relation, index, process
  в нём нет.
- `EntityStates` заполняется только репликационными сущностями и
  границами снапшотов; для секций вкладок в нём нет ни одной записи.
- Извлечение метрик (`metric_extract.rs`) — явный allowlist по
  `type_id`; высококардинальные секции (statements, tables, indexes,
  activity, processes) в allowlist не входят и при построении фактов
  сегодня не декодируются.
- Ресеты счётчиков выражены эпохами (`ResetMarkers`); первичный
  детектор границы эпохи — отрицательная дельта.

## Решения и их причины

### Почему не существующие блоки

`GaugeSamples`/`CounterSamples` хранят instance-уровневые серии с
полной точностью значений и требуют идентичности через закрытый
`EntityKind`; пер-сущностные ряды секций туда не выражаются без
слома контракта. `EntityStates` семантически про доказанные переходы
состояний, а не про активность, и заполняется только репликацией.
Расширять `EntityKind` восемью новыми классами — значит менять
codec-enum, общий для всех существующих блоков, ради данных с другим
жизненным циклом. Отвергнуто в пользу самодостаточной идентичности
внутри нового блока.

### Один физический блок, две проекции

Спека web API вводила два имени: EntitySparks и HeatmapSeries.
Детальный разбор показывает, что это один формат: список секций,
внутри — метрики, внутри — серии top-сущностей по бакетам. Спарклайн
— в точности серия одной выделенной метрики секции; хранить её
вторым блоком — значит дублировать байты и держать два кодека, два
набора bounds и две ветки построителя без выгоды: оба блока читает
один web, оба строятся одним проходом, позиционное чтение делает
разницу «маленький блок против большого» несущественной при размерах
в десятки КиБ.

Решение: один физический вид блока — `EntitySeries`, код 10, флаг
`required_for_schema` снят. EntitySparks и HeatmapSeries остаются
именами проекций: «канонические метрики секций» и «все метрики
секций». Каноническая метрика помечена флагом в записи метрики.

Следствие для сметы: серии канонической метрики не хранятся дважды;
итоговый прирост — ~60–70 КиБ несжато (см. «Смета размера»), меньше
суммы двух отдельных блоков.

### Прочие развилки

- Минутная сетка UTC, а не доли сегмента: сегмент запечатывается по
  размеру и возрасту, его длительность переменна; бакеты, привязанные
  к стене часов, склеиваются между сегментами без пересчёта.
- u8-квант против максимума серии в сегменте: спарклайну и heatmap
  нужна форма, шаг квантования ≤1/255 максимума; абсолютная шкала
  восстанавливается через максимум в физических единицах.
- top-64 на пару (секция, метрика) — механический отбор по сумме за
  сегмент, без эвристик. Сущность вне top не имеет ряда в сегменте;
  её история доступна через `/v1/entity/...` из PGM.
- population в заголовке секции: полный счётчик сущностей секции за
  сегмент. Построитель видит все строки при декодировании, счётчик
  достаётся бесплатно и закрывает панель вкладок без чтения PGM.

## Формат блока EntitySeries

Кодек блока — `None`: это сохраняет главный контракт совместимости
(читатель текущего main пропускает блок кода 10 без
`required_for_schema` молча, файл остаётся валидным). Переход на
`Zstd` возможен позже, отдельным изменением verify, и не является
условием v1; цена — тело блока хранится несжатым, что учтено в
смете.

Числовые поля — little-endian фиксированной ширины; ссылки на
StringTable — `uvarint`, как в существующих блоках. Тело блока:

```text
header:
  semantics_version  u32   # каталог секций/метрик/ключей, см. ниже
  grid_start_us      i64   # начало первой минуты, кратно 60e6
  bucket_count       u16   # минут в сетке сегмента
  section_count      u16
  minute_mask        [u8]  # ceil(bucket_count/8), бит = в минуте
                           # есть снапшоты хотя бы одной секции
section (повторяется section_count раз):
  section_name_ref   uvarint  # StringTable: имя секции реестра
  population         u32      # сущностей секции за сегмент, всего
  section_mask       [u8]     # минуты со снапшотами этой секции
  metric_count       u16
  metric (повторяется metric_count раз):
    metric_code      u16      # из каталога версии семантики
    flags            u16      # бит 0: каноническая метрика секции
    unit_code        u16      # единица физической шкалы
    series_count     u16      # ≤ 64
    series (повторяется series_count раз):
      entity_key_ref uvarint  # StringTable: канонический ключ
      max_value      f64      # максимум минутного значения серии
      values         [u8; bucket_count]  # квант 0..255 от max_value
```

Порядок канонической сортировки: секции — по `section_name_ref`,
метрики — по `metric_code`, серии — по убыванию суммы значений,
при равенстве — по `entity_key_ref`. Блок объявляет
`canonically_sorted` и `has_time_range` (диапазон — границы сетки).

Сегмент без строк секций даёт естественно пустой блок: нулевые число
элементов и тело, по конвенции §9.1. Пустое тело не несёт
`semantics_version`, и это не создаёт неоднозначности: пустой
сегмент пуст при любой версии каталога, поэтому присутствующий
пустой блок считается актуальным и пересборке по версии не подлежит.
Отсутствие блока в файле допустимо только для файлов, записанных до
этой версии, и читается как «сегмент ждёт пересборки».

Сегмент длиннее сетки (возраст сверх 256 минут — оператор поднял
`KRONIKA_SEGMENT_MAX_AGE_S` выше ~4.2 часа) усекает сетку справа:
минуты за пределом не сохраняются, ручки показывают хвост как
непокрытый. Вечного `pending` такой сегмент не создаёт.

### Границы допуска

В `Bounds` добавляются: `entity_series_sections` (64),
`entity_series_per_metric` (64), `entity_series_buckets` (256 — с
запасом против минимальной минутной сетки при максимальном возрасте
сегмента). Существующие пределы таблицы строк и элементов блока
действуют без изменений; ключи сущностей входят в бюджет
`string_table_bytes`.

## Идентичность сущностей

Ключ — байт-строка в StringTable, самодостаточная и не зависящая от
`EntityKind`. Канонические ключи v1:

| Секция | Канонический ключ |
| --- | --- |
| pg_stat_statements | `dbid:userid:queryid` |
| pg_store_plans_vadv | `dbid:userid:planid` |
| pg_store_plans_ossc | `dbid:userid:queryid:planid` |
| pg_stat_activity | `pid:backend_start_us` |
| pg_stat_user_tables | `schema.relname` |
| pg_stat_user_indexes | `schema.relname.indexrelname` |
| processes (/proc) | `pid:starttime` |
| locks | `pid:backend_start_us` ожидающего или держащего |
| журнал (log events) | категория события |

Ключ следует идентичности строки, задекларированной реестром для
конкретной секции: statements ключуются `(userid, dbid, queryid)`,
планы — пофорково, `(dbid, userid, planid)` у vadv и
`(dbid, userid, queryid, planid)` у ossc. Ключ уже идентичности
реестра объединил бы несколько строк снапшота в одну серию, и пары
соседних снапшотов для дельт стали бы неопределёнными. Группировка
по queryid для отображения — операция клиента поверх серий, не
идентичность.

Ключи pid-секций включают время старта процесса: pid внутри сегмента
может быть переиспользован, и без старта две разные жизни процесса
слиплись бы в одну серию. Табличные ключи текстовые: rename таблицы
разрывает серию между сегментами — это видимое свойство данных, а не
дефект; стабильность против rename потребовала бы oid-идентичности и
обратного разрешения имён, что для тренда не оправдано.

## Семантика значений

- Counter-колонки: значение минуты — сумма положительных дельт пар
  соседних снапшотов, попавших правой границей в минуту.
  Отрицательная дельта — граница эпохи ресета: пара отбрасывается,
  вклад не фабрикуется. Ресет, после которого счётчик успел
  превысить прежнее значение к следующему снапшоту, положительной
  дельтой не обнаруживается и даёт завышенный вклад одной пары —
  принимаемая погрешность: эпох `ResetMarkers` для этих секций нет,
  а точность формы тренда от единичной пары не страдает. Минуты вне
  `section_mask` не означают ноль — там не было снапшотов.
- Gauge-колонки: значение минуты — максимум по снапшотам минуты.
- Доли (каноническая метрика activity): числитель и знаменатель
  считаются по снапшотам минуты до квантования.

Каталог метрик v1 (`metric_code`, источник, агрегат) фиксируется
таблицей при реализации по колонкам реестра; составы метрик по
секциям — из спеки web API (переключатели макета плюс канонические
метрики). Изменение каталога — bump `semantics_version` целиком:
частичные версии по секциям запрещены, чтобы «сегмент собран» было
бинарным свойством.

## Построение

Строит владелец `.pgkronika-overview.owner.lock` в том же проходе,
что и остальные факты сегмента; отдельного прохода по PGM нет.

Существенное следствие: сегодня построитель декодирует только
allowlist instance-секций, с этим блоком он начинает декодировать и
высококардинальные секции — время и память сборки фактов растут.
Аккумулятор ограничен: на секцию — карта «сущность → суммы по
метрикам» с ёмкостью, кратной top-64 (отбор top — в конце прохода по
сегменту, один проход, без второго чтения), плюс страничные значения
минут только для сущностей-кандидатов. Верхняя память аккумулятора
оценивается при реализации и входит в отчёт демо-стенда вместе со
сметой размера.

Живой хвост: построитель активных данных ведёт тот же аккумулятор по
завершённым активным частям; ручки читают его из памяти. При seal
аккумулятор сбрасывается в блок без повторного чтения журнала.

Пересборка: сегменты, чей OVF не содержит блока актуальной
`semantics_version`, пересобираются владельцем в фоне, новейшие
первыми; до пересборки ручки отдают эти сегменты в `pending`. Это
единственный случай повторного декодирования запечатанного PGM.

## Смета размера

На сегмент при 8 секциях, ~20 парах (секция, метрика), top-64,
15 минутных бакетах, кодек `None` (несжато):

- серии: ~1300 × (~4 + 8 + 15) ≈ 35 КиБ;
- ключи сущностей: union top-сущностей секции, ~100–150 ключей на
  высококардинальную секцию, ≈ 20–30 КиБ в StringTable;
- заголовки, маски — единицы КиБ.

Прирост ~60–70 КиБ на сегмент против сегодняшних 34–44 КиБ всего
OVF: файл вырастает до ~95–115 КиБ, в ~2.6–2.8 раза. За сутки при 96
сегментах итоговые OVF занимают ~9–11 МиБ бюджета ротации, из них
прирост от блока — ~5.5–6.5 МиБ. Числа проверяются на демо-стенде
до фиксации формата; критерий пересмотра — блок больше половины
итогового OVF или больше 10% родительского PGM на
production-подобном сегменте (тогда возвращается вопрос кодека
`Zstd` ценой расширения verify).

## Взаимодействие с остальной системой

- Ротация: блок внутри OVF, сегментный юнит ротации не меняется.
- Читатели текущего main: блок кода 10 без `required_for_schema` и с
  кодеком `None` пропускается контейнером молча, файл остаётся
  валидным — аддитивность соблюдена.
- Dump: не разбирает содержимое OVF (учитывает только наличие
  файла) — изменений не требует; печать блоков OVF dump'ом — вне
  объёма этой спеки.
- Карантин, layout, грамматика обхода — без изменений.
- Существующие блоки и их коды не меняются; удаление блока из файла
  не требуется никогда — пересборка заменяет файл целиком по
  существующей публикационной дисциплине владельца.

## Тестирование

- Кодек блока — golden-тесты по образцу существующих блоков: точная
  байтовая идентичность кодирования и отказ на нарушенных границах.
- Чистые функции (квантование, минутная сетка, суммирование дельт с
  отбросом отрицательных, отбор top-64) — юнит-тесты.
- Поведение ручек поверх блока — живые BDD-сценарии вместе с
  реализацией ручек (шаг 2 порядка из спеки web API), не раньше.

## Вне объёма

- Контракты HTTP-ручек — спека web API.
- Пер-сущностные ряды для секций вне списка (progress_vacuum и
  instance-секции) — не нужны: малая кардинальность читается из
  frame.
- Исторические бэкфилы старых сегментов сверх фоновой пересборки —
  отдельная утилита не вводится, пересборка покрывает.
