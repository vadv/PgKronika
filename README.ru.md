# PgKronika

[English version](README.md)

PgKronika сохраняет диагностическую историю экземпляра PostgreSQL в локальных
неизменяемых файлах PGM. Коллектор читает статистику PostgreSQL, данные Linux
из `/proc` и cgroup, а при включении — журнал stderr PostgreSQL. Отдельный
веб-процесс показывает записанные строки, diff'ы счётчиков, сводки временной
шкалы в разрезе источников, показатели здоровья, примечательные события,
эпизоды аномалий и кластеры инцидентов — через локальный интерфейс и JSON API.

Проект активно развивается. Коллектор, локальное хранилище сегментов, reader и
веб-API реализованы и проверяются BDD-матрицей на PostgreSQL 15–18. Готовой
поставки, управления сроками хранения, удалённой архивации, `pg_kronika-dump`,
MCP, доставки оповещений и определения первопричины пока нет.

## Путь данных

```text
PostgreSQL 15–18       Linux /proc, /sys, cgroups       журнал stderr
        \                     |                           /
         kronika-source-pg / kronika-source-os / kronika-source-log
                              |
                 kronika-registry + kronika-derive
                              |
                kronika-writer -> active.parts -> *.pgm
                              |
                 kronika-store -> kronika-reader
                              |
             kronika-analytics -> pg_kronika-web
         diff, аномалии, здоровье    JSON/UI, временная шкала, инциденты
```

Коллектор работает на сервере базы данных и не слушает сеть. Он пишет
дополняемый журнал `active.parts`, а затем финализирует его кадры в автономные
файлы `.pgm`. Веб-процесс читает из того же каталога готовые файлы и целостные
части живого журнала, не подключаясь к PostgreSQL.

PgKronika полезна для сохранения детальных данных высокой кардинальности рядом
с базой: сессий, запросов, планов, статистики отношений, репликации, нагрузки
ОС, счётчиков процессов и cgroup, типизированных событий журнала. Она не
заменяет систему метрик и алертинга и не выдаёт корреляцию за причину
инцидента.

## Поддержка и требования

| Область | Текущий контракт |
| --- | --- |
| PostgreSQL | BDD-матрица запускается на версиях 15, 16, 17 и 18. |
| Платформа | Linux. CI и образ BDD сейчас проверяют `x86_64`. |
| Rust | Rust 1.96.0, зафиксированный в [`rust-toolchain.toml`](rust-toolchain.toml). |
| Сборка для разработки | Цель GNU; команда ниже совпадает с целью в CI. |
| Сборка выпуска | По умолчанию репозиторий использует `x86_64-unknown-linux-musl`; нужны `musl-gcc` и соответствующая цель Rust. Готового комплекта выпуска пока нет. |
| Доступ к PostgreSQL | Роль с правом входа и `CONNECT` к нужным базам. `pg_monitor` или более узкие эквивалентные права дают доступ к статистике чужих сеансов. |
| Расширения | Необязательны. `pg_stat_statements` и поддерживаемый вариант `pg_store_plans` обнаруживаются в базе установки; без них основной сбор продолжает работать. |

Коллектор перечисляет доступные пользовательские базы и держит не более 20
подключений — по одному на каждую базу-источник. База в DSN задаёт начальное
соединение, а не режим сбора одной базы. Права и поведение расширений описаны в
[контракте сбора PostgreSQL](docs/type-registry/postgresql-collection.md).

## Кратчайший путь от сборки до данных

Команды ниже создают сегмент, открывают его веб-процессом и возвращают первый
осмысленный ответ API. Запускайте из корня репозитория на Linux.

Соберите два пользовательских бинарника:

```sh
rustup target add x86_64-unknown-linux-gnu --toolchain 1.96.0
cargo +1.96.0 build --locked --target x86_64-unknown-linux-gnu \
  -p pg_kronika-collector -p pg_kronika-web
mkdir -p var/segments
```

Запустите коллектор, подставив DSN доступной PostgreSQL 15–18 и отдельной роли.
`KRONIKA_SEGMENT_MAX_BYTES=0` финализирует каждое окно сбора, так что первый
результат появляется сразу.

```sh
KRONIKA_PG_DSN='host=127.0.0.1 port=5432 dbname=postgres user=kronika password=change-me' \
KRONIKA_OUT_DIR="$PWD/var/segments" \
KRONIKA_SEGMENT_MAX_BYTES=0 \
./target/x86_64-unknown-linux-gnu/debug/pg_kronika-collector
```

После успешного окна процесс печатает `ready`, затем
`sealed <path> reason=tick`. Ошибка отдельного цикла попадает в stderr; демон
продолжает работу и повторяет сбор позже.

Во втором терминале откройте каталог на локальном адресе:

```sh
KRONIKA_WEB_DIR="$PWD/var/segments" \
KRONIKA_WEB_ADDR=127.0.0.1:8688 \
./target/x86_64-unknown-linux-gnu/debug/pg_kronika-web
```

Получите список источников и доступных секций:

```sh
curl -sS http://127.0.0.1:8688/v1/sources
curl -sS http://127.0.0.1:8688/v1/sections
```

Встроенный интерфейс доступен на `http://127.0.0.1:8688/`. TLS в сервер не
встроен. Без `KRONIKA_WEB_BASIC_AUTH` интерфейс и `/v1/*` открыты;
`/healthz`, `/readyz` и `/metrics` публичны даже при включённой Basic
Auth.

## Карта рабочего пространства

Все пакеты внутренние, имеют общую версию и не публикуются на crates.io.

| Пакет | Ответственность |
| --- | --- |
| [`kronika-format`](crates/kronika-format/) | Кадры PGM, каталог, CRC32C, словари и проверка кадров журнала. |
| [`kronika-derive`](crates/kronika-derive/) | Внутренний макрос `Section`, создающий контракт реестра и кодек Parquet. |
| [`kronika-registry`](crates/kronika-registry/) | Стабильные идентификаторы типов, схемы, семантика столбцов, ворота сбора, кодеки и проверка реестра. |
| [`kronika-writer`](crates/kronika-writer/) | Буферы секций с ограничением размера, интернер строк, `active.parts` и финализация. |
| [`kronika-store`](crates/kronika-store/) | Сканирование локального каталога сегментов и активного журнала в режиме read-only. |
| [`kronika-reader`](crates/kronika-reader/) | Проверенное декодирование секций, снапшоты, пагинация, логические секции, gauge, diff и факты overview (в первую очередь из долговременных OVF). |
| [`kronika-analytics`](crates/kronika-analytics/) | Независимое от источника ядро: счётчики, аномалии, примечательные события и оценка здоровья. |
| [`kronika-source-pg`](crates/kronika-source-pg/) | Запросы PostgreSQL и раскладка разных версий в строки реестра. |
| [`kronika-source-os`](crates/kronika-source-os/) | Ограниченное чтение Linux `/proc`, `/sys`, файловых систем, процессов и cgroup. |
| [`kronika-source-log`](crates/kronika-source-log/) | Ограниченное чтение хвоста stderr, нормализация, типизированные события и учёт пропусков. |
| [`pg_kronika-collector`](bins/pg_kronika-collector/) | Жизненный цикл сбора, интервалы, пределы, покрытие, журнал и ротация. |
| [`pg_kronika-web`](bins/pg_kronika-web/) | Локальный интерфейс, JSON API, аутентификация, готовность, ограниченные запросы временной шкалы с явным выбором источников, аномалии, кластеризация инцидентов и диагностические findings. |
| [`kronika-bdd`](crates/kronika-bdd/) | Раннер интеграционных тестов Docker/Nix для PostgreSQL 15–18. |
| [`xtask`](xtask/) | Проверка границ зависимостей в CI. |
| `pg_kronika-archiver`, `pg_kronika-dump` | Заглушки: печатают ошибку и завершаются с кодом 2. |

Актуальные границы зависимостей и путь данных описаны в
[`docs/architecture.md`](docs/architecture.md). CI проверяет разрешённый список
зависимостей командой `cargo run -p xtask -- check-deps`.

## Контракты, важные при эксплуатации

- **Формат и целостность.** PGM использует little-endian-кадры,
  CRC32C каждой секции и каталог с собственной CRC. CRC обнаруживает случайную
  порчу, но не защищает от подмены. Ошибочные данные не превращаются в строки:
  reader возвращает типизированную ошибку или сообщает о пропуске.
- **Надёжность записи.** Кадр журнала синхронизируется до завершения добавления.
  При seal writer создаёт и синхронизирует временный файл, затем публикует его
  без перезаписи существующего сегмента. Оборванный последний кадр усекается
  при восстановлении; прочие повреждения отражаются в диагностике сканирования.
  Для готовых сегментов индекс временной шкалы сначала проверяет допущенные
  сайдкар-файлы фактов с совпадающим lineage и лишь затем обращается к
  ограниченному fallback-кэшу в памяти процесса. Факты попадают в этот кэш только
  после восстановимой ошибки публикации.
- **Сайдкар-файлы фактов.** Каталог `KRONIKA_WEB_DIR` целиком принадлежит
  PgKronika. У каждого готового `N.pgm` может быть только один сайдкар
  `N.ovf`:

  ```text
  /data/active.parts
  /data/N.pgm
  /data/N.ovf
  ```

  Право изменять каталог удерживает один независимо созданный `FactStore` или
  процесс; его клоны разделяют это право. GC просматривает каталог с жёстким
  пределом, ничего не удаляет после неполного, неавторитетного или прерванного
  из-за лимита сканирования, не удаляет исходные PGM и не переходит по
  символьным ссылкам. Необязательные ограничения по логическому размеру и числу
  файлов учитывают только распознанные сайдкар-файлы. Задержка повторной записи
  не блокирует чтение корректных OVF.
- **Границы ресурсов.** Секция ограничена 65 536 строками, 8 МиБ кодированных
  данных и 16 группами строк Parquet. Коллектор ограничивает кардинальность
  наборов, словари, время цикла и журнал. Reader ограничивает число строк и
  материализованных ячеек. Веб-процесс допускает один тяжёлый запрос аномалий,
  инцидентов или временной шкалы без готового ответа и отвечает `503`, если
  слот исполнителя занят. Хранилище ответов временной шкалы ограничено по числу
  записей и байтам. У представлений, закреплённых курсорами, есть отдельные
  ограничения по числу, байтам и времени жизни.
- **Качество данных.** Неизменившийся счётчик даёт реальную нулевую дельту.
  Сброс, разрыв покрытия, первая точка, неверный порядок времени и выключенный
  сбор — разные причины отсутствия данных. Ответы временной шкалы раздельно
  сообщают точность сохранённых данных, полноту источника, смысл физического
  счётчика и известные потери. Diff и поиск аномалий не заменяют пропуски нулями
  и не перекрывают разрывы.
- **Безопасность.** Сегменты могут содержать SQL, планы, имена объектов,
  аргументы процессов и текст журнала. Ограничьте доступ к каталогу и копиям:
  коллектор не шифрует и не редактирует содержимое. Веб-процесс следует слушать
  на локальном интерфейсе или ставить за обратным прокси с TLS; Basic
  Auth не шифрует транспорт.

Полные лимиты и варианты ошибок — в README и rustdoc соответствующих крейтов.
