# PgKronika

[English version](README.md)

PgKronika сохраняет диагностическую историю экземпляра PostgreSQL в локальных
неизменяемых файлах PGM. Коллектор читает статистику PostgreSQL, данные Linux
из `/proc` и cgroup, а по умолчанию — доступный журнал stderr PostgreSQL.
Отдельный веб-процесс показывает записанные строки, разности счётчиков, сводки
временной шкалы в разрезе источников, показатели здоровья, примечательные
события, эпизоды аномалий и кластеры инцидентов — через локальный интерфейс и
JSON API.

Проект активно развивается. Коллектор, локальное хранилище сегментов, модуль
чтения, офлайн-команда `pg_kronika-dump`, ротация хранилища и веб-API
реализованы. Сценарии, использующие PostgreSQL, проверяются BDD-матрицей на
версиях 15–18. Готовой поставки, удалённой архивации, MCP, доставки
оповещений и определения первопричины пока нет.

## Путь данных

```text
PostgreSQL 15–18       Linux /proc, /sys, cgroups       журнал stderr
        \                     |                           /
         kronika-source-pg / kronika-source-os / kronika-source-log
                              |
                 kronika-registry + kronika-derive
                              |
          kronika-writer -> active.parts -> YYYY/MM/DD/*.pgm
                              |
                 kronika-store -> kronika-reader
                              |
             kronika-analytics -> pg_kronika-web
      разности, аномалии, здоровье   JSON/UI, временная шкала, инциденты

          корень / PGM / active.parts -> pg_kronika-dump -> JSON
```

Коллектор работает на сервере базы данных и не слушает сеть. Он пишет
синхронизированные кадры в корневой журнал `active.parts`, а затем финализирует
их в автономные файлы `.pgm`. Веб-процесс читает из того же корня готовые файлы
и целостные части живого журнала, не подключаясь к PostgreSQL.

PgKronika полезна для сохранения детальных данных высокой кардинальности рядом
с базой: сессий, запросов, планов, статистики отношений, репликации, нагрузки
ОС, счётчиков процессов и cgroup, типизированных событий журнала. Она не
заменяет систему метрик и алертинга и не выдаёт корреляцию за причину
инцидента.

## Поддержка и требования

| Область | Текущий контракт |
| --- | --- |
| PostgreSQL | BDD-матрица запускается на версиях 15, 16, 17 и 18. |
| Платформа | Linux. CI и образ BDD сейчас проверяют `x86_64`. |
| Rust | Rust 1.96.0, зафиксированный в [`rust-toolchain.toml`](rust-toolchain.toml). |
| Сборка для разработки | Цель GNU; команда ниже совпадает с целью в CI. |
| Сборка выпуска | По умолчанию репозиторий использует `x86_64-unknown-linux-musl`; нужны `musl-gcc` и соответствующая цель Rust. Готового комплекта выпуска пока нет. |
| Доступ к PostgreSQL | Роль с правом входа и `CONNECT` к нужным базам. `pg_monitor` или более узкие эквивалентные права дают доступ к статистике чужих сеансов. |
| Расширения | Необязательны. `pg_stat_statements` и поддерживаемый вариант `pg_store_plans` обнаруживаются в базе установки; без них основной сбор продолжает работать. |

Коллектор перечисляет доступные пользовательские базы и держит не более 20
подключений — по одному на каждую базу-источник. База в DSN задаёт начальное
соединение, а не режим сбора одной базы. Права и поведение расширений описаны в
[контракте сбора PostgreSQL](docs/type-registry/postgresql-collection.md).

## Кратчайший путь от сборки до данных

Команды ниже создают сегмент, открывают его веб-процессом и возвращают первый
осмысленный ответ API. Запускайте из корня репозитория на Linux.

Соберите три пользовательских бинарника:

```sh
rustup target add x86_64-unknown-linux-gnu --toolchain 1.96.0
make build TARGET=x86_64-unknown-linux-gnu
mkdir -p var/segments
```

Запустите коллектор, подставив DSN доступной PostgreSQL 15–18 и отдельной роли.
`KRONIKA_SEGMENT_MAX_BYTES=0` финализирует каждое окно сбора, так что первый
результат появляется сразу.

```sh
KRONIKA_PG_DSN='host=127.0.0.1 port=5432 dbname=postgres user=kronika password=change-me' \
KRONIKA_OUT_DIR="$PWD/var/segments" \
KRONIKA_LOG_STATE_PATH="$PWD/var/pg_log_tail.state" \
KRONIKA_SEGMENT_MAX_BYTES=0 \
./target/x86_64-unknown-linux-gnu/debug/pg_kronika-collector
```

После успешного окна процесс печатает `ready`, затем
`sealed <path> reason=tick`. Ошибка отдельного цикла попадает в stderr; демон
продолжает работу и повторяет сбор позже.

Во втором терминале откройте каталог на локальном адресе:

```sh
KRONIKA_WEB_DIR="$PWD/var/segments" \
KRONIKA_WEB_ADDR=127.0.0.1:8688 \
./target/x86_64-unknown-linux-gnu/debug/pg_kronika-web
```

Получите список доступных секций:

```sh
curl -sS http://127.0.0.1:8688/v1/sections
```

Встроенный интерфейс доступен на `http://127.0.0.1:8688/`, интерактивный
Swagger UI — на `http://127.0.0.1:8688/swagger-ui/`, а генерируемый документ
OpenAPI — на `http://127.0.0.1:8688/openapi.json`. Ошибка API — обычный
JSON-объект с полями `code` и `params`. TLS в сервер не встроен. Без
`KRONIKA_WEB_BASIC_AUTH` интерфейс, Swagger UI, документ OpenAPI и `/v1/*`
открыты; `/healthz`, `/readyz` и `/metrics` публичны даже при включённой
Basic Auth.

Единый реестр в
[`bins/pg_kronika-web/src/api_docs.rs`](bins/pg_kronika-web/src/api_docs.rs)
подключает документированные обработчики одновременно к Axum и OpenAPI.
Rust DTO ответов задают успешные схемы, а каждая операция перечисляет
достижимые HTTP-статусы. Нейтральное представление начинается с
[`openapi/openapi.yaml`](bins/pg_kronika-web/openapi/openapi.yaml); пути и
схемы разнесены по YAML-файлам `core`, `sections`, `analytics`, `timeline` и
`ui` со стандартными относительными `$ref`. Для обновления дерева и его
структурной проверки с обратной сборкой:

```sh
make openapi
```

CI выполняет ту же команду и отклоняет изменение сгенерированного дерева.
Rust-контрактные тесты дополнительно требуют именованную успешную схему и один
доменный tag у всех 15 операций. Если внешнему инструменту нужен один файл,
`make openapi-bundle` записывает некоммитный bundle в
`target/pg-kronika-openapi.yaml`.

Когда demo уже запущен, выполните по одному детерминированному запросу к каждой
операции с проверкой схемы и лёгким доказательством наличия сохранённых данных:

```sh
make demo-api-smoke
```

Локальный smoke запускает закреплённую версию Schemathesis через `uvx` и
намеренно не входит в CI. Другой адрес задаётся через `DEMO_API_URL`, а при
включённой Basic Auth используется
`PG_KRONIKA_SMOKE_AUTH=user:password`.

## Контракты, важные при эксплуатации

- **Формат и целостность.** Формат PGM v1 хранит многобайтовые числа от младшего
  байта к старшему (`little-endian`), использует CRC32C каждой секции и каталог
  с собственной CRC. CRC обнаруживает случайную порчу, но не защищает от
  подмены. Ошибочные данные не превращаются в строки: модуль чтения возвращает
  типизированную ошибку или сообщает о пропуске.
- **Структура корня данных.** `KRONIKA_OUT_DIR` и `KRONIKA_WEB_DIR` указывают на
  один корень, целиком принадлежащий PgKronika:

  ```text
  /data/active.parts
  /data/.pgkronika-quarantine-v1/
  /data/.pgkronika-writer.owner.lock
  /data/.pgkronika-overview.owner.lock
  /data/YYYY/MM/DD/N.pgm
  /data/YYYY/MM/DD/N.ovf
  ```

  `N` — это `SegmentId`: метка Unix в микросекундах для первого окна сбора,
  которое успешно добавлено в сегмент. День UTC этого идентификатора задаёт
  `YYYY/MM/DD`; сегмент, пересекающий полночь, остаётся в каталоге дня начала.
  Запросы используют `min_ts` и `max_ts` каталога PGM, а не путь. В один корень
  может писать один коллектор. Неизвестные файлы, каталоги и символьные ссылки
  никогда не обходятся и не интерпретируются. Владелец записи пытается
  переместить каждую непрозрачную запись в ограниченный карантин без
  перезаписи; локальная ошибка rename видна в диагностике, но не скрывает
  валидные сегменты и не останавливает сбор. Это единственная поддерживаемая
  структура; предыдущего публичного формата каталога не было.
- **Надёжность записи.** Журнал `active.parts` версии 1 использует магическое
  число `PGKJNL1\0` и заголовок с контрольной суммой и активным `SegmentId`.
  Это первый и единственный поддерживаемый формат журнала; другого формата и
  механизма миграции нет. Первый кадр и идентификатор синхронизируются вместе
  до завершения добавления. При локальном повреждении точный inode журнала
  сохраняется в карантине; ограниченное восстановление принимает только полные
  кадры с корректными CRC кадра, PGM, каталога и секций и проводит их через
  обычные append/seal. Отброшенные байты учитываются, начинается свежее
  поколение, а сбор продолжается даже при локальной ошибке перемещения улики.
  Невалидный PGM целиком сохраняется в карантине и исключается из чтения, не
  блокируя корректные сегменты. При финализации модуль записи создаёт и
  синхронизирует временный файл в том же каталоге дня, затем публикует его без
  перезаписи существующего сегмента. При запуске владелец блокировки записи
  сохраняет распознанные временные файлы публикации PGM в карантине; временные
  файлы OVF остаются под управлением модуля обзора.
  Для готовых сегментов индекс временной шкалы сначала проверяет допущенные
  сайдкар-файлы фактов с совпадающим идентификатором происхождения (`lineage`) и
  лишь затем обращается к ограниченному резервному кэшу в памяти процесса.
  Факты попадают в этот кэш только после восстановимой ошибки публикации.
- **Сайдкар-файлы фактов.** Корень `KRONIKA_WEB_DIR` целиком принадлежит
  PgKronika. У каждого готового `YYYY/MM/DD/N.pgm` может быть только один
  соседний `N.ovf` в том же дне. Каталог OVF адресует блоки парой
  `(block_kind, logical_id)`: каждый файл содержит один `UiSummary`, а каждый
  присутствующий view — независимый `EntitySeries(view_code)`. Читатель
  загружает один view, не затрагивая остальные. `EntitySeries` использует Zstd
  level 1,
  только если сжатие экономит более 64 байт; CRC32C защищает сохранённые байты,
  а декомпрессия обязана дать точный ограниченный `decoded_len`. Отсутствующий
  bucket отличается от наблюдаемого нуля. Право изменять OVF удерживает один
  независимо созданный `FactStore` или процесс; его клоны разделяют это право.
  GC
  просматривает дерево с жёстким пределом, ничего не удаляет после неполного,
  неавторитетного или прерванного из-за лимита сканирования обхода, не удаляет
  исходные PGM и не переходит по символьным ссылкам. Необязательные ограничения
  по логическому размеру и числу файлов учитывают только распознанные
  сайдкар-файлы. Задержка повторной записи не блокирует чтение корректных OVF.
- **Ротация хранилища.** `KRONIKA_RETENTION` ограничивает всё дерево
  `KRONIKA_OUT_DIR`; без переменной поведение прежнее — рост без предела.
  Значение `<байты>` — фиксированный бюджет, он должен быть не меньше
  `2 × KRONIKA_SEGMENT_MAX_BYTES`. `auto` (то же самое, что `auto:80`) или
  `auto:<P>` задаёт целевую долю занятости раздела, `P` в диапазоне `1..=99`.
  Ротацией владеет коллектор: после каждой публикации и по тику раз в 60 секунд
  он удаляет старейшие заменимые данные — временные файлы писателя, затем
  осиротевшие OVF, затем карантинные улики от старейшей, затем запечатанные
  сегменты от старейшего, забирая парный `N.ovf` в тот же проход, — и вычищает
  опустевшие каталоги дней. Улики входят в бюджет. Один проход удаляет в счёт
  дефицита, посчитанного в его начале, и останавливается на первой ошибке
  удаления; в режиме `auto` байты, освобождённые unlink, засчитываются даже
  пока читатели держат файлы открытыми, поэтому удержанные дескрипторы не
  приводят к удалению лишней истории. Прямой unlink безопасен: читатели держат
  открытые дескрипторы, а владелец OVF ревалидирует идентичность. Активный
  журнал и новейший запечатанный сегмент не удаляются никогда; когда дерево
  прижато к этому минимуму, коллектор пишет событие деградации не чаще раза в
  тик и продолжает сбор. При `KRONIKA_INTERVAL_S=0` таймер ротации будит
  процесс только ради ротации — сбор остаётся сигнальным. Режим `auto`
  кооперативен на разделяемом разделе — чужой рост ускоряет вычищение нашей
  истории до минимума, — но свободного места не резервирует. В фиксированном
  режиме размер может превышать бюджет на рост активного журнала между тиками
  и на OVF-сайдкары, опубликованные после последнего enforcement-скана; каждый
  скан пересеивает счётчик, а ежечасный принудительный пересчёт ограничивает
  этот дрейф даже когда инкрементальный счётчик сам порога не пересекает.
  Каждое удаление логируется с путём, `SegmentId`, освобождёнными байтами,
  причиной `budget` или `auto`, а также текущим размером относительно порога.
- **Границы ресурсов.** Секция ограничена 65 536 строками, 8 МиБ кодированных
  данных и 16 группами строк Parquet. Коллектор ограничивает кардинальность
  наборов, словари, время цикла и журнал. Reader ограничивает число строк и
  материализованных ячеек. Веб-процесс допускает один тяжёлый запрос аномалий,
  инцидентов или временной шкалы без готового ответа и отвечает `503`, если
  слот исполнителя занят. Хранилище ответов временной шкалы ограничено по числу
  записей и байтам. У представлений, закреплённых курсорами, есть отдельные
  ограничения по числу, байтам и времени жизни.
- **Качество данных.** Неизменившийся счётчик даёт реальную нулевую дельту.
  Сброс, разрыв покрытия, первая точка, неверный порядок времени и выключенный
  сбор — разные причины отсутствия данных. Ответы временной шкалы раздельно
  сообщают точность сохранённых данных, полноту источника, смысл физического
  счётчика и известные потери. Diff и поиск аномалий не заменяют пропуски нулями
  и не перекрывают разрывы.
- **Безопасность.** Сегменты могут содержать SQL, планы, имена объектов,
  аргументы процессов и текст журнала. Ограничьте доступ к каталогу и копиям:
  коллектор не шифрует и не редактирует содержимое. Веб-процесс следует слушать
  на локальном интерфейсе или ставить за обратным прокси с TLS; Basic
  Auth не шифрует транспорт.

Сбор журнала PostgreSQL включён по умолчанию. Путь долговременной позиции
`KRONIKA_LOG_STATE_PATH` должен находиться вне `KRONIKA_OUT_DIR`; если важна
точная позиция чтения после восстановления, снимайте его отдельно в тот же
момент согласованности.

Полные лимиты и варианты ошибок — в README и rustdoc соответствующих крейтов.
