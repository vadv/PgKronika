# pg_kronika-dump

[English version](README.md)

`pg_kronika-dump` читает данные PgKronika без PostgreSQL и веб-процесса. Он
нужен, когда оператору или разработчику необходимо:

- увидеть, какие сегменты и карантинные улики находятся в корне данных;
- понять, какие секции занимают место внутри PGM и насколько они сжаты;
- вывести сохранённые строки с разыменованными значениями словаря;
- определить, какие кадры `active.parts` целы и где начинается повреждение.

Утилита ничего не изменяет: не ремонтирует журнал, не публикует сегменты, не
удаляет улики и не берёт блокировку владельца записи или overview. Успешный
результат — один объект JSON в stdout. Диагностика попадает только в stderr.

## Сборка

Из корня репозитория:

```sh
make dump
```

Бинарник находится в `target/<TARGET>/debug/pg_kronika-dump`. Цель
`make build` собирает `collector`, `web` и `dump` вместе. Отдельные цели
называются `make collector`, `make web` и `make dump`; без `TARGET` Makefile
выбирает целевую платформу текущего компьютера. Для другой платформы сначала
установите Rust target и передайте его явно, например
`make dump TARGET=x86_64-unknown-linux-gnu`.

## Синтаксис

```text
pg_kronika-dump <path> [--rows] [--limit N]
```

| Аргумент | Значение |
| --- | --- |
| `<path>` | Корень данных PgKronika, один PGM или журнал `active.parts`/карантинная улика. |
| `--rows` | Добавить декодированные строки к секциям PGM или целым кадрам журнала. Для корня данных параметр запрещён. |
| `--limit N` | Вывести не более `N` строк каждой секции. По умолчанию — `1000`; параметр допустим только вместе с `--rows`. `N=0` выводит пустые массивы и отмечает непустые секции как урезанные. |

Тип входа определяется без отдельной команды:

| Вход | Режим |
| --- | --- |
| Каталог | Строгий ограниченный обход корня данных. |
| Обычный файл, начинающийся с `PGM1` | Разбор готового PGM или самостоятельной PGM-части. |
| Другой обычный файл | Форензика журнала версии 1. |

Символьная ссылка в качестве `<path>` отклоняется. При одновременной записи в
файл утилита проверяет его идентичность до и после чтения и возвращает ошибку,
а не смешивает два состояния.

## Корень данных

```sh
pg_kronika-dump /var/lib/pg_kronika | jq .
```

Режим использует ту же закрытую грамматику `kronika-layout`, что collector и
web. Он не переходит по символьным ссылкам и применяет штатные пределы на число
каталогов, записей и сегментов.

Результат содержит:

| Поле | Что означает |
| --- | --- |
| `journal` | Состояние корневого `active.parts`, число проверенных кадров, физический размер и первая причина повреждения. `state: "absent"` означает, что файла нет. |
| `quarantine` | Канонические улики `qv1`: непрозрачный `id`, причина перемещения, размер и тип файлового объекта. Неизвестные имена внутри карантина не интерпретируются. |
| `days` | Все корректные каталоги UTC, включая пустые; внутри — готовые PGM по возрастанию `SegmentId`. |
| `totals` | Число сегментов и суммы размеров по всему дереву. |

Для каждого сегмента выводятся:

- `segment_id` — микросекунды Unix первого успешно добавленного окна; по нему
  вычислен каталог `YYYY/MM/DD`;
- `pgm_bytes` — полный физический размер файла;
- `ovf` — существует ли соседний файл производных фактов;
- `sections` — число секций данных без `dict.strings` и `dict.blobs`;
- `stored_bytes` — сумма Parquet-тел секций и словарей;
- `decoded_bytes` и `ratio` — `null`: режим дерева не читает тела секций;
- `windows` — сколько окон сбора объединено в PGM;
- `first_window_us` и `last_window_us` — `min_ts` и `max_ts` каталога PGM.

`first_window_us` и `last_window_us` описывают диапазон содержимого, а не
каталог, в котором лежит файл. Сегмент, пересёкший полночь, остаётся в дне
своего `segment_id`.

Режим дерева читает только хвостовые каталоги PGM. Поэтому он быстро даёт
инвентаризацию и точный сохранённый размер, но не проверяет CRC тел и не
вычисляет размер после распаковки. Для точных `decoded_bytes` и `ratio`
запустите команду отдельно для нужного PGM.

## Один PGM

```sh
pg_kronika-dump \
  /var/lib/pg_kronika/2026/07/27/1785100000000000.pgm |
  jq '{windows, dictionary, sections, totals}'
```

Раздел `windows` показывает число объединённых окон и временной диапазон
каталога. Обычная самостоятельная часть, созданная для одного окна, хранит
`count: 1`; финализированный сегмент хранит точное число частей, объединённых
операцией `seal`. Значение `0` в низкоуровневом вручную собранном контейнере
означает «неизвестно» и выводится как `null`.

Словари вынесены в объект `dictionary`, а `sections` содержит только секции
данных:

| Поле секции | Что означает |
| --- | --- |
| `type_id` | Идентификатор реестра в виде `S_105_001`; неизвестный класс выводится десятичной строкой. |
| `type_name` | Логическое имя из текущего `kronika-registry` или `null` для неизвестного типа. |
| `rows` | Число строк, объявленное каталогом и сверенное с Parquet. |
| `stored_bytes` | Физический размер Parquet-тела. Каталог, начальная сигнатура и хвост сюда не входят. |
| `decoded_bytes` | Точная сумма заголовков страниц и их несжатых данных после проверки структуры footer и страниц. Это не оценка памяти Arrow. |
| `ratio` | `decoded_bytes / stored_bytes`. Например, `4.0` означает, что проверенный несжатый объём в четыре раза больше тела в PGM. |
| `share_of_file` | `stored_bytes / file_bytes`, доля полного файла. |

`totals` суммирует секции данных и словари. Если заявленный объём декодирования
одной секции превышает предел 128 МиБ, утилита не передаёт её в Arrow:
`decoded_bytes` и общий `ratio` становятся `null`, а `decode_skipped` получает
значение `"limit"`.

Неизвестный `type_id` не мешает получить размеры и профиль Parquet. С
`--rows` такая секция получает `rows_skipped: "unknown_type"`, потому что без
контракта реестра нельзя надёжно назвать и типизировать столбцы.

## Строки

```sh
pg_kronika-dump \
  /var/lib/pg_kronika/2026/07/27/1785100000000000.pgm \
  --rows --limit 20 |
  jq '.sections[] | {type_name, rows, rows_data, truncated}'
```

`rows_data` — массив объектов с именами столбцов из контракта реестра.
`StrId(0)` и PostgreSQL `NULL` выводятся как JSON `null`. Остальные `str_id`
обязательно разыменовываются через словарь этого же PGM; отсутствующая ссылка
считается повреждением данных и даёт код выхода 1.

Обычная строка словаря выводится строкой JSON. Для `dict.blobs` значение имеет
вид:

```json
{
  "text": "stored prefix",
  "full_len": 42000,
  "truncated": true
}
```

Невалидная последовательность UTF-8 заменяется символом `U+FFFD`. Значения
float, которые JSON не умеет представить числом, выводятся строками `"NaN"`,
`"Infinity"` и `"-Infinity"`; они не смешиваются с `null`.

`truncated: true` у секции означает только то, что `--limit` скрыл часть
декодированных строк. Это не признак потери данных в PGM и не связано с
`truncated` внутри значения `dict.blobs`.

## Журнал и повреждение

```sh
pg_kronika-dump /var/lib/pg_kronika/active.parts | jq .
pg_kronika-dump /path/to/qv1-evidence --rows --limit 20 | jq .
```

Утилита проверяет 36-байтовый заголовок и запускает ограниченный
resync-сканер `kronika-format` по физическому телу. Каждый элемент `frames`
соответствует полному кадру с корректным заголовком, PGM, каталогом и CRC
секций.

| Поле | Что означает |
| --- | --- |
| `header.recorded_body_len` | Число байтов тела, записанное в заголовке. |
| `physical_bytes` | Полный текущий размер файла вместе с заголовком. |
| `valid_prefix_bytes` | Непрерывный корректный префикс от начала файла. Найденные после повреждения кадры сюда не добавляются. |
| `damage` | Первое обнаруженное повреждение или `null`: смещение, стабильный вид и пояснение. |
| `recoverable` | Все полные кадры, найденные ограниченным сканером, включая кадры после области resync. |

Повреждённый журнал — штатный результат форензики, поэтому команда возвращает
код 0 и описывает повреждение в JSON. Это не означает, что утилита
восстановила или опубликовала найденные кадры. Заголовок без допустимого
`SegmentId` не даёт доверенной идентичности сегмента.

С `--rows` каждый проверенный кадр дополнительно получает `dictionary` и
`sections` по тем же правилам, что отдельный PGM. `--limit` применяется
отдельно к каждой секции каждого кадра.

## Коды выхода и ограничения

| Код | Значение |
| ---: | --- |
| 0 | JSON сформирован, в том числе для журнала с описанным повреждением. |
| 1 | Вход нельзя прочитать или его структура/CRC/ссылки словаря противоречат контракту. |
| 2 | Неверные аргументы или недопустимое сочетание параметров. |

Утилита ограничена теми же пределами layout, format, registry и reader, что
остальные компоненты PgKronika: каталог PGM — не более 64 МиБ, тело секции —
не более 8 МиБ, декодирование секции — не более 128 МиБ. Вывод `--rows` может
содержать SQL, планы, имена объектов, аргументы процессов и текст журнала
PostgreSQL. Обращайтесь с JSON как с исходным каталогом данных.

`pg_kronika-dump` не выполняет фильтрацию по значениям и времени, не
экспортирует CSV/Parquet, не сравнивает сегменты и не исправляет файлы.
