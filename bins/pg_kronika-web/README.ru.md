# pg_kronika-web

[English version](README.md)

`pg_kronika-web` отдаёт данные из локального каталога PGM через встроенный
интерфейс, JSON API и точку Prometheus. Он читает готовые сегменты и целостные
кадры `active.parts` через `LocalDirSnapshot`, держит индекс событий по времени,
раз в секунду обновляет опубликованный снапшот каталога и не подключается к
PostgreSQL. Один долгоживущий компонент сворачивает изменения журнала, переносит
факты из точно совпавших готовых сегментов и атомарно публикует неизменяемые
представления дескрипторов и текущих данных. Тела секций из готовых сегментов
загружаются только для допущенных запросов.

```sh
KRONIKA_WEB_DIR=/var/lib/pg_kronika \
KRONIKA_WEB_ADDR=127.0.0.1:8688 \
KRONIKA_WEB_BASIC_AUTH='operator:change-me' \
pg_kronika-web
```

TLS не встроен: слушайте только локальный интерфейс или используйте обратный
прокси с TLS. Basic Auth защищает встроенный интерфейс и `/v1/*`; `/healthz`,
`/readyz` и `/metrics` всегда открыты. Учётные данные скрываются в ошибках
конфигурации и диагностическом выводе, но сама Basic Auth соединение не
шифрует.

Числовые параметры `KRONIKA_WEB_OVERVIEW_*` задаются беззнаковыми десятичными
целыми. Обязательные бюджеты, интервалы, размеры очереди и взвешенные ёмкости
должны быть ненулевыми; оба предела сайдкар-файлов можно не задавать. Значения
байтов, записей, очереди и представлений, которые становятся размерами структур
процесса, должны помещаться в `usize`. Fallback-кэш дополнительно отклоняет
значения больше 744 сегмент-часов или 268435456 байт. Лимит выбранных сегментов
должен быть в диапазоне `1..=4096`. Неверное значение завершает процесс до
открытия порта.

## Сайдкар-файлы фактов

`KRONIKA_WEB_DIR` — один каталог, целиком принадлежащий PgKronika. Отдельного
корня для производных данных и дополнительного идентификатора хранилища нет.
`active.parts`, готовый сегмент и его факты лежат рядом:

```text
/data/active.parts
/data/N.pgm
/data/N.ovf
```

`FactStore` получает имя `.ovf` заменой расширения `.pgm`; остальная часть
имени не меняется. Первый `FactStore`, захвативший
`.pgkronika-overview.owner.lock`, удерживает эксклюзивное право изменять
сайдкар-файлы в каталоге. Другие процессы могут читать полностью проверенные
`.ovf`. При конфликте публикации или GC новые факты остаются в ограниченном
fallback-кэше процесса.

Веб-процесс запускает GC после каждых 60 успешных публикаций. Число поколений
увеличивается только после нового полного и авторитетного просмотра каталога, а
не при обычном обновлении. По умолчанию удаление требует двух таких поколений и
120 секунд с первого подтверждения, что исходного сегмента больше нет.
Недоступный сегмент, ошибка просмотра или достижение лимита запрещают удаление
и не увеличивают число поколений. GC просматривает каталог напрямую, допускает
`.ovf` только после проверки заголовка PGKOVF по соответствующему PGM, не
переходит по символьным ссылкам и не удаляет PGM, `active.parts` или блокировку
владельца.

Необязательные пределы учитывают логический размер и число распознанных `.ovf`
и временных файлов публикации. Это не свободное место и не физическая квота
файловой системы. Если новый `.ovf` не помещается в полностью учтённый объём
сайдкар-файлов, ответ использует fallback-кэш. При `ENOSPC` или исчерпании
квоты выполняется не более одного авторитетного прохода GC и одной повторной
публикации.

Задержка повторной записи не блокирует чтение корректных `.ovf`. Даже если
новых фактов нет, обновление запускает одну созревшую проверку восстановления.
После ошибок доступа и «только чтение» первая проверка выполняется через пять
минут. При нехватке места и временных ошибках I/O действует экспоненциальная
задержка с джиттером (для каждого экземпляра отдельно) и пределом пять минут.
Ошибки пути, состояния сайдкар-файла, соответствия источнику и
неклассифицированные ошибки I/O сообщаются без общей задержки.

## Конечные точки

Для знакомства с хранилищем сначала вызовите `/v1/sources`, `/v1/sections` и
`/v1/segments`. Эти методы показывают, какие данные доступны, до чтения строк и
запуска анализа.

| Конечная точка | Параметры | Что возвращает |
| --- | --- | --- |
| `GET /healthz` | нет | Подтверждает, что HTTP-процесс работает. |
| `GET /readyz` | нет | Показывает системе мониторинга, успевает ли сервер обновлять снапшот каталога, и сообщает возраст последнего успешного обновления. |
| `GET /metrics` | нет | Отдаёт метрики Prometheus об ошибках чтения, возрасте данных, HTTP-запросах, RSS и открытых файловых дескрипторах. |
| `GET /v1/version` | нет | Сообщает значения JSON API и внутреннего контракта PGM для этой сборки. |
| `GET /v1/sources` | нет | Перечисляет источники коллектора в хранилище: для каждого указаны первая и последняя временные отметки и число сегментов. |
| `GET /v1/sections` | нет | Показывает доступные наборы данных, их семантику, ключ сортировки и объединённый список зарегистрированных колонок. |
| `GET /v1/segments` | `source`, `from`, `to` | Показывает сегменты, пересекающие выбранный период, и число строк в каждой секции. Читает только метаданные каталога, не тела секций. |
| `GET /v1/section/{name}` | `source`, `from`, `to`; необязательные `limit`, `cursor` | Возвращает строки выбранного набора данных в порядке времени. В `gaps` указаны отсутствующие или нечитаемые интервалы, `next_cursor` появляется, если осталась следующая страница. |
| `GET /v1/sections/batch` | `source`, `from`, `to`, список `names` через запятую; необязательный `limit` | Возвращает такие же страницы строк для нескольких наборов данных, по ключу с именем секции, за один проход по пересекающимся сегментам. |
| `GET /v1/section/{name}/diff` | `source`, `from`, `to` | Преобразует накопительные счётчики в дельты и скорости в секунду для каждого объекта. Точка содержит `delta`, `rate` и `dt_micros` либо причину `nodata`, если корректную скорость вычислить нельзя. |
| `GET /v1/sections/batch/diff` | `source`, `from`, `to`, список `names` через запятую | Возвращает такой же расчёт дельт для нескольких наборов данных, по ключу с именем секции, за один проход по сегментам. |
| `GET /v1/timeline/overview` | ровно один `source`, `from`, `to` | Возвращает сводку событий, ограниченный список примечательных событий, сводку здоровья, покрытие, свежесть, полноту, точность, смысл счётчиков и известные потери. |
| `GET /v1/timeline/events` | один или несколько повторяемых `source`, `from`, `to`; необязательные `limit`, `cursor`, `min_severity`, `kind` | Возвращает стабильную страницу типизированных примечательных фактов событий и непрозрачный курсор, если события ещё остались. |
| `GET /v1/timeline/health` | ровно один `source`, `from`, `to`; необязательный `step` как целое число микросекунд | Возвращает не более 2 000 точек здоровья с применёнными при вычислении правилами, покрытием и фактическим шагом. |
| `GET /v1/anomalies` | `source`, `from`, `to`; необязательные `window`, `step`, `threshold`, `eps_rel`, `limit`, `section` | Находит необычные интервалы скоростей и gauge. Для сохранённых планов отдельно сообщает об изменении смеси планов с нормализацией по вызовам и о росте буферной работы того же плана. Возвращает ранжированные `episodes` и `plan_signals`, счётчики проверки, применимость и качество анализа планов, покрытие, усечение и пропущенную работу. |
| `GET /v1/incidents` | `source`, `from`, `to`; необязательные `window`, `step`, `threshold`, `eps_rel`, `epsilon`, `max_cluster_span`, `section` | Объединяет близкие по времени аномальные эпизоды в кандидаты на инциденты. Когда входных данных достаточно, возвращает findings и машинные подтверждения; также сообщает покрытие, качество данных, состояние каталога и пропущенную работу. |
| `GET /` | нет | Открывает встроенный браузерный интерфейс над тем же локальным снапшотом данных. |

`source` — беззнаковый идентификатор из ответа `/v1/sources`. `from` и `to` —
знаковые временные отметки Unix в микросекундах. Параметры длительности
принимают `250ms`, `90s`, `15m`, `2h` или секунды без суффикса. По умолчанию
методы чтения строк возвращают 1 000 строк и ограничивают `limit` значением
10 000. Содержимое курсора непрозрачно для клиента: передавайте его в следующий
запрос без изменений.

Диапазон временной шкалы `from`/`to` полуоткрытый и не может превышать 31
сутки. `/overview` и `/health` отклоняют отсутствующий или повторный `source`;
`/events` упорядочивает повторяемый набор источников и удаляет дубликаты.
`/health` принимает в `step` целое число микросекунд и при необходимости
увеличивает его, чтобы ответ не превышал 2 000 точек. До поиска готового
ответа, регистрации общей задачи, admission анализа и закрепления нового
курсора первый запрос страницы выбирает пересекающиеся дескрипторы готовых
сегментов для канонического набора источников. Превышение лимита возвращает
`400` с `code=query_limit_exceeded` и `params.resource=selected_segments`.
`/events` применяет один общий лимит ко всему набору источников без дубликатов.
Данные активного журнала не считаются готовыми сегментами и ограничиваются
отдельно. `/events` по умолчанию возвращает 100 фактов и никогда больше 1 000.
Неверный курсор или курсор от другого запроса даёт `400`. Истёкший курсор, в
том числе после перезапуска, даёт `410` с `code=cursor_expired`; вытесненное или
иначе отсутствующее закреплённое представление — `410` с `code=view_gone`.
Нехватка ёмкости реестра даёт `503` с `code=cursor_capacity_unavailable` без
`Retry-After`.

```sh
curl -u operator:change-me \
  'http://127.0.0.1:8688/v1/segments?source=1&from=0&to=9223372036854775807'
```

Успешные ответы с данными не зависят от языка. `Accept-Language` не меняет
ответы, а `/v1` не отправляет `Content-Language` и языковой `Vary`. Строки из
PostgreSQL, ОС и пользовательского ввода остаются как есть; продуктовые
подписи и объяснения принадлежат UI.

Каждая прикладная ошибка `/v1` имеет одну форму RFC 9457 Problem Details с
типом содержимого `application/problem+json` и ровно пятью полями: `type`,
`status`, `code`, типизированный `params` и непрозрачный `instance`.
Человекочитаемых `title` и `detail` нет. Ответ содержит
`Cache-Control: no-store`, а созданный сервером идентификатор сопоставления
помещается в `instance` и `X-Request-ID`. Заголовки `WWW-Authenticate`, `Allow`
и `Retry-After` сохраняются там, где их требует HTTP. Неизвестная секция даёт
`404`, неверные параметры — `400`, а превышение ограничений входных данных и
материализации — `413`. Превышение лимита выбранных готовых сегментов считается
ошибкой формы запроса и возвращает `400`. Полный контракт описан в
[OpenAPI](openapi.json) и
[нормативной спецификации](../../docs/superpowers/specs/2026-07-21-i18n-machine-api-contract.md).

## Контракты чтения и анализа

- Запрос строк читает только пересекающиеся сегменты, проверяет CRC формата PGM
  и секций до декодирования, сводит зарегистрированные версии схемы под одним
  логическим именем секции и сортирует по ключу реестра. Совпадающая запись из
  готового сегмента и `active.parts` попадает в ответ один раз.
- Факты временной шкалы изолированы по источнику. Превью `/overview` и страницы
  `/events` используют одну типизированную проекцию `EventFact`: смысловой
  `event_id`, привязанный к lineage `event_instance_id`, поля источника и
  времени, классы примечательности и подтверждений, показатели качества,
  типизированную нагрузку, подтверждающие данные и сведения о потерях. Порядок
  страниц точно равен `(sort_ts_us, event_id, event_instance_id)`.
- При обновлении временной шкалы публикуются полученные из каталогов дескрипторы
  готовых сегментов и одно ограниченное поколение текущих данных; тела секций
  при этом не декодируются. Допущенный запрос загружает только факты из
  сегментов, выбранных для его источников и интервала. Попадания в память, в
  корректный сайдкар `.ovf` или в fallback-кэш после ошибки публикации обходят
  admission сборки из PGM. Одновременные запросы отсутствующих фактов делят
  работу по полному `FactBuildKey`; сборка продолжается после отмены запроса и
  проходит через общий настраиваемый FIFO-планировщик. Переполнение очереди,
  превышение веса или истечение времени ожидания дают `503` с
  `code=cold_build_overloaded` и настроенным `Retry-After`.
- Если выбранный готовый сегмент не читается во время загрузки фактов, он не
  превращается в успешный пустой сегмент и не рушит весь запрос ошибкой. Ответ
  `200` содержит его интервал в `known_gaps`, пониженную полноту и идентификатор
  набора фактов, отличный от запланированного полного набора. Такой частичный
  ответ не сохраняется под ключом полного ответа. Фоновая потоковая проверка CRC
  обнаруживает скрытое повреждение тела секции, помечает сегмент недоступным и
  не позволяет старому `.ovf` спрятать разрыв.
- Счётчики событий используют проверяемую арифметику. Суммы по примечательности
  и категориям, группы SQLSTATE `top/other/missing` и совместные группы
  `top/other` независимо сходятся с числом сохранённых ошибок. Сохранённые
  группы и физические строки наблюдений считаются отдельно. Точность сохранённых
  данных, полнота источника, смысл физического счётчика, свежесть и известные
  потери остаются независимыми полями ответа.
- Корректный сайдкар `.ovf` всегда проверяется до fallback-кэша процесса. Кэш
  заполняется только после восстановимой ошибки публикации. Хранилище точных
  ответов `/overview` и `/health` ограничено числом записей и байтами. Курсоры
  событий закрепляют точное неизменяемое представление в реестре с ограничениями
  по числу, байтам и времени жизни. Курсор связывает канонический набор
  источников, запрос, правила и последнюю позицию сортировки со случайным ключом
  процесса, полученным от ОС.
- Ответ `/diff` отличает измеренный ноль от отсутствующего результата. Точка без
  корректной скорости содержит один из кодов: `reset`, `gap`, `first_point`,
  `anomaly` или `not_collected`. В этом API `anomaly` означает, что время не
  продвинулось вперёд или типы чисел не совпали.
- Поиск аномалий сравнивает каждое текущее окно с остальными пригодными точками
  выбранного периода. Первым идёт эпизод с наибольшим `abs(peak.m)`.
  При равном балле порядок однозначно задают секция, колонка/измерение,
  идентичность и границы интервала, поэтому порядок сбора не влияет на
  усечение. Объект
  `sections` считает проверенные и непроверенные положения окна, а
  `nodata_points` даёт только общую сумму: ответ `/anomalies` не разбивает её на
  сбросы, пропуски и интервалы выключенного сбора. Положение окна, пересекающее
  разрыв временного ряда, учитывается в `not_evaluated.discontinuity`.
  Пропущенные данные не заменяются нулями.
- Для сохранённых планов есть два стабильных вида подтверждений. Для upstream
  `pg_store_plans` сигнал `pg.query.plan_distribution_shift.v1` сравнивает
  смесь планов одного `query_id` ядра PostgreSQL: приращения `calls`
  нормализуются в доли планов. Нужно не менее 20 вызовов с каждой стороны и
  расстояние полной вариации не меньше `0.20`. В форке vadv строка
  идентифицируется как `(dbid, userid, planid)`, поэтому
  `queryid_stat_statements` остаётся приблизительной атрибуцией, а смесь планов
  явно помечается неприменимой.
- `pg.plan.buffer_work_per_call_increase.v1` работает для обоих поддерживаемых
  форков. Сравнивается одна и та же сохранённая идентичность плана, накопленные
  буферные счётчики делятся на приращение `calls`; нужны не менее 20 вызовов с
  каждой стороны, прирост не меньше `1` блока на вызов и не меньше `50%`.
  Shared и local `hit/read/dirtied/written`, а также temp `read/written`
  остаются десятью разными измерениями. Счётчиков temp hit и dirtied расширение
  не предоставляет.
- Окно плана не пересекает границы сброса, версии расширения, экземпляра,
  разрыва покрытия или наблюдаемого вытеснения. Каждому снимку планов нужна
  строка reset-метаданных с точно тем же `ts`; более старая строка не считается
  подтверждением происхождения. Для вывода о смеси планов нужен полный снимок.
  Сохранённую строку плана из доказанного top-N снимка можно
  использовать для её собственного сравнения буферов, но полнота генеральной
  совокупности всё равно остаётся частичной. Отсутствующие или разбитые на
  страницы данные планов и происхождения, диапазоны пропусков считывателя,
  некорректные строки, противоречивые покрытие или метаданные, отсутствующая
  системная идентичность, неподдерживаемая версия, лимит работы и усечение
  подтверждений явно отражаются в `plan_analysis.quality`, верхних `coverage`,
  `truncation`, `complete` и `status`. Отсутствие источника считается полным
  только при доказанной полноте этих входов; иначе статус анализа плана —
  `partial`.
- Верхнее поле `coverage.plan_positions_evaluated` считает положения
  специализированных детекторов с итогом stable/changed. Оно участвует в
  выборе `no_data`, `insufficient_data` и `calm` независимо от положений
  универсального детектора.
- Оба детектора ретроспективны: опора — остальная часть того же непрерывного
  участка выбранного периода, в том числе более поздние отсчёты. Сами по себе
  они не диагностируют регрессию оптимизатора и не активируют причинный вывод
  инцидента `PG-PLAN-002`. Параметр `limit` независимо ограничивает
  ранжированные числовые `episodes` и `plan_signals`; числа отброшенных
  результатов сообщаются раздельно.
- Группировка инцидентов детальнее показывает неполные входные данные:
  `data_quality` отдельно считает `resets`, `gaps` и `not_collected`,
  `coverage_by_section` перечисляет интервалы без покрытия, а `skipped`
  объясняет работу, отброшенную из-за лимита. Период запроса ограничен 24
  часами; также ограничены юниты, секции, материализованные ячейки, точки
  рядов, байты идентификаторов, объём оценки и число эпизодов.
- Подтверждение связи блокировок между секциями требует явно сохранённого
  токена производителя для общего наблюдения и точного совпадения
  `(snapshot timestamp, PID, backend_start)`. Равные временные отметки сами по
  себе связь не доказывают. Текущие сборщики активности и блокировок выполняют
  разные запросы, поэтому `cross_section_entity_join` остаётся недоступным, пока
  производитель не сохранит такой токен.
- Объяснения неполного результата используют закрытую схему
  `{ "kind": "...", "params": { ... } }`. Идентификаторы представлений,
  значения перечислений, формулы, единицы и подтверждения остаются стабильными
  машинными данными; в каталоге инцидентов нет локализованных `title` и
  `question`.
- Одновременно выполняется одна тяжёлая проекция ответа `/anomalies`,
  `/incidents` или временной шкалы без готового ответа. Одинаковые отсутствующие
  ответы разделяют одну общую задачу, а готовые ответы не занимают слот
  исполнителя. Другой отдельный тяжёлый запрос получает `503` с
  `code=analytic_capacity_unavailable` и `Retry-After: 1`, а не ждёт в очереди.

Предупреждения сканирования и повреждённые диапазоны журнала остаются в reader
и влияют на разрывы и полноту. Они не превращаются в успешные строки.

## Метрики временной шкалы

`/metrics` публикует монотонные счётчики работы временной шкалы:
`kronika_web_overview_durable_hits_total`,
`kronika_web_overview_fallback_hits_total`,
`kronika_web_overview_rebuilt_total`,
`kronika_web_overview_promotions_total`,
`kronika_web_overview_persistence_failures_total`,
`kronika_web_overview_sealed_failures_total`. Счётчики загрузки фактов
увеличиваются, когда допущенный запрос загружает выбранные факты; первая
публикация содержит только дескрипторы. Продвижение представления показывают
`kronika_web_store_view_generation`,
`kronika_web_overview_view_generation`,
`kronika_web_overview_data_through_us` и
`kronika_web_overview_refresh_errors_total`.

Состояние долговременной записи показывают
`kronika_web_overview_persist_{mode,failures,retry_after_seconds,probe_in_flight}`,
взаимоисключающие индикаторы с закрытым набором значений меток
`kronika_web_overview_persist_reason{reason}` и
`kronika_web_overview_persist_failure_class{class}`, а также
`kronika_web_overview_persist_probe_{attempts,failures,skipped}_total`. GC
публикует индикаторы полноты сканирования, разрешения удаления, превышения
квоты, ожидающих файлов и числа просмотренных записей; индикаторы файлов,
логических и выделенных байтов для закрытых классов
`kind={sidecar,temporary,lock}`; счётчики пропусков, удалённых файлов и
отвязанных логических/выделенных байтов. «Отвязанные выделенные байты» —
значение `st_blocks` открытого файла перед удалением имени; открытый дескриптор
или другая жёсткая ссылка могут сохранить эти блоки на диске.

Загрузка реестра курсоров видна в `kronika_web_timeline_cursor_views`,
`kronika_web_timeline_cursor_bytes` и
`kronika_web_timeline_cursor_pins_total`,
`kronika_web_timeline_cursor_resolves_total`,
`kronika_web_timeline_cursor_evictions_total`,
`kronika_web_timeline_cursor_expired_total` и
`kronika_web_timeline_cursor_capacity_rejections_total`. Работу хранилища
ответов и координации одинаковых задач отражают
`kronika_web_timeline_response_cache_{hits,misses,evictions}_total`,
`kronika_web_timeline_response_cache_{entries,bytes}` и
`kronika_web_timeline_singleflight_{leaders,joins}_total`. Политику выбранных
сегментов показывают `kronika_web_timeline_selected_segments_limit` и
`kronika_web_timeline_query_limit_rejections_total{resource="selected_segments"}`.
Перегрузку холодной загрузки фактов считает
`overview_cold_reject_total{reason}` с закрытым набором причин
`queue_full`, `weight_exceeds_capacity` и `timeout`. Загрузку планировщика
показывают `overview_cold_wait_seconds`, `overview_cold_queue_depth`,
`overview_cold_work_inflight{kind="workers"}`,
`overview_inflight_bytes{kind="pgm"|"decoded"}` и `overview_open_files`.
Совместимый счётчик
`kronika_web_overview_cold_work_rejections_total{reason="capacity"}`
инкрементируется при HTTP-ответах о перегрузке.

Чтение декодированных фактов из памяти и сайдкар OVF показывают
`overview_fact_lookup_total{layer,result,reason}`,
`overview_fact_read_bytes`, `overview_pgm_body_read_bytes`,
`overview_pgm_sections_decoded`,
`overview_fact_build_total{result,source_type}` и
`overview_fact_build_seconds`; записи считает `overview_fact_write_bytes`.
Слой декодированных фактов в памяти публикует
`overview_cache_{entries,bytes}{class="decoded_facts"}` и
`overview_cache_evictions_total{class="decoded_facts",reason}`.

В перечень эксплуатационных метрик `parity-v1` также входят взаимоисключающая
`overview_cache_mode{mode,reason}`, `overview_persist_failures_total{reason}`,
`overview_persist_backoff_seconds`,
`overview_singleflight_{builds,waiters}`,
`overview_live_state{state,reason}`, `overview_live_folded_parts_total`,
`overview_live_data_through_us`, `overview_live_visibility_lag_seconds`,
`overview_view_generation`, `overview_cursor_views`,
`overview_cursor_view_bytes` и `overview_cursor_expired_total{reason}`.
Корректность показывают `overview_source_failures_total{reason}`,
`overview_coverage_loss_total{source,factor,reason}`,
`overview_retained_observations_total{kind}`,
`overview_overflow_total{kind}`, `overview_raw_fallback_total{reason}`,
`overview_gc_files_total{action,reason}` и
`overview_gc_bytes_total{action}`. При сборке маршрутизатора для каждого имени
регистрируются тип и справочный текст. Динамические значения источника и фактора
берутся только из ограниченных опубликованных перечней; остальные значения
меток имеют закрытый набор.

Целостность источника и частичные результаты показывают
`overview_source_read_failures_total{outcome="partial"}`,
`overview_source_scrub_total{outcome}`,
`overview_source_scrub_bytes_total`, `overview_source_scrub_seconds` и
`overview_source_damaged_segments`. Наборы меток этих метрик, планировщика и
хранилищ памяти фиксированы; метки HTTP-запросов используют шаблоны
сопоставленных маршрутов, а не исходный URI.

## Завершение и отказы

`SIGTERM` и `SIGINT` запускают корректное завершение HTTP-сервера. Ошибка
обновления записывается в журнал, а последнее опубликованное представление
остаётся доступным; после заданного порога `/readyz` сообщает устаревшее
состояние. Если каталог источников успешно просмотрен, но построить временную
шкалу не удалось, сервер публикует свежие метаданные вместе с последним
пригодным представлением и не показывает частично собранный результат. Неверная
конфигурация окружения, ошибка первого открытия каталога или фактов либо
недоступная энтропия ОС для аутентификации курсора завершают процесс до
открытия порта.

## BDD перезапуска и восстановления реального процесса

Матрица BDD для PostgreSQL 15–18 запускает
`timeline_web_lifecycle.feature` с собранным исполняемым файлом
`pg_kronika-web`, а не с маршрутизатором внутри процесса и не с заново
созданным `AppState`. Каждый сценарий копирует готовый PGM коллектора в
собственный временный каталог и последовательно запускает несколько новых
процессов с этим каталогом. Настоящие HTTP-запросы проверяют создание
сайдкар-файла OVF, неизменность inode, времени изменения и хеша при чтении
после перезапуска, отсутствие чтений тел PGM и декодирования секций,
восстановление повреждённых и устаревших заголовков, обработку остатка
прерванной публикации, ограниченный fallback-кэш при ошибке записи, истечение
курсора прошлого процесса и предсказуемую конкуренцию владельцев записи.

Готовность подтверждается сообщением после открытия порта, а штатное
завершение процесса проверяется по коду выхода. Для остановки публикации и
конкуренции используется доступный только в квалификационной сборке
Unix-сокет: барьер срабатывает после синхронизации временного OVF, но до
атомарного переименования. Результат не зависит от задержек и циклов повторных
попыток. Запуск всей матрицы жизненного цикла:

```sh
DEBUG=1 make test-bdd TAGS=@timeline_web_lifecycle
```

Запуск для одной поддерживаемой версии, например PostgreSQL 15:

```sh
DEBUG=1 make test-bdd TAGS='@timeline_web_lifecycle and @pg15'
```

У бинарника нет параметров командной строки. MCP, удалённые хранилища,
управление сроком хранения исходных сегментов и доставка оповещений не
реализованы.
